Chapter 05

안전하게 변경하기 (1): 권한과 승인

기초

안전하게 변경하기 (1): 권한과 승인

이 챕터에서 배우는 것

  • 어떤 도구 호출에서 권한 확인이 발생하는지 부수효과 도구와 읽기 전용 도구를 구분해 설명할 수 있습니다.
  • 주어진 작업에 맞춰 settings.json에 allow·deny·ask 규칙을 작성해, 안전한 명령은 허용하고 위험한 명령은 차단하도록 도구를 통제할 수 있습니다.
  • 도구·명령 패턴(예: Bash(pytest:*)·Edit(routers/**))으로 허용 범위를 좁힌 최소 권한 규칙을 작성할 수 있습니다.
  • 사용자·프로젝트 공유·로컬 세 범위를 구분해, 팀 공유 규칙과 개인 설정을 각각 올바른 settings 파일에 배치할 수 있습니다.
  • 전체 자동 승인의 위험을 근거로 들어, 최소 권한 원칙에 맞는 규칙으로 첫 변경 환경을 안전하게 준비할 수 있습니다.

이번 챕터에서 가르치는 개념은 권한과 승인(permissions and approval) 한 가지입니다. 선수 개념은 ch_04에서 익힌 기존 코드베이스 탐색·이해시키기(exploring and understanding an existing codebase)입니다. ch_04에서는 코드를 바꾸지 않고 읽기만 하는 안전한 탐색으로 팀 저장소를 파악했습니다. 이제 드디어 코드에 손을 댈 차례인데, 그 전에 한 가지를 먼저 갖춰야 합니다. 바로 "에이전트가 무엇을 자동으로 해도 되고, 무엇은 반드시 물어봐야 하는가"를 정하는 안전장치입니다. 탐색은 읽기라 위험이 없었지만, 변경은 파일을 바꾸고 명령을 실행하므로 통제가 필요합니다. 이 챕터는 그 통제 장치인 권한 시스템을 다룹니다.

5.1 도입: 손대기 전에 안전장치부터

신입이 입사 첫 주에 가장 듣기 싫은 말이 있습니다. "그거 네가 지웠어?" 낯선 코드베이스에서 명령 하나를 잘못 실행해 데이터베이스를 날리거나, 엉뚱한 파일을 덮어쓰는 일은 실제로 자주 일어납니다. 사람도 실수하는데, 파일을 직접 편집하고 터미널 명령을 실행하는 에이전트라면 더 조심해야 합니다.

ch_02에서 우리는 Claude Code가 부수효과 도구(편집·실행)를 써서 실제로 파일을 바꾸고 명령을 돌린다는 것을 배웠습니다. 이것이 자동완성과의 결정적 차이였습니다. 그런데 바로 그 힘 때문에, 통제 없이 모든 것을 자동으로 맡기면 위험합니다. 예를 들어 에이전트가 "테스트 데이터를 정리하겠습니다" 하면서 rm -rf 명령을 실행하려 한다면, 그게 정말 의도한 것인지 한 번은 확인하고 싶을 것입니다.

Claude Code는 이 문제를 권한(permission) 시스템으로 풉니다. 에이전트가 부수효과 도구를 호출할 때마다 "이 작업을 해도 됩니까?"를 사용자에게 확인하고, 사용자는 그때그때 승인하거나, 미리 규칙을 정해 자주 쓰는 안전한 작업은 자동으로 허용하고 위험한 작업은 아예 막을 수 있습니다. 이 규칙을 잘 설계하면, 신입도 위험 없이 빠르게 일할 수 있습니다. 마찰(매번 묻는 번거로움)은 줄이되, 사고(돌이킬 수 없는 실수)는 막는 것이 목표입니다.

한눈에 보는 권한과 승인

Claude Code는 파일 편집·명령 실행처럼 부수효과가 있는 도구를 호출할 때 권한을 확인합니다. 규칙은 settings.json에 allow(자동 허용)·deny(차단)·ask(물어보기)로 선언하며, 도구·명령 패턴(예: Bash(pytest:*))으로 범위를 좁힙니다. 규칙은 사용자·프로젝트 공유·로컬 개인 세 범위에 나눠 두고, 신입에게는 전체 자동 승인보다 최소 권한(least privilege)이 안전의 기본입니다.

5.2 정의: 부수효과 도구와 읽기 전용 도구의 권한 차이

권한과 승인(permissions and approval)이란, Claude Code가 부수효과를 일으키는 도구를 실행하기 전에 사용자의 허락을 확인하고, 그 허락을 규칙으로 미리 정해 두는 통제 체계입니다.

여기서 핵심은 모든 도구가 권한 확인 대상이 아니라는 점입니다. 도구는 두 종류로 나뉩니다.

  • 읽기 전용 도구(read-only tools): 파일을 읽거나(Read) 패턴으로 파일을 찾거나(Glob) 내용을 검색합니다(Grep). 아무것도 바꾸지 않으므로 위험이 없고, 기본적으로 권한을 묻지 않고 자유롭게 실행됩니다.
  • 부수효과 도구(side-effect tools): 파일을 고치거나(Edit) 새로 쓰거나(Write) 터미널 명령을 실행합니다(Bash). 시스템 상태를 바꾸므로, 기본적으로 실행 전에 권한을 확인합니다.

ch_04의 탐색이 안전했던 이유가 바로 이것입니다. 코드베이스를 요약시키고 함수를 추적시키는 작업은 전부 읽기 전용 도구로 이뤄지므로 권한 확인이 거의 없었습니다. 하지만 이번 챕터부터 다룰 "변경"은 부수효과 도구를 쓰므로, 매번 권한 확인이 따라붙습니다.

구분 읽기 전용 도구 부수효과 도구
예 Read(읽기), Glob(파일 찾기), Grep(검색) Edit(편집), Write(쓰기), Bash(명령 실행)
하는 일 정보 수집(변경 없음) 파일·시스템 상태 변경
위험도 낮음(되돌릴 것이 없음) 높음(잘못 실행 시 손상 가능)
기본 동작 권한 확인 없이 실행 실행 전 권한 확인
통제 필요성 거의 없음 allow·deny·ask로 통제

이 구분이 권한 시스템 전체의 출발점입니다. "왜 어떤 작업은 묻고 어떤 작업은 안 묻나?"라는 질문의 답이 바로 "그 도구가 무언가를 바꾸는가"이기 때문입니다.

용어 정리: 부수효과(side effect)

부수효과란 어떤 작업이 정보를 돌려주는 것 외에 시스템의 상태를 바꾸는 것을 말합니다. 파일을 저장하면 디스크가 바뀌고, git push를 하면 원격 저장소가 바뀌고, rm을 하면 파일이 사라집니다. 이렇게 "실행하고 나면 세상이 달라지는" 작업이 부수효과 도구이고, 권한 시스템이 통제하는 대상입니다.

5.3 동작 원리: allow·deny·ask 판정 흐름

에이전트가 부수효과 도구를 호출하면, Claude Code는 그 도구 호출을 settings.json의 권한 규칙과 대조해 어떻게 처리할지 판정합니다. 규칙은 세 종류이고, 정해진 순서대로 검사합니다.

  1. deny(차단): 이 패턴에 맞으면 도구를 실행하지 못하게 막습니다. 사용자에게 묻지도 않습니다. 위험한 명령(예: 파일 삭제)을 여기에 둡니다.
  2. ask(물어보기): 이 패턴에 맞으면 매번 사용자에게 확인합니다. 승인하면 그 한 번만 실행됩니다. 신중을 기하고 싶은 작업(예: git push)을 여기에 둡니다.
  3. allow(자동 허용): 이 패턴에 맞으면 묻지 않고 자동으로 실행합니다. 자주 쓰고 안전한 작업(예: 테스트 실행)을 여기에 둡니다.

가장 중요한 규칙은 검사 순서가 deny → ask → allow이고, 먼저 맞는 규칙이 결과를 정한다는 것입니다. 규칙이 더 구체적이라고 우선되는 것이 아니라, 순서가 우선을 정합니다. 그래서 어떤 명령이 deny에 걸리면, 설령 allow에도 똑같이 적혀 있어도 차단됩니다. deny가 가장 강합니다. 이 점이 안전 설계의 핵심입니다. "절대 하면 안 되는 것"을 deny에 두면, 다른 규칙이 아무리 느슨해도 그것만은 막힙니다.

세 규칙 중 어디에도 맞지 않으면 Claude Code는 기본 동작으로 돌아가 사용자에게 한 번 물어봅니다. 즉 규칙을 안 정해 두면 부수효과 도구는 그때그때 확인을 거칩니다. 규칙은 이 "매번 묻기"를 줄이거나(allow) 더 엄격하게 막기(deny) 위한 장치입니다.

판정 의미 사용자 경험 적합한 작업
deny 차단(실행 불가) 막혔다는 안내, 실행 안 됨 rm, 비밀 파일 읽기 등 위험 작업
ask 매번 확인 승인/거부를 그때그때 선택 git push, 배포처럼 신중할 작업
allow 자동 허용 묻지 않고 바로 실행 pytest, 코드 포맷처럼 안전·반복 작업
(해당 없음) 기본값 한 번 물어봄 규칙을 아직 안 정한 작업

이 흐름을 머릿속에 그려 두면, "왜 이 명령은 막히고 저 명령은 그냥 실행되지?"라는 의문이 풀립니다. 항상 deny부터 차례로 검사한다는 것만 기억하면 됩니다.

순서가 곧 안전이다

deny가 ask·allow보다 먼저 검사되므로, 위험한 작업을 deny에 두면 어떤 allow 규칙도 그것을 뚫지 못합니다. 반대로 deny에 안 두고 allow만 넓게 잡으면, 위험한 명령이 자동 실행될 수 있습니다. "막고 싶은 것은 반드시 deny에 명시한다"가 첫 번째 안전 습관입니다.

5.4 worked example: pytest만 allow·위험 삭제는 deny하는 settings.json

이제 실제 규칙을 작성해 보겠습니다. 상황은 이렇습니다. 우리는 1장에서 셋업한 팀의 FastAPI 할 일 관리 저장소 team-tasks-api에서 작업 중이고, 앞으로 테스트(pytest)는 수없이 돌릴 것이므로 매번 승인하기 번거롭습니다. 반면 파일 삭제(rm)는 절대 자동으로 실행되면 안 됩니다. 이 두 가지를 규칙으로 만들겠습니다.

저장소 루트에 .claude/settings.json 파일을 만들고 다음과 같이 작성합니다. 권한 규칙은 모두 permissions 객체 안에 둡니다.

json
{
  "permissions": {
    "allow": [
      "Bash(pytest:*)",
      "Bash(python -m pytest:*)"
    ],
    "ask": [
      "Bash(git push:*)"
    ],
    "deny": [
      "Bash(rm:*)",
      "Bash(git reset --hard:*)"
    ]
  }
}
  • "permissions": 모든 권한 규칙을 담는 최상위 객체입니다. settings.json은 권한 외 다른 설정도 담을 수 있어 이렇게 한 단계 안에 둡니다.
  • "allow": 묻지 않고 자동 실행할 작업 목록입니다. Bash(pytest:*)는 "pytest로 시작하는 모든 명령"을, Bash(python -m pytest:*)는 모듈 형태 실행을 자동 허용합니다. 테스트를 마음껏 돌리되 승인 클릭이 사라집니다.
  • "ask": 매번 확인할 작업입니다. Bash(git push:*)는 원격에 코드를 올리는 작업이라, 자동화하지 않고 매번 사람이 한 번 더 확인하게 둡니다.
  • "deny": 차단할 작업입니다. Bash(rm:*)는 모든 rm 삭제 명령을, Bash(git reset --hard:*)는 작업 내용을 날리는 강제 리셋을 막습니다. deny가 가장 먼저 검사되므로, 이 명령들은 어떤 경우에도 자동 실행되지 않습니다.

이 설정을 둔 상태에서 에이전트와 작업하면 다음과 같이 동작합니다. 터미널 세션의 모습은 이렇습니다.

console
> tasks 라우터에 테스트를 돌려서 통과하는지 확인해 줘

● Bash(pytest tests/test_tasks.py -q)
  (allow 규칙에 맞아 자동 실행됨 - 승인 묻지 않음)

  .......                                     [100%]
  7 passed in 0.34s

> 임시 파일들을 정리하려고 rm으로 지워 줘

● Bash(rm -rf tmp/)
  차단됨: 이 명령은 deny 규칙(Bash(rm:*))에 막혀 실행할 수 없습니다.

실행 결과를 보면, pytest는 묻지 않고 바로 실행되어 7 passed가 나왔고, rm은 deny 규칙에 걸려 아예 실행되지 않았습니다. 우리가 의도한 그대로입니다. 자주 쓰는 안전한 작업은 마찰 없이, 위험한 작업은 확실히 차단했습니다.

왜 git push는 deny가 아니라 ask인가

git push는 위험하다기보다 신중해야 하는 작업입니다. 막아 버리면 정작 필요할 때 못 하니, deny가 아니라 ask에 둡니다. ask는 "해도 되지만, 할 때마다 사람이 한 번 확인한다"는 뜻입니다. 이렇게 deny(절대 금지)·ask(확인 후 허용)·allow(자유)를 작업의 위험도에 맞게 배분하는 것이 권한 설계의 감각입니다.

5.5 도구·명령 패턴 매칭(Bash(pytest:)·Edit(routers/*))

권한 규칙의 힘은 패턴 매칭(pattern matching)에서 나옵니다. 도구 이름만 적으면 그 도구 전체가 대상이 되지만, 괄호 안에 패턴을 적으면 특정 명령이나 특정 파일 경로로 범위를 좁힐 수 있습니다. 신입에게는 이 "좁히기"가 안전의 핵심입니다.

Bash 명령 패턴

Bash(...) 안에는 실행 명령을 패턴으로 적습니다. *는 임의의 문자열을 뜻하는 와일드카드입니다.

  • Bash(pytest:*) — pytest로 시작하는 모든 명령. :*는 "뒤에 무엇이 와도 좋다"는 꼬리 와일드카드입니다. pytest, pytest -q, pytest tests/가 모두 맞습니다.
  • Bash(git commit:*) — git commit으로 시작하는 명령만. git push는 맞지 않습니다.
  • Bash(rm:*) — 모든 rm 명령. 삭제를 통째로 막을 때 씁니다.

여기서 띄어쓰기가 중요합니다. Bash(pytest:*)는 Bash(pytest *)와 같은 의미이며, pytest라는 명령 뒤에 인자가 붙는 형태를 가리킵니다. 만약 띄어쓰기 없이 Bash(pytest*)처럼 적으면 pytest-cov 같은 다른 명령까지 걸릴 수 있으므로, 명령 단위로 정확히 좁히려면 :* 형태를 쓰는 것이 안전합니다.

Edit 파일 경로 패턴

Edit(...)·Read(...) 안에는 파일 경로를 패턴으로 적습니다. 경로 패턴은 .gitignore와 비슷한 글롭(glob) 문법을 씁니다.

  • Edit(routers/**) — routers/ 폴더 아래의 모든 파일 편집을 허용. **는 하위 폴더까지 전부 포함합니다. routers/tasks.py, routers/__init__.py가 모두 맞습니다.
  • Edit(tests/**) — 테스트 폴더만 편집 허용.
  • Read(.env) — .env 파일 읽기를 (deny에 두면) 차단. 비밀 키가 든 파일을 에이전트가 못 읽게 할 때 씁니다.

예를 들어 "에이전트가 routers/ 아래는 자유롭게 고치되, 그 밖의 설정 파일(requirements.txt 등)은 함부로 못 건드리게" 하고 싶다면 Edit(routers/**)만 allow에 두고 나머지는 기본값(물어보기)으로 둡니다. 이렇게 경로로 작업 영역을 가두는 것이 패턴 매칭의 진짜 가치입니다.

json
{
  "permissions": {
    "allow": [
      "Bash(pytest:*)",
      "Edit(routers/**)",
      "Edit(tests/**)"
    ],
    "deny": [
      "Read(.env)",
      "Read(secrets/**)",
      "Bash(rm:*)"
    ]
  }
}
  • Edit(routers/**)·Edit(tests/**): 라우터 코드와 테스트 코드 폴더는 자유롭게 편집하도록 허용해 작업 속도를 높입니다.
  • Read(.env)·Read(secrets/**): 환경 변수 파일과 비밀 폴더는 읽기 자체를 차단합니다. 읽기 전용 도구라도 비밀 노출은 막아야 하므로 deny에 둡니다. 이처럼 deny는 부수효과 도구뿐 아니라 민감 파일 읽기에도 씁니다.
  • Bash(rm:*): 삭제 명령 전체 차단은 유지합니다.

이름만 허용하면 너무 넓다

Bash를 통째로 allow에 두면 모든 셸 명령이 자동 실행됩니다. rm이든 curl이든 가리지 않습니다. 이건 사실상 "전체 자동 승인"과 같아 매우 위험합니다. 반드시 Bash(pytest:*)처럼 명령을 좁혀 허용하십시오. 도구 이름만 적는 넓은 허용은 신입이 가장 자주 저지르는 실수입니다.

5.6 권한 범위: 사용자·프로젝트 공유·로컬 개인

규칙을 어디에 저장하느냐에 따라 적용 범위가 달라집니다. 같은 allow·deny 규칙이라도 저장 위치가 다르면 "나에게만", "팀 전체에", "이 프로젝트의 나에게만"처럼 적용 대상이 바뀝니다. 범위는 세 가지입니다.

범위 파일 위치 적용 대상 Git 공유 담는 내용 예
사용자(개인) ~/.claude/settings.json 그 사용자의 모든 프로젝트 안 됨(개인 머신) 어디서나 쓰는 개인 기본 규칙
프로젝트(팀 공유) .claude/settings.json 그 저장소의 모든 팀원 됨(저장소에 커밋) 팀 공통 안전 규칙(테스트 허용·삭제 차단)
로컬(개인·프로젝트 한정) .claude/settings.local.json 그 저장소의 나에게만 안 됨(보통 .gitignore) 내 머신에만 필요한 임시 허용

여기서 ~는 Windows 11에서 사용자 홈 폴더(예: C:\Users\내이름)를 가리킵니다. Git Bash에서는 ~로 그대로 쓸 수 있습니다.

세 범위를 나누는 이유는 명확합니다. 팀 전체가 지켜야 할 안전 규칙(예: "삭제 명령은 차단한다")은 프로젝트 공유(.claude/settings.json)에 두고 저장소에 커밋해, 새로 합류하는 모든 신입에게 자동으로 적용되게 합니다. 반면 나만의 사정(예: "이 프로젝트에서 잠깐 특정 스크립트를 자동 허용하고 싶다")은 로컬(.claude/settings.local.json)에 둬, 다른 사람에게 영향을 주지 않게 합니다. 로컬 파일은 보통 .gitignore에 들어가 공유되지 않습니다.

가장 중요한 실무 규칙은 이것입니다. 팀이 함께 지켜야 할 규칙은 로컬이 아니라 프로젝트 공유에 둔다. 안전 규칙을 자기 로컬에만 넣으면, 같은 팀의 다른 신입에게는 그 보호막이 없습니다. 반대로 개인 취향이나 임시 허용을 프로젝트 공유에 넣으면 팀원 모두에게 강요가 됩니다.

또 하나 기억할 것은, deny는 어느 범위에 있든 가장 강하게 작동한다는 점입니다. 프로젝트 공유에 Bash(rm:*) 차단을 두면, 개인이 로컬에서 rm을 허용하려 해도 차단이 우선합니다. 안전의 바닥선은 팀 차원에서 deny로 깔아 두는 것이 좋습니다.

신입의 기본 배치

  • 팀 공통 안전선(삭제·강제리셋 차단, 테스트·포맷 허용) → .claude/settings.json(프로젝트 공유, 커밋)
  • 내 머신에서만 필요한 임시 허용 → .claude/settings.local.json(로컬, 커밋 안 함)
  • 모든 프로젝트에서 쓰는 내 기본값 → ~/.claude/settings.json(사용자)

이 배치만 지켜도 "팀 규칙과 개인 설정이 섞이는" 혼란을 피할 수 있습니다.

5.7 worked example: /permissions로 안전 명령 미리 허용·체크인

규칙을 손으로 settings.json에 적는 대신, Claude Code 안에서 /permissions 슬래시 커맨드로 권한 규칙을 보고 추가할 수 있습니다. 작업 중 "이 명령은 자주 쓰니 앞으로 자동 허용하자"는 판단이 서면, 그 자리에서 규칙을 더하는 방식입니다.

흐름을 따라가 보겠습니다. 테스트를 돌릴 때마다 승인을 묻는 게 번거로워, pytest를 자동 허용으로 바꾸려는 상황입니다.

console
> /permissions

  권한 규칙 (Permissions)
  ──────────────────────────────
  allow:
    (없음)
  ask:
    (없음)
  deny:
    Bash(rm:*)

  [a] 규칙 추가   [d] 삭제   [q] 닫기

여기서 규칙 추가를 골라 Bash(pytest:*)를 allow에 더하면, 이후 테스트 실행은 묻지 않고 진행됩니다. 또 다른 방법으로, 에이전트가 권한을 물어보는 그 순간 "이번만 허용"이 아니라 "항상 허용"을 고르면, 같은 패턴이 자동으로 allow 규칙에 추가됩니다.

console
● Bash(pytest -q)
  이 명령을 실행할까요?
  > 1. 예 (이번만)
    2. 예, 그리고 앞으로 Bash(pytest:*)는 항상 허용
    3. 아니요

  (2번 선택 → settings.json의 allow에 Bash(pytest:*) 추가됨)

이렇게 추가된 규칙은 어느 범위에 저장할지 고를 수 있는데, 팀과 공유할 안전 규칙이라면 프로젝트 공유(.claude/settings.json)에 저장하고, 그 파일을 git에 커밋(체크인)합니다. 그러면 다음에 합류하는 동료도 같은 허용·차단 규칙을 그대로 물려받습니다.

bash
git add .claude/settings.json
git commit -m "chore: pytest 자동 허용, rm 차단 권한 규칙 추가"

실행 결과로, 이 커밋 이후 저장소를 받는 모든 팀원은 pytest를 자동 허용하고 rm을 차단하는 동일한 안전 설정에서 일하게 됩니다. 권한을 개인이 매번 다시 만드는 것이 아니라, 팀의 자산으로 공유하는 것이 핵심입니다.

"항상 허용"을 누르기 전에 한 번 생각하기

승인 창에서 "항상 허용"은 편하지만, 그 패턴이 정말 항상 안전한지 따져 보고 누르십시오. Bash(pytest:*)처럼 좁고 안전하면 좋지만, Bash(git:*)처럼 넓게 항상 허용하면 git push·git reset까지 자동화되어 위험합니다. 좁게 허용하는 습관이 사고를 막습니다.

5.8 전체 자동 승인의 위험과 최소 권한 원칙

Claude Code에는 권한 확인을 통째로 끄는 모드(흔히 "전체 자동 승인" 또는 bypass라 부르는 방식)가 있습니다. 모든 부수효과 도구를 묻지 않고 실행하므로 빠르지만, 신입에게는 권하지 않습니다. 에이전트가 잘못된 가정으로 위험한 명령을 실행해도 막을 사람이 없기 때문입니다. 격리된 일회용 환경(예: 컨테이너)이 아니라면, 자기 작업 머신에서 전체 자동 승인을 켜는 것은 안전벨트를 풀고 운전하는 것과 같습니다.

대신 따라야 할 원칙이 최소 권한(least privilege)입니다. 이는 보안의 오랜 기본 원칙으로, "작업에 꼭 필요한 만큼만 권한을 준다"는 뜻입니다. 권한 설계에 적용하면 이렇습니다.

  • 자동 허용(allow)은 자주 쓰고 확실히 안전한 것만 좁게 추가합니다(예: Bash(pytest:*), Edit(routers/**)).
  • 위험하거나 되돌릴 수 없는 작업은 deny로 막습니다(예: Bash(rm:*)).
  • 나머지는 굳이 미리 허용하지 말고 기본값(물어보기)으로 둡니다. 필요할 때 그 자리에서 한 번 승인하면 됩니다.

이렇게 하면 "마찰은 줄이되 위험은 막는" 균형이 잡힙니다. 자주 하는 안전한 일은 빠르게, 가끔 하는 위험한 일은 신중하게 처리됩니다. 신입일수록 처음에는 좁게 시작해, 익숙해지면서 안전이 확인된 작업을 조금씩 allow에 더해 가는 것이 좋습니다.

전체 자동 승인을 켜기 전에

전체 자동 승인은 "에이전트가 무엇을 하든 다 실행해도 좋다"는 선언입니다. 신입이 낯선 코드베이스에서 이걸 켜면, 의도치 않은 삭제·덮어쓰기·외부 전송이 확인 없이 일어날 수 있습니다. 정말 필요하다면 인터넷이 차단된 일회용 컨테이너처럼 피해가 격리되는 환경에서만 쓰고, 평소 작업 머신에서는 최소 권한을 유지하십시오.

5.9 즉시 연습 (2종 1세트): team-tasks-api에 권한 규칙을 실제로 만들고 동작을 확인

배운 것을 종이로 채우는 대신, team-tasks-api에 실제 .claude/settings.json을 만들고 허용·차단이 정말 동작하는지 화면으로 확인합니다. allow가 자동 통과되는지, deny가 실제로 막는지는 직접 돌려 봐야 손에 잡힙니다.

5.10 흔한 오류와 오개념: 전체 bypass·이름만 허용·로컬 오남용

마지막으로, 신입이 권한 설정에서 자주 저지르는 실수와 그 교정을 정리합니다.

오개념 1: "전체 자동 승인이 편하니 그냥 켜자"

전체 bypass(자동 승인)는 편하지만, 에이전트의 모든 부수효과 작업이 확인 없이 실행됩니다. 잘못된 가정 한 번이 삭제·덮어쓰기로 이어질 수 있습니다.

교정: 전체 자동 승인 대신 최소 권한으로 시작하십시오. 자주 쓰는 안전한 작업만 좁게 allow에 두고, 위험 작업은 deny, 나머지는 기본값(물어보기)으로 둡니다. 마찰은 생각보다 적고, 안전은 훨씬 커집니다.

오개념 2: "Bash를 통째로 허용하면 명령마다 안 물어봐서 좋다"

Bash를 이름만으로 allow에 두면 모든 셸 명령이 자동 실행됩니다. pytest뿐 아니라 rm·curl·git push까지 전부입니다. 이름만 허용은 사실상 전체 자동 승인과 같습니다.

교정: 허용은 항상 명령·경로 패턴까지 좁혀 적습니다. Bash(pytest:*), Edit(routers/**)처럼 범위를 명시하면, 그 패턴에 맞는 것만 자동 허용되고 나머지는 여전히 확인을 거칩니다.

오개념 3: "안전 규칙은 내 로컬 파일에 넣으면 되겠지"

.claude/settings.local.json(로컬)은 공유되지 않습니다(보통 .gitignore). 여기에 팀 안전 규칙(예: rm 차단)을 넣으면, 같은 저장소를 받는 다른 신입에게는 그 보호막이 없습니다.

교정: 팀이 함께 지킬 규칙은 프로젝트 공유(.claude/settings.json)에 두고 git에 커밋하십시오. 로컬은 "나에게만, 이 프로젝트에서만" 필요한 임시 설정에만 씁니다.

자주 묻는 질문(FAQ)

Q. allow에도 deny에도 똑같은 명령이 있으면 어떻게 되나요? A. deny가 이깁니다. 검사 순서가 deny → ask → allow이고 먼저 맞는 규칙이 결과를 정하므로, deny에 걸리면 allow에 있어도 차단됩니다.

Q. 규칙을 아무것도 안 정하면 위험한가요? A. 위험하지 않습니다. 규칙이 없으면 부수효과 도구는 매번 사용자에게 물어봅니다(기본값). 규칙은 이 "매번 묻기"를 줄이거나(allow) 더 엄격히 막기(deny) 위한 선택입니다. 다만 rm 같은 위험 작업은 실수 방지를 위해 deny로 명시해 두는 편이 안전합니다.

Q. ~/.claude/settings.json과 .claude/settings.json은 어떻게 다른가요? A. 앞은 사용자(모든 프로젝트), 뒤는 이 프로젝트(팀 공유, 커밋 대상)입니다. 팀 규칙은 뒤에, 어디서나 쓰는 내 기본값은 앞에 둡니다.

5.11 마무리: 안전장치를 갖췄으니, 다음은 계획이다

이번 챕터에서 우리는 코드에 손대기 전에 갖춰야 할 첫 번째 안전장치인 권한과 승인을 배웠습니다. 핵심을 정리하면 다음과 같습니다.

  • 권한 확인은 부수효과 도구(Edit·Write·Bash)를 호출할 때 발생하고, 읽기 전용 도구는 묻지 않습니다.
  • 규칙은 settings.json의 allow·deny·ask로 선언하며, 검사 순서는 deny → ask → allow, 먼저 맞는 규칙이 결과를 정합니다(deny가 가장 강함).
  • 패턴 매칭(Bash(pytest:*)·Edit(routers/**))으로 명령·경로를 좁혀 안전하게 허용합니다.
  • 규칙은 사용자·프로젝트 공유·로컬 범위로 나누고, 팀 안전 규칙은 프로젝트 공유에 커밋합니다.
  • 전체 자동 승인 대신 최소 권한으로 시작합니다.

이제 "에이전트가 무엇을 해도 되는지"의 경계는 정해졌습니다. 하지만 안전에는 한 겹이 더 필요합니다. 권한은 "이 명령을 실행해도 되는가"를 통제하지만, "애초에 무엇을 바꿀 계획인가"를 먼저 보는 것은 또 다른 안전장치입니다. 다음 챕터(ch_06)에서는 변경을 실행하기 전에 계획부터 받아 검토하는 플랜 모드를 배웁니다. 권한(이번 챕터)과 플랜 모드(다음 챕터)를 함께 갖추면, 신입도 낯선 코드에 위험 없이 첫 변경을 시작할 수 있습니다.
