실무

종합 프로젝트: 첫 기능·첫 PR — 설계(데이터·모듈·ADR)

이 챕터에서 배우는 것

  • 추가할 두 엔드포인트의 요청·응답 데이터 구조(필드·타입·상태 값)를 모델로 설계해 명시할 수 있습니다.
  • 기존 모듈(라우터·모델·저장소·테스트)에 변경을 어디에 어떻게 끼울지, 모듈·함수 단위로 분해해 목록화할 수 있습니다.
  • 플랜 모드로 도출한 설계 결정을 ADR 5필드(결정·맥락·선택지·근거·결과)로 기록할 수 있습니다.
  • 입력→검증→상태 변경→응답의 요청 처리 순서를 다이어그램 1장으로 표현할 수 있습니다.

설계 개요: 기존 구조에 최소 변경으로 끼우기

앞 챕터(ch_13)에서 우리는 분석을 마쳤습니다. 무엇을 만드는지(FR: 완료 처리·상태 필터·에러 응답)와 어떻게 만드는지(NFR: 테스트·안전·팀 규약)를 검증 가능한 요구사항으로 적고, 범위를 작게 통제했으며, 기존 저장소가 id·title·status를 가진 인메모리 tasks API임을 탐색으로 파악했습니다. 이제 그 요구사항을 실제 코드 구조로 옮기는 설계(design) 단계입니다.

설계의 첫 원칙은 이미 정해져 있습니다. 기존 구조에 최소 변경으로 끼웁니다. 우리는 빈 폴더에서 새 앱을 만드는 것이 아니라, 이미 동작하는 팀의 코드에 작은 기능을 더하는 신입입니다. 그러므로 새 구조를 발명하기보다, 탐색으로 파악한 기존 패턴(라우터에 엔드포인트 정의, 없는 id는 404, 저장소 함수로 데이터 접근)을 그대로 따라 최소한만 더합니다.

설계 단계도 새 개념을 배우지 않습니다

이 챕터의 설계는 앞 단원 개념을 통합 적용합니다. 데이터 구조·모듈 분해는 ch_04 탐색(c04)으로 파악한 기존 구조 위에 얹고, ADR(설계 결정 기록)은 ch_06 플랜 모드(c06)로 계획을 받아 검토하며 도출하고, 에러 처리 설계(404·422)는 ch_11 디버깅(c11)의 시각으로 봅니다. 설계는 "코드를 쓰기 전에 머릿속 그림을 종이에 옮기는" 단계이며, 그 그림은 구현(ch_15)의 설계도가 됩니다.

이 챕터의 설계는 세 가지를 산출합니다. (1) 데이터 구조(요청·응답 모델과 상태 필드), (2) 모듈 변경 분해(어느 파일을 어떻게 바꾸는가), (3) ADR(왜 그렇게 결정했는가). 그리고 이 셋을 묶는 요청 처리 순서도로 마무리합니다.

데이터 구조 설계: 요청·응답 모델과 상태 필드

데이터 구조 설계란 "이 기능이 주고받는 데이터가 어떤 모양인가"를 정하는 일입니다. 우리 기능이 다루는 데이터는 세 가지입니다.

첫째, 할 일 한 건(Task)의 모양. 탐색에서 확인했듯 status 필드는 이미 존재합니다. 우리는 이 필드의 값을 명확히 두 가지(todo·done)로 제한하기 위해 문자열 열거형(enum, 이넘)으로 표현합니다. 열거형은 "허용된 값이 정해진 목록"을 코드로 못박는 방법입니다.

python
from enum import Enum
from pydantic import BaseModel


class Status(str, Enum):
    todo = "todo"
    done = "done"


class Task(BaseModel):
    id: int
    title: str
    status: Status = Status.todo
  • class Status(str, Enum)는 문자열이면서 열거형인 타입을 만듭니다. str을 함께 상속해, JSON 응답에서 "todo"·"done" 같은 문자열로 그대로 나가게 합니다. 허용된 값이 이 둘로 고정되므로, 다른 값("foo" 등)은 들어올 수 없습니다.
  • Task는 기존 모델을 그대로 따릅니다. status: Status = Status.todo는 "status는 Status 타입이고 기본값은 todo"라는 뜻입니다. 기존 저장소의 동작(새 작업은 todo로 시작)을 바꾸지 않으면서, 타입만 문자열에서 열거형으로 좁혔습니다.
  • 왜 불리언(done: bool)이 아니라 열거형일까요? 지금은 두 상태뿐이지만, 나중에 in_progress(진행 중) 같은 상태가 생길 수 있습니다. 열거형은 값을 한 줄 추가하는 것만으로 확장되지만, 불리언은 구조를 갈아엎어야 합니다(이 결정의 근거는 뒤의 ADR2에서 정식으로 기록합니다).

둘째, 완료 처리의 응답(complete response). 완료 처리는 새 데이터를 만들지 않고 기존 task의 status만 바꿉니다. 그러므로 응답은 별도 모델이 아니라, 변경된 Task 객체 그 자체(status가 done이 된)입니다. 클라이언트(요청한 쪽)는 응답을 보고 "정말 done이 됐구나"를 바로 확인할 수 있습니다.

셋째, 상태 필터의 입력(filter query). 상태 필터는 목록 엔드포인트에 쿼리 파라미터(query parameter) status를 더해 거릅니다. 쿼리 파라미터는 URL의 ? 뒤에 붙는 이름=값 형식의 입력입니다(/tasks?status=done). 받을 수 있는 값을 위에서 정의한 Status 열거형으로 제한하면, 허용 외 값은 FastAPI가 자동으로 막아 줍니다(뒤에서 다룰 422).

세 데이터 구조를 표로 정리하면 이렇습니다.

데이터 모양 쓰이는 곳
Task {id: int, title: str, status: Status} 모든 응답의 기본 단위
status 열거형 Status = todo \| done (문자열) 완료 처리의 결과 값, 필터의 입력 값
완료 응답 변경된 Task 객체(status=done) PATCH /tasks/{id}/complete의 200 응답
필터 입력 쿼리 파라미터 status(todo|done) GET /tasks?status= 의 입력

새 데이터를 만들기보다 기존을 좁히고 재사용합니다

우리 설계의 데이터 구조는 거의 전부 기존 Task의 재사용입니다. 완료 응답은 Task 그대로, 필터 입력은 기존 status 값 그대로입니다. 새로 더한 것은 "status를 열거형으로 좁힌 것" 하나뿐입니다. 신입의 좋은 설계는 화려한 새 구조가 아니라, 기존 것을 최대한 재사용하면서 필요한 만큼만 좁히거나 더하는 절제에서 나옵니다.

모듈·함수 변경 분해 (라우터·모델·저장소·테스트)

이제 "어느 파일을 어떻게 바꾸는가"를 정합니다. 이를 모듈 변경 분해(module decomposition)라고 합니다. 큰 변경을 한 덩어리로 보지 않고, 파일·함수 단위의 작은 변경 묶음으로 쪼개면, 각 변경이 무엇을 책임지는지 분명해지고 구현·커밋 단위(ch_09)로도 자연스럽게 이어집니다.

탐색으로 파악한 기존 구조(main·routers·models·store·tests)에 우리 변경을 어떻게 끼울지 정리하면 다음과 같습니다.

모듈(파일) 기존 책임 이번 변경 변경 크기
main.py FastAPI 앱 생성·라우터 등록 변경 없음(기존 라우터에 더하므로) 없음
routers/tasks.py tasks 엔드포인트 정의 완료 처리·상태 필터 엔드포인트 추가 중
models.py pydantic 모델 status를 Status 열거형으로 정의 소
store.py 인메모리 저장소 함수 상태 변경·필터 조회 함수 추가 소
tests/test_tasks.py 기존 엔드포인트 테스트 추가 엔드포인트의 테스트 추가(또는 새 파일) 중

각 모듈의 변경을 한 걸음 더 들여다봅니다.

  • models.py: 위에서 설계한 Status 열거형을 정의하고, Task.status의 타입을 그 열거형으로 둡니다. 가장 작은 변경이지만, 다른 모듈이 이 타입을 함께 쓰므로 가장 먼저 자리잡혀야 합니다.
  • store.py: 저장소에 두 함수를 더합니다. 하나는 "특정 id의 작업 상태를 done으로 바꾸는" 함수, 다른 하나는 "주어진 status로 목록을 거르는" 함수입니다. 엔드포인트가 직접 리스트를 만지지 않고 이 함수를 통하게 해, 데이터 접근을 한곳에 모읍니다(기존 패턴 유지).
  • routers/tasks.py: 실제 엔드포인트 두 개를 더합니다. 라우터는 "요청을 받아 → 검증하고 → store 함수를 호출하고 → 응답을 돌려주는" 얇은 층입니다. 데이터 처리는 store에 맡기고, 라우터는 HTTP의 입출력·에러(404·422)만 책임집니다.
  • tests/test_tasks.py: 분석의 유스케이스(UC1·UC2)와 에러 요구사항(FR4)을 테스트로 옮깁니다. 정상 경로(완료되면 200·done, 필터하면 거른 목록)와 비정상 경로(없는 id 404, 잘못된 status 422)를 모두 검증합니다.
  • main.py가 변경 없음이라는 점이 좋은 신호입니다. 기존 라우터에 엔드포인트를 더하는 방식이라, 앱 진입점은 건드리지 않아도 됩니다. 변경이 닿는 파일이 적을수록 위험과 리뷰 부담이 줍니다.
  • 변경 순서는 의존성 방향을 따릅니다. models(타입) → store(데이터 함수) → routers(엔드포인트) → tests(검증). 다만 NFR4(TDD)에 따라 실제 구현에서는 테스트를 먼저 쓰고 그다음 구현합니다(ch_15에서 다룸). 분해도는 "무엇이 무엇에 의존하는가"의 그림이고, 구현 순서는 TDD가 정합니다.
  • 각 모듈 변경이 커밋 단위 후보입니다(ch_09). 예컨대 "models·store 추가"와 "라우터 엔드포인트 추가"를 별도 논리 단위로 나눌 수 있습니다. 설계 분해가 곧 커밋 계획으로 이어집니다.

설계 결정 기록: ADR 5건 (플랜 모드로 도출)

설계에는 선택이 따릅니다. 완료 처리를 PATCH로 할까 POST로 할까? 상태를 불리언으로 둘까 열거형으로 둘까? 이런 선택을 그냥 코드에만 남기면, 나중에 "왜 이렇게 했지?"라는 질문에 아무도 답하지 못합니다. 그래서 ADR(Architecture Decision Record, 아키텍처 결정 기록)로 결정의 이유를 남깁니다.

ADR은 다음 5필드로 한 결정을 기록합니다.

필드 무엇을 적나
결정(Decision) 무엇으로 정했는가
맥락(Context) 어떤 상황·문제에서 결정하는가
선택지(Options) 고려한 대안들은 무엇인가
근거(Rationale) 왜 그 선택지를 골랐는가
결과(Consequences) 이 결정이 가져올 영향(좋은·나쁜)

이 ADR들은 플랜 모드(c06)로 도출합니다. 변경을 시작하기 전에 에이전트에게 "어떤 설계 선택지가 있고 무엇을 추천하는지" 읽기 전용으로 계획을 받아, 그 계획을 검토하며 결정을 확정합니다. 플랜 모드는 "바꾸기 전에 먼저 생각하고 합의하는" 단계이고, ADR은 그 합의의 기록입니다.

다음은 이번 프로젝트의 핵심 설계 결정 다섯 건입니다.

ADR1. 완료 처리 메서드 선택

필드 내용
결정 PATCH /tasks/{id}/complete
맥락 기존 task의 일부 상태(status)만 바꾼다
선택지 PATCH 전용 경로 · PUT 전체 교체 · POST 액션
근거 부분 상태 변경에는 PATCH가 의미상 맞고 /complete 경로가 의도를 명확히 드러낸다
결과 나중에 전체 교체가 필요해지면 별도 PUT을 추가하면 된다

PATCH는 "자원의 일부만 수정"을 뜻하는 HTTP 메서드입니다. 완료 처리는 title은 그대로 두고 status만 바꾸므로, 전체를 교체하는 PUT보다 PATCH가 정확합니다.

ADR2. 상태 표현 방식

필드 내용
결정 status 필드에 문자열 열거형(todo | done)
맥락 완료 여부를 표현해야 한다
선택지 불리언 done · 문자열 열거형 · 별도 상태 테이블
근거 향후 상태 확장(in_progress 등) 여지를 위해 열거형을 택한다
결과 불리언보다 검증 코드가 약간 늘지만 확장에 유연하다

ADR3. 필터 인터페이스

필드 내용
결정 GET /tasks에 status 쿼리 파라미터
맥락 기존 목록 엔드포인트를 거른다
선택지 쿼리 파라미터 · 별도 경로(/tasks/done) · 본문 필터
근거 REST 관례상 목록 필터는 쿼리 파라미터(?status=done)가 표준이다
결과 필터가 늘면 파라미터가 많아질 수 있어 문서화가 필요하다

ADR4. 에러 처리 정책

필드 내용
결정 없는 id는 404, 잘못된 status 값은 422
맥락 신입도 일관된 에러를 내야 한다
선택지 일괄 400 · 표준 상태 코드 · 커스텀 코드
근거 FastAPI·HTTP 관례를 따르는 표준 상태 코드가 클라이언트에 명확하다
결과 프런트가 상태 코드로 분기할 수 있고, 메시지 일관성을 유지해야 한다

사실 확인: 404와 422는 의미가 다릅니다

  • 404 Not Found: 요청한 자원이 없을 때입니다. 예: 존재하지 않는 PATCH /tasks/999/complete. 우리가 직접 HTTPException(status_code=404, ...)로 냅니다(기존 저장소 패턴과 동일).
  • 422 Unprocessable Entity: 요청 형식은 맞지만 값이 검증을 통과하지 못할 때입니다. 예: GET /tasks?status=foo처럼 허용 외 값. status를 Status 열거형으로 받게 하면, FastAPI가 자동으로 422를 냅니다(우리가 코드를 따로 쓰지 않아도 됩니다). 둘을 섞어 일괄 400으로 내면 클라이언트가 "없는 것"과 "잘못 보낸 것"을 구분하지 못합니다.

ADR5. 작업 방식(Claude Code 워크플로)

필드 내용
결정 탐색 → 플랜 모드 계획 → TDD 구현 → 커밋·PR → 리뷰 대응
맥락 신입이 안전하게 첫 기능을 추가해야 한다
선택지 바로 편집 · 탐색·플랜·TDD·리뷰 흐름
근거 안전(권한·플랜)·검증(TDD)·협업(커밋·PR·리뷰)을 결합해 신뢰성을 확보한다
결과 절차가 늘지만 첫 업무를 안전하고 검증 가능하게 수행한다

ADR5는 코드 구조가 아니라 일하는 방식 자체에 대한 결정입니다. 이 결정이 곧 구현 챕터(ch_15)의 마일스톤 순서(셋업·계획 → 테스트 먼저 → 구현 → 커밋·PR → 리뷰)가 됩니다. 종합 프로젝트의 12개 개념이 어떻게 하나의 흐름으로 묶이는지를 한 줄로 요약한 결정이기도 합니다.

요청 처리 순서도: 입력 → 검증 → 상태 변경 → 응답

데이터 구조와 모듈 분해, ADR을 모두 정했다면, 마지막으로 요청이 들어와 응답이 나가기까지의 처리 순서를 그립니다. 이 순서도는 구현(ch_15)에서 그대로 코드의 골격이 됩니다. 두 엔드포인트의 처리 순서를 차례로 봅니다.

완료 처리(PATCH /tasks/{id}/complete)의 순서는 다음과 같습니다.

  1. 입력: 경로에서 id(완료할 작업 번호)를 받는다.
  2. 검증: 저장소에서 그 id의 작업을 찾는다. 없으면 404로 응답하고 끝낸다.
  3. 상태 변경: 찾은 작업의 status를 done으로 바꾼다.
  4. 응답: 변경된 작업 객체를 200으로 돌려준다.

상태 필터(GET /tasks?status=)의 순서는 다음과 같습니다.

  1. 입력: 쿼리 파라미터에서 status를 받는다.
  2. 검증: status가 허용 값(todo·done)인지 확인한다. 허용 외면 422(FastAPI가 자동 처리).
  3. 조회: 저장소에서 그 status인 작업만 거른다. status가 없으면 전체를 돌려준다.
  4. 응답: 거른 목록을 200으로 돌려준다.

두 순서를 표로 비교하면 "정상 흐름"과 "에러 분기"가 한눈에 들어옵니다.

단계 완료 처리(PATCH) 상태 필터(GET)
입력 경로 파라미터 id 쿼리 파라미터 status
검증 작업 존재? 없으면 404 허용 값? 아니면 422(자동)
처리 status를 done으로 변경 status로 목록 필터
정상 응답 200 + 변경된 작업 200 + 거른 목록

설계대로 완료 처리 엔드포인트의 골격을 코드로 옮기면 다음과 같습니다. 아직 구현 챕터가 아니므로 설계가 어떻게 코드 모양으로 이어지는지 확인하는 용도로 봅니다.

python
from fastapi import APIRouter, HTTPException

import store
from models import Task, Status

router = APIRouter()


@router.patch("/tasks/{task_id}/complete", response_model=Task)
def complete_task(task_id: int) -> Task:
    task = store.get_task(task_id)
    if task is None:
        raise HTTPException(status_code=404, detail="task를 찾을 수 없습니다")
    task.status = Status.done
    store.save_task(task)
    return task
  • @router.patch(...)이 ADR1의 결정(PATCH 메서드·/complete 경로)을 코드로 옮긴 것입니다. 순서도의 1번(입력)이 함수 매개변수 task_id로 들어옵니다.
  • if task is None: raise HTTPException(status_code=404, ...)가 순서도 2번(검증·404)이며, 기존 저장소의 404 패턴을 그대로 따랐습니다(ch_04 탐색에서 확인한 패턴 재사용).
  • task.status = Status.done이 순서도 3번(상태 변경), return task가 4번(200 응답)입니다. response_model=Task로 응답이 Task 모양임을 명시해, 완료 응답이 곧 변경된 Task라는 ADR/데이터 설계와 일치시켰습니다.
  • 데이터 접근은 store.get_task·store.save_task 함수를 통합니다. 라우터가 리스트를 직접 만지지 않고 store에 맡겨, 모듈 분해(라우터=HTTP, store=데이터)를 지킵니다.

이렇게 분석(ch_13)의 요구사항이 설계(ch_14)의 데이터 구조·모듈 분해·ADR·순서도를 거쳐, 다음 챕터(ch_15)의 구현으로 매끄럽게 이어집니다. 설계가 충실하면 구현은 "설계도를 코드로 옮기는" 비교적 단순한 작업이 됩니다.

설계를 직접 해 봅니다. 먼저 ① 모범 예시를 확인하고, ② 빈 템플릿을 스스로 채운 뒤, ③ 자가체크로 점검합니다.

모범 예시: ADR 한 건 작성

"상태 필터 결과를 어떻게 정렬할까"라는 작은 설계 결정을 ADR 5필드로 적으면 다음과 같습니다.

필드 내용
결정 필터 결과를 id 오름차순으로 반환한다
맥락 필터한 목록의 순서가 정해지지 않으면 응답이 들쭉날쭉해 테스트가 불안정하다
선택지 정렬 안 함(저장 순서) · id 오름차순 · 생성 시각 내림차순
근거 id 오름차순은 단순하고 예측 가능하며, 인메모리 저장소에서 추가 비용이 거의 없다
결과 순서가 고정돼 테스트가 안정적이고, 나중에 정렬 옵션이 필요하면 쿼리 파라미터로 확장한다

핵심은 "정렬을 한다/안 한다"의 한 줄 결정에도 맥락·선택지·근거·결과를 함께 남겨, 나중에 누구든 "왜 이렇게 했는지" 알 수 있게 한 점입니다.

연습 1: 내 설계 결정을 ADR로 직접 작성하라

"완료된 작업을 다시 완료 처리하면(중복 완료) 어떻게 할까"라는 설계 결정을 내려, 위 모범 예시를 본떠 ADR 5필드로 직접 작성하세요. 정답을 빈칸에 맞추는 것이 아니라, 자신이 실제로 어떻게 설계하기로 정했는지를 적는 것이 핵심입니다.

아래 표를 그대로 옮겨, 오른쪽 칸에 내가 내린 결정을 직접 적으세요.

필드 내가 작성한 ADR
결정 (여기에 직접 적는다: 내가 택한 한 줄 결정)
맥락 (여기에 직접 적는다: 왜 이 결정이 필요한 상황인가)
선택지 (여기에 직접 적는다: 내가 비교한 대안들)
근거 (여기에 직접 적는다: 왜 그 선택지를 골랐나)
결과 (여기에 직접 적는다: 이 결정으로 무엇이 달라지나)

작성 안내: 선택지로 "이미 done이면 에러(409)를 낸다 / 그냥 200으로 현재 상태를 돌려준다 / 아무 변화 없이 멱등하게 둔다"를 떠올려 보세요. 신입의 첫 기능이라는 맥락에서 무엇이 더 단순하고 안전한지 자신의 판단과 근거를 직접 적습니다.

자가체크

  • [ ] status를 불리언이 아니라 열거형(todo·done)으로 설계해 확장 여지를 남겼는가?
  • [ ] 완료 응답을 새 모델이 아니라 변경된 Task 재사용으로 설계했는가?
  • [ ] 모듈 변경 분해에서 각 파일의 책임(라우터=HTTP, store=데이터)을 분리했는가?
  • [ ] 각 ADR이 5필드(결정·맥락·선택지·근거·결과)를 모두 갖췄는가?
  • [ ] 에러 설계에서 없는 id=404, 잘못된 status=422를 구분했는가?
  • [ ] 요청 처리 순서도에 정상 경로와 에러 분기를 함께 그렸는가?
  • [ ] 설계를 ch_06 플랜 모드로 받아 검토하며 도출했는가(바로 편집하지 않았는가)?

흔한 오류와 오개념

1. 기존 구조를 무시하고 새 구조를 발명한다

신입이 의욕이 앞서 "더 좋은 구조"를 새로 만들려다, 팀의 기존 패턴(라우터·store 분리, 404 패턴)과 어긋난 코드를 내놓는 일이 흔합니다. 설계의 기본은 기존 구조에 최소 변경으로 끼우기입니다. 탐색(c04)으로 파악한 패턴을 그대로 따르고, 정말 필요한 만큼만 더하세요. 새 구조는 리뷰에서 "왜 기존과 다르냐"는 질문을 부릅니다.

2. 결정만 적고 이유(맥락·근거·결과)를 빠뜨린다

"PATCH로 한다"만 적으면 ADR이 아닙니다. 나중에 "왜 POST가 아니라 PATCH지?"라는 질문에 답할 수 없기 때문입니다. ADR의 가치는 결정이 아니라 이유에 있습니다. 맥락·선택지·근거·결과를 함께 남겨야, 미래의 동료(그리고 미래의 나)가 결정을 이해하고 안전하게 바꿀 수 있습니다.

3. 404와 422를 일괄 400으로 뭉갠다

"에러면 다 400"으로 처리하면, 클라이언트가 "없는 것(404)"과 "잘못 보낸 것(422)"을 구분하지 못합니다. 표준 상태 코드를 의미에 맞게 쓰세요. 없는 자원은 404, 검증 실패는 422입니다. FastAPI는 열거형 쿼리 파라미터의 422를 자동으로 내주므로, 우리는 404만 직접 처리하면 됩니다.

4. 플랜 없이 바로 편집하며 설계한다

설계를 머릿속으로만 하고 곧장 코드를 쓰면, 잘못된 방향으로 여러 파일을 바꾼 뒤에야 문제를 발견합니다. 플랜 모드(c06)로 먼저 계획을 받아 데이터 구조·모듈 분해·결정을 검토하고, 합의된 설계를 ADR로 남긴 다음 구현에 들어가세요. "바꾸기 전에 생각한다"가 안전한 신입의 기본기입니다.

이 챕터 한 줄 정리

설계는 기존 구조에 최소 변경으로 끼우는 원칙 아래, 데이터 구조(status 열거형·Task 재사용)와 모듈 변경 분해(라우터·모델·저장소·테스트)를 정하고, 결정의 이유를 ADR 5필드로 남기며, 요청 처리 순서를 순서도로 그려 구현의 설계도를 완성하는 단계입니다. 다음 챕터(ch_15)에서는 이 설계를 TDD·마일스톤 증분으로 실제 구현하고 첫 PR을 올립니다.
