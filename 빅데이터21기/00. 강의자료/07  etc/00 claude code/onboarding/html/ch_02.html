Chapter 02

에이전트형 코딩의 작동 방식: 관찰→계획→도구→확인

입문

에이전트형 코딩의 작동 방식: 관찰 → 계획 → 도구 → 확인

이 장의 학습 목표

  • 같은 작업 하나를 두고 자동완성과 에이전트형 코딩의 차이를 구체적 예 1개 이상으로 설명할 수 있습니다.
  • 에이전트가 수행한 한 작업의 실행 기록에서 관찰·계획·도구 호출·결과 확인 네 단계를 각각 짚어 식별할 수 있습니다.
  • 주어진 도구 호출 순서에서 읽기 전용 도구(Read·Glob·Grep)와 부수효과 도구(Edit·Write·Bash)를 구분해 각각 언제 쓰였는지 읽어 낼 수 있습니다.
  • 에이전트 루프의 어느 단계에서 모호한 지시가 잘못된 가정으로 이어지는지 짚어, 명확한 지시와 검토가 왜 필요한지 근거를 들어 설명할 수 있습니다.

선수 지식 상기(c01): 앞 장에서 Claude Code를 설치·인증하고 첫 세션을 열어, 빈 폴더에서 hello.py를 만들어 실행시켜 보았습니다. 그때 "지시 → 파일 생성 → 실행 → 결과 확인"이 한 흐름으로 이어지는 것을 보았는데, 이 장은 바로 그 흐름의 정체를 자세히 들여다봅니다. 1장에서 도구를 켜는 법을 배웠다면, 2장에서는 그 도구가 어떻게 일하는지를 이해합니다.

이 장에서 가르치는 개념은 하나입니다.

  • 개념 c02 — 에이전트 루프와 자동완성과의 차이(the agent loop versus autocomplete): 에이전트형 코딩이 자동완성과 근본적으로 다른 이유를 "관찰 → 계획 → 도구 호출 → 결과 확인"의 루프로 이해하고, 어떤 도구가 언제 쓰이는지 읽어 내며, 왜 명확한 지시와 검토가 핵심인지 설명하는 법.

1. 도입: 자동완성과 무엇이 다른가

신입이 면접이나 학교에서 써 본 AI 코딩 도구는 대개 자동완성(autocomplete) 이었을 것입니다. 편집기에서 코드를 타이핑하면 회색 글씨로 다음 몇 줄이 떠오르고, Tab을 누르면 받아들여지는 방식입니다. 빠르고 편리하지만 한계가 분명합니다. 자동완성은 "지금 커서가 놓인 한 지점" 의 문맥만 봅니다. 옆 파일을 열어 보지도, 테스트를 돌리지도, 여러 파일에 걸친 변경을 스스로 적용하지도 못합니다. 결정과 실행은 전부 사람의 손에 남습니다.

1장에서 본 Claude Code는 달랐습니다. "hello.py를 만들어 실행해 줘"라는 한 문장에, 도구는 파일을 만들고(쓰기) 명령을 실행하고(Bash) 결과를 확인하는 데까지 스스로 갔습니다. 사람은 한 줄 한 줄을 받아 적은 것이 아니라, 목표를 주고 결과를 검토했습니다.

이 차이가 어디서 오는지를 정확히 이해하는 것이 이 장의 목표입니다. 왜냐하면 이 작동 방식을 알아야 "왜 모호하게 지시하면 엉뚱한 결과가 나오는지", "왜 에이전트가 만든 변경을 반드시 검토해야 하는지" 가 자연스럽게 이해되기 때문입니다. 도구의 작동 원리를 모르면 도구를 탓하게 되지만, 알면 더 잘 부릴 수 있습니다.

한눈에 보는 이 장의 지도

  • 자동완성과 에이전트의 근본 차이 → "다음 토큰 제안" vs "목표를 받아 루프를 돎"
  • 에이전트가 일하는 방식 → 관찰 → 계획 → 도구 호출 → 결과 확인의 4단계 루프
  • 에이전트가 쓰는 두 종류 도구 → 읽기 전용(Read·Glob·Grep) vs 부수효과(Edit·Write·Bash)
  • 변경을 안전하게 보는 법 → diff로 제시하고 사람이 검토
  • 루프가 끊기는 지점 → 모호한 지시·잘못된 가정

2. 정의: 에이전트형 코딩이란

정의

이 장의 핵심 개념을 한 문장으로 정의하겠습니다.

에이전트형 코딩(agentic coding) 은 모델이 커서 위치에서 다음 코드 한 토막을 제안하는 자동완성과 달리, 목표를 받아 "관찰(코드·파일을 읽고 검색) → 계획(무엇을 할지 정함) → 도구 호출(Read·Glob·Grep·Edit·Write·Bash 등 실제 도구 실행) → 결과 확인(실행·테스트로 검증)"의 루프를 스스로 반복하는 작동 방식입니다. Claude Code는 이 루프를 돌며 코드베이스를 직접 탐색하고 변경을 만들어 diff로 보여 주므로, 사용자는 코드를 통째로 붙여넣을 필요 없이 에이전트가 직접 파일을 읽게 합니다.

용어를 정리하겠습니다.

  • 토큰(token): 모델이 다루는 텍스트의 작은 조각(대략 단어·기호 단위)입니다. 자동완성은 본질적으로 "다음 토큰"을 예측해 이어 붙이는 일입니다.
  • 도구(tool): 에이전트가 실제 세계에 작용하기 위해 호출하는 기능입니다. 파일을 읽는 Read, 검색하는 Grep, 편집하는 Edit, 명령을 실행하는 Bash 등이 있습니다.
  • 루프(loop): 한 번 하고 끝나는 것이 아니라, 결과를 보고 다시 관찰·계획·실행으로 돌아오는 반복 구조입니다.

자동완성과의 대비

구분 자동완성(autocomplete) 에이전트형 코딩(Claude Code)
보는 범위 커서 주변 한 지점 프로젝트 전체(스스로 탐색)
받는 입력 지금까지 타이핑한 코드 자연어로 된 목표
하는 일 다음 몇 토큰 제안 읽기·검색·편집·실행까지
누가 실행하나 사람이 직접 타이핑·실행 에이전트가 도구로 실행
작업 단위 한 줄~한 블록 완결된 작업(여러 파일·여러 단계)
검증 사람이 따로 에이전트가 실행해 확인, 사람은 검토

한 문장 비유 자동완성이 "받아쓰기를 도와주는 손"이라면, 에이전트형 코딩은 "일을 통째로 맡길 수 있는 동료" 입니다. 손에게는 "이 단어 다음"을 맡기지만, 동료에게는 "이 기능을 추가해 테스트까지 통과시켜 줘"를 맡길 수 있습니다. 그래서 동료에게는 명확한 지시가 필요합니다.

3. 동작 원리: 관찰 → 계획 → 도구 호출 → 결과 확인 루프

에이전트형 코딩이 자동완성과 근본적으로 다른 이유는 루프로 동작하기 때문입니다. 사람이 한 번 지시하면, 에이전트는 다음 네 단계를 한 번 또는 여러 번 돕니다.

  1. 관찰(observe): 작업에 필요한 코드를 스스로 읽습니다. 폴더 구조를 훑고(Glob), 키워드를 검색하고(Grep), 관련 파일을 엽니다(Read). 사람이 코드를 붙여넣어 줄 필요가 없습니다.
  2. 계획(plan): 관찰한 내용을 바탕으로 "어떤 파일의 어디를 어떻게 바꿀지" 순서를 세웁니다. 복잡한 작업이면 사람에게 계획을 먼저 보여 주기도 합니다(플랜 모드, 6장).
  3. 도구 호출(act): 계획대로 부수효과가 있는 도구를 씁니다. 파일을 외과적으로 고치고(Edit), 새 파일을 만들고(Write), 명령을 실행합니다(Bash). 부수효과 도구는 권한 확인을 거칩니다(5장).
  4. 결과 확인(verify): 변경을 적용한 뒤 테스트나 실행으로 결과를 확인합니다. 기대와 다르면 1번으로 돌아가 다시 관찰·교정합니다.

이 네 단계가 사람의 피드백을 받아 반복되는 것이 핵심입니다. 자동완성은 1회성 제안이지만, 에이전트는 "고쳤다 → 실행했다 → 실패했다 → 원인을 찾아 다시 고쳤다"를 스스로 돌 수 있습니다.

한 작업을 루프로 따라가 보기

예를 들어 "tasks 목록을 돌려주는 엔드포인트가 빈 리스트를 반환하는 문제를 고쳐 줘"라는 지시를 받으면, 에이전트의 머릿속은 대략 이렇게 흐릅니다.

단계 에이전트가 하는 일 쓰는 도구
관찰 "tasks"가 어디서 정의·사용되는지 검색하고 관련 파일을 읽음 Grep, Read
계획 "라우터의 반환 부분이 빈 리스트를 주고 있으니 저장소에서 읽어오도록 고친다" (도구 없음, 추론)
도구 호출 해당 줄을 수정 Edit
결과 확인 테스트를 돌려 통과를 확인 Bash(pytest)

만약 결과 확인에서 테스트가 실패하면, 에이전트는 실패 메시지를 새로운 관찰로 삼아 다시 루프를 돕니다. 이 반복이 에이전트형 코딩의 본질입니다.

기억할 한 가지 사람의 역할이 "코드를 받아 적는 사람"에서 "목표를 주고 결과를 검토·교정하는 사람" 으로 바뀝니다. 그래서 다음 장(3장)이 곧바로 "어떻게 지시할 것인가(프롬프팅)"입니다. 좋은 지시가 좋은 루프를 만듭니다.

4. 읽기 전용 도구(Read·Glob·Grep)와 부수효과 도구(Edit·Write·Bash)

에이전트가 루프를 돌며 쓰는 도구는 성격에 따라 두 부류로 나뉩니다. 이 구분은 단순 분류가 아니라, 5장의 권한·승인 전체를 떠받치는 토대이므로 지금 정확히 익혀 둡니다.

읽기 전용 도구: 보기만 한다

도구 하는 일 비유
Read 파일 하나를 열어 내용을 읽음 책을 펼쳐 읽기
Glob 이름 패턴으로 파일 목록을 찾음(예: **/*.py) 서가에서 제목으로 책 찾기
Grep 파일 안의 텍스트를 검색(예: def create_task) 책 안에서 단어 찾기

읽기 전용 도구는 파일을 바꾸지 않습니다. 관찰(루프 1단계)에서 주로 쓰이며, 무엇이 어디 있는지 파악하는 데 쓰입니다. 아무것도 망가뜨리지 않으므로 안심하고 마음껏 쓸 수 있습니다.

부수효과 도구: 실제로 바꾼다

도구 하는 일 비유
Edit 기존 파일의 일부를 외과적으로 고침 문서에서 한 문장 고쳐 쓰기
Write 파일을 새로 만들거나 통째로 덮어씀 새 문서 작성·기존 문서 갈아엎기
Bash 터미널 명령을 실행(테스트·실행·삭제 등) 실제로 손을 써서 작동시키기

부수효과 도구는 파일을 바꾸거나 명령을 실행해 세계에 영향을 줍니다. 도구 호출(루프 3단계)과 결과 확인(4단계, 예: pytest 실행)에서 쓰입니다. 영향이 있으므로 Claude Code는 이런 도구를 호출할 때 권한을 확인합니다(5장에서 상세히). "보기만 하는 도구는 자유롭게, 바꾸는 도구는 확인을 거쳐"가 핵심입니다.

왜 이 구분이 중요한가 이 책의 흐름이 "탐색(4장) → 안전장치(5·6장) → 변경·검증(7장)"인 이유가 여기 있습니다. 읽기 전용 도구만 쓰는 탐색은 위험이 없어 먼저 익히고, 부수효과 도구를 쓰는 변경은 권한·플랜 모드라는 안전장치를 갖춘 뒤에 합니다. 신입이 "이 작업이 읽기만 하는가, 바꾸는가"를 구분할 줄 알면 사고를 크게 줄입니다.

5. worked example: 같은 작업을 자동완성식 vs 에이전트식으로 관찰

같은 목표 "인사 함수를 추가한다"를 두 방식으로 처리하면 어떻게 다른지 직접 비교해 보겠습니다.

자동완성식: 사람이 다 한다

자동완성 도구를 쓰면 사람이 직접 파일을 열고, 함수 이름을 타이핑하기 시작하면 본문을 제안받아 Tab으로 받아들입니다.

python
def greet(name: str) -> str:
    return f"안녕하세요, {name}님"

여기서 끝입니다. 이 함수가 정말 동작하는지 확인하려면 사람이 직접 호출 코드를 쓰고, 직접 터미널을 열어 실행해야 합니다.

python
print(greet("지훈"))
# 출력: 안녕하세요, 지훈님

파일 저장도, 실행도, 결과 확인도 전부 사람의 몫입니다.

에이전트식: 목표만 주면 루프가 돈다

같은 작업을 Claude Code에 맡기면 한 문장이면 됩니다.

console
> greet.py에 이름을 받아 "안녕하세요, {이름}님"을 돌려주는 greet 함수를
  추가하고, greet("지훈")을 실행해 결과를 보여 줘.

에이전트는 루프를 돕니다.

  • 관찰: greet.py가 있는지 확인합니다(Glob/Read).
  • 계획: 함수를 추가하고 호출해 실행한다는 순서를 세웁니다.
  • 도구 호출: 파일을 만들거나 고칩니다(Write/Edit).
  • 결과 확인: python greet.py를 실행해 출력을 보여 줍니다(Bash).

만들어진 파일과 실행 결과는 다음과 같습니다.

python
def greet(name: str) -> str:
    return f"안녕하세요, {name}님"


print(greet("지훈"))
# 출력: 안녕하세요, 지훈님
console
> python greet.py
안녕하세요, 지훈님

두 방식의 결정적 차이

  • 자동완성은 "본문 제안" 에서 멈춥니다. 파일 저장·실행·확인은 사람이 합니다.
  • 에이전트는 목표 한 문장을 받아 관찰·편집·실행·확인까지 한 흐름으로 처리합니다.
  • 결과물(코드)은 같아 보여도, 누가 일을 했는가가 다릅니다. 에이전트식에서는 사람이 "검토자"가 됩니다.
  • 그래서 사람의 핵심 능력이 "타이핑"에서 "명확한 지시 + 결과 검토" 로 옮겨갑니다.

6. diff로 변경을 제시하고 검토하기

에이전트가 부수효과 도구로 파일을 바꿀 때, Claude Code는 무엇을 어떻게 바꿨는지를 diff(차이) 로 보여 줍니다. diff는 변경 전후를 한눈에 비교해 주는 표준 형식으로, 신입이 에이전트의 변경을 검토하는 가장 중요한 화면입니다.

예를 들어 위 greet.py에 인사말 끝에 느낌표를 더하라고 지시하면, 다음과 같은 diff가 제시됩니다.

diff
  def greet(name: str) -> str:
-     return f"안녕하세요, {name}님"
+     return f"안녕하세요, {name}님!"

읽는 법은 간단합니다.

  • -로 시작하는 줄(빨강): 삭제되는 줄(변경 전).
  • +로 시작하는 줄(초록): 추가되는 줄(변경 후).
  • 기호 없는 줄: 바뀌지 않고 맥락으로 보여 주는 줄.

이 diff를 보면 "함수 본문의 반환 문자열 끝에 !가 붙는다"는 변경을 정확히 파악할 수 있습니다. 다른 줄은 건드리지 않았다는 것도 확인됩니다.

한 변경이 여러 곳에 걸칠 때

변경이 한 줄에 그치지 않고 여러 곳에 흩어지면, diff는 변경된 묶음을 각각 보여 줍니다. 예를 들어 greet 함수에 인사말 끝의 느낌표를 더하면서 호출부의 이름도 바꾸면 두 묶음이 나옵니다.

diff
  def greet(name: str) -> str:
-     return f"안녕하세요, {name}님"
+     return f"안녕하세요, {name}님!"


- print(greet("지훈"))
+ print(greet("수민"))

이때 검토 포인트는 "두 변경이 내가 지시한 것과 같은가"입니다. 느낌표 추가만 지시했는데 호출부의 이름까지 바뀌었다면, 그것은 요청하지 않은 변경이므로 되돌리도록 지시해야 합니다. diff는 이런 "은근슬쩍 섞인 변경"을 잡아내는 그물입니다. 변경 묶음이 많을수록 한 번에 통과시키기 쉬운데, 묶음이 늘어날수록 오히려 더 천천히 한 묶음씩 확인하는 습관이 사고를 줄입니다.

diff를 검토하는 신입의 눈 변경을 무심코 통과시키지 말고 세 가지를 봅니다.

  1. 의도한 곳만 바뀌었나 — 엉뚱한 파일·엉뚱한 줄이 바뀌지 않았는지.
  2. 빠진 것은 없나 — 지시한 변경이 빠짐없이 반영됐는지.
  3. 부작용은 없나 — 다른 동작을 깨뜨릴 변경이 섞이지 않았는지.

이 검토 습관이 7장의 "실행·테스트로 검증"과 짝을 이뤄, 에이전트가 만든 코드를 신뢰할 수 있게 만듭니다.

7. worked example: 도구 호출 순서(Grep → Read → Edit → Bash) 따라 읽기

이번에는 조금 더 실무에 가까운 상황에서, 에이전트가 어떤 도구를 어떤 순서로 쓰는지 따라 읽어 보겠습니다. 무대는 1장에서 셋업한 실습 저장소 team-tasks-api입니다. 이 저장소의 routers/tasks.py에는 다음 목록 엔드포인트가 있습니다.

python
# routers/tasks.py (team-tasks-api 발췌)
@router.get("", response_model=list[Task])
def list_tasks() -> list[Task]:
    return store.get_all_tasks()

여기에 "할 일 개수를 돌려주는 GET /tasks/count 엔드포인트를 추가해 줘"라고 지시했을 때, 에이전트가 도는 루프를 도구 호출 순서로 보겠습니다.

1) Grep — 어디서 정의되나 검색(관찰)

console
> Grep: "tasks" in routers/
  → routers/tasks.py:11  @router.get("", response_model=list[Task])
    routers/tasks.py:12  def list_tasks() -> list[Task]:

/tasks 관련 엔드포인트가 routers/tasks.py에 모여 있다는 것을 찾아냈습니다.

2) Read — 해당 파일을 읽어 맥락 파악(관찰)

console
> Read: routers/tasks.py (30 lines)

기존 엔드포인트가 @router.get(...) 데코레이터와 함수로 정의되고, 데이터는 store에서 읽어오는 스타일을 파악합니다. 같은 스타일로 추가해야 하기 때문입니다.

3) Edit — 새 엔드포인트를 같은 스타일로 추가(도구 호출)

에이전트가 제시하는 diff는 다음과 같습니다. 새 /count 경로는 /{task_id}보다 위에 두어야 합니다. 그렇지 않으면 count가 task_id 값으로 잡혀 버립니다.

diff
      return store.create_task(data)


+ @router.get("/count")
+ def count_tasks() -> dict:
+     return {"count": len(store.get_all_tasks())}
+
+
  @router.get("/{task_id}", response_model=Task)
  def get_task(task_id: int) -> Task:

4) Bash — 테스트로 결과 확인(결과 확인)

마지막으로 동작을 검증합니다. team-tasks-api의 tests/test_tasks.py에 테스트를 더해 저장소 전체를 돌립니다.

python
# tests/test_tasks.py (추가)
def test_count_tasks() -> None:
    client.post("/tasks", json={"title": "빨래"})
    client.post("/tasks", json={"title": "설거지"})
    response = client.get("/tasks/count")
    assert response.status_code == 200
    assert response.json() == {"count": 2}
console
> python -m pytest -q
........                                                                 [100%]
8 passed

도구 호출 순서를 읽어 내는 법

  • Grep → Read(관찰): "무엇이 어디 있나"를 먼저 찾고, 그 파일을 읽어 기존 스타일을 파악합니다. 그래서 추가된 엔드포인트가 기존과 같은 모양(@router.get, store 사용)입니다.
  • Edit(도구 호출): 파일 전체를 갈아엎지 않고, 필요한 부분만 외과적으로 더합니다(diff의 + 줄).
  • Bash: pytest(결과 확인): 기존 7개에 새 1개가 더해져 8 passed가 나옵니다. 이는 /tasks/count가 빨래·설거지 2개에 대해 {"count": 2}를 정확히 돌려준다는 증거입니다. 이 마지막 단계가 없으면 "동작한다"는 주장은 근거가 없습니다(7장).
  • 신입은 이 순서를 화면에서 따라 읽으며 "에이전트가 지금 관찰 중인가, 바꾸는 중인가, 검증 중인가"를 가늠할 수 있어야 합니다.

8. 루프가 끊기는 지점: 모호함·잘못된 가정

에이전트 루프는 강력하지만 만능이 아닙니다. 루프가 헛돌거나 엉뚱한 방향으로 가는 데는 거의 항상 같은 원인이 있습니다. 바로 지시의 모호함과 그로 인한 잘못된 가정입니다.

에이전트는 관찰한 것과 지시받은 것을 합쳐 계획을 세웁니다. 그런데 지시가 모호하면 빈틈을 가정으로 메웁니다. 그 가정이 사용자의 의도와 다르면, 그 뒤의 도구 호출·결과 확인이 전부 어긋난 방향으로 진행됩니다.

예: 모호한 지시가 부르는 어긋남

console
> 엔드포인트 좀 고쳐 줘.

이 지시에는 어느 엔드포인트인지, 무엇이 문제인지, 어떻게 되어야 하는지가 없습니다. 에이전트는 가정할 수밖에 없습니다. "아마 /tasks겠지", "아마 반환 형식을 바꾸라는 거겠지" 하고 추측해 엉뚱한 곳을 고칩니다. 결과는 사용자가 원한 것과 다릅니다.

반면 같은 의도를 구체적으로 주면 가정의 여지가 사라집니다.

console
> team-tasks-api의 routers/tasks.py에서 목록 엔드포인트 옆에
  GET /tasks/count를 추가해, store.get_all_tasks()의 개수를
  {"count": n}으로 반환하도록 고치고, pytest로 개수가 맞는지 확인해 줘.

이제 에이전트는 추측 없이 정확한 파일·문제·기대 결과·완료 조건을 알고 루프를 돕니다.

지시 에이전트의 가정 결과
"엔드포인트 좀 고쳐 줘" 대상·문제·기대를 전부 추측 어긋날 가능성 큼
"routers/tasks.py에 GET /tasks/count를 추가해 store 개수를 반환하도록 고치고 pytest로 확인" 추측할 여지 거의 없음 의도대로 진행

이것이 다음 장(3장 효과적 프롬프팅)이 필요한 이유입니다. 루프를 이해하면, 좋은 지시가 곧 좋은 결과의 전제임이 분명해집니다.

루프가 끊기는 또 다른 지점: 검증 생략 지시가 좋아도 결과 확인(4단계)을 건너뛰면 루프가 미완성으로 끝납니다. 에이전트가 "고쳤습니다"라고 해도 실행·테스트로 확인하기 전까지는 추정일 뿐입니다. 7장에서 이 습관을 본격적으로 다룹니다.

10. 흔한 오류와 오개념

오개념 1: "에이전트는 한 번에 완성된 정답을 내놓는다." 아닙니다. 에이전트는 루프를 돌며 점진적으로 만듭니다. 관찰 → 계획 → 도구 호출 → 결과 확인을 돌고, 결과 확인에서 문제가 보이면 그것을 새 관찰로 삼아 다시 돕니다. 7장 worked example의 pytest 실패처럼, 실패는 루프의 끝이 아니라 다음 반복의 입력입니다. "한 방에 완벽"을 기대하면 에이전트를 잘못 쓰게 됩니다. 검토와 교정 반복이 정석입니다.

오개념 2: "도구 호출은 일종의 마법이다." 아닙니다. 도구 호출은 읽기(Read)·검색(Grep·Glob)·편집(Edit·Write)·실행(Bash)의 평범한 조합일 뿐입니다. 7장에서 본 것처럼 "Grep으로 찾고 → Read로 읽고 → Edit로 고치고 → Bash로 테스트"가 전부입니다. 이 점을 알면 에이전트가 지금 무엇을 하는지 화면에서 따라 읽을 수 있고, 엉뚱한 도구를 쓰면 바로 알아챌 수 있습니다.

오개념 3: "에이전트가 '됐다'고 하면 된 것이다." 틀립니다. 결과 확인(실행·테스트) 없이 끝난 작업은 검증된 것이 아닙니다. 에이전트가 "엔드포인트를 추가했습니다"라고 해도, pytest가 통과했다는 출력이 없으면 그것은 추정입니다. 루프의 4번째 단계인 결과 확인을 사람이 함께 챙겨야 합니다(7장에서 본격적으로). diff 검토(6장)와 테스트 확인은 신입이 절대 건너뛰면 안 되는 두 관문입니다.

오개념 4: "코드를 채팅창에 붙여넣어 줘야 에이전트가 본다." 아닙니다. 에이전트는 직접 파일을 읽습니다(Read·Grep). 코드를 붙여넣으면 오히려 실제 파일과 어긋난 옛 버전을 보게 될 수 있습니다. 정확한 작업을 원하면 붙여넣기 대신 "routers/tasks.py를 읽고..."처럼 실제 파일을 가리키는 것이 맞습니다(다음 장의 @파일 멘션으로 더 정교해집니다).

자주 묻는 질문

Q. 에이전트가 도구를 쓰는 게 화면에 어떻게 보이나요? A. REPL에서 작업을 지시하면, 에이전트가 도구를 호출할 때마다 화면에 어떤 도구로 무엇을 했는지가 줄 단위로 표시됩니다(예: Read routers/tasks.py, Edit routers/tasks.py, Bash: python -m pytest -q). 이 줄들을 따라 읽으면 지금 에이전트가 관찰 중인지, 바꾸는 중인지, 검증 중인지 알 수 있습니다. 7장 worked example의 1)~4)가 바로 그 화면을 글로 옮긴 것입니다.

Q. 에이전트가 엉뚱한 방향으로 가면 어떻게 멈추나요? A. 1장에서 배운 대로 Esc로 진행 중인 작업을 중단합니다. 그런 뒤 지시를 더 구체적으로 다듬어 다시 줍니다. 루프가 어긋나는 원인은 대개 모호한 지시(8장)이므로, 멈추고 지시를 고치는 것이 가장 빠른 교정입니다.

Q. 읽기 전용 도구만 쓰는 작업은 권한 확인이 없나요? A. 읽기 전용 도구(Read·Glob·Grep)는 파일을 바꾸지 않으므로 자유롭게 쓰입니다. 권한 확인이 붙는 것은 부수효과 도구(Edit·Write·Bash)입니다. 자세한 권한 규칙은 5장에서 다룹니다. 지금은 "보기만 하는 도구와 바꾸는 도구가 나뉘고, 안전장치는 바꾸는 쪽에 붙는다"만 기억하면 됩니다.

Q. 결과 확인은 항상 테스트로 해야 하나요? A. 테스트(pytest)가 가장 분명한 증거이지만, 작업에 따라 명령 실행 결과·서버 응답·출력 확인으로도 합니다. 핵심은 "에이전트의 말"이 아니라 "실제 실행 결과"로 확인한다는 점입니다. 7장에서 실행·테스트 검증을 본격적으로 익힙니다.

이 장 요약

  • 에이전트형 코딩은 자동완성("다음 토큰 제안")과 달리 목표를 받아 루프를 도는 작동 방식입니다.
  • 루프는 관찰(Read·Grep·Glob) → 계획 → 도구 호출(Edit·Write·Bash) → 결과 확인(실행·테스트) 의 4단계이며, 미완이면 다시 관찰로 돌아옵니다.
  • 도구는 읽기 전용(보기만 함) 과 부수효과(실제로 바꿈) 로 나뉘고, 부수효과 도구는 권한 확인을 거칩니다(5장).
  • 변경은 diff로 제시되며, 신입은 "의도한 곳만·빠짐없이·부작용 없이" 바뀌었는지 검토합니다.
  • 루프가 끊기는 주범은 모호한 지시 → 잘못된 가정과 검증 생략입니다. 그래서 다음 장은 명확한 지시(프롬프팅) 입니다.

다음 장에서는 루프를 제대로 굴리는 출발점, 곧 목표·맥락·제약·완료 조건을 갖춘 좋은 작업 지시를 작성하는 법을 배웁니다.
