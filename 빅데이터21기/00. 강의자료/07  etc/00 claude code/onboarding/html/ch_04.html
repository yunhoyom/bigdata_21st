Chapter 04

낯선 팀 코드 파악하기: 에이전트로 코드베이스 탐색

기초

4장 낯선 팀 코드 파악하기: 에이전트로 코드베이스 탐색

이 장은 단원 4(u4)의 유일한 챕터이며, 여기서 배우는 개념은 기존 코드베이스 탐색·이해시키기(exploring and understanding an existing codebase, c04) 한 가지입니다. 앞 단원에서 익힌 작업 지시 기술(c03)을 낯선 팀 코드를 이해하는 일에 적용합니다. 무엇을 바꿀지 정하기 전에, 코드를 안전하게 파악하는 법을 다룹니다.

이 장을 마치면 할 수 있는 것

  • 처음 받은 FastAPI 저장소에서 에이전트에게 구조와 핵심 흐름을 요약시켜, 엔드포인트·핵심 모듈을 담은 구조 지도 1장을 작성할 수 있습니다.
  • 낯선 코드에 대해 시니어 엔지니어에게 묻듯 구체적 질문 3개 이상을 던져 동작·책임을 파악할 수 있습니다.
  • 특정 라우터·함수가 어디서 정의·사용되는지 에이전트에게 추적시켜 그 위치(파일·줄)를 특정할 수 있습니다.
  • 주어진 작업이 변경 없이 이해만 하는 읽기 전용 탐색인지 변경 작업인지 구분해, 탐색 단계에서 파일을 바꾸지 않도록 판단할 수 있습니다.

4.1 도입: 신입의 첫 난관은 낯선 코드다

팀에 합류한 신입이 가장 먼저 마주하는 벽은 기능이 어렵다가 아니라 코드가 낯설다입니다. 처음 받은 저장소를 열면 폴더가 수십 개, 파일이 수백 개이고, 어디서부터 봐야 할지, 이 함수가 어디서 불리는지, 데이터가 어디를 거쳐 흐르는지 막막합니다. 예전 같으면 며칠을 들여 파일을 하나씩 열어 보거나, 바쁜 시니어를 붙잡고 물어봐야 했습니다.

Claude Code는 이 벽을 낮춰 줍니다. 에이전트가 직접 저장소를 훑어 구조·의존성·흐름을 몇 초 만에 설명할 수 있기 때문입니다. 신입은 시니어 동료에게 묻듯 "이 프로젝트는 무엇을 하나요?", "할 일은 어디에 저장되나요?", "이 함수가 던지는 예외는 뭐죠?"라고 물으면 됩니다. 다른 점은, 이 시니어는 24시간 옆에 있고, 같은 질문을 백 번 물어도 귀찮아하지 않으며, 답의 근거가 된 실제 파일·줄까지 짚어 준다는 것입니다.

왜 이 개념이 지금 필요한가

종합 프로젝트에서 여러분은 기존 팀 FastAPI 저장소에 첫 기능을 추가하게 됩니다. 이 책이 제공하는 team-tasks-api(1장에서 셋업한 그 저장소)가 바로 그 "기존 팀 저장소"입니다. 그런데 낯선 코드를 이해하지 못한 채로 바꾸면, 기존 동작을 깨뜨리거나 팀 스타일과 어긋나기 쉽습니다. 그래서 "안전하게 변경하기"(5~6장)보다 먼저 "안전하게 이해하기"를 배웁니다. 탐색은 변경의 선행 단계이고, 잘 묻는 능력은 잘 바꾸는 능력의 토대입니다.

선수 개념 한 줄 상기(c03). 앞 장에서 좋은 작업 지시는 목표·맥락·제약·완료 조건을 담는다고 배웠습니다. 탐색 질문에도 같은 원칙이 적용됩니다. "코드 좀 설명해 줘"(모호)보다 "app/ 아래 구조를 폴더별 역할로 요약하고, 엔드포인트 목록을 표로 정리해 줘"(목표·맥락·완료 조건이 있음)가 훨씬 쓸모 있는 답을 끌어냅니다. 잘 묻는 것은 잘 지시하는 것의 한 갈래입니다.

4.2 정의: 에이전트 검색으로 구조·의존성·흐름을 자동 파악

개념을 한 문장으로 못 박습니다.

기존 코드베이스 탐색·이해시키기(c04)란, Claude Code의 에이전트 검색(agentic search)을 이용해 저장소의 구조·의존성·핵심 흐름을 스스로 훑게 하고, 시니어에게 묻듯 구체적 질문을 던져, 코드를 바꾸지 않고 이해만 하는 읽기 전용(read-only) 활동을 말합니다.

여기서 에이전트 검색이 무슨 뜻인지 풀어 봅니다. 2장에서 에이전트는 관찰 단계에서 Glob(파일 이름 찾기)·Grep(내용 검색)·Read(파일 읽기) 같은 읽기 전용 도구를 쓴다고 배웠습니다. 에이전트 검색이란 바로 이 도구들을 에이전트가 스스로 조합해 코드베이스를 훑는 것입니다. 여러분이 "이 프로젝트 뭐 하는 거야?"라고 물으면, 에이전트는 다음과 같이 알아서 움직입니다.

  1. Glob으로 어떤 파일들이 있는지 목록을 봅니다(**/*.py, README* 등).
  2. Read로 진입점(main.py)·설정(requirements.txt·README)을 읽습니다.
  3. Grep으로 핵심 키워드(FastAPI, APIRouter, include_router 등)가 어디 있는지 찾습니다.
  4. 모은 정보를 종합해 구조·역할·흐름을 설명합니다.

핵심은, 여러분이 컨텍스트 파일을 일일이 고를 필요가 없다는 점입니다. 어떤 파일을 봐야 답할 수 있는지 에이전트가 스스로 판단해 찾아 읽습니다. 신입이 "어느 파일을 봐야 할지 모르겠다"는 바로 그 막막함을, 에이전트 검색이 대신 풀어 줍니다.

탐색은 "읽기 전용"이 기본입니다

이 장의 활동은 전부 읽고 답만 받는 것입니다. 파일을 바꾸지 않으므로 위험이 없고, 따라서 마음껏 물어봐도 됩니다. 관찰에 쓰이는 Glob·Grep·Read는 부수효과가 없어 권한 확인 없이 자유롭게 실행됩니다(권한은 5장에서 다룹니다). "이해가 먼저, 변경은 나중"이라는 순서를 몸에 익히는 것이 이 장의 큰 목표입니다.

4.3 동작 원리: 탐색 질문이 코드 이해로 이어지는 흐름

낯선 저장소를 이해하는 데에는 효과적인 질문의 순서가 있습니다. 넓게 시작해 점점 좁혀 들어가는 깔때기(funnel) 모양입니다.

단계 질문의 성격 예 얻는 것
1. 전체 조망 "이 프로젝트는 무엇을 하나?" "이 API가 무슨 일을 하고, 폴더 구조는 어떻게 나뉘나요?" 큰 그림·진입점
2. 표면 목록 "무엇이 노출돼 있나?" "엔드포인트 목록을 메서드·경로·역할 표로 정리해 주세요." 기능의 목록
3. 흐름 추적 "데이터가 어디를 거치나?" "할 일을 만들면 요청이 어느 함수들을 거쳐 저장되나요?" 모듈 간 연결
4. 국소 심화 "이 한 곳은 어떻게 동작하나?" "create_task가 처리하는 입력과 던지는 예외는 무엇인가요?" 변경할 지점의 세부

이 순서가 중요한 이유는, 위에서 아래로 좁혀야 길을 잃지 않기 때문입니다. 처음부터 한 함수의 세부(4단계)로 뛰어들면 그 함수가 전체에서 어떤 역할인지 몰라 맥락이 붕 뜹니다. 반대로 1~2단계로 큰 지도를 먼저 그리면, 이후의 세부 질문이 그 지도 위에 정확히 꽂힙니다.

각 단계의 답은 다음 질문을 낳습니다. 2단계에서 "할 일을 만드는 POST /tasks가 있구나"를 알면, 3단계에서 "그럼 만든 할 일은 어디에 저장되지?"가 자연스럽게 나오고, 그 답이 store.py를 가리키면 4단계에서 "store.create_task는 정확히 무엇을 하지?"로 이어집니다. 이렇게 질문 → 답 → 다음 질문이 사슬처럼 연결되며 이해가 쌓입니다. 이것이 탐색 질문이 코드 이해로 이어지는 흐름입니다.

4.4 worked example: FastAPI 저장소 구조·엔드포인트 요약시키기

이제 실제로 해 봅니다. 무대는 팀에서 처음 받은 FastAPI 저장소 — 바로 1장에서 셋업한 실습 저장소 team-tasks-api — 이고, 구조는 다음과 같습니다(이 저장소는 이 장 전체에서 계속 씁니다).

text
team-tasks-api/
├── main.py             # FastAPI 앱 생성, 라우터 등록, GET /health
├── models.py           # TaskStatus, TaskCreate, Task (pydantic 모델)
├── store.py            # 메모리 저장소 함수
├── routers/
│   ├── __init__.py
│   └── tasks.py        # /tasks 엔드포인트들
├── tests/
│   └── test_tasks.py
└── requirements.txt

각 파일의 실제 내용은 다음과 같습니다. 신입의 눈으로는 처음엔 이게 어떻게 연결되는지 한눈에 안 보입니다.

python
# main.py
from fastapi import FastAPI
from routers import tasks

app = FastAPI(title="Tasks API")
app.include_router(tasks.router)


@app.get("/health")
def health_check() -> dict[str, str]:
    return {"status": "ok"}
python
# models.py
from enum import Enum
from pydantic import BaseModel


class TaskStatus(str, Enum):
    todo = "todo"
    done = "done"


class TaskCreate(BaseModel):
    title: str


class Task(BaseModel):
    id: int
    title: str
    status: TaskStatus = TaskStatus.todo
python
# store.py
from typing import Optional
from models import Task, TaskCreate, TaskStatus

_db: dict[int, Task] = {}
_next_id: int = 1


def create_task(data: TaskCreate) -> Task:
    global _next_id
    task = Task(id=_next_id, title=data.title, status=TaskStatus.todo)
    _db[_next_id] = task
    _next_id += 1
    return task


def get_all_tasks() -> list[Task]:
    return list(_db.values())


def get_task(task_id: int) -> Optional[Task]:
    return _db.get(task_id)
python
# routers/tasks.py
from fastapi import APIRouter, HTTPException
from models import Task, TaskCreate
import store

router = APIRouter(prefix="/tasks", tags=["tasks"])


@router.get("", response_model=list[Task])
def list_tasks() -> list[Task]:
    return store.get_all_tasks()


@router.post("", response_model=Task, status_code=201)
def create_task(data: TaskCreate) -> Task:
    return store.create_task(data)


@router.get("/{task_id}", response_model=Task)
def get_task(task_id: int) -> Task:
    task = store.get_task(task_id)
    if task is None:
        raise HTTPException(status_code=404, detail="Task not found")
    return task

  그리고 노출된 엔드포인트를 메서드·경로·하는 일 표로 정리해 줘.

에이전트는 에이전트 검색으로 main.py·routers/tasks.py·models.py·store.py를 찾아 읽고, 다음과 같이 답합니다.

text
이 프로젝트는 "할 일(task)"을 만들고 조회하는 작은 FastAPI 기반 REST API입니다.

구조:
- main.py     : FastAPI 앱을 만들고 tasks 라우터를 등록하는 진입점(+ /health)
- models.py   : 요청·응답 데이터 구조(TaskCreate, Task)와 상태 열거형(TaskStatus)
- store.py    : 메모리(dict)에 할 일을 보관·조회하는 저장소 함수
- routers/tasks.py : /tasks 경로의 엔드포인트들

엔드포인트:
| 메서드 | 경로            | 하는 일                                   |
|--------|-----------------|-------------------------------------------|
| GET    | /health         | 서버 상태 확인({"status": "ok"})          |
| GET    | /tasks          | 모든 할 일 목록 반환                       |
| POST   | /tasks          | 새 할 일 생성(201), status는 todo로 시작   |
| GET    | /tasks/{task_id}| 단건 조회, 없으면 404                      |

이 한 번의 질문으로, 며칠 걸릴 "구조 파악"이 몇 초로 줄었습니다. 이제 큰 지도가 손에 들어왔습니다.

이 질문이 좋은 답을 끌어낸 이유

  • 넓게 시작(1~2단계): 세부 함수가 아니라 "무엇을 하는 API인가 + 구조 + 엔드포인트 목록"이라는 큰 그림을 먼저 물었습니다.
  • 완료 조건 명시: "역할별로 요약", "메서드·경로·하는 일 표"처럼 답의 형태를 지정해, 산만한 설명 대신 정리된 표를 받았습니다(c03의 완료 조건이 탐색 질문에도 그대로 적용됩니다).
  • 읽기 전용: 이 과정에서 파일은 한 글자도 바뀌지 않았습니다. 에이전트는 Read·Grep으로 읽기만 했습니다.

4.5 온보딩 질문법: 시니어에게 묻듯 질문하기

큰 지도를 그렸으면, 이제 시니어에게 묻듯 구체적으로 파고들 차례입니다. 좋은 온보딩 질문에는 공통된 형태가 있습니다. 신입이 막연하게 "이거 어떻게 되나요?"라고 묻는 대신, 다음 네 종류의 질문을 의식적으로 던지면 이해가 빠릅니다.

질문 유형 무엇을 알아내나 예
무엇을(what) 책임·역할 "store.py는 무슨 책임을 지나요?"
어디서(where) 정의·사용 위치 "Task 모델은 어디서 정의되고 어디서 쓰이나요?"
어떻게(how) 흐름·연결 "할 일을 만들면 요청이 어느 함수들을 차례로 거치나요?"
만약(what if) 예외·엣지 케이스 "빈 제목으로 만들면 어떻게 되나요? 없는 id를 조회하면요?"

이 네 가지는 사실 실제 시니어에게 온보딩 받을 때 묻는 질문과 똑같습니다. 다른 점은, 에이전트는 답하면서 근거가 된 파일과 줄을 함께 짚어 준다는 것입니다. 그래서 답을 받은 뒤 "그 부분을 직접 열어 확인"하기가 쉽습니다.

질문에 "근거를 보여 줘"를 붙이세요

탐색 질문 끝에 "그 근거가 되는 파일·함수도 같이 알려 줘"를 붙이면, 에이전트가 추측이 아니라 실제 코드를 짚어 답하게 유도할 수 있습니다. 예: "할 일이 어디 저장되는지, 그 근거 함수까지 알려 줘." 이러면 "store.py의 create_task가 _db 딕셔너리에 넣습니다"처럼 검증 가능한 답이 옵니다. 요약을 곧이곧대로 믿지 않고 근거로 확인하는 습관이 신입에게 특히 중요합니다(4.10 참고).

이제 이 네 유형 질문을 종이에 만들지 말고 team-tasks-api 에이전트에게 실제로 물어 봅니다. 이 장의 모든 연습은 읽기 전용 탐색이므로 코드를 바꾸지 않습니다.

모범: 네 유형 질문을 실제로 물어 근거까지 받은 예

team-tasks-api에서 claude를 실행하고 네 유형 질문을 던지면, 에이전트는 답과 함께 근거 파일·함수를 짚어 줍니다(아래는 화면 답을 요약해 옮긴 예).

text
[무엇을] "이 저장소는 무엇을 하나요? 한 줄로." → 할 일을 만들고 조회하는 FastAPI REST API
[어디서] "할 일이 실제로 어디에 저장되나요? 근거 함수까지." → store.py의 create_task가 _db(dict)에 저장
[어떻게] "할 일을 만들면 요청이 어느 함수를 차례로 거치나요?" → create_task(routers) → store.create_task → _db
[만약]   "빈 제목으로 만들면 어떻게 되나요?" → models.py TaskCreate.title 검증, 없으면 422

직접 해보기 (team-tasks-api 에이전트에게 실제로 물어보기)

즉시 연습 A — 네 유형 질문을 실제로 물어 답과 근거를 기록하라 (2종 1세트 · 1/2)

team-tasks-api에서 claude를 실행하고, 네 유형(무엇을·어디서·어떻게·만약) 질문을 각각 하나씩 실제로 물어보세요(4.4의 예와 겹치지 않게). 각 질문 끝에 "그 근거가 되는 파일·함수도 같이 알려 줘"를 붙입니다. 그리고 에이전트가 실제로 답한 내용과 짚어 준 근거를 옮겨 적으세요.

text
[무엇을] 내가 물은 질문 / 에이전트 답 / 짚어 준 파일:
[어디서] 내가 물은 질문 / 에이전트 답 / 짚어 준 파일·함수:
[어떻게] 내가 물은 질문 / 에이전트 답(거치는 함수 순서):
[만약]   내가 물은 질문 / 에이전트 답 / 검증이 일어나는 위치:

확인: 위 답 중 하나를 골라, 에이전트가 짚어 준 파일을 직접 열어(Read 또는 에디터로) 답이 실제 코드와 맞는지 한 번 대조하세요.

text
직접 열어 대조한 파일과, 답이 실제 코드와 맞았는지:

즉시 연습 A 자가체크 — 손으로 물어봤는지 확인하세요.

  • [ ] 네 유형 질문을 team-tasks-api 에이전트에게 실제로 물었다.
  • [ ] 각 답에 에이전트가 짚어 준 근거 파일·함수를 함께 기록했다.
  • [ ] 답 하나 이상을 실제 파일을 열어 대조해, 요약을 맹신하지 않고 근거로 확인했다.
  • [ ] 이 연습 동안 코드를 한 줄도 바꾸지 않았다(읽기 전용 유지).

4.6 worked example: tasks 데이터 흐름·검증 경로 추적

이번에는 흐름 추적(3단계)을 해 봅니다. "할 일을 만들 때 요청이 어디를 거쳐 저장되고, 어디서 검증되는가"를 추적시킵니다.

console
> POST /tasks로 할 일을 만들면, 요청이 어느 함수들을 차례로 거쳐 저장되는지
  흐름을 단계로 정리해 줘. 제목 검증은 어디서 일어나는지도 근거 코드와 함께 알려 줘.

에이전트는 routers/tasks.py → store.py → models.py를 따라가며 다음과 같이 답합니다.

text
POST /tasks 요청의 흐름:
1. routers/tasks.py 의 create_task(data: TaskCreate)가 요청을 받습니다.
   - FastAPI가 요청 본문을 TaskCreate로 만들면서 *검증*이 먼저 일어납니다.
2. 검증 통과 시, store.create_task(data)를 호출합니다.
3. store.create_task는 새 id를 매겨 Task(id=..., title=..., status=todo)를 만들고
   _db 딕셔너리에 저장한 뒤 그 Task를 반환합니다.
4. 반환된 Task가 201 상태로 응답됩니다.

검증 경로:
- models.py 의 TaskCreate.title 은 str 타입으로 선언돼 있습니다. title이
  빠지거나 문자열이 아니면 FastAPI가 422를 자동 반환합니다.
  (지금은 길이·빈 문자열 제한이 없습니다 — 그 제한을 더하는 것이 이후 과제입니다.)

이 설명이 맞는지 검증 규칙만 떼어 직접 돌려 확인해 봅니다.

python
# 검증 규칙 동작 확인(pydantic 발췌 실행)
from pydantic import BaseModel, ValidationError


class TaskCreate(BaseModel):
    title: str


print(TaskCreate(title="문서 읽기").title)

try:
    TaskCreate()  # title 누락
except ValidationError:
    print("title 누락 거부됨")
# 출력: 문서 읽기
# 출력: title 누락 거부됨

정상 요청은 통과하고, title이 빠진 요청은 검증에서 막힙니다. 에이전트가 설명한 "검증은 TaskCreate에서 일어난다"가 실제와 일치함을 직접 확인했습니다.

흐름 추적에서 본 것

  • 데이터는 라우터(입구) → 저장소(보관) → 모델(검증·형태) 의 세 모듈을 거칩니다. 한 파일만 봐서는 안 보이던 연결이 드러났습니다.
  • 검증은 핸들러 안의 if문이 아니라 모델(TaskCreate의 타입 선언) 에서 선언적으로 일어납니다. 이걸 알면, 나중에 검증 규칙(예: 빈 제목 거부)을 더할 때 어느 파일을 고쳐야 하는지가 분명해집니다.
  • 추적 결과를 직접 실행으로 검증했습니다 — 요약을 믿기만 하지 않고 근거로 확인하는 태도입니다.

4.7 특정 함수·엔드포인트의 책임과 예외 흐름 묻기

마지막 깊이는 국소 심화(4단계)입니다. 변경할 후보 지점을 정했다면, 그 함수 하나의 책임과 예외 흐름을 정밀하게 묻습니다.

console
> routers/tasks.py 의 get_task 함수가 정확히 무슨 책임을 지고,
  어떤 경우에 어떤 예외(상태 코드)를 내는지 알려 줘.
text
get_task(task_id: int)의 책임:
- 주어진 task_id로 단건 할 일을 조회해 반환합니다.

분기·예외 흐름:
- store.get_task(task_id)가 None을 돌려주면(=해당 id 없음)
  HTTPException(status_code=404, detail="Task not found")를 던집니다.
- 존재하면 그 Task를 그대로 반환합니다(200).
- 참고: task_id는 경로 파라미터가 int로 선언돼, 숫자가 아닌 값이 오면
  FastAPI가 핸들러에 들어오기 전에 422로 막습니다.

이 "분기·예외 흐름"이 정확히 변경 작업의 출발점입니다. 예를 들어 "없는 id면 404 대신 빈 응답을 주자"는 요구가 생기면, 어디를 고쳐야 하는지(이 if task is None 분기)가 이미 명확합니다. 탐색이 변경의 좌표를 찍어 준 셈입니다.

분기 동작을 핵심만 떼어 확인합니다.

python
# get_task 분기 로직 확인(발췌 실행)
_db = {1: {"id": 1, "title": "문서 읽기", "status": "todo"}}

def get_task(task_id):
    task = _db.get(task_id)
    if task is None:
        return (404, "Task not found")
    return (200, task)

print(get_task(1))
print(get_task(2))
# 출력: (200, {'id': 1, 'title': '문서 읽기', 'status': 'todo'})
# 출력: (404, 'Task not found')

존재하는 id는 200을, 없는 id는 404를 돌려주어, 에이전트가 설명한 예외 흐름과 정확히 맞습니다.

4.8 읽기 전용 탐색과 결과 메모로 정리하기

탐색의 마지막 습관은 두 가지입니다. 읽기 전용을 지키는 것과 알아낸 것을 메모로 남기는 것.

읽기 전용을 지킨다. 탐색 단계에서는 코드를 바꾸지 않습니다. 목적이 "이해"이기 때문입니다. 그런데 탐색하다 보면 "여기 이거 잘못된 것 같은데 김에 고칠까?" 하는 충동이 듭니다. 이건 위험합니다. 아직 전체 맥락을 다 파악하지 못한 상태라, 멀쩡한 것을 망가뜨리거나 다른 작업과 섞여 리뷰가 어려워집니다. 이해와 변경을 분리하는 것이 안전의 기본입니다.

순수하게 읽기만 하고 싶을 때 쓸 수 있는 두 가지 방법이 있습니다.

  • 1회성 질의(claude -p): 한 번 묻고 답만 받습니다. 세션을 길게 열지 않고 빠르게 확인할 때 좋습니다.
console
$ claude -p "이 폴더의 엔드포인트를 메서드·경로 표로 요약해 줘"
  • 플랜 모드: 에이전트를 읽기 전용으로 묶어 두는 모드입니다. 편집·쓰기 도구가 아예 차단되므로, 탐색·분석에 안성맞춤입니다. (플랜 모드는 6장에서 본격적으로 배웁니다 — 지금은 "탐색을 읽기 전용으로 강제하는 장치가 있다" 정도만 알아 둡니다.)

알아낸 것을 메모로 남긴다. 탐색으로 그린 지도는 머릿속에만 두면 곧 흐려집니다. 구조·엔드포인트·데이터 흐름·주의점을 짧은 메모(예: 저장소 안의 NOTES.md나 개인 노트)로 정리해 두면, 다음 작업에서 같은 탐색을 반복하지 않아도 됩니다. 에이전트에게 정리까지 시킬 수도 있습니다.

console
> 지금까지 파악한 구조·엔드포인트·데이터 흐름·검증 위치를 NOTES.md 초안으로
  정리해 줘. (이건 새 파일 작성이니, 내용만 보여 주고 내가 확인한 뒤 저장할게.)

메모 작성은 "변경"이라는 점에 주의

구조 이해는 읽기 전용이지만, NOTES.md를 디스크에 만드는 것은 파일을 쓰는 변경 작업입니다. 그래서 위 예처럼 "내용만 보여 주고 내가 확인한 뒤 저장"으로 분리하거나, 권한 설정(5장)으로 통제하는 것이 좋습니다. 순수 탐색 중이라면 메모는 따로 모아 두었다가 탐색이 끝난 뒤 정리합니다.

4.9 즉시 연습(2종 1세트): team-tasks-api를 에이전트에 물어 구조 지도를 실제로 작성

탐색의 산출물은 머릿속 지도입니다. 이 지도를 종이 빈칸으로 추측해 채우는 게 아니라, team-tasks-api 에이전트에게 실제로 물어 받은 답으로 한 장의 구조 지도를 작성합니다. 모든 작업은 읽기 전용이라 코드를 바꾸지 않습니다.

모범: 에이전트에 물어 정리한 구조 지도(예)

아래는 4.4~4.7의 질문을 team-tasks-api에 실제로 던져 받은 답을 한 장으로 정리한 예입니다.

text
[프로젝트] 할 일(task)을 만들고 조회하는 작은 FastAPI REST API
[진입점]   main.py (FastAPI 앱 생성 + tasks 라우터 등록 + /health)

[모듈 역할]
- routers/tasks.py : /tasks 엔드포인트(입구)
- store.py         : 메모리(dict) 저장·조회
- models.py        : TaskCreate/Task 데이터 구조와 TaskStatus 열거형

[엔드포인트]
- GET  /tasks            → 전체 목록
- POST /tasks            → 생성(201), status는 todo로 시작
- GET  /tasks/{task_id}  → 단건, 없으면 404

[데이터 흐름(생성)] 요청 → create_task → store.create_task → _db에 저장
[검증 위치] models.py TaskCreate.title (str 타입, 누락/타입 오류 → 422)
[주의점] 저장이 메모리라 서버 재시작 시 사라짐

직접 해보기 (team-tasks-api 에이전트에게 실제로 물어 지도 작성)

  • [ ] 모듈 역할·엔드포인트·데이터 흐름·검증 위치를 각각 실제 파일을 열어 대조했다.

4.10 흔한 오류와 오개념: 다 읽고 시작·요약 맹신·탐색 중 변경

오개념 1 — "낯선 코드는 전부 읽고 나서 시작해야 한다"

신입이 흔히 첫 주를 "저장소의 모든 파일을 처음부터 끝까지 정독"하는 데 씁니다. 실제 업무 저장소는 수만 줄이라 이 방식은 비효율적이고, 다 읽어도 무엇이 중요한지는 여전히 안 보입니다.

교정: 다 읽지 말고 에이전트에게 물어 핵심부터 파악합니다(4.3의 깔때기: 전체 조망 → 엔드포인트 목록 → 흐름 → 국소 심화). 지금 하려는 작업에 관련된 부분만 깊이 보고, 나머지는 필요할 때 다시 묻습니다. "이해는 작업에 필요한 만큼, 깊이는 그때그때"가 원칙입니다.

오개념 2 — "에이전트가 요약해 줬으니 그대로 믿으면 된다"

에이전트의 요약은 빠르고 대개 정확하지만, 항상 정확하지는 않습니다. 특히 비슷한 이름의 함수가 여럿이거나, 동적으로 호출되는 코드에서는 요약이 미묘하게 틀릴 수 있습니다. 요약만 믿고 변경에 들어가면, 틀린 가정 위에 코드를 쌓게 됩니다.

교정: 변경의 근거가 되는 부분은 요약을 받은 뒤 직접 파일을 열어 확인합니다(4.5의 "근거를 보여 줘", 4.6~4.7의 발췌 실행처럼). 요약은 어디를 볼지를 빠르게 좁혀 주는 안내일 뿐, 최종 근거는 실제 코드입니다. 신입일수록 "요약 → 근거 확인"의 두 박자를 지킵니다.

오개념 3 — "탐색하다 보이는 문제를 김에 같이 고친다"

코드를 읽다 보면 오타나 어색한 부분이 눈에 띄어 "이왕 보는 김에" 고치고 싶어집니다. 하지만 아직 전체 맥락을 다 파악하지 못한 상태의 즉흥 수정은, 의도치 않게 기존 동작을 깨거나 지금 하려던 작업과 뒤섞여 리뷰를 어렵게 만듭니다.

교정: 이해(읽기 전용)와 변경을 분리합니다(4.8). 탐색 중 발견한 개선점은 메모에 적어 두었다가, 별도의 작업·별도의 커밋으로 다룹니다. 한 번에 한 가지 의도만 변경에 담는 것이 9장(작은 논리 단위 커밋)에서 배울 좋은 PR의 출발점입니다.

4.11 단원 미니 프로젝트: 팀 저장소 구조 지도 만들기

이 단원에서 배운 것(에이전트 검색·깔때기 질문·온보딩 질문법·읽기 전용)을 모아, 1장에서 셋업한 실습 저장소 team-tasks-api를 한 장의 구조 지도로 정리합니다. 이것이 u4의 미니 프로젝트이며, 종합 프로젝트에서 "기존 저장소 파악" 단계의 예행연습입니다.

4.12 마무리: 이 장에서 무엇을 가져가나

이 장에서 우리는 낯선 팀 코드를 안전하게 이해하는 법을 배웠습니다. 핵심은 넷입니다.

  1. 에이전트 검색 — 어느 파일을 봐야 할지 에이전트가 스스로 찾아 읽으므로, 신입은 컨텍스트 파일을 고를 필요 없이 질문만 하면 됩니다.
  2. 깔때기 질문 — 전체 조망 → 엔드포인트 목록 → 흐름 추적 → 국소 심화로 좁혀 가면 길을 잃지 않습니다.
  3. 온보딩 질문법 — 무엇을·어디서·어떻게·만약, 그리고 "근거를 보여 줘"로 검증 가능한 답을 끌어냅니다.
  4. 읽기 전용 분리 — 이해와 변경을 나누고, 요약은 근거로 확인하며, 발견한 개선점은 변경에 섞지 않습니다.

다음 장(5장)에서는 드디어 코드에 손대기 전의 안전장치 — 권한과 승인 — 를 배웁니다. 무엇을 바꿀지 정했으니, 이제 그 변경을 안전하게 통제하는 법으로 넘어갑니다.
