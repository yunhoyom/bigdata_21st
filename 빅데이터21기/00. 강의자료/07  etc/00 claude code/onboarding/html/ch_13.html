Chapter 13

종합 프로젝트: 첫 기능·첫 PR — 분석(요구사항·범위)

실무

종합 프로젝트: 첫 기능·첫 PR — 분석(요구사항·범위)

이 챕터에서 배우는 것

  • 드라이빙 퀘스천(핵심 질문)을 기능 요구사항(FR)과 비기능 요구사항(NFR) 항목으로 각각 구체화해 표로 작성할 수 있습니다.
  • 처음 받은 FastAPI 저장소를 에이전트 탐색으로 파악해, 첫 기능을 사용자 스토리와 유스케이스 1건 이상으로 정의할 수 있습니다.
  • 범위를 In/Out으로 나눠, 신입이 감당할 작은 첫 기능으로 한정되도록 통제할 수 있습니다.
  • 각 요구사항이 앞서 배운 어느 단원 개념으로 구현되는지 요구사항↔개념 매핑 표로 작성할 수 있습니다.

종합 프로젝트를 시작하며: 지금까지 배운 것을 하나의 업무로 엮습니다

여기까지 우리는 11개 단원에 걸쳐 12개의 개념을 하나씩 배웠습니다. 설치·인증(c01)으로 시작해, 에이전트 루프(c02)와 효과적인 작업 지시(c03)를 익히고, 낯선 코드를 탐색하는 법(c04), 권한(c05)과 플랜 모드(c06)로 안전하게 변경하는 법, 실행·테스트로 검증하기(c07), CLAUDE.md로 팀 규약을 주입하기(c08), 첫 커밋과 첫 PR(c09), 코드 리뷰 대응(c10), 디버깅(c11), 그리고 서브에이전트·MCP 맛보기(c12)까지 왔습니다.

각 단원의 미니 프로젝트로 개념을 따로따로 적용해 보았지만, 실제 신입의 첫 업무는 이 개념들이 하나의 흐름으로 모일 때 비로소 완성됩니다. 이번 종합 프로젝트(capstone, 캡스톤)는 그 흐름을 처음부터 끝까지 한 번에 통과하는 통과의례입니다. 이 챕터부터 네 챕터(분석 → 설계 → 구현 → 발표·성찰)에 걸쳐, 다음 한 가지 실제 업무를 끝까지 수행합니다.

종합 프로젝트 주제: 기존 팀 FastAPI 저장소에 첫 기능 추가하고 첫 PR 올리기 받은 팀의 team-tasks-api(할 일 관리 API) 저장소에 완료 처리(PATCH /tasks/{id}/complete)와 상태 필터(GET /tasks?status=) 두 엔드포인트를 테스트와 함께 추가하고, 작은 논리 단위로 커밋해 첫 PR을 올려 리뷰까지 통과시킵니다.

이 챕터는 새 개념을 배우지 않습니다

종합 프로젝트의 네 챕터는 새로운 도구나 개념을 가르치지 않습니다. 대신 앞 12개 개념을 실제 업무에 통합 적용합니다. 그래서 이 챕터의 모든 요구사항과 결정에는 "이건 어느 단원에서 배운 무엇인가"를 함께 표시합니다. 만약 어떤 부분이 막힌다면, 매핑된 단원으로 돌아가 복습하면 됩니다. 종합 프로젝트는 복습이자 전이(transfer)의 장입니다.

드라이빙 퀘스천과 POV 다시 보기

프로젝트 기반 학습(PBL)은 하나의 드라이빙 퀘스천(driving question, 핵심 질문)을 끝까지 붙들고 답을 만들어 가는 방식입니다. 우리의 드라이빙 퀘스천은 다음과 같습니다.

드라이빙 퀘스천

신입 개발자가 처음 받은 팀의 FastAPI 저장소를 Claude Code로 안전하게 파악하고, 작은 기능 하나를 테스트와 함께 추가해 리뷰어가 신뢰할 수 있는 첫 PR로 올리려면 어떻게 해야 할까?

이 질문은 "정답이 하나로 정해진" 질문이 아니라, 여러 단계의 판단과 검증을 요구하는 열린 질문입니다. 분석 → 설계 → 구현 → 발표의 네 단계가 바로 이 질문에 답해 가는 과정입니다.

이 질문의 주인공이 누구인지를 분명히 해 두면 모든 결정의 기준이 또렷해집니다. 이것이 POV(Point of View, 관점)입니다. POV는 "누가(user) · 무엇이 필요하며(need) · 왜 그것이 핵심인가(insight)"를 한 문장으로 모은 것입니다.

POV 요소 내용
사용자(user) 팀에 막 합류해 첫 업무로 기존 FastAPI 저장소에 작은 기능 추가를 맡은 주니어 신입 개발자
필요(need) 낯선 팀 코드를 안전하게 파악해 작은 기능 하나를 테스트와 함께 추가하고, 리뷰어가 신뢰할 수 있는 첫 PR을 올려 리뷰까지 통과한다
통찰(insight) 기능을 따로 배우는 것과 한 번의 실제 업무로 엮어 쓰는 것은 다르다. 첫 기능을 직접 추가해 PR까지 올려 보면 설치·탐색·권한·플랜·검증·CLAUDE.md·커밋·리뷰·디버깅이 어떻게 하나의 온보딩 흐름으로 모이는지를 비로소 체득한다

POV가 있으면 "기능을 더 화려하게 만들까?" 같은 유혹 앞에서 멈출 수 있습니다. 우리의 사용자는 신입이고, 그가 필요한 것은 화려함이 아니라 안전하게·검증 가능하게·리뷰어가 신뢰할 수 있게 작은 기능 하나를 끝까지 해내는 것이기 때문입니다. 이 기준이 다음 절부터의 모든 요구사항과 범위 결정을 이끕니다.

기존 FastAPI 저장소 파악 (에이전트 탐색)

분석의 첫걸음은 "무엇을 만들지" 정하기 전에 무엇이 이미 있는지 아는 것입니다. 신입이 받은 것은 빈 폴더가 아니라 이미 동작하는 팀의 코드입니다. 여기서 ch_04에서 배운 코드베이스 탐색(c04)을 그대로 씁니다. 변경 없이 읽기만 하면서, 시니어에게 묻듯 에이전트에게 질문해 구조를 파악합니다.

먼저 저장소가 무엇을 하는지, 엔드포인트가 무엇인지 요약하게 합니다.

console
> 이 저장소가 무엇을 하는 API인지, 어떤 엔드포인트가 있는지,
  핵심 파일 구조가 어떻게 되는지 한국어로 요약해 줘. 아직 아무것도
  바꾸지 말고 읽기만 해.

(Claude Code가 Glob·Read·Grep으로 저장소를 훑은 뒤 요약)

이 저장소(team-tasks-api)는 할 일(task)을 관리하는 FastAPI 기반 REST API
입니다. 데이터는 데이터베이스 없이 인메모리(메모리 안 리스트)에 저장합니다.
현재 엔드포인트는 세 개입니다.

- GET  /tasks          전체 할 일 목록 조회
- POST /tasks          새 할 일 생성(title을 받음)
- GET  /tasks/{id}     단일 할 일 조회(없으면 404)

핵심 파일 구조는 다음과 같습니다.
  main.py            FastAPI 앱 생성, 라우터 등록
  routers/tasks.py   tasks 관련 엔드포인트 정의
  models.py          Task 등 pydantic 모델
  store.py           인메모리 저장소(목록·조회·추가 함수)
  tests/test_tasks.py  기존 엔드포인트 테스트
  • 에이전트는 Glob(파일 찾기)·Read(파일 읽기)·Grep(코드 검색) 같은 읽기 전용 도구만 써서 구조를 파악했습니다. "아직 아무것도 바꾸지 말고"라는 제약(c03의 작업 지시 4요소 중 하나)을 명시해, 탐색 단계에서 코드가 변하지 않게 했습니다.
  • 핵심 산출물은 "엔드포인트 목록"과 "파일 구조"입니다. 이 두 가지를 알면 "내 기능을 어디에 끼워 넣을지"의 출발점이 잡힙니다. 완료 처리·상태 필터는 모두 tasks에 관한 일이므로 routers/tasks.py가 주된 작업 무대가 될 것임을 짐작할 수 있습니다.
  • 데이터가 인메모리라는 점도 중요합니다. 데이터베이스 연동이 없으므로, 우리 작업의 범위가 "저장소(store.py)의 리스트를 다루는 일"로 좁혀집니다(범위 결정의 근거).

다음으로, 우리가 바꿀 핵심인 데이터(할 일 한 건)가 어떻게 생겼는지와 검증·에러가 어떻게 처리되는지를 더 구체적으로 묻습니다.

console
> Task 데이터 한 건이 어떤 필드로 이루어져 있는지, 그리고 없는 id를
  조회할 때 404를 어떻게 내는지 해당 코드를 인용해서 설명해 줘.

(Claude Code가 models.py와 routers/tasks.py의 관련 부분을 읽어 설명)

Task 모델(models.py)은 다음 필드를 가집니다.
  - id:    정수, 생성 시 자동 부여
  - title: 문자열, 필수
  - status: 문자열, 기본값 "todo"   (이미 status 필드가 존재합니다)

없는 id 처리는 routers/tasks.py의 GET /tasks/{id}에서
store.get_task(id)가 None을 반환하면 다음과 같이 404를 냅니다.

    task = store.get_task(task_id)
    if task is None:
        raise HTTPException(status_code=404, detail="task를 찾을 수 없습니다")
    return task
  • 가장 값진 발견은 status 필드가 이미 존재한다는 사실입니다. 기본값이 "todo"이므로, 우리는 새 필드를 만드는 게 아니라 기존 필드의 값을 "done"으로 바꾸는 일을 하면 됩니다. 탐색이 작업의 난이도를 크게 낮춰 준 것입니다. 추측으로 시작했다면 불필요한 필드를 새로 추가했을지도 모릅니다.
  • 기존 코드가 없는 id에 HTTPException(status_code=404, ...)로 응답한다는 기존 패턴도 확인했습니다. 우리가 추가할 완료 처리도 "없는 id면 404"라는 같은 패턴을 따르면, 코드가 팀의 스타일과 일관됩니다(ch_03에서 배운 "기존 스타일 따르기").
  • 이처럼 탐색은 "무엇을 만들지"가 아니라 "무엇이 이미 있어서 재사용·일관되게 따라갈 수 있는지"를 알려 줍니다. 이 정보가 다음 절의 요구사항을 현실적으로 만듭니다.

탐색으로 파악한 핵심을 한 문단으로 정리하면 이렇습니다. team-tasks-api는 인메모리 tasks API이고, 할 일은 id·title·status를 가지며 status는 이미 존재해 "todo"가 기본값입니다. 엔드포인트는 목록·생성·단건 조회 세 개이고, 없는 id에는 404를 내는 패턴이 자리잡혀 있습니다. 변경 없이 이만큼 파악했으니, 이제 "무엇을 더할지"를 요구사항으로 적을 수 있습니다.

기능 요구사항(FR): 완료 처리·상태 필터 엔드포인트

요구사항(requirement)은 "이 기능이 무엇을 해야 하는가"를 검증 가능한 문장으로 적은 것입니다. 그중 기능 요구사항(FR, Functional Requirement)은 시스템이 무엇을 하는지(동작·기능)를 정의합니다. 모호한 "완료 기능을 추가한다" 대신, 확인할 수 있는 구체적 문장으로 적습니다.

탐색 결과를 바탕으로 이번 첫 기능의 기능 요구사항을 다음 일곱 가지로 정리했습니다. 각 요구사항 끝에는 그것을 구현할 때 쓰는 단원·개념을 함께 적었습니다(추적성).

ID 기능 요구사항 적용 단원 적용 개념
FR1 기존 tasks API의 구조·엔드포인트·데이터 흐름을 파악해 변경 지점을 찾는다 u4 c04 탐색
FR2 완료 처리 엔드포인트(PATCH /tasks/{id}/complete)로 해당 작업의 status를 done으로 변경한다 u3, u5 c03 지시, c06 플랜
FR3 상태 필터 엔드포인트(GET /tasks?status=done|todo)로 목록을 상태별로 거른다 u3, u5 c03 지시, c06 플랜
FR4 없는 id는 404, 잘못된 status 값은 422로 적절한 상태 코드와 에러 응답을 낸다 u10 c11 디버깅
FR5 추가한 두 엔드포인트를 pytest(TestClient)로 검증한다 u6 c07 검증
FR6 변경을 작은 논리 단위로 커밋하고 첫 PR로 올린다 u8 c09 커밋·PR
FR7 코드 리뷰를 받아 지적을 반영하거나 근거로 대응한다 u9 c10 리뷰

각 요구사항이 왜 이렇게 적혔는지 핵심만 짚겠습니다.

  • FR2(완료 처리)는 "어떻게(PATCH)"와 "무엇이 바뀌는가(status가 done으로)"를 모두 담았습니다. "complete 엔드포인트 추가"보다 훨씬 검증하기 쉽습니다. 나중에 "PATCH /tasks/1/complete를 호출하면 1번 작업의 status가 done이 된다"를 테스트로 그대로 옮길 수 있습니다.
  • FR3(상태 필터)는 입력(쿼리 파라미터 status)과 출력(거른 목록)을 명시했습니다. todo|done 두 값만 받는다고 못박아, FR4의 "잘못된 status는 422"와 자연스럽게 연결됩니다.
  • FR4(에러 응답)는 "잘 안 되면 어떻게 되는가"라는 불행 경로(unhappy path)를 미리 정의합니다. 신입이 가장 자주 빠뜨리는 부분이지만, 실제 업무에서는 "정상일 때"만큼 "비정상일 때"가 중요합니다. 기존 코드가 이미 404를 쓰므로 같은 패턴을 따릅니다.

좋은 요구사항은 "테스트로 옮길 수 있는" 문장입니다

요구사항이 잘 적혔는지 판단하는 가장 쉬운 기준은 "이 문장을 그대로 테스트(pytest)로 옮길 수 있는가?"입니다. "완료 기능을 잘 만든다"는 테스트로 옮길 수 없지만, "PATCH /tasks/{존재하는 id}/complete를 호출하면 200과 status=done이 반환된다"는 그대로 한 줄짜리 테스트가 됩니다. 요구사항을 적을 때부터 ch_07의 검증(c07)·TDD를 염두에 두면, 분석 단계가 곧 테스트 설계가 됩니다.

비기능 요구사항(NFR): 테스트·안전·팀 규약

비기능 요구사항(NFR, Non-Functional Requirement)은 "무엇을 하는가"가 아니라 "어떻게·얼마나 잘 하는가"(품질·방식·제약)를 정의합니다. 같은 기능이라도 안전하게·검증 가능하게·일관되게 만드는 것이 NFR입니다. 신입의 첫 기능에서는 결과물의 기능만큼 일하는 방식이 평가받으므로 NFR이 특히 중요합니다.

ID 비기능 요구사항 적용 개념
NFR1 에이전트 루프를 이해하고 목표·맥락·제약·완료 조건의 4요소 지시로 작업한다 c02 루프, c03 지시
NFR2 부수효과 도구(편집·실행)를 최소 권한 settings.json으로 통제한다 c05 권한
NFR3 변경 전에 플랜 모드로 계획을 받아 검토한다(안전) c06 플랜
NFR4 테스트 우선(TDD)으로 완료 조건을 먼저 세운다 c07 검증
NFR5 팀 규약을 CLAUDE.md로 영속화해 세션 간 일관성을 유지한다 c08 CLAUDE.md
NFR6 막힘은 디버깅 루프(재현→가설→최소 수정→회귀 테스트)로 해소한다 c11 디버깅
NFR7 반복 작업은 서브에이전트로, 외부 자료는 MCP로 가볍게 활용한다(맛보기) c12 자동화

기능 요구사항(FR)과 비기능 요구사항(NFR)의 차이를 한 문장으로 구분하면 이렇습니다. FR은 "무엇을 만드는가"(완료 처리·상태 필터), NFR은 "어떻게 만드는가"(안전하게·검증하며·일관되게)입니다. 둘 다 충족해야 신입의 첫 업무가 "동작하긴 하는데 위험하게 만든 코드"가 아니라 "안전하게·검증 가능하게 만든 신뢰할 수 있는 코드"가 됩니다.

NFR을 빠뜨리면 "동작은 하지만 못 믿을" 결과가 됩니다

기능(FR)만 채우고 비기능(NFR)을 무시하면, 엔드포인트는 동작하지만 테스트가 없고(NFR4 위반), 권한 통제 없이 위험하게 만들어졌으며(NFR2 위반), 팀 규약과 어긋나(NFR5 위반) 리뷰에서 막힙니다. 평가 루브릭(ch_16)이 기능 완성도뿐 아니라 안전·절차·협업을 함께 보는 이유가 여기 있습니다. 신입의 첫 PR이 신뢰를 얻는지는 NFR에서 갈립니다.

사용자 스토리와 유스케이스

요구사항을 사용자의 입장에서 다시 적으면, "왜 이 기능이 필요한가"가 또렷해집니다. 이를 위한 두 가지 도구가 사용자 스토리와 유스케이스입니다.

사용자 스토리(user story)는 "[누구]로서, [무엇을] 하고 싶다, [왜]"의 형식으로 요구를 사용자 관점에서 적은 짧은 문장입니다. 우리 프로젝트의 사용자(신입 개발자)가 가진 네 가지 스토리는 다음과 같습니다.

  1. 신입으로서, 받은 저장소가 무엇을 하는지 빠르게 파악해 어디를 바꿔야 할지 알고 싶다. (→ FR1 탐색)
  2. 신입으로서, 기존 코드를 망가뜨릴까 봐 두렵지 않게 안전장치(권한·플랜)를 갖추고 손대고 싶다. (→ NFR2·NFR3)
  3. 신입으로서, 추가한 기능이 정말 동작하는지 테스트로 증명하고 싶다. (→ FR5·NFR4)
  4. 신입으로서, 리뷰어가 빠르게 이해하는 좋은 첫 PR을 올리고 리뷰를 통과하고 싶다. (→ FR6·FR7)

유스케이스(use case)는 한 걸음 더 들어가, 사용자가 시스템과 어떻게 상호작용해 목표를 이루는지를 입력→처리→결과의 흐름으로 적은 시나리오입니다. 스토리가 "무엇을 원하는가"라면, 유스케이스는 "그래서 실제로 어떤 요청을 보내고 어떤 응답을 받는가"입니다.

ID 유스케이스 흐름(입력 → 결과)
UC1 완료 처리 PATCH /tasks/1/complete → 1번 task의 status가 done으로 바뀌고 200 응답
UC2 상태 필터 GET /tasks?status=done → status가 done인 task만 목록으로 반환
UC3 첫 PR 작업 브랜치 커밋 → PR 생성 → /code-review·자동 리뷰 → 반영 → 통과
  • UC1·UC2의 흐름이 곧 테스트 시나리오입니다. 예컨대 UC1은 "1번 작업을 만들고 → PATCH로 완료 처리하고 → 응답이 200이고 status가 done인지 확인"이라는 pytest 한 케이스로 그대로 옮겨집니다(ch_07·ch_15에서 구현).
  • UC3은 코드가 아니라 협업 절차의 유스케이스입니다. 커밋·PR·리뷰·반영이라는 사람과 사람(그리고 자동 리뷰)의 상호작용을 담아, 종합 프로젝트가 "코드 작성"으로 끝나지 않고 "팀에 합류시키기"까지 포함함을 보여 줍니다.
  • 사용자 스토리·유스케이스를 분석 단계에서 적어 두면, 구현(ch_15)에서 "무엇을 만들고 무엇을 테스트할지"를 다시 고민하지 않고 이 목록을 그대로 따라가면 됩니다. 분석이 충실하면 구현이 단순해집니다.

범위 In/Out 확정 (작은 첫 기능으로)

신입이 첫 업무에서 저지르는 흔한 실수는 범위를 키우는 것입니다. "기왕 하는 김에 인증도 붙이고, 데이터베이스도 연동하고…"라는 생각은 첫 PR을 끝없이 미루게 만듭니다. POV가 알려 주듯 우리의 사용자는 신입이고, 필요한 것은 작은 기능 하나를 끝까지 해내는 것입니다. 그래서 무엇을 포함(In)하고 무엇을 제외(Out)할지 명시적으로 못박습니다.

범위 In (이번에 한다) 범위 Out (이번에 하지 않는다)
기존 저장소 탐색·구조 지도 작성 데이터베이스 연동·마이그레이션(기존 인메모리 유지)
완료 처리 엔드포인트(PATCH /tasks/{id}/complete) 추가 인증·권한 같은 큰 신규 기능(범위 초과)
상태 필터 엔드포인트(GET /tasks?status=done|todo) 추가 프런트엔드·UI
입력 검증과 적절한 상태 코드·에러 응답(404·422) 배포·인프라·CI 무인 자동화(본서는 맛보기까지만)
각 변경에 대한 pytest 테스트(TestClient) 서브에이전트·MCP 심화 설계(맛보기 단원까지만)
권한 설정·플랜 모드·CLAUDE.md 적용
작은 논리 단위 커밋과 첫 PR 작성·리뷰 대응

범위를 좁히면 무엇이 좋을까요? 첫째, 끝낼 수 있습니다. 작은 범위는 한 번의 작업 세션으로 완결되어 첫 PR을 실제로 올릴 수 있습니다. 둘째, 리뷰가 쉽습니다. 변경이 작으면 리뷰어가 빠르고 정확하게 봐 주고, 문제가 생겨도 영향 범위가 좁습니다(ch_09에서 배운 "신입의 PR은 작을수록 좋다"). 셋째, 다음을 위한 여지가 생깁니다. "완료 취소"나 "완료 시각 기록" 같은 확장은 후속 PR로 미루면 되므로, 이번 PR이 깔끔하게 유지됩니다.

MVP: 가장 작은 첫 버전부터

범위 안에서도 MVP(Minimum Viable Product, 최소 기능 제품)를 먼저 정합니다. 우리의 MVP는 "완료 처리 엔드포인트(PATCH /tasks/{id}/complete) 하나를 테스트와 함께 추가해 통과시키고 첫 커밋·PR을 올리는 최소 버전"입니다. 상태 필터·에러 응답 보강·리뷰 대응은 MVP 이후의 증분 확장입니다. 한꺼번에 다 만들려다 아무것도 끝내지 못하는 대신, 가장 작은 동작하는 버전을 먼저 완성하고 거기서 키워 갑니다. 이 증분 전략이 구현 챕터(ch_15)의 마일스톤 순서가 됩니다.

추적성: 요구사항 ↔ 단원 개념 매핑

종합 프로젝트의 핵심은 추적성(traceability)입니다. 모든 요구사항이 "허공에서 나온 것"이 아니라 앞서 배운 어느 개념으로 구현되는지 한눈에 이어지게 만드는 것입니다. 추적성 표가 있으면 두 가지가 가능합니다. (1) 구현 중 막히면 해당 개념의 단원으로 정확히 돌아가 복습할 수 있고, (2) 이 프로젝트가 정말 12개 개념을 모두 통합하는지 빠짐없이 확인할 수 있습니다.

아래는 이번 프로젝트가 다루는 요구사항(FR·NFR·UC)을 단원·개념별로 모은 전체 추적성 표입니다.

표를 보면 12개 개념이 빠짐없이 이 프로젝트의 어딘가로 이어진다는 것을 확인할 수 있습니다. 이것이 종합 프로젝트가 "그냥 던져 주는 과제"가 아니라 커리큘럼 전체를 통합 적용하도록 역설계된 업무라는 증거입니다. 다음 챕터(ch_14)에서는 이 요구사항들을 실제 설계(데이터 구조·모듈 변경·ADR)로 옮깁니다.

흔한 오류와 오개념

1. 기존 코드를 안 보고 바로 만들기 시작한다

신입이 가장 자주 하는 실수는 받은 저장소를 파악하지 않고 곧장 코드를 쓰는 것입니다. 그러면 이미 있는 status 필드를 모른 채 새 필드를 만들거나, 팀의 404 패턴과 다른 방식으로 에러를 내 일관성이 깨집니다. 분석은 만들기 전에 무엇이 이미 있는지 아는 단계입니다. ch_04의 탐색(c04)으로 먼저 읽고, 그다음에 요구사항을 적으세요.

2. 요구사항을 "잘 만든다"처럼 막연하게 적는다

"완료 기능을 잘 만든다"는 요구사항이 아닙니다. 무엇이 "잘"인지 검증할 수 없기 때문입니다. 요구사항은 입력·정상 결과·비정상 결과를 담아 그대로 테스트로 옮길 수 있어야 합니다. "테스트로 옮길 수 있는가?"를 매 요구사항마다 자문하세요.

3. 범위를 키워 첫 PR을 끝내지 못한다

"기왕 하는 김에" 인증·데이터베이스·UI까지 붙이려다 첫 PR을 영원히 올리지 못하는 함정입니다. 범위 Out을 명시하고 MVP(완료 처리 하나)부터 완성하세요. 작게 끝내고 다음 PR로 키우는 것이 크게 벌이고 못 끝내는 것보다 항상 낫습니다.

4. 비기능 요구사항(NFR)을 무시한다

"동작만 하면 됐지"라며 테스트·권한·플랜·CLAUDE.md를 건너뛰면, 기능은 되지만 리뷰에서 막히고 팀의 신뢰를 잃습니다. 신입의 첫 업무는 결과만큼 일하는 방식으로 평가받습니다. FR과 NFR을 함께 채우세요.

이 챕터 한 줄 정리

분석은 드라이빙 퀘스천·POV로 방향을 잡고, 기존 저장소를 변경 없이 탐색해 파악한 뒤, 무엇을 만드는지(FR)와 어떻게 만드는지(NFR)를 검증 가능한 요구사항으로 적고, 범위(In/Out)로 작게 통제하며, 각 요구사항을 단원 개념으로 추적하는 단계입니다. 다음 챕터(ch_14)에서는 이 요구사항을 설계(데이터 구조·모듈 변경·ADR·순서도)로 옮깁니다.
