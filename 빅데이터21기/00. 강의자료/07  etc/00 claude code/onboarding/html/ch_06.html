Chapter 06

안전하게 변경하기 (2): 플랜 모드로 먼저 계획

기초

안전하게 변경하기 (2): 플랜 모드로 먼저 계획

이 챕터에서 배우는 것

  • 다중 파일을 건드리는 변경에서 플랜 모드를 켜(Shift+Tab) 읽기 전용으로 변경 계획을 받고, 그 단계 동안 파일이 바뀌지 않음을 확인할 수 있습니다.
  • 제시된 계획에 담긴 잘못된 가정 1개 이상을 찾아, 단계 추가·삭제·재정렬로 방향을 바로잡는 교정 지시를 작성할 수 있습니다.
  • 검토·교정한 계획을 승인한 뒤 실행 모드로 전환해, 계획대로 변경이 적용되는 흐름을 운용할 수 있습니다.
  • 주어진 작업이 복잡·고위험·다중 파일·첫 기능 추가에 해당하는지 따져 계획-실행 분리가 필요한지 판단할 수 있습니다.
  • (단원 미니 프로젝트) pytest·편집만 허용하는 최소 권한 settings를 구성하고 플랜 모드로 작은 변경의 단계별 계획을 받아, 잘못된 가정을 교정한 뒤 확정할 수 있습니다.

이번 챕터에서 가르치는 개념은 플랜 모드(plan mode) 한 가지입니다. 선수 개념은 바로 앞 챕터(ch_05)에서 익힌 권한과 승인(permissions and approval)입니다. ch_05에서 우리는 "에이전트가 어떤 명령을 실행해도 되는가"를 allow·deny·ask로 통제했습니다. 권한은 개별 도구 호출 단위의 안전장치였습니다. 그런데 안전에는 한 겹이 더 있습니다. 권한이 "이 명령 하나를 실행해도 되나"를 본다면, 플랜 모드는 그보다 한 걸음 앞서 "애초에 무엇을 바꿀 셈인가, 그 전체 계획부터 보자"를 봅니다. ch_05가 실행의 안전이라면, 이번 챕터는 계획의 안전입니다. 둘을 함께 갖추면 신입도 낯선 코드에 위험 없이 첫 변경을 시작할 수 있습니다. 이 챕터는 단원 u5의 마지막 챕터이므로, 끝에 권한과 플랜 모드를 통합하는 단원 미니 프로젝트도 함께 다룹니다.

6.1 도입: 바꾸기 전에 계획을 먼저 본다

목수에게는 "두 번 재고 한 번 자른다"는 격언이 있습니다. 한 번 자른 나무는 되돌릴 수 없으니, 자르기 전에 충분히 재라는 뜻입니다. 코드 변경도 같습니다. 특히 신입이 낯선 팀 코드베이스에 첫 변경을 가할 때, 에이전트가 곧장 파일을 고치기 시작하면 위험합니다. 만약 에이전트가 잘못된 파일을 골랐거나, 엉뚱한 방식으로 접근하고 있다면, 이미 여러 파일이 바뀐 뒤에야 그 사실을 알게 됩니다.

ch_02에서 배운 에이전트 루프를 떠올려 봅시다. 에이전트는 관찰 → 계획 → 도구 호출 → 결과 확인을 돕니다. 보통은 이 루프가 빠르게 돌면서 관찰하자마자 편집(도구 호출)으로 넘어갑니다. 빠른 작업에는 좋지만, 변경의 규모가 크거나 방향이 틀리면 손해가 큰 작업에서는 "계획" 단계에서 한 번 멈춰 사람이 검토하고 싶습니다.

플랜 모드는 바로 그 "멈춤"을 만드는 장치입니다. 에이전트에게 코드를 바꾸지 말고, 무엇을 어떻게 바꿀지 계획부터 세워 보여 달라고 지시하는 모드입니다. 사용자는 그 계획을 읽고, 틀린 가정이 있으면 교정하고, 방향이 맞으면 그때 승인해 실행으로 넘깁니다. 자르기 전에 두 번 재는 것입니다. ch_05의 권한이 "위험한 실행을 막는" 안전장치였다면, 플랜 모드는 "잘못된 방향의 변경을 시작 전에 바로잡는" 안전장치입니다.

한눈에 보는 플랜 모드

플랜 모드(plan mode)는 에이전트가 코드를 바꾸기 전에 무엇을 어떻게 바꿀지 계획을 먼저 제시하고 승인을 받는 읽기 전용 모드입니다. 이 모드에서는 편집·쓰기 도구가 차단되어 파일이 바뀌지 않으므로 안전하게 탐색·분석하고 계획을 검토·교정할 수 있습니다. Shift+Tab으로 모드를 전환하며, 복잡·고위험·다중 파일·첫 기능 추가처럼 방향이 틀리면 손해가 큰 작업에서 계획-실행을 분리해 줍니다.

6.2 정의: 플랜 모드란 — 변경 전 읽기 전용 계획 단계

플랜 모드(plan mode)란, 에이전트가 코드베이스를 읽기 전용으로만 탐색·분석해 변경 계획을 세워 제시하고, 사용자가 그 계획을 승인하기 전까지는 파일을 수정하지 않는 작업 모드입니다.

핵심 성질을 정리하면 이렇습니다.

  • 읽기 전용(read-only): 플랜 모드에서 에이전트는 Read·Glob·Grep 같은 읽기 도구로 코드를 살펴볼 수 있지만, Edit·Write로 파일을 바꾸거나 부수효과 명령을 실행하지는 않습니다. 그래서 계획 단계에서는 무엇도 망가지지 않습니다.
  • 계획을 산출물로 제시: 에이전트는 분석을 마치면 "이 파일들을 이렇게 바꾸겠다"는 단계별 계획을 제시합니다. 이것이 플랜 모드의 결과물입니다.
  • 승인 게이트: 사용자가 계획을 검토해 승인하면, 그때 비로소 실행 모드로 넘어가 실제 변경이 시작됩니다. 승인 전에는 한 줄도 바뀌지 않습니다.
  • 모드 전환은 Shift+Tab: 터미널에서 Shift+Tab을 누르면 모드가 순환합니다(기본 → 편집 자동 수락 → 플랜). 화면 아래에 현재 모드가 표시됩니다.

비유하자면, 플랜 모드는 공사를 시작하기 전에 받는 설계 도면입니다. 도면을 보고 "여기 벽은 빼고, 저 창문은 키워 달라"고 고친 뒤 착공을 승인하는 것과 같습니다. 도면 단계에서는 실제 건물이 손상되지 않으므로, 마음껏 검토하고 바꿀 수 있습니다.

권한과 플랜 모드는 어떻게 다른가

  • 권한(ch_05): 도구 호출 하나하나를 검사해 실행 여부를 통제합니다(allow·deny·ask). "이 rm 명령을 실행해도 되나?"
  • 플랜 모드(이번 챕터): 변경을 시작하기 전에 전체 계획을 먼저 보게 합니다. "무엇을 바꿀 계획인지부터 보자."

둘은 경쟁하지 않고 겹쳐서 작동합니다. 플랜 모드로 방향을 잡고, 실행 단계에서 개별 명령은 권한이 통제합니다. 안전의 두 겹입니다.

6.3 동작 원리: 계획→승인→실행 분리 흐름(Shift+Tab)

플랜 모드의 동작은 계획 → 검토·교정 → 승인 → 실행의 네 단계로 흐릅니다. 각 단계를 따라가 보겠습니다.

  1. 플랜 모드 진입(Shift+Tab): 터미널에서 Shift+Tab을 눌러 플랜 모드로 전환합니다. 모드는 기본(Normal) → 편집 자동 수락(acceptEdits) → 플랜(Plan) 순으로 순환하며, 플랜 모드에 들어가면 화면 하단에 "plan mode on"처럼 표시됩니다. 이 상태에서 작업을 지시합니다.
  2. 읽기 전용 분석·계획 제시: 에이전트는 읽기 도구로 관련 코드를 탐색하고, "어떤 파일을 어떻게 바꿀지"를 단계별 계획으로 정리해 제시합니다. 이 동안 파일은 바뀌지 않습니다.
  3. 검토·교정: 사용자가 계획을 읽습니다. 틀린 가정(엉뚱한 파일·잘못된 접근)이 있으면 자연어로 교정 지시를 주고, 에이전트는 계획을 다시 다듬어 제시합니다. 이 검토·교정은 원하는 만큼 반복할 수 있습니다.
  4. 승인 → 실행 전환: 계획이 만족스러우면 승인합니다. 그러면 에이전트가 실행 모드로 넘어가 계획대로 실제 변경을 시작하고, 이때부터 개별 도구 호출은 ch_05의 권한 규칙으로 통제됩니다.

이 흐름의 핵심은 계획과 실행을 분리한다는 점입니다. 보통 모드에서는 관찰 직후 곧장 편집으로 넘어가지만, 플랜 모드는 그 사이에 "계획 제시 → 사람 승인"이라는 게이트를 끼웁니다. 덕분에 잘못된 방향의 변경이 시작되기 전에 사람이 개입할 기회가 생깁니다.

단계 사용자 행동 에이전트 동작 파일 변경
1. 진입 Shift+Tab으로 플랜 모드 켜기 플랜 모드로 전환 없음
2. 계획 작업 지시 읽기 전용 분석 → 계획 제시 없음
3. 교정 틀린 가정 교정 지시 계획 재작성 없음
4. 실행 계획 승인 실행 모드로 전환 → 변경 시작 발생(권한이 통제)

승인하지 않고 플랜 모드를 빠져나오고 싶다면 Shift+Tab을 다시 눌러 계획을 실행하지 않고 모드를 벗어날 수도 있습니다. 즉 계획을 받았다고 반드시 실행할 의무는 없습니다. 검토 후 "이 방향은 아니다" 싶으면 버리면 됩니다.

계획 단계는 "되돌릴 것이 없는" 안전 지대

플랜 모드에서는 파일이 바뀌지 않으므로, 계획이 아무리 엉뚱해도 실제 손상은 없습니다. 그래서 신입이 낯선 코드베이스에서 마음 편히 "일단 계획부터 받아 보는" 데 적합합니다. 손해 없이 에이전트의 의도를 미리 들여다볼 수 있는 것이 플랜 모드의 가장 큰 가치입니다.

6.4 플랜 모드에서 편집·쓰기 도구가 차단되는 이유

플랜 모드의 핵심 성질은 편집·쓰기 도구가 차단된다는 것입니다. 그런데 여기서 신입이 자주 헷갈리는 점이 있습니다. "ch_05에서 Edit(routers/**)을 allow로 자동 허용했는데, 플랜 모드에서는 왜 편집이 안 되나?"

답은 이렇습니다. 플랜 모드의 읽기 전용 제약은 권한 규칙(allow)보다 우선합니다. 즉 Edit(routers/**)을 allow에 두었더라도, 플랜 모드에 있는 동안에는 그 편집이 허용 규칙과 무관하게 차단됩니다. 왜 이렇게 설계했을까요?

이유는 플랜 모드의 목적이 "계획"이지 "실행"이 아니기 때문입니다. 만약 플랜 모드에서도 allow된 편집이 그냥 실행돼 버린다면, "계획만 받고 검토하려던" 의도가 깨집니다. 사용자가 계획을 미처 검토하기도 전에 파일이 바뀌어 있을 테니까요. 그래서 플랜 모드는 "이 모드에 있는 동안에는 무조건 읽기 전용"이라는 강한 보장을 줍니다. 이 보장이 있어야 "계획 단계에서는 절대 파일이 안 바뀐다"고 신뢰할 수 있습니다.

정리하면 안전장치가 두 겹으로 쌓입니다.

  • 플랜 모드(이번 챕터): 모드 전체에 걸친 "읽기 전용" 보장. 계획 단계에서는 어떤 편집도 일어나지 않습니다.
  • 권한 규칙(ch_05): 실행 모드에서 개별 명령을 통제. 승인 후 실제 변경이 시작될 때 작동합니다.

이 둘의 관계를 한 문장으로 하면, "플랜 모드는 계획 단계 전체를 잠그고, 권한은 실행 단계의 명령 하나하나를 통제한다"입니다. 둘 다 있어야 "방향도 안전하고 실행도 안전한" 변경이 됩니다.

왜 읽기 도구는 되고 편집 도구는 안 되나

플랜 모드에서도 Read·Glob·Grep 같은 읽기 도구는 동작합니다. 계획을 세우려면 코드를 봐야 하니까요. 읽기는 아무것도 바꾸지 않으므로(부수효과 없음) 허용해도 안전합니다. 반면 Edit·Write·부수효과 Bash는 파일·시스템을 바꾸므로, 계획 단계에서는 막습니다. 이 구분은 ch_05에서 배운 "읽기 전용 도구 vs 부수효과 도구"와 정확히 같은 선입니다.

6.5 worked example: 엔드포인트 추가를 플랜 모드로 계획받아 실행

이제 실제로 플랜 모드를 써 보겠습니다. 상황은 이렇습니다. 우리는 1장에서 셋업한 팀의 FastAPI 할 일 관리 저장소 team-tasks-api에서, 특정 할 일 하나를 삭제하는 엔드포인트 DELETE /tasks/{task_id}를 추가하려 합니다(이 저장소에는 아직 삭제 기능이 없습니다). 첫 기능 추가이니 곧장 편집하지 않고 플랜 모드로 계획부터 받겠습니다.

먼저 기존 코드의 일부를 봐 둡니다. 라우터 파일은 이런 모습입니다(데이터는 store를 통해 다룹니다).

python
# routers/tasks.py
from fastapi import APIRouter, HTTPException
from models import Task, TaskCreate
import store

router = APIRouter(prefix="/tasks", tags=["tasks"])


@router.get("", response_model=list[Task])
def list_tasks() -> list[Task]:
    return store.get_all_tasks()

이제 터미널에서 Shift+Tab을 눌러 플랜 모드로 들어간 뒤 작업을 지시합니다.

  • 에이전트는 플랜 모드에서 Read·Grep 같은 읽기 도구만 써서 기존 코드를 분석했습니다. 이 동안 파일은 전혀 바뀌지 않았습니다.
  • 제시된 계획은 단계별입니다. 어떤 함수를 추가하고, 어떤 예외를 쓰고, 데이터 계층(store)을 어떻게 거치고, 테스트까지 어디에 추가할지 명시했습니다.
  • 마지막에 승인 게이트가 있습니다. "네, 실행하세요"를 고르기 전까지는 실행 모드로 넘어가지 않습니다.

계획이 합리적이므로 승인합니다. 그러면 에이전트가 실행 모드로 전환해 계획대로 코드를 추가하고, 결과는 이렇게 됩니다.

python
# store.py (추가된 함수)
def delete_task(task_id: int) -> bool:
    return _db.pop(task_id, None) is not None
python
# routers/tasks.py (추가된 엔드포인트)
@router.delete("/{task_id}", status_code=204)
def delete_task(task_id: int) -> None:
    if not store.delete_task(task_id):
        raise HTTPException(status_code=404, detail="Task not found")

실행 결과를 보면, 계획대로 엔드포인트가 추가되고 기존 7개에 204·404 두 경우 테스트가 더해져 모두 통과했습니다. 핵심은 곧장 편집하지 않고 계획을 먼저 받아 검토한 뒤 실행했다는 점입니다. 만약 계획이 엉뚱했다면, 파일이 바뀌기 전에 바로잡을 수 있었습니다.

6.6 계획 교정: 단계 추가·삭제·재정렬

플랜 모드의 진짜 가치는 계획을 받는 것이 아니라 계획을 고치는 것에 있습니다. 에이전트가 제시한 계획이 항상 완벽하지는 않습니다. 단계가 빠졌거나, 순서가 어색하거나, 불필요한 단계가 섞일 수 있습니다. 이때 사용자는 자연어로 계획을 교정합니다.

계획을 고치는 방식은 크게 세 가지입니다.

  • 단계 추가: 빠진 작업을 넣습니다. 예: "테스트를 추가하는 단계가 빠졌어. 204·404 테스트도 계획에 넣어 줘."
  • 단계 삭제: 불필요한 작업을 뺍니다. 예: "기존 list_tasks는 건드리지 마. 그 수정 단계는 빼 줘."
  • 단계 재정렬: 순서를 바꿉니다. 예: "테스트를 먼저 작성하고 구현하는 순서로 바꿔 줘(TDD)."

이렇게 교정 지시를 주면 에이전트는 계획만 다시 그려 제시합니다. 여전히 플랜 모드이므로 파일은 바뀌지 않습니다. 만족할 때까지 이 과정을 반복한 뒤 승인하면 됩니다. 계획 단계에서의 교정은 공짜입니다. 실제 코드가 바뀐 뒤 되돌리는 것보다 훨씬 싸고 안전합니다.

console

  > 2. 아니요, 수정할게요

> 테스트 단계가 빠졌어. 그리고 테스트를 먼저 작성한 뒤 구현하는
  순서로 바꿔 줘.

● 계획(Plan, 수정됨):
  1. tests/test_tasks.py에 204·404 테스트 먼저 작성
  2. delete_task 함수 구현해 테스트 통과시키기
  3. HTTPException import 추가
  4. pytest로 통과 확인

  이 계획대로 진행할까요?

좋은 교정 지시의 요령

ch_03에서 배운 "구체적인 지시"가 여기서도 통합니다. "계획이 별로야" 같은 모호한 말 대신, 무엇을(단계) 어떻게(추가·삭제·재정렬) 바꿀지 콕 집어 말하십시오. "4번 단계는 빼고, 테스트를 1번으로 올려 줘"처럼 구체적일수록 계획이 정확히 다듬어집니다.

6.7 worked example: 잘못된 가정을 교정 지시로 바로잡기

계획 교정이 가장 빛나는 순간은 에이전트가 잘못된 가정을 했을 때입니다. 낯선 코드베이스에서는 에이전트도 구조를 오해할 수 있습니다. 플랜 모드는 그 오해가 실제 변경으로 번지기 전에 드러나게 해 줍니다.

6.8 언제 쓰는가: 복잡·고위험·다중 파일·첫 기능 추가

플랜 모드는 강력하지만 모든 작업에 쓸 필요는 없습니다. 오타 하나 고치는 데 계획부터 받으면 오히려 번거롭습니다. 그래서 "언제 쓰는가"를 판단하는 감각이 중요합니다. 다음과 같은 작업에 플랜 모드가 특히 가치 있습니다.

상황 플랜 모드가 필요한 이유
복잡한 작업 여러 결정이 얽혀 있어, 방향이 틀리면 손해가 큼
고위험 변경 핵심 로직·데이터처럼 잘못되면 영향이 큰 부분
다중 파일 변경 여러 파일에 걸쳐 일관되게 바꿔야 해, 전체 그림이 먼저 필요
첫 기능 추가 낯선 코드베이스라 에이전트의 가정이 틀릴 가능성이 큼

반대로 다음과 같은 작업에는 플랜 모드가 과합니다.

  • 오타·문구 수정처럼 결과가 뻔하고 위험이 없는 작업.
  • 한 파일의 한 줄만 바꾸는 사소한 변경.
  • 이미 구조를 잘 아는 곳의 단순 반복 작업.

신입에게 권하는 기본 습관은 이렇습니다. 낯선 코드베이스의 첫 기능 추가나, 여러 파일에 걸친 변경은 일단 플랜 모드로 시작한다. 익숙해지고 위험이 작은 작업은 보통 모드로 빠르게 처리합니다. "이 변경이 틀리면 손해가 큰가?"를 스스로 물어, 답이 "그렇다"면 플랜 모드를 켜십시오.

판단 기준 한 줄: "틀리면 손해가 큰가?"

플랜 모드를 쓸지 말지는 작업의 '방향이 틀렸을 때의 손해'로 판단합니다. 손해가 크면(복잡·고위험·다중 파일·첫 기능) 계획을 먼저 받고, 손해가 작으면(오타·사소한 수정) 바로 진행합니다. 이 기준 하나면 대부분의 상황을 판단할 수 있습니다.

6.10 흔한 오류와 오개념: 단순작업 과용·무비판 실행·읽기전용 오해

신입이 플랜 모드에서 자주 저지르는 실수와 그 교정을 정리합니다.

오개념 1: "안전하니까 모든 작업을 플랜 모드로 하자"

플랜 모드는 단순 작업에는 과합니다. 오타 하나 고치는 데 계획부터 받으면 오히려 느려지고 번거롭습니다.

교정: 플랜 모드는 복잡·고위험·다중 파일·첫 기능 추가처럼 방향이 틀리면 손해가 큰 작업에 씁니다. "틀리면 손해가 큰가?"를 기준으로, 손해가 작은 사소한 작업은 보통 모드로 빠르게 처리하십시오.

오개념 2: "계획을 받았으니 그대로 승인하면 되겠지"

계획을 받았다고 무비판적으로 실행하면 플랜 모드의 의미가 없습니다. 핵심은 계획을 받는 것이 아니라 검토·교정하는 것입니다.

교정: 제시된 계획을 반드시 읽고, 잘못된 가정·빠진 단계·불필요한 단계가 없는지 확인하십시오. 의심스러우면 교정 지시를 주거나, 방향이 아니면 버립니다. 검토 없는 승인은 보통 모드와 다를 바 없습니다.

오개념 3: "플랜 모드에서도 allow한 편집은 실행되겠지"

플랜 모드는 읽기 전용이라, Edit(routers/**)을 allow에 두었더라도 그 모드에 있는 동안에는 편집이 차단됩니다. "왜 허용했는데 안 바뀌지?"라고 당황하기 쉽습니다.

교정: 플랜 모드의 읽기 전용 제약은 권한 규칙보다 우선합니다. 계획 단계에서는 파일이 절대 안 바뀐다는 보장이 플랜 모드의 핵심입니다. 실제 편집은 계획을 승인해 실행 모드로 전환한 뒤에야 시작됩니다.

자주 묻는 질문(FAQ)

Q. 플랜 모드는 어떻게 켜고 끄나요? A. 터미널에서 Shift+Tab으로 모드를 순환합니다(기본 → 편집 자동 수락 → 플랜). 화면 하단에 현재 모드가 표시됩니다. 계획을 승인하면 실행 모드로 넘어가고, 승인하지 않고 Shift+Tab을 다시 눌러 플랜 모드를 빠져나올 수도 있습니다.

Q. 계획이 마음에 안 들면 꼭 실행해야 하나요? A. 아닙니다. 계획을 받았다고 실행할 의무는 없습니다. 방향이 아니면 교정 지시를 주거나 그냥 버리면 됩니다. 계획 단계에서는 파일이 바뀌지 않으므로 손해가 없습니다.

Q. 권한(ch_05)만 잘 설정하면 플랜 모드는 없어도 되지 않나요? A. 둘은 역할이 다릅니다. 권한은 개별 명령의 실행을 통제하고, 플랜 모드는 변경의 전체 방향을 먼저 보게 합니다. 권한은 "이 rm을 실행해도 되나"를, 플랜 모드는 "애초에 무엇을 바꿀 계획인가"를 다룹니다. 안전은 두 겹일 때 가장 튼튼합니다.

6.11 단원 미니 프로젝트: 안전 장비 갖추고 변경 계획 받기 (2종 1세트)

이 챕터로 단원 u5(안전하게 변경하기)가 끝납니다. 마무리로, 이 단원에서 배운 권한과 승인(c05)과 플랜 모드(c06)를 하나로 통합하는 작은 프로젝트를 수행합니다. 목표는 "신입이 낯선 FastAPI 저장소에서 안전 장비를 갖추고, 작은 변경의 계획을 받아 확정하는" 전체 흐름을 한 번에 체험하는 것입니다.

프로젝트 목표

  1. team-tasks-api에서 새 작업 브랜치를 만들고, pytest·routers/ 편집은 자동 허용하고, 삭제·강제리셋·비밀 파일 읽기는 차단하는 권한 규칙을 settings.json에 작성한다(c05).
  2. 작은 변경(엔드포인트 하나 추가)을 플랜 모드로 계획받아 검토·교정한 뒤 확정한다(c06).
  3. 권한 규칙을 프로젝트 공유 범위에 저장해 팀이 공유할 수 있게 한다.

마일스톤(증분)

  • M0. 작업 브랜치: team-tasks-api에서 git checkout -b feat/status-filter로 브랜치를 만든다.
  • M1. 안전 장비 설치(권한): .claude/settings.json에 allow·deny·ask 규칙을 작성한다.
  • M2. 계획 받기(플랜 모드): Shift+Tab으로 플랜 모드에 들어가, 작은 엔드포인트 추가의 계획을 받는다.
  • M3. 검토·교정·확정·검증: 계획의 가정·단계를 점검해 교정하고, 승인해 실행한 뒤 python -m pytest -q로 검증한다.

json

    "deny": [

M1. 권한 규칙을 실제로 작성·적용하라. team-tasks-api에 .claude/settings.json을 직접 만들고, 5장에서 배운 allow/ask/deny로 권한을 정해 저장하세요. 무엇을 어디에 둘지는 스스로 판단합니다.

  • 허용(allow) — 자주 쓰고 안전한 작업: 예) 테스트 실행 명령(pytest)과 routers/ 폴더 편집. 와일드카드는 Bash(pytest:*)·Edit(routers/**)처럼 명령·경로 단위로 좁혀 씁니다.

6.12 마무리: 단원 u5를 마치며

이번 챕터에서 우리는 변경을 시작하기 전에 계획을 먼저 받는 플랜 모드를 배웠습니다. 핵심을 정리하면 다음과 같습니다.

  • 플랜 모드는 읽기 전용으로 변경 계획을 먼저 제시하는 모드이며, Shift+Tab으로 전환합니다.
  • 계획 단계에서는 편집·쓰기 도구가 권한과 무관하게 차단되어 파일이 바뀌지 않습니다.
  • 흐름은 계획 → 검토·교정 → 승인 → 실행이며, 계획 교정(추가·삭제·재정렬)이 핵심 가치입니다.
  • 틀리면 손해가 큰 작업(복잡·고위험·다중 파일·첫 기능)에 쓰고, 사소한 작업에는 쓰지 않습니다.

이로써 단원 u5(안전하게 변경하기)가 끝났습니다. ch_05의 권한과 승인으로 "어떤 명령을 실행해도 되는가"를 통제하고, ch_06의 플랜 모드로 "무엇을 바꿀 계획인가"를 먼저 보는, 두 겹의 안전장치를 갖췄습니다. 이제 신입은 낯선 코드에 위험 없이 첫 변경을 시작할 준비가 되었습니다. 다음 단원(u6)에서는 그렇게 만든 변경이 정말 동작하는지 실행·테스트로 검증하는 법을 배웁니다. 안전하게 바꿨다면, 다음은 제대로 됐는지 증명할 차례입니다.
