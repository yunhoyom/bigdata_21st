Chapter 10

코드 리뷰 받기·대응하기

실무

코드 리뷰 받기·대응하기

이 챕터에서 배우는 것

  • PR을 올리기 전 /code-review로 변경(diff)을 점검해, 지적된 개선점 1개 이상을 미리 반영할 수 있습니다.
  • 자동 코드 리뷰가 PR에 단 인라인 코멘트를 읽고, 그 지적이 버그·보안·엣지·회귀 중 무엇을 가리키는지 해석할 수 있습니다.
  • PR 열림·매 푸시·요청('@claude review') 세 가지 리뷰 트리거를 구분해 필요한 시점에 리뷰를 실행할 수 있습니다.
  • 리뷰 코멘트마다 타당한 지적은 변경으로 반영하고 부적절한 지적에는 근거 있는 반론을 달아 처리할 수 있습니다.

도입: PR을 올리면 리뷰가 따라온다

앞 단원(u8)에서 우리는 작은 논리 단위로 커밋하고, 변경 요약·근거·테스트 결과를 담은 첫 PR을 올렸습니다. 그런데 PR을 올리는 것은 끝이 아니라 대화의 시작입니다. PR은 "이 변경을 메인에 합쳐 주세요"라는 요청이고, 팀은 그 요청에 코드 리뷰(code review)로 응답합니다. 리뷰어가 변경을 읽고, 질문하고, 개선을 제안하고, 마침내 승인하면 비로소 메인에 합쳐집니다.

신입에게 코드 리뷰는 양날의 경험입니다. 한편으로는 가장 많이 배우는 자리입니다. 시니어가 "여기는 이렇게 하는 게 우리 팀 관례예요", "이 경우 입력이 비어 있으면 어떻게 되죠?"라고 짚어 줄 때, 책에 없는 실무 감각이 쌓입니다. 다른 한편으로는 가장 긴장되는 자리이기도 합니다. 내 코드에 빨간 줄이 그어지는 것을 비난으로 받아들이면, 방어적으로 굳어 버리기 쉽습니다.

이 챕터의 목표는 두 가지입니다. 첫째, 리뷰를 받기 전에 스스로 점검해서 뻔한 지적을 미리 줄이는 법입니다. Claude Code(클로드 코드)의 /code-review로 올리기 전에 셀프 점검을 하면, 리뷰어는 더 중요한 설계 논의에 집중할 수 있습니다. 둘째, 리뷰 피드백에 성숙하게 대응하는 법입니다. 타당한 지적은 침착하게 반영하고, 동의하기 어려운 지적에는 근거를 들어 정중히 반론하는 것. 신입의 진짜 역량은 코드 그 자체보다 이 대응의 태도에서 드러납니다.

선수 개념 상기

이 챕터는 git 워크플로: 커밋과 첫 PR(c09)을 바로 앞 선수로 합니다. 리뷰는 "올린 PR"이 있어야 시작되므로, ch_09에서 배운 작업 브랜치·논리 단위 커밋·PR 본문 작성이 전제입니다. 또 리뷰 지적을 반영해 코드를 고칠 때는 실행·테스트로 검증하기(c07)가 다시 등장합니다. 지적을 반영한 뒤 "고쳤습니다"가 아니라 "고치고 테스트가 여전히 통과합니다"를 보여야 리뷰어가 안심합니다. 멀게는 디버깅(c11, 다음 단원)과도 이어지는데, 리뷰가 짚은 버그를 재현하고 최소 수정하는 과정이 곧 디버깅이기 때문입니다.

/code-review: 터미널에서 올리기 전 자가 점검

리뷰의 첫 단계는 사실 남이 아니라 내가 하는 것입니다. PR을 올리기 전에 내 변경을 한 번 더 점검하면, 사소한 실수로 리뷰 왕복을 낭비하지 않습니다.

정의: /code-review

/code-review(코드 리뷰 커맨드)는 Claude Code에 기본 내장된(번들) 슬래시 커맨드로, GitHub 앱을 설치하지 않고도 터미널에서 현재 변경(diff)을 리뷰해 정확성 버그와 재사용·단순화·효율 개선점을 짚어 주는 자가 점검 도구입니다.

/code-review의 동작을 정확히 알아 둡니다.

  • 무엇을 보나: 기본적으로 현재 브랜치가 upstream(보통 main)보다 앞선 커밋들 + 아직 커밋하지 않은 워킹 트리의 변경을 함께 봅니다. 곧 "이 PR이 될 변경 전체"를 점검합니다.
  • 무엇을 짚나: 정확성 버그(correctness bug)와 함께, 중복 제거(reuse)·단순화(simplification)·효율(efficiency) 같은 개선점을 보고합니다. 단순한 스타일 지적을 넘어 "이 로직이 빈 입력에서 깨질 수 있다" 같은 실질적 문제를 잡습니다.
  • 고치기까지: --fix 옵션을 붙이면 발견한 문제를 바로 반영하도록 할 수 있습니다. 다만 신입에게는 먼저 점검 결과를 읽고 무엇을 받아들일지 판단한 뒤 고치는 것을 권합니다.

비슷한 이름의 형제 명령도 함께 기억해 둡니다. /review는 같은 읽기 전용 리뷰를 GitHub의 특정 PR에 대해 수행하고, /security-review는 보안에 집중한 더 깊은 점검입니다(이 챕터 뒤에서 다룹니다). 이 셋은 모두 실제 내장 명령입니다.

/code-review(내장)와 자동 코드 리뷰(GitHub 연동)를 구분하기

두 가지를 헷갈리지 마십시오. /code-review는 내 터미널에서, 올리기 전에, 내가 직접 돌리는 자가 점검입니다. 반면 다음 절에서 다룰 자동 코드 리뷰는 조직이 GitHub에 Code Review를 활성화했을 때, PR이 올라오면 자동으로 돌아 PR 화면에 인라인 코멘트를 다는 별도 기능입니다. 전자는 사전 점검, 후자는 사후 자동 리뷰입니다. 좋은 신입은 둘을 함께 씁니다. 올리기 전 /code-review로 거르고, 올린 뒤 자동 리뷰와 사람 리뷰로 한 번 더 거릅니다.

동작 원리: 자동 리뷰가 PR에 인라인 코멘트를 다는 흐름

조직이 Claude Code의 Code Review(코드 리뷰 서비스)를 활성화하면, PR이 올라올 때 전문 에이전트가 변경을 분석해 문제를 발견한 바로 그 코드 줄에 인라인 코멘트(inline comment)로 남깁니다. 이 자동 리뷰가 일하는 흐름을 단계로 풀면 다음과 같습니다.

  1. 트리거(trigger) — 설정된 조건이 충족되면 리뷰가 시작됩니다. 보통은 PR이 열리는 순간입니다(자세한 트리거 방식은 다음 절에서 다룹니다).

  2. 분석(analyze) — 에이전트가 PR의 변경(diff)과 주변 코드를 읽어, 논리 오류·보안 취약점·엣지 케이스·미묘한 회귀(regression, 기존 동작이 깨지는 것)를 찾습니다. 단순히 줄 단위로 보는 것이 아니라 변경의 맥락을 함께 봅니다.

  3. 정리(dedupe·rank) — 발견한 문제들을 중복 제거(dedupe)하고 심각도순으로 정렬(rank)합니다. 같은 문제를 여러 번 반복해 코멘트하지 않고, 중요한 것이 위로 오게 합니다. 신입이 "코멘트 폭탄"에 압도되지 않도록 걸러 주는 단계입니다.

  4. 인라인 코멘트(comment) — 각 문제를 해당 코드 줄에 직접 코멘트로 답니다. "이 줄에서 task_id가 없으면 KeyError가 납니다" 같은 식으로, 어느 코드의 무엇이 문제인지가 한눈에 연결됩니다.

  5. 대응(respond) — 신입은 각 코멘트를 읽고 대응합니다. 타당하면 코드를 고쳐 다시 푸시하고, 동의하기 어려우면 코멘트에 답글로 근거를 답니다. 이 왕복이 끝나고 사람 리뷰어가 승인하면 머지(merge)됩니다.

단계 무엇이 일어나나 신입이 할 일
트리거 PR 열림·푸시·요청으로 리뷰 시작 트리거 방식을 알고 기다림
분석 버그·보안·엣지·회귀 탐색 (기다림)
정리 중복 제거·심각도 정렬 (기다림)
인라인 코멘트 문제 줄에 코멘트 부착 코멘트를 읽고 이해
대응 반영·재요청·반론 판단해 대응, 테스트로 검증

자동 리뷰는 사람 리뷰를 대체하지 않는다

자동 코드 리뷰는 뻔한 버그·보안 문제·엣지 케이스를 빠르게 걸러 사람 리뷰어의 부담을 덜어 줍니다. 하지만 "이 기능이 우리 제품 방향에 맞는가", "이 설계가 6개월 뒤에도 유지보수하기 좋은가" 같은 판단은 여전히 사람의 몫입니다. 자동 리뷰를 "1차 필터"로, 사람 리뷰를 "최종 판단"으로 보는 것이 건강한 관점입니다.

worked example: /code-review로 점검해 지적 미리 반영

ch_09에서 만든 "작업 완료 처리 엔드포인트" 브랜치를 PR로 올리기 전에 /code-review로 점검해 보겠습니다. 목표는 "리뷰어가 짚기 전에 내가 먼저 발견해 고치기"입니다.

리뷰 대상 코드는 다음과 같다고 합시다. 언뜻 동작하지만 숨은 문제가 있습니다.

python
# routers/tasks.py (점검 대상)
@router.patch("/tasks/{task_id}/complete")
def complete_task(task_id: int):
    task = TASKS[task_id]          # 없는 id 면 KeyError
    task["done"] = True
    return task

[높음] 정확성 — routers/tasks.py:3

[낮음] 견고성 — routers/tasks.py:4

  중복 완료 요청을 멱등(idempotent)하게 처리한다는 점을 테스트로
  명시해 두면 좋습니다.
  • /code-review는 인자 없이 부르면 현재 브랜치의 변경 전체를 점검합니다. PR을 올리기 전에 돌렸다는 점이 핵심입니다. 리뷰어가 아니라 내가 먼저 봅니다.
  • 결과가 심각도([높음]·[낮음])와 파일:줄로 정리되어 있습니다. routers/tasks.py:3처럼 위치가 명확해 어디를 고칠지 바로 압니다.
  • [높음] 지적은 실제 버그입니다. 없는 task_id로 요청하면 KeyError가 나 500 오류가 됩니다. 이런 건 리뷰어가 짚기 전에 반드시 고쳐야 할 정확성 문제입니다.
  • [낮음] 지적은 버그는 아니지만 견고성 제안입니다. 모든 지적을 같은 무게로 받지 말고, 심각도에 따라 우선순위를 두는 것이 좋습니다.

이제 높음 지적을 반영합니다. /code-review --fix로 자동 반영할 수도 있지만, 여기서는 무엇을 고칠지 명시해 직접 고치게 합니다.

console
> [높음] 지적을 반영해 줘. 없는 task_id 면 404 를 반환하도록
  HTTPException 으로 고치고, 그 경우를 검증하는 테스트도 추가해 줘.

반영 후 코드는 다음과 같이 바뀝니다.

python
# routers/tasks.py (반영 후)
from fastapi import HTTPException

@router.patch("/tasks/{task_id}/complete")
def complete_task(task_id: int):
    task = TASKS.get(task_id)
    if task is None:
        raise HTTPException(status_code=404, detail="작업을 찾을 수 없습니다")
    task["done"] = True
    return task

  • TASKS[task_id]를 TASKS.get(task_id)로 바꿔 없는 키에 None을 받게 하고, None이면 HTTPException(404)로 명확한 응답을 줍니다. 500(서버 오류)이 아니라 404(찾을 수 없음)는 "클라이언트가 없는 자원을 요청했다"는 정확한 의미입니다.
  • 고친 뒤 반드시 테스트를 돌려 통과를 확인했습니다(c07). "고쳤다"가 아니라 "고치고 3개 테스트가 통과한다"가 진짜 완료입니다.
  • 이렇게 올리기 전에 정확성 버그를 스스로 잡으면, 실제 PR 리뷰는 더 가벼워지고 리뷰어는 더 중요한 부분에 집중합니다.

리뷰 트리거: PR 열림·매 푸시·요청('@claude review')

자동 코드 리뷰가 언제 돌지는 저장소별로 설정합니다. 조직이 Code Review를 활성화하면, 저장소마다 "리뷰 동작(Review Behavior)"을 골라 트리거 방식을 정합니다. 세 가지 방식이 있습니다.

트리거 언제 리뷰가 도나 어울리는 상황
PR 생성 후 1회 PR이 열리거나 'Ready for review'가 될 때 한 번 기본값. 완성된 변경을 한 번 점검
매 푸시마다 PR 브랜치에 푸시할 때마다 변경이 자주 바뀌는 PR을 계속 추적
수동(요청 시) 코멘트로 @claude review라고 적을 때만 필요할 때만 비용 없이 호출
  • PR 생성 후 1회가 기본입니다. PR을 열면 리뷰가 한 번 돌아 초기 점검을 해 줍니다. 대부분의 작은 PR에는 이걸로 충분합니다.
  • 매 푸시마다는 PR이 진화하는 동안 새로 들어온 문제를 계속 잡아 줍니다. 다만 푸시가 잦으면 리뷰도 자주 돌아 비용·코멘트가 늘 수 있습니다.
  • 수동은 평소엔 돌지 않다가, 누군가 PR 코멘트에 @claude review라고 적으면 그때 리뷰합니다. 비용을 아끼면서 "지금 봐 줘"라고 명시적으로 부를 때 유용합니다.

여기서 @claude는 GitHub의 멘션(mention)입니다. PR이나 이슈 코멘트에 @claude로 부르면 Claude가 요청을 받아 분석·리뷰·수정 같은 작업을 수행합니다(GitHub Actions 연동 기반). 예컨대 자동 리뷰가 한 번 끝난 뒤 코드를 더 고쳐 올리고 나서, @claude review로 다시 봐 달라고 명시적으로 요청할 수 있습니다.

트리거를 알면 리뷰를 능동적으로 쓴다

트리거 방식을 모르면 "왜 리뷰가 안 달리지?" 하고 막연히 기다리게 됩니다. 우리 저장소가 "수동" 설정이라면 PR을 올려도 자동으로 리뷰가 돌지 않으니, 직접 @claude review로 불러야 합니다. 반대로 "매 푸시마다"라면 작은 수정을 푸시할 때마다 리뷰가 돌 수 있습니다. 내 저장소의 설정을 알아 두는 것이 리뷰를 능동적으로 활용하는 출발점입니다.

다음은 "수동" 트리거 저장소에서, 리뷰 지적을 반영해 다시 푸시한 뒤 명시적으로 재리뷰를 요청하는 흐름입니다. PR 화면의 코멘트 입력란에 멘션을 적습니다.

text
[PR #42 코멘트 입력]
@claude review

이렇게 @claude를 멘션하면 Claude가 PR의 최신 상태를 다시 분석해 새 인라인 코멘트를 답니다. "수동" 트리거에서는 이 멘션이 있어야 리뷰가 돌므로, 고치고 푸시한 뒤 재요청하는 것을 잊지 마십시오. 같은 멘션 방식으로 @claude에게 특정 작업(예: "이 함수의 테스트를 추가해 줘")을 PR 안에서 직접 부탁할 수도 있습니다.

worked example: 인라인 코멘트를 읽고 해당 줄 수정

PR을 올리자 자동 리뷰가 한 코드 줄에 인라인 코멘트를 달았다고 합시다. 이를 읽고 해당 줄을 고치는 흐름을 따라가 봅니다.

상태 필터를 추가한 다음 엔드포인트가 리뷰 대상입니다.

python
# routers/tasks.py (리뷰가 코멘트를 단 코드)
@router.get("/tasks")
def list_tasks(status: str = None):
    return [t for t in TASKS.values() if t["status"] == status]

자동 리뷰가 return 줄에 다음 인라인 코멘트를 남겼습니다.

text
[자동 리뷰 코멘트 — routers/tasks.py:4]
status 파라미터가 주어지지 않으면(None) 어떤 작업도 status == None 과
일치하지 않아 항상 빈 목록이 반환됩니다. 필터가 없을 때는 전체 목록을
반환해야 의도에 맞습니다.

이 코멘트는 회귀에 가까운 논리 오류를 짚었습니다. "필터를 안 주면 전체가 나와야 하는데, 빈 목록이 나온다"는 것입니다. 코멘트가 가리키는 줄을 에이전트와 함께 고칩니다.

console
> routers/tasks.py:4 에 달린 리뷰 코멘트를 반영해 줘. status 가
  None 이면 전체를 반환하고, 값이 있으면 그 값으로 필터링하도록 고치고,
  두 경우를 모두 검증하는 테스트를 추가해 줘.
python
# routers/tasks.py (반영 후)
@router.get("/tasks")
def list_tasks(status: str | None = None):
    tasks = list(TASKS.values())
    if status is None:
        return tasks
    return [t for t in tasks if t["status"] == status]

  • 인라인 코멘트의 위치(:4)와 내용을 그대로 지시에 담아, 에이전트가 어느 줄의 무엇을 고칠지 정확히 알게 했습니다. "코멘트 반영해 줘"라고만 하지 않고 "어떻게 고칠지"(None이면 전체, 값이 있으면 필터)를 명시한 점이 중요합니다.
  • 고친 로직은 status is None을 먼저 분기해 필터가 없으면 전체를 반환합니다. 리뷰가 짚은 논리 오류를 정확히 해소했습니다.
  • 한 코멘트를 반영할 때도 그 경우를 검증하는 테스트(필터 없음·필터 있음 두 경우)를 함께 추가하고 통과를 확인했습니다. 이렇게 하면 같은 문제가 다시 생기지 않습니다(회귀 방지).
  • 고친 뒤에는 다시 푸시합니다. 트리거가 "매 푸시마다"라면 자동 리뷰가 다시 돌고, "수동"이라면 @claude review로 다시 봐 달라고 요청합니다.

/security-review로 취약점 사전 점검

정확성 버그를 잡았다면, 한 가지 점검이 더 남았습니다. 보안입니다. 보안 결함은 평소엔 잘 드러나지 않다가, 공격자가 악용할 때 큰 사고가 됩니다. 신입이 무심코 흘리기 쉬운 영역이라 별도의 도구가 있습니다.

정의: /security-review

/security-review(보안 리뷰 커맨드)는 Claude Code에 내장된 슬래시 커맨드로, 변경을 보안 관점에서 더 깊이 점검해 SQL 인젝션·XSS(크로스 사이트 스크립팅)·인증 결함·안전하지 않은 데이터 처리·의존성 취약점 같은 흔한 보안 문제를 찾아 주는 읽기 전용 점검입니다.

/security-review는 터미널에서 바로 돌려 올리기 전에 보안을 점검할 수 있고, 발견한 문제를 고쳐 달라고 바로 이어서 요청할 수도 있습니다. GitHub Actions로 연동하면 PR마다 보안 리뷰를 자동으로 돌릴 수도 있습니다. 권장 습관은 의미 있는 변경을 커밋하기 전에 /security-review를 한 번 돌리는 것입니다.

다음은 사용자 검색 엔드포인트를 보안 점검하는 예입니다.

console
> /security-review

(Claude Code가 변경을 보안 관점에서 분석)

보안 리뷰 결과 (1건)

[높음] SQL 인젝션 — routers/search.py:7
  사용자 입력 keyword 를 f-string 으로 SQL 문에 직접 끼워 넣어,
  공격자가 임의 SQL 을 실행할 수 있습니다.
  제안: 파라미터 바인딩(플레이스홀더)을 사용해 입력을 값으로 전달하세요.

문제가 된 코드와 안전한 수정은 다음과 같습니다.

python
# 취약: 사용자 입력을 SQL 에 직접 끼워 넣음 (SQL 인젝션)
query = f"SELECT * FROM users WHERE name LIKE '%{keyword}%'"
db.execute(query)

# 안전: 파라미터 바인딩으로 입력을 값으로 전달
query = "SELECT * FROM users WHERE name LIKE ?"
db.execute(query, (f"%{keyword}%",))
  • 취약한 코드는 keyword를 문자열로 직접 SQL에 붙였습니다. 공격자가 keyword에 ' OR '1'='1 같은 값을 넣으면 의도하지 않은 쿼리가 실행됩니다(SQL 인젝션).
  • 안전한 코드는 값이 들어갈 자리를 ? 플레이스홀더로 두고, 실제 값을 별도 인자로 전달합니다. 데이터베이스가 입력을 코드가 아니라 값으로 취급하므로 인젝션이 막힙니다.
  • /security-review는 이런 결함을 사람 리뷰어가 놓치기 쉬운 단계에서 미리 잡아 줍니다. 다만 보안 리뷰가 모든 취약점을 잡는다고 맹신하지 말고, 입력 검증·인증 같은 기본기는 평소에 갖추는 것이 우선입니다.

피드백 대응: 반영·재요청·근거 있는 반론

리뷰 코멘트를 받았을 때의 대응은 세 가지로 나뉩니다. 신입의 성숙도는 이 셋을 상황에 맞게 고르는 데서 드러납니다.

  1. 반영(accept) — 지적이 타당하면 코드를 고치고, 테스트로 검증한 뒤, 무엇을 어떻게 고쳤는지 코멘트에 한 줄로 답합니다. 가장 흔하고 기본이 되는 대응입니다.

  2. 재요청(re-review) — 고쳐 푸시한 뒤 다시 봐 달라고 요청합니다. 트리거가 "매 푸시마다"면 자동으로 다시 돌고, "수동"이면 @claude review나 리뷰어 멘션으로 명시적으로 부릅니다.

  3. 근거 있는 반론(push back with reason) — 모든 지적을 무조건 수용할 필요는 없습니다. 동의하기 어렵다면, 감정이 아니라 근거로 정중히 반론합니다. "그건 이미 상위 미들웨어에서 검증하고 있어서 여기서 다시 검사하면 중복입니다. 관련 코드는 middleware.py:20입니다"처럼 사실과 위치를 들어 답합니다.

세 대응의 좋은 답글 예시를 비교합니다.

상황 나쁜 답글 좋은 답글
타당한 지적 (무시하고 그냥 머지) "맞습니다. get+404로 고치고 테스트 추가했습니다. 통과 확인했습니다."
고치고 재요청 "고쳤어요" "404 처리와 테스트를 추가해 다시 푸시했습니다. @claude review로 재점검 부탁드립니다."
동의 어려움 "이게 맞는데요" "이 검증은 middleware.py:20에서 이미 수행해 중복이라 판단합니다. 그래도 여기 두는 게 좋을까요?"

리뷰는 비난이 아니라 코드에 대한 대화다

리뷰 코멘트는 "당신이 틀렸다"가 아니라 "이 코드를 더 좋게 만들자"는 제안입니다. 지적의 대상은 여러분이 아니라 코드입니다. 이 관점을 가지면 방어적으로 굳지 않고, 지적을 학습 기회로 받아들일 수 있습니다. 반대로 모든 지적을 무비판적으로 수용하는 것도 좋지 않습니다. 근거를 이해하지 못한 채 고치면 같은 실수를 반복합니다. "왜 이런 지적이 나왔는가"를 이해하는 것이 반영이든 반론이든 모든 좋은 대응의 출발점입니다.

자주 묻는 질문

/code-review와 /review는 무엇이 다른가요?

/code-review는 내 터미널의 현재 변경(diff)을 점검합니다. 아직 PR을 올리지 않았거나 커밋하지 않은 변경까지 봅니다. /review는 같은 읽기 전용 리뷰를 이미 GitHub에 올라간 특정 PR에 대해 수행합니다. 곧 "올리기 전 내 변경 점검"은 /code-review, "올라간 PR 점검"은 /review로 기억하면 됩니다.

자동 리뷰가 코멘트를 너무 많이 달면 어떻게 하나요?

Code Review 서비스는 발견한 문제를 중복 제거하고 심각도순으로 정렬해 답니다. 그래도 코멘트가 많다면 [높음]부터 차례로 대응하세요. 모든 코멘트를 한 번에 완벽히 처리하려 하기보다, 심각도가 높은 것부터 반영하고 푸시해 가며 좁혀 가는 편이 현실적입니다.

리뷰 지적이 틀린 것 같으면 그냥 무시해도 되나요?

무시하지 말고 근거를 들어 답글로 반론하세요. 지적이 정말 부적절하다면 "이 검증은 middleware.py:20에서 이미 수행해 중복입니다"처럼 사실과 위치로 답하면 됩니다. 답 없이 무시하면 리뷰어(사람이든 자동이든)는 여러분이 코멘트를 못 봤는지, 동의하는지 알 수 없습니다. 반론도 대응의 한 형태입니다.

/security-review는 언제 돌리는 게 좋나요?

권장 습관은 의미 있는 변경을 커밋하기 전에 한 번 돌리는 것입니다. 특히 사용자 입력을 다루거나(검색·로그인), 데이터베이스 쿼리를 만들거나, 외부 요청을 보내는 코드를 바꿨다면 반드시 점검하세요. 프로덕션 코드 저장소라면 GitHub Actions로 PR마다 자동 보안 리뷰를 돌리도록 설정하는 것도 좋습니다.

이 미니 프로젝트는 9장에서 만든 team-tasks-api의 작업 브랜치를, PR로 올리기 전에 /code-review·/security-review로 스스로 점검하고 지적을 반영하는 과제입니다. 9장 미니 프로젝트의 변경(예: routers/tasks.py의 작은 기능 추가와 그 테스트)이 작업 브랜치에 있다고 가정합니다.

마일스톤(증분):

  1. M1 정확성 자가 점검. team-tasks-api 루트에서 작업 브랜치에 선 채로 /code-review를 실행해, 현재 브랜치의 변경 전체에 대한 정확성·개선 지적을 받습니다. (적용 개념: /code-review 자가 점검)
  2. M2 보안 자가 점검. 이어서 /security-review를 실행해 보안 관점의 지적이 없는지 확인합니다. 사용자 입력을 다루는 부분이 있다면 특히 주의해 봅니다. (적용 개념: /security-review)
  3. M3 심각도순 반영. [높음] 지적부터 차례로 반영합니다. 없는 자원에 404를 주는지, 필터 없는 요청에 전체를 반환하는지 같은 경계 동작을 점검해 고칩니다. (적용 개념: 심각도순 대응)
  4. M4 검증·재요청. 반영 후 테스트를 돌려 통과를 확인하고, 그 결과를 답글·PR 본문에 적습니다. "수동" 트리거 저장소라면 @claude review로 재점검을 요청합니다. (적용 개념: 반영·재요청·검증)

실제 검증 단계. 지적을 반영한 뒤 반드시 저장소 전체 테스트를 돌려 통과를 확인합니다(c07). 한 군데를 고치다 다른 곳을 깨지 않았는지까지 봅니다.

미니 프로젝트 자가체크

  • [ ] team-tasks-api에서 올리기 전 /code-review를 직접 돌렸는가
  • [ ] /security-review로 보안 관점도 점검했는가
  • [ ] 지적을 심각도순으로 우선순위를 두어 반영했는가
  • [ ] 반영 후 python -m pytest -q로 전체 통과를 확인했는가(부분 테스트만 보지 않았는가)
  • [ ] 동의하기 어려운 지적에는 근거·위치(파일:줄)로 답했는가
  • [ ] 우리 저장소의 리뷰 트리거 방식(1회·매 푸시·수동)을 확인하고 필요 시 @claude review로 재요청했는가

참고: 위 worked example의 routers/tasks.py·routers/search.py 코드 조각은 리뷰가 잡아내는 "고치기 전 초안"을 보여 주기 위한 예시입니다. 실제 team-tasks-api의 라우터는 1장에서 본 대로 store.py에 로직을 위임하므로, 여러분의 점검 대상은 여러분이 그 저장소에 더한 실제 변경입니다.

흔한 오류와 오개념

1. 리뷰 지적을 방어적으로 받아들인다

빨간 줄을 비난으로 느껴 굳어 버리면 배울 기회를 잃습니다. 리뷰의 대상은 여러분이 아니라 코드입니다. "왜 이런 지적이 나왔는가"를 먼저 이해하면, 반영하든 반론하든 한 단계 성장합니다. 신입의 평판은 완벽한 첫 코드가 아니라 피드백에 대응하는 태도에서 만들어집니다.

2. 자동 리뷰가 모든 걸 잡아 준다고 맹신한다

자동 코드 리뷰·/code-review·/security-review는 강력하지만 만능이 아닙니다. "이 기능이 제품 방향에 맞는가", "이 설계가 장기적으로 유지보수하기 좋은가" 같은 판단은 사람의 몫이고, 자동 리뷰가 놓치는 도메인 특유의 버그도 있습니다. 자동 리뷰는 "1차 필터"이지 "최종 보증"이 아닙니다. 통과했다고 검증을 생략하지 마십시오.

3. 모든 지적을 무비판적으로 반영한다

지적이 타당한지 따져 보지 않고 기계적으로 다 고치면, 근거 없는 변경이 쌓이고 때로는 멀쩡한 코드를 망칩니다. 이미 다른 곳에서 처리되는 검증을 중복으로 넣거나, 우리 맥락에 맞지 않는 일반론을 따르는 일이 생깁니다. 근거를 이해하고 판단해 반영하거나, 합당한 이유가 있으면 정중히 반론하세요.

4. 고치기만 하고 검증하지 않는다

리뷰 지적을 반영한 뒤 "고쳤습니다"로 끝내면, 그 수정이 다른 곳을 깨뜨렸을 수 있습니다. 반영 후에는 반드시 테스트를 돌려 통과를 확인(c07)하고, 그 결과를 답글에 함께 적으세요. "고치고 테스트가 통과합니다"가 "고쳤습니다"보다 훨씬 신뢰를 줍니다.

5. /code-review와 자동 코드 리뷰를 혼동한다

/code-review는 내 터미널에서 올리기 전에 내가 돌리는 자가 점검이고, 자동 코드 리뷰는 조직이 GitHub에 활성화했을 때 PR에 자동으로 인라인 코멘트를 다는 기능입니다. 둘은 시점과 주체가 다릅니다. 또 /code-review·/security-review는 진짜 내장 명령이지만, 앞 챕터의 /commit-push-pr은 커스텀 커맨드였다는 점도 함께 기억하면 "이 명령이 어디서 왔는가"를 정확히 구분할 수 있습니다.

이 챕터 한 줄 정리

좋은 리뷰 대응은 "올리기 전 /code-review·/security-review로 자가 점검 → 자동 리뷰의 인라인 코멘트를 심각도순으로 이해 → 타당하면 반영하고 테스트로 검증, 동의 어려우면 근거로 반론"의 흐름이며, 리뷰는 비난이 아니라 코드를 함께 다듬는 대화입니다. 다음 단원(u10)에서는 리뷰가 짚은 버그를 본격적으로 추적해 고치는 디버깅을 배웁니다.
