종합 프로젝트: 첫 기능·첫 PR — 발표·평가·성찰

실무

종합 프로젝트: 첫 기능·첫 PR — 발표·평가·성찰

이 챕터에서 배우는 것

  • 완성한 첫 기능·통과한 테스트·올린 PR을 공개 산출물로 시연할 수 있습니다.
  • 주어진 평가 루브릭의 항목별 기준에 맞춰 자신과 동료의 작업을 점수·근거로 평가할 수 있습니다.
  • 12개 개념(c01~c12) 각각을 종합 프로젝트의 어느 단계에서 어떻게 적용했는지 성찰 회고로 작성할 수 있습니다.
  • 현재 결과물의 한계 1개 이상과 다음 학습(서브에이전트·MCP 심화) 방향을 제시할 수 있습니다.

이 챕터는 종합 프로젝트의 마지막 단계인 발표·평가·성찰(present & reflect)입니다. 새 개념을 배우지 않습니다. 구현(ch_15)한 산출물을 남에게 보이고, 기준으로 평가하며, 온보딩 여정 전체를 되짚어 다음 단계로 연결합니다.

산출물 시연: 동작하는 기능·통과한 테스트·올린 PR

발표의 핵심은 "잘 만들었다"는 말이 아니라 보이는 증거입니다. 신입의 첫 기능 발표는 세 가지를 순서대로 보여 주면 충분합니다. 동작하는 기능, 통과한 테스트, 올린 PR입니다.

1) 동작하는 기능 시연

서버를 띄우고, 추가한 두 엔드포인트가 실제로 응답하는 모습을 보여 줍니다. 말이 아니라 요청·응답으로 증명합니다.

text
$ python -m uvicorn app.main:app --reload
INFO:     Uvicorn running on http://127.0.0.1:8000 (Press CTRL+C to quit)
INFO:     Application startup complete.

$ curl -X PATCH http://127.0.0.1:8000/tasks/1/complete
{"id":1,"title":"온보딩 문서 읽기","status":"done"}

$ curl "http://127.0.0.1:8000/tasks?status=done"
[{"id":1,"title":"온보딩 문서 읽기","status":"done"}]

$ curl -i "http://127.0.0.1:8000/tasks?status=working"
HTTP/1.1 422 Unprocessable Entity

완료 처리가 상태를 done으로 바꾸고(UC1), 필터가 done인 항목만 거르며(UC2), 잘못된 상태는 422로 막힙니다(FR4). 정상 경로뿐 아니라 에러 경로까지 보여 주는 것이 신뢰를 줍니다.

2) 통과한 테스트 시연

기능이 "지금 이 순간"만이 아니라 반복적으로 동작함을 테스트로 보입니다.

text
$ python -m pytest -q
......                                                                   [100%]
6 passed in 0.48s

완료·404·필터·422·멱등·빈값의 여섯 경로가 모두 통과합니다. 이 출력이 "동작합니다"라는 주장의 증거입니다.

3) 올린 PR 시연

마지막으로 PR을 보여 줍니다. 변경 요약·근거·내용·테스트 결과가 담겨 리뷰어가 1분 안에 파악할 수 있는 형태입니다.

text
$ gh pr view 57
title:  feat(tasks): 완료 처리·상태 필터 추가
state:  OPEN
url:    https://github.com/team/team-tasks-api/pull/57

완료 처리(PATCH /tasks/{id}/complete)와 상태 필터(GET /tasks?status=)를
추가했습니다. 없는 id 는 404, 잘못된 status 는 422. 테스트 6개 통과.

발표 한 장 요약 틀

발표는 다음 한 문장 틀에 맞춰 말하면 군더더기 없이 전달됩니다. "[무엇을] 추가했고, [어떤 테스트]로 검증했으며, [어떤 PR]로 올렸습니다. 설계에서는 [핵심 ADR]을 택했고, 남은 범위는 [제외 항목]입니다." 예: "완료 처리·상태 필터를 추가했고, 여섯 개 테스트로 검증했으며, #57 PR로 올렸습니다. 상태는 확장을 위해 enum으로 택했고(ADR2), 완료 취소는 후속으로 남겼습니다."

평가 루브릭

좋은 평가는 "느낌"이 아니라 공유된 기준으로 합니다. 아래 루브릭은 이 종합 프로젝트의 여섯 가지 기준과 가중치, 그리고 미흡·보통·우수의 수준을 정의합니다. 자신을 먼저 평가하고, 동료의 작업도 같은 기준으로 봅니다.

기준 가중치 미흡 보통 우수
기능 완성도(완료 처리·상태 필터·에러 응답) 0.20 한 엔드포인트만 부분 동작 두 엔드포인트 동작 두 엔드포인트 + 404·422 에러 응답까지 동작
검증(테스트) 0.20 테스트 없음 행복 경로 테스트만 TDD로 작성한 행복·에러 경로 테스트가 모두 통과
안전·절차(권한·플랜·CLAUDE.md) 0.15 바로 편집 권한 또는 플랜 중 하나만 최소 권한·플랜 모드·CLAUDE.md를 모두 적용
협업(커밋·PR 품질) 0.20 한 덩어리 커밋·빈약한 PR 관례 커밋과 기본 PR 작은 논리 커밋 + 요약·근거·테스트 결과를 담은 PR
리뷰 대응·디버깅 0.15 대응 없음 지적을 반영만 근거를 이해해 반영·반론하고 회귀 테스트로 확인
발표·성찰 0.10 동작만 보여 줌 변경 의도 설명 ADR 근거·개념 적용 회고·다음 학습 방향까지 제시

점수를 매기는 법

각 기준의 수준(미흡 1점·보통 2점·우수 3점)에 가중치를 곱해 더하면 가중 평균이 나옵니다. 예를 들어 모든 기준이 "보통(2점)"이면 2.00, 모두 "우수(3점)"이면 3.00입니다. 점수 자체보다 어느 기준이 약한지를 찾아 다음에 보완하는 데 의미가 있습니다.

worked example: 이 프로젝트를 루브릭으로 자가 평가하기

ch_15에서 완성한 산출물을 루브릭으로 직접 채점해 보겠습니다. 각 기준마다 수준을 고르고, 그 판단의 근거를 한 줄로 답니다. 근거 없이 점수만 매기면 다음에 무엇을 고칠지 알 수 없습니다.

기준 가중치 내 수준 점수 근거
기능 완성도 0.20 우수 3 두 엔드포인트 + 404·422 에러 응답까지 동작
검증(테스트) 0.20 우수 3 완료·404·필터·422를 TDD로 작성, 6개 통과
안전·절차 0.15 우수 3 최소 권한·플랜·CLAUDE.md를 M1에서 모두 적용
협업(커밋·PR) 0.20 우수 3 feat·test 분리 커밋 + 근거·테스트 담은 PR
리뷰 대응·디버깅 0.15 우수 3 지적을 재현·검증하고 회귀 테스트로 못 박음
발표·성찰 0.10 보통 2 변경 의도는 설명했으나 ADR 근거 연결이 얕음

가중 평균은 3*0.20 + 3*0.20 + 3*0.15 + 3*0.20 + 3*0.15 + 2*0.10 = 2.90입니다. 점수가 높아도 의미는 마지막 줄에 있습니다. 발표·성찰 기준이 가장 약했고, "ADR 근거를 발표에 더 분명히 연결한다"가 다음에 보완할 한 가지입니다. 이렇게 루브릭은 잘한 점을 확인하는 동시에 다음 목표 하나를 집어 줍니다.

연습: 나의 실제 산출물을 루브릭으로 자가 평가하라

자신이 실제로 만든 첫 기능(team-tasks-api의 완료 처리·상태 필터)을 위 모범 표처럼 직접 평가해 작성하세요. 점수보다 근거와 가장 약한 기준을 찾는 데 집중합니다. 각 칸은 추측이 아니라, 내가 실제로 한 작업(커밋·테스트·리뷰 대응)에 비추어 적습니다.

아래 표를 그대로 옮겨, 각 칸을 자신의 산출물로 직접 채우세요.

text
| 기준              | 내 수준 | 점수 | 근거(내가 실제로 한 것) |
| 기능 완성도        | (직접 적기) | (직접) | (내 산출물 근거를 직접 적는다) |
| 검증(테스트)       | (직접 적기) | (직접) | (내 산출물 근거를 직접 적는다) |
| 안전·절차          | (직접 적기) | (직접) | (내 산출물 근거를 직접 적는다) |
| 협업(커밋·PR)      | (직접 적기) | (직접) | (내 산출물 근거를 직접 적는다) |
| 리뷰 대응·디버깅    | (직접 적기) | (직접) | (내 산출물 근거를 직접 적는다) |
| 발표·성찰          | (직접 적기) | (직접) | (내 산출물 근거를 직접 적는다) |

가중 평균: (직접 계산해 적기)   가장 약한 기준: (직접 적기)   다음에 보완할 한 가지: (직접 적기)

루브릭은 채점표가 아니라 길잡이

루브릭의 진짜 쓸모는 점수를 매기는 데 있지 않고, "우수"의 모습을 미리 보여 주는 데 있습니다. 예컨대 검증 기준의 "우수"는 "행복 경로만이 아니라 에러 경로(404·422)까지 TDD로 검증"입니다. 작업을 시작하기 전에 이 기준을 읽으면, 무엇을 목표로 삼아야 할지가 분명해집니다. 끝나고 채점하기보다, 시작 전에 목표로 읽으십시오.

동료 피드백 (모의 리뷰)

발표 뒤에는 동료의 눈으로 한 번 더 점검합니다. 실제 팀에서는 동료가 PR에 코멘트를 달지만, 여기서는 모의 동료 리뷰로 연습합니다. 좋은 동료 리뷰는 비난이 아니라, 같은 기준(루브릭)을 근거로 한 구체적 제안입니다.

다음은 이 프로젝트에 대한 모의 동료 리뷰의 예입니다.

동료 A (검증 기준): 에러 경로(404·422)까지 테스트한 점이 좋습니다. 다만 완료 처리를 연속 두 번 호출했을 때도 안전한지 궁금합니다. 멱등성 테스트가 이미 있다면 그 의도를 PR 본문에도 한 줄 적어 주면 리뷰어가 더 빨리 이해할 것 같습니다.

동료 B (협업 기준): 구현과 테스트를 feat·test로 나눈 커밋이 깔끔합니다. PR 제목도 관례를 잘 따랐습니다. 한 가지, "범위 - 제외"에 적힌 완료 취소 기능은 후속 이슈로 등록해 두면 추적이 쉬울 것 같습니다.

동료 C (설계 기준): 상태를 불리언이 아니라 enum으로 택한 결정(ADR2)이 확장에 유리해 보입니다. 다만 enum 값이 늘어날 때를 대비해, 필터가 여러 상태를 받는 경우(예: ?status=todo,done)는 어떻게 할지 후속에서 한 번 정리하면 좋겠습니다.

이 리뷰들에 대응하는 방식은 ch_15에서 배운 그대로입니다. 타당한 지적은 반영하고, 확인이 필요하면 재현·검증하며, 부적절하면 근거로 답합니다. 예컨대 동료 A의 제안은 PR 본문에 한 줄 추가하는 것으로 바로 반영할 수 있고, 동료 C의 제안은 이번 범위 밖이므로 "후속 이슈로 남기겠습니다"라고 근거와 함께 답하면 됩니다.

모의 동료 리뷰 작성 연습

짝의 산출물(또는 자신의 실제 산출물)에 대해, 루브릭 기준 하나를 골라 동료 리뷰 한 건을 직접 작성하세요. 비난이 아니라 근거 있는 구체적 제안으로 적습니다. 위 동료 A·B·C 예시를 본떠, 실제로 본 코드·PR에 근거해 적습니다.

아래 형식을 그대로 옮겨, 각 항목을 직접 작성하세요.

text
[고른 기준]  (직접 적는다 — 예: 검증)
[좋은 점]    (직접 적는다)
[제안]       (직접 적는다)
[근거]  루브릭의 "우수" 수준은 (직접 적는다) 인데,
        현재는 (직접 적는다) 이므로 한 걸음 더 가면 좋겠습니다.

성찰 회고: 12개 개념의 적용

이 온보딩 여정의 핵심은, 따로 배운 12개 개념이 한 번의 실제 업무에서 어떻게 하나로 모이는가를 체득하는 것이었습니다. 첫 기능 추가의 각 단계가 어느 개념에서 왔는지 되짚어 봅니다.

개념 단원 첫 기능 추가의 어느 단계로 이어졌나
c01 설치·인증·세션 u1 작업 시작 전 환경을 갖추고 세션을 열어 첫 작업을 지시
c02 에이전트 루프 u2 구현(M3)에서 관찰→계획→도구→확인의 흐름으로 변경을 진행
c03 작업 지시 4요소 u3 테스트·구현 지시(M2·M3)를 목표·맥락·제약·완료 조건으로 작성
c04 코드베이스 탐색 u4 분석(ch_13)에서 기존 저장소 구조·데이터 흐름을 파악
c05 권한·승인 u5 M1에서 최소 권한 settings.json으로 안전한 명령만 허용
c06 플랜 모드 u5 M1에서 변경 전 계획을 받아 검토·교정해 확정
c07 실행·테스트 검증 u6 M2·M3에서 TDD로 완료 조건을 먼저 세우고 통과를 확인
c08 CLAUDE.md u7 M1에서 빌드·테스트 명령·컨벤션을 메모리에 영속화
c09 커밋·PR u8 M4에서 작은 논리 단위 커밋과 첫 PR 초안 작성
c10 코드 리뷰 u9 M5에서 /code-review로 점검하고 지적에 대응
c11 디버깅 u10 M5에서 리뷰 지적을 재현→검증→회귀 테스트로 처리
c12 서브에이전트·MCP u11 M6(선택)에서 테스트 실행 위임·외부 자료 참조를 맛봄

이렇게 보면, 12개 개념이 분석·설계·구현·발표의 한 흐름에 빠짐없이 녹아 있습니다. 따로 배울 때는 조각이었지만, 한 번의 첫 기능 추가로 엮으니 비로소 "온보딩이 이렇게 하나로 이어지는구나"를 체득하게 됩니다. 이것이 POV에서 말한 통찰 — "기능을 따로 배우는 것과 한 번의 실제 업무로 엮어 쓰는 것은 다르다" — 의 실제 모습입니다.

성찰 질문

다음 다섯 질문에 스스로 답해 보며 여정을 정리합니다.

  1. 12개 개념이 첫 기능 추가의 어느 단계로 이어졌는지, 위 표를 바탕으로 자신의 말로 다시 적어 보세요.
  2. 플랜 모드(M1)로 받은 초기 계획과 실제 구현(M3)이 달라진 부분이 있다면, 그 이유는 무엇이었습니까?
  3. 코드 리뷰(M5)에서 가장 배운 점은 무엇이고, 지적을 방어적으로 받지 않으려면 어떤 태도가 필요합니까?
  4. 테스트를 먼저 쓰는 것(TDD, M2)이 결과 품질에 어떤 차이를 만들었습니까?
  5. 다음 단계로 서브에이전트·MCP를 더 깊이 쓴다면, 어떤 반복 작업부터 자동화하고 싶습니까?

깊이 있는 답을 위한 예시 (질문 3·4)

성찰 질문은 한 문장으로 끝내기보다, 구체적 사건과 연결할 때 값이 생깁니다. 두 질문의 모범 답을 봅니다.

질문 3(리뷰에서 배운 점·방어적이지 않으려면)의 예시 답: "가장 배운 점은, 리뷰 지적이 '내 코드가 틀렸다'는 비난이 아니라 '여기 확인이 필요하다'는 신호라는 것이었습니다. /code-review가 던진 '빈 status는 어떻게 되나'라는 질문에 처음엔 방어하고 싶었지만, 직접 재현해 보니 이미 422로 막히고 있었습니다. 만약 확인 없이 '괜찮습니다'라고만 답했다면 근거 없는 방어였을 것입니다. 방어적으로 받지 않으려면, 지적을 검증할 사실로 바꿔 재현해 보는 습관이 필요합니다."

질문 4(TDD가 품질에 만든 차이)의 예시 답: "테스트를 먼저 쓰니(M2) '무엇이 되면 끝인지'가 구현 전에 분명해졌습니다. 특히 404·422 같은 에러 경로를 먼저 테스트로 적어 두니, 구현할 때 그 경우를 빠뜨리지 않았습니다. 만약 구현부터 했다면 정상 경로만 만들고 에러 처리는 잊었을 가능성이 큽니다. TDD는 '완료 조건을 앞당겨 정의'해 구현이 흔들리지 않게 잡아 주었습니다."

성찰은 "다음에 무엇을 바꿀까"로 끝낸다

성찰의 목적은 잘잘못을 가리는 것이 아니라, 다음 작업에서 바꿀 한 가지를 건지는 것입니다. 예컨대 질문 2에서 "계획에 없던 회귀 테스트를 나중에야 추가했다"를 깨달았다면, 다음에는 "리뷰 대응 단계를 처음부터 계획에 넣자"가 건진 교훈입니다. 막연한 반성보다 구체적인 다음 행동 하나가 더 값집니다.

다음 단계: 서브에이전트·MCP 심화로 가는 길

이 책은 온보딩, 곧 "첫 기능부터 첫 PR까지"를 다뤘습니다. 여기서부터 더 나아갈 길의 출발점이 단원 11에서 맛본 서브에이전트와 MCP입니다. 본서는 맛보기까지만 다뤘으므로(scope_out), 다음 학습 방향을 안내합니다.

  • 반복 작업의 위임(서브에이전트): 이번 프로젝트에서 가장 자주 반복한 일은 "테스트를 돌려 결과를 확인"하는 것이었습니다. 이런 경계가 분명한 작업을 별도 컨텍스트의 서브에이전트(.claude/agents/tester.md)에 맡기면, 메인 대화를 어지럽히지 않고 위임할 수 있습니다. 다음 단계에서는 역할·도구를 더 정교하게 설계하는 법을 익힙니다.
  • 외부 자료의 표준 연결(MCP): 팀의 API 컨벤션 문서나 이슈 트래커처럼 코드 밖의 자료를 MCP 서버로 연결하면, 에이전트가 외부 맥락을 참조하며 일할 수 있습니다. 다음 단계에서는 .mcp.json 등록과 권한·비밀 관리를 더 깊이 다룹니다.
  • CI·자동화로의 확장: 본서는 무인 자동화를 범위 밖으로 두었지만(scope_out), 통과한 테스트와 좋은 PR 습관이 갖춰지면 자연스러운 다음 걸음은 PR마다 자동으로 테스트·리뷰를 도는 흐름입니다.

온보딩 이후의 한 걸음

가장 좋은 다음 단계는 거창한 자동화가 아니라, 이번에 가장 자주 반복한 일 하나를 골라 위임해 보는 것입니다. 성찰 질문 5에 적은 "자동화하고 싶은 반복 작업"이 바로 그 출발점입니다. 작게 시작해 통과를 확인하며 넓혀 가는 리듬은, 온보딩에서 배운 그대로입니다.

작성형 연습 (2종 1세트)

여정을 마무리하는 성찰을 직접 정리합니다. ① 모범 예시를 보고, ② 빈 템플릿을 채운 뒤, ③ 자가체크로 점검합니다.

모범 예시: 성찰 회고 한 편

다음은 한 신입이 작성한 성찰 회고의 모범입니다.

무엇을 했나: 기존 team-tasks-api에 완료 처리·상태 필터를 추가하고, 여섯 개 테스트로 검증해 #57 PR로 올렸습니다.

개념 적용: 가장 크게 와닿은 것은 c07(검증)과 c06(플랜)이었습니다. 테스트를 먼저 쓰니(M2) "무엇이 되면 끝인지"가 분명해져, 구현이 흔들리지 않았습니다. 플랜 모드(M1)로 계획을 먼저 받아 보니, status를 새로 추가할 뻔한 가정을 시작 전에 교정할 수 있었습니다.

달라진 점: 초기 계획에는 리뷰 대응 단계가 없었습니다. 막상 /code-review(M5)에서 "빈 status는 어떻게 되나"라는 지적을 받고 나서야, 재현·검증·회귀 테스트가 필요함을 알았습니다.

다음에 바꿀 것: 다음에는 리뷰 대응과 회귀 테스트를 처음부터 계획(M1)에 넣겠습니다. 또 반복된 "테스트 실행"을 서브에이전트에 위임해 보겠습니다.

연습: 나의 성찰 회고 채우기

위 모범을 참고해, 자신이 실제로 거친 첫 기능 추가 여정을 성찰 회고로 직접 작성하세요. 다섯 성찰 질문을 녹여, 추측이 아니라 자신이 실제로 한 것(시연·평가·12개념 적용)을 서술합니다.

아래 형식을 그대로 옮겨, 각 항목을 자신의 경험으로 직접 채우세요.

text
[무엇을 했나]  (직접 서술한다: 내가 실제로 추가한 기능과 올린 PR)

[개념 적용]  가장 크게 와닿은 개념과 그 이유를 직접 서술한다.
  (예: c07 검증, c06 플랜 — 왜 그랬는지 내 경험으로)

[달라진 점]  플랜 모드 초기 계획과 실제 구현이 달라진 부분과 그 이유:
  (직접 서술한다)

[리뷰에서 배운 점]  내가 받은 리뷰에서 배운 것과, 방어적으로 받지 않으려면:
  (직접 서술한다)

[다음에 바꿀 것]  다음 작업에서 바꿀 한 가지와 자동화하고 싶은 반복 작업:
  (직접 서술한다)

자가체크

  • [ ] 산출물 시연에 동작하는 기능·통과한 테스트·올린 PR의 세 증거를 모두 담았는가
  • [ ] 루브릭 여섯 기준으로 자신의 작업을 평가하고, 약한 기준을 찾았는가
  • [ ] 12개 개념이 각각 어느 단계로 이어졌는지 자신의 말로 적었는가
  • [ ] 성찰을 막연한 반성이 아니라 "다음에 바꿀 한 가지"로 끝맺었는가
  • [ ] 다음 학습(서브에이전트·MCP 심화)에서 먼저 시도할 작업을 골랐는가

자주 묻는 질문

Q. 발표 때 코드를 한 줄씩 다 설명해야 하나요?

아닙니다. 리뷰어·청중이 알고 싶은 것은 줄 단위 구현이 아니라 무엇을·왜·어떻게 검증했는가입니다. "완료 처리·상태 필터를 추가했고(무엇), 상태 확장을 위해 enum을 택했으며(왜·ADR2), 여섯 개 테스트로 검증했습니다(검증)"처럼 핵심 결정과 증거 위주로 말하세요. 세부 구현은 질문이 나올 때 PR의 해당 줄을 열어 보이면 충분합니다.

Q. 테스트가 모두 통과했는데도 "보통"보다 낮게 평가될 수 있나요?

있습니다. 검증 기준의 "우수"는 단순 통과가 아니라 "행복 경로와 에러 경로(404·422)를 TDD로 검증"입니다. 정상 동작만 테스트하고 에러 경로를 빠뜨렸다면, 모두 통과했더라도 "보통"에 머뭅니다. 루브릭은 통과 여부가 아니라 무엇을 검증했는지의 폭을 봅니다.

Q. 리뷰 지적에 반론해도 괜찮나요? 신입이 건방져 보일까 걱정됩니다.

근거가 있다면 괜찮습니다. 중요한 것은 태도가 아니라 근거의 유무입니다. "빈 status는 이미 422로 막힙니다. 다음 회귀 테스트로 확인했습니다"처럼 재현·검증 결과를 들어 정중히 답하면, 오히려 "확인하고 말하는 사람"이라는 신뢰를 줍니다. 반대로 확인 없이 "제 코드가 맞아요"라고만 하면 방어로 보입니다. 반론은 감정이 아니라 증거로 합니다.

Q. 성찰은 형식적인 글쓰기 아닌가요?

성찰이 형식이 되는 것은 "잘 배웠다" 같은 막연한 문장으로 끝낼 때입니다. 성찰의 값은 다음에 바꿀 구체적 한 가지를 건지는 데 있습니다. "다음에는 리뷰 대응을 처음부터 계획에 넣겠다"처럼 행동으로 적으면, 그 한 줄이 다음 작업의 품질을 실제로 바꿉니다.

이 책 한 줄 정리

설치·탐색·권한·플랜·검증·CLAUDE.md·커밋·PR·리뷰·디버깅 — 따로 배운 12개 개념은, 기존 팀 저장소에 작은 기능 하나를 테스트와 함께 추가해 첫 PR로 올리는 한 번의 실제 업무로 엮일 때 비로소 하나가 됩니다. 첫 기능을 끝까지 해 본 지금, 여러분은 이미 신입의 첫 통과의례를 지났습니다. 다음 기능은 더 자신 있게, 더 안전하게, 더 빠르게 해낼 수 있습니다.
