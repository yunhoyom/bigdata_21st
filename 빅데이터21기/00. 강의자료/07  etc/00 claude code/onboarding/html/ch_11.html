실무

11장 에이전트와 함께 디버깅하기

이 장은 단원 10 "에이전트와 함께 디버깅하기"의 단일 챕터입니다. 여기서는 개념 에이전트와 함께 디버깅하기(debugging with the agent) 하나를 깊이 있게 배웁니다. 신입 개발자는 자주 막힙니다. 그리고 그 막힘을 얼마나 빠르고 정확하게 푸느냐가 곧 생산성입니다. 이 장을 마치면 에러 메시지를 에이전트에게 제대로 건네 원인을 진단하고, 재현 → 가설 → 최소 수정 → 회귀 테스트의 루프로 버그를 잡고, 같은 버그가 다시 나지 않게 막는 방법을 갖게 됩니다.

이 장의 학습 목표

  • 실패한 테스트나 예외의 전체 에러 메시지·스택 트레이스를 에이전트에게 그대로 주어 원인을 진단시킬 수 있습니다.
  • 막연한 '고쳐 줘' 대신 증상·기대·실제 동작을 구체적으로 전달해 더 정확한 진단을 끌어낼 수 있습니다.
  • 재현 → 가설 → 최소 수정 → 회귀 테스트의 디버깅 루프를 한 바퀴 돌려 버그를 해결할 수 있습니다.
  • 수정 후 회귀 테스트를 실행해 다른 곳이 깨지지 않았는지 확인하고, 같은 버그의 재발을 막을 수 있습니다.

11.1 도입: 막힘을 푸는 능력이 곧 생산성이다

신입으로 팀에 합류해 첫 몇 주를 보내면, 코드를 새로 쓰는 시간보다 막혀서 멈춰 있는 시간이 더 길다는 사실을 곧 알게 됩니다. 테스트가 빨갛게 떨어지고, 서버가 500을 뱉고, 분명 맞게 짠 것 같은 코드가 422를 돌려줍니다. 베테랑과 신입의 차이는 "버그를 안 만드느냐"가 아니라 "막혔을 때 얼마나 빨리 빠져나오느냐"에서 더 크게 벌어집니다. 누구나 버그를 만듭니다. 다만 어떤 사람은 30초 만에 원인을 찾고, 어떤 사람은 한나절을 헤맵니다.

이 장 직전까지 우리는 변경을 안전하게 만들고(5장 권한·6장 플랜 모드) 실행·테스트로 검증하는 법(7장)을 배웠습니다. 특히 7장에서 "검증 전까지는 끝난 게 아니다"라는 습관을 들였습니다. 그런데 검증을 하면 필연적으로 실패하는 검증을 만나게 됩니다. 테스트가 빨갛게 뜨는 순간이 바로 디버깅의 출발점입니다.

선수 개념 한 줄 상기. 7장에서 배운 "변경 → 실행 → 테스트 → 통과 확인" 루프(개념 c07)에서, 테스트가 실패했을 때 무엇을 해야 하는가를 다루는 것이 이 장입니다. 실패한 테스트는 디버깅의 시작 신호이고, 회귀 테스트는 디버깅의 마무리 도구입니다.

좋은 소식은, 디버깅이야말로 에이전트와 함께할 때 가장 큰 도움을 받는 작업이라는 점입니다. 에이전트는 에러 메시지를 읽고, 스택 트레이스가 가리키는 파일을 직접 열어 보고, 관련 코드를 추적해 원인을 짚어 줍니다. 하지만 여기에는 함정이 있습니다. 신입이 가장 흔히 저지르는 실수는 막연하게 "에러 나는데 고쳐 줘"라고 말하는 것입니다. 정보가 부족하면 에이전트도 추측에 의존하게 되고, 추측은 엉뚱한 수정으로 이어집니다. 이 장의 핵심은 에이전트가 정확히 진단할 수 있도록 정보를 제대로 건네는 기술과, 고친 뒤 그것이 진짜 고쳐졌는지 증명하는 절차입니다.

11.2 에러 메시지·스택 트레이스를 통째로 전달하기

디버깅의 첫 단추는 정보 전달입니다. 에이전트는 여러분의 화면에 무엇이 떴는지 직접 보지 못합니다. 여러분이 건네는 만큼만 압니다. 그래서 에러 메시지와 스택 트레이스를 자르지 말고 통째로 주는 것이 디버깅의 가장 기본적이면서도 가장 자주 빠뜨리는 원칙입니다.

스택 트레이스(stack trace, 호출 추적)는 에러가 발생한 순간까지 어떤 함수가 어떤 함수를 불렀는지의 경로를 보여 주는 기록입니다. 파이썬은 보통 가장 바깥쪽 호출부터 시작해 마지막 줄에 실제 예외 종류와 메시지를 보여 줍니다. 신입이 흔히 저지르는 실수는 "마지막 한 줄만" 복사해 주는 것입니다. 예를 들어 KeyError: 'done'만 건네면, 에이전트는 그 키가 어느 파일 몇 번째 줄에서, 어떤 호출 경로를 거쳐 터졌는지 알 수 없어 다시 되물어야 합니다.

다음은 잘라서 주는 나쁜 예와, 통째로 주는 좋은 예의 비교입니다.

구분 나쁜 전달 좋은 전달
내용 "KeyError 나는데 고쳐 줘" 명령 + 전체 스택 트레이스 + 마지막 예외 줄 전부
위치 정보 없음 파일·줄 번호가 트레이스에 포함
호출 경로 없음 어떤 함수가 어디서 불렸는지 전부
에이전트 행동 어디를 볼지 되물음, 추측 시작 즉시 해당 파일을 열어 추적 시작

에이전트에게 건넬 때는 다음 세 가지를 함께 주는 것이 좋습니다. 첫째, 무엇을 실행했더니 에러가 났는지(예: python -m pytest tests/test_services.py). 둘째, 전체 출력(스택 트레이스의 처음부터 끝까지). 셋째, 무엇을 기대했는지(다음 절에서 자세히 다룹니다). 셸에서 실행한 명령과 출력을 한 덩어리로 복사해 붙여 넣으면, 에이전트가 가장 빠르게 일을 시작할 수 있습니다.

실무 팁. 터미널에서 직접 명령을 실행해 에이전트가 출력을 그대로 보게 하면 가장 좋습니다. Claude Code에게 "python -m pytest를 실행하고 실패하는 테스트의 원인을 진단해 줘"라고 지시하면, 에이전트가 직접 명령을 돌려 전체 출력을 읽고 스택 트레이스가 가리키는 파일을 열어 추적합니다. 사람이 손으로 복사·붙여넣기 하다가 일부를 빠뜨리는 위험도 없습니다.

11.3 동작 원리: 재현 → 가설 → 최소 수정 → 회귀 테스트 루프

좋은 디버깅은 즉흥적인 시도의 반복이 아니라 정해진 루프를 도는 일입니다. 막무가내로 이것저것 바꿔 보다 우연히 고쳐지는 것은 디버깅이 아니라 도박입니다. 그렇게 고치면 왜 고쳐졌는지 모르고, 같은 버그가 다시 나며, 그 과정에서 멀쩡한 코드를 망가뜨리기 쉽습니다. 프로다운 디버깅은 다음 네 단계를 순서대로 돕니다.

  1. 재현(reproduce). 버그를 항상 똑같이 일으키는 방법을 먼저 확보합니다. 가장 좋은 재현 수단은 실패하는 테스트입니다. "가끔 안 돼요"는 디버깅의 적입니다. 같은 입력으로 같은 실패가 반복돼야 원인을 좁히고, 고친 뒤 진짜 고쳐졌는지 확인할 수 있습니다. 실패하는 pytest 한 개가 있다면 이미 재현을 손에 쥔 것입니다.

  2. 가설(hypothesis). 에러 메시지·스택 트레이스·코드를 근거로 "원인은 아마 여기일 것"이라는 한 가지 추정을 세웁니다. 핵심은 한 번에 하나입니다. "키 이름이 틀렸거나, 조건이 반대거나, 타입이 안 맞거나…" 여러 개를 동시에 손대면 무엇이 진짜 원인이었는지 영영 알 수 없습니다.

  3. 최소 수정(minimal fix). 세운 가설을 검증할 가장 작은 변경만 합니다. 한 줄이면 한 줄만 바꿉니다. "온 김에" 다른 곳을 정리하거나 리팩터링하지 않습니다. 수정 범위가 작아야 결과의 인과가 분명하고, 틀렸을 때 되돌리기도 쉽습니다.

  4. 회귀 테스트(regression test). 재현용 테스트를 다시 돌려 통과로 바뀌는지 확인하고, 동시에 나머지 테스트도 모두 통과하는지를 확인합니다. 내 수정이 이 버그는 고쳤지만 다른 기능을 깨뜨렸을 수 있기 때문입니다. 통과하면 해결, 실패하면 가설이 틀린 것이니 2단계로 돌아갑니다.

이 루프의 가치는 각 단계가 다음 단계의 근거가 된다는 데 있습니다. 재현이 있어야 가설을 시험할 수 있고, 최소 수정이라야 통과·실패의 원인이 명확하며, 회귀 테스트가 있어야 "정말 고쳤다"고 말할 자격이 생깁니다.

에이전트는 이 루프의 어디를 돕나요? 에이전트는 모든 단계를 함께 돕습니다. 재현 단계에서는 실패를 일으키는 테스트를 작성하고, 가설 단계에서는 스택 트레이스가 가리키는 코드를 읽어 원인을 설명하며, 최소 수정 단계에서는 작은 변경을 diff로 제안하고, 회귀 단계에서는 pytest를 다시 돌려 결과를 보여 줍니다. 여러분이 할 일은 루프를 통제하는 것입니다. "한 번에 한 가설만", "고쳤으면 전체 테스트를 돌려 확인"이라는 규율을 잡아 주는 것이 신입의 몫입니다.

11.4 worked example: 실패한 pytest 메시지로 원인 진단·수정

이제 루프를 실제로 한 바퀴 돌려 봅니다. 여러분이 팀에서 받은 FastAPI 기반 할 일(tasks) 서비스에 작은 요약 기능이 있다고 합시다. 할 일 목록을 받아 전체·완료·미완료 개수를 돌려주는 함수입니다.

다음은 team-tasks-api에 새로 추가한 요약 헬퍼 services.py의 코드입니다(할 일을 dict로 받는 작은 순수 함수). 어딘가에 버그가 숨어 있습니다.

python
# services.py
def summarize_tasks(tasks: list[dict]) -> dict:
    """할 일 목록을 받아 전체·완료·미완료 개수를 요약합니다."""
    done = [t for t in tasks if not t["done"]]
    pending = len(tasks) - len(done)
    return {
        "total": len(tasks),
        "done": len(done),
        "pending": pending,
    }

그리고 팀이 함께 쓰는 테스트가 tests/test_services.py에 있습니다.

python
# tests/test_services.py
from services import summarize_tasks


def test_summarize_counts():
    tasks = [
        {"id": 1, "title": "배포", "done": True},
        {"id": 2, "title": "리뷰", "done": False},
        {"id": 3, "title": "문서", "done": True},
    ]
    result = summarize_tasks(tasks)
    assert result["done"] == 2
    assert result["pending"] == 1

1단계 재현. 먼저 테스트를 돌려 실패를 확인합니다. 에이전트에게 "tests/test_services.py를 pytest로 실행하고 결과를 보여 줘"라고 지시하면 다음과 같은 출력을 받습니다.

이 출력이 곧 재현입니다. 같은 명령으로 언제나 같은 실패가 납니다. 이제 이 전체 출력을 통째로 에이전트에게 줍니다(11.2의 원칙). 잘라서 assert 1 == 2만 주지 않습니다.

2단계 가설. 출력을 읽어 봅니다. result["done"]이 2가 아니라 1이 나왔습니다. 완료 처리한 할 일은 배포, 문서 두 개인데 1만 셌습니다. 거꾸로 미완료(리뷰)는 한 개입니다. 즉 함수가 완료와 미완료를 거꾸로 세고 있다는 가설이 섭니다. 코드를 보면 원인이 보입니다.

python
done = [t for t in tasks if not t["done"]]

done이라는 변수에 담으려는 것은 완료된 할 일인데, 조건에 not이 붙어 미완료를 담고 있습니다. 가설: "not이 잘못 들어가 완료/미완료가 뒤바뀌었다."

3단계 최소 수정. 가설을 검증하는 가장 작은 변경은 not 한 단어를 지우는 것입니다. 에이전트에게 "summarize_tasks에서 완료/미완료가 뒤바뀐 것 같다. done 리스트의 조건을 최소한으로 고쳐 줘"라고 지시합니다. 에이전트는 다음 diff를 제안합니다.

python
# services.py (수정 후)
def summarize_tasks(tasks: list[dict]) -> dict:
    """할 일 목록을 받아 전체·완료·미완료 개수를 요약합니다."""
    done = [t for t in tasks if t["done"]]   # not 제거
    pending = len(tasks) - len(done)
    return {
        "total": len(tasks),
        "done": len(done),
        "pending": pending,
    }
  • if t["done"]: 조건에서 not만 제거했습니다. 이제 done 리스트에는 done이 참인(완료된) 할 일만 담깁니다.
  • 나머지는 손대지 않음: pending 계산식·반환 구조는 그대로 둡니다. 가설은 "완료/미완료가 뒤바뀜" 하나뿐이므로 수정도 한 곳뿐입니다. 이것이 최소 수정 원칙입니다.

4단계 회귀 테스트. 같은 명령으로 테스트를 다시 돌립니다.

text
$ python -m pytest tests/test_services.py -q
.                                                                        [100%]
1 passed in 0.03s

통과로 바뀌었습니다. 재현용 테스트가 빨강에서 초록으로 바뀐 것이 "고쳤다"의 증거입니다. 여기에 더해 저장소 전체 테스트(python -m pytest)도 돌려, 이 수정이 다른 기능을 깨지 않았는지까지 확인하면 한 바퀴가 완성됩니다. 이것이 디버깅 루프의 모범적인 한 회전입니다.

11.5 증상·기대·실제 동작을 구체적으로 진술하기

에이전트에게 디버깅을 부탁할 때 가장 큰 차이를 만드는 것은 진술의 구체성입니다. "안 돼요", "고쳐 줘"는 정보가 거의 없습니다. 좋은 디버깅 요청은 다음 세 가지를 분명히 담습니다.

  • 증상(symptom): 무엇이 어떻게 잘못됐나. "POST /tasks에 요청하면 422가 돌아온다."
  • 기대(expected): 원래 어떻게 동작해야 하나. "201과 함께 생성된 할 일이 돌아와야 한다."
  • 실제(actual): 지금 실제로 무슨 일이 일어나나. "응답 본문에 priority 필드가 필수라는 검증 에러가 담겨 온다."

이 세 가지는 사실 의사에게 증상을 설명하는 것과 같습니다. "아파요"가 아니라 "어제부터 오른쪽 아랫배가, 누르면 더, 열은 없이"라고 말해야 정확한 진단이 나옵니다. 코드도 똑같습니다.

다음은 같은 버그를 두 가지 방식으로 전달한 비교입니다.

구분 막연한 요청 구체적 요청(증상·기대·실제)
말 "엔드포인트가 안 됩니다. 고쳐 주세요." "POST /tasks에 {\"title\": \"배포\"}를 보내면(증상) 422가 난다. 201로 생성되길 기대(기대)했는데, 응답에 priority 필드가 필수라는 검증 에러가 온다(실제). 전체 응답 본문은 아래와 같다."
에이전트 행동 어디가 안 되는지 되묻거나, 엉뚱한 곳을 추측 모델 정의와 핸들러를 바로 열어 priority 필수 여부를 확인
결과 왕복이 늘어남 한 번에 원인 지점으로 직행

한 문장 틀. 디버깅 요청을 이 틀에 맞춰 적는 습관을 들이세요. "[무엇을 했더니] [실제 무슨 일]이 일어난다. [기대한 동작]이어야 한다. 전체 메시지는 다음과 같다: [전체 출력]." 이 틀 하나면 신입의 디버깅 요청 품질이 단번에 올라갑니다.

11.6 worked example: FastAPI 422 검증 에러를 최소 수정

이번에는 FastAPI에서 신입이 가장 자주 만나는 422 검증 에러를 루프로 잡아 봅니다. 422 Unprocessable Entity는 요청은 도달했지만 본문이 모델이 요구하는 형식에 맞지 않을 때 FastAPI가 자동으로 돌려주는 응답입니다. 즉 서버 버그가 아니라 데이터 계약 불일치 신호인 경우가 많습니다.

team-tasks-api에서 작업을 우선순위로 다루려고, models.py의 TaskCreate에 우선순위(priority) 필드를 새로 추가했다고 합시다. 생성 엔드포인트는 1장에서 본 대로 routers/tasks.py의 POST /tasks(store.create_task에 위임)에 있습니다.

python
# models.py — TaskCreate 에 priority 필드를 새로 추가한 변경
class TaskCreate(BaseModel):
    """새 할 일 생성 요청 모델"""
    title: str
    priority: int   # 새로 추가 — 기본값을 빠뜨렸다

그리고 신입이 새로 추가한 테스트가 있습니다. 제목만 주면 기본 우선순위로 할 일이 만들어지길 기대합니다(테스트는 1장 저장소의 관례대로 from main import app으로 앱을 가져옵니다).

python
# tests/test_tasks_priority.py
import sys

sys.path.insert(0, os.path.dirname(os.path.dirname(os.path.abspath(__file__))))

from fastapi.testclient import TestClient
from main import app

def test_create_task_minimal():
    response = client.post("/tasks", json={"title": "배포"})
    assert response.status_code == 201

201을 기대했는데 422가 왔습니다. 증상·기대·실제로 정리합니다. 증상: 제목만 보내면 422가 난다. 기대: 201로 생성된다. 실제: 검증 에러가 돌아온다. 그런데 422 응답 본문에는 더 정확한 단서가 들어 있습니다. 에이전트에게 "이 요청의 422 응답 본문(response.json())을 보여 줘"라고 하면 다음을 확인합니다.

json
{
  "detail": [
    {
      "type": "missing",
      "loc": ["body", "priority"],
      "msg": "Field required",
      "input": {"title": "배포"}
    }
  ]
}

2단계 가설. 이 본문이 원인을 명확히 가리킵니다. loc가 ["body", "priority"], msg가 Field required, type이 missing입니다. 즉 요청 본문에 priority가 없는데, 모델이 그것을 필수로 요구하고 있습니다. TaskCreate를 보면 priority: int라서 기본값이 없어 필수 필드입니다. 가설: "priority에 기본값이 없어 제목만 보내면 검증에 걸린다. 우선순위를 선택 항목으로 만들면 된다."

422 응답 본문의 세 열쇠를 읽는 법을 정리해 둡니다.

필드 의미 이 예에서
type 검증 실패 종류 missing(필드 없음)
loc 문제가 난 위치 경로 ["body", "priority"](본문의 priority)
msg 사람이 읽을 설명 Field required(필수 필드)

3단계 최소 수정. 가설을 검증하는 최소 변경은 priority에 기본값을 주는 것입니다. 핸들러·반환 구조·다른 필드는 건드리지 않습니다.

python
# models.py (수정 후 — 모델만 변경)
class TaskCreate(BaseModel):
    """새 할 일 생성 요청 모델"""
    title: str
    priority: int = 3   # 기본값 부여 → 선택 필드가 됨
  • priority: int = 3: 기본값 3을 주어 priority를 선택 필드로 바꿨습니다. 클라이언트가 priority를 보내지 않으면 3이 채워지고, 보내면 그 값이 쓰입니다.
  • 타입은 그대로 int: 우선순위는 여전히 정수여야 하므로 타입 검증은 유지합니다. 기본값만 더했을 뿐, 검증 규칙을 느슨하게 풀지 않았습니다.
  • 핸들러 무수정: create_task 함수와 응답 구조는 손대지 않았습니다. 가설이 "필수 여부" 하나였으므로 수정도 한 줄입니다.

4단계 회귀 테스트. 다시 돌립니다.

text
$ python -m pytest tests/test_tasks_priority.py -q
.                                                                        [100%]
1 passed in 0.10s

통과했습니다. 여기서 한 걸음 더 나아가, 우선순위를 명시한 요청도 여전히 잘 동작하는지까지 확인하는 회귀 테스트를 추가하면(다음 절) 수정이 기존 동작을 깨지 않았음을 증명할 수 있습니다.

주의: 422를 무조건 모델 완화로 풀지 마세요. 이 예에서는 "제목만으로 생성"이 정당한 요구라 기본값이 맞는 해법이었습니다. 하지만 422가 진짜로 클라이언트가 필수 데이터를 빠뜨린 경우라면, 모델을 느슨하게 푸는 것은 버그를 가리는 잘못된 수정입니다. 그때는 요청 쪽을 고쳐야 합니다. 422를 만나면 "이 필드가 정말 선택이어도 되는가"를 먼저 판단하세요.

11.7 최소 수정 원칙: 한 번에 한 가설

앞의 두 예제에서 반복된 규율이 있습니다. 바로 한 번에 한 가설, 한 번에 최소 변경입니다. 이 원칙이 왜 그토록 중요한지 짚어 봅니다.

버그를 만나면 머릿속에 동시에 여러 의심이 떠오릅니다. "키 이름이 틀렸나? 조건이 반댄가? 타입이 안 맞나? 저 함수도 좀 이상한데 같이 고칠까?" 이때 욕심을 내 한꺼번에 여러 곳을 손대면 두 가지 문제가 생깁니다.

  1. 인과가 흐려진다. 세 곳을 고치고 테스트가 통과하면, 그중 무엇이 진짜 원인이었는지 알 수 없습니다. 다음에 비슷한 버그를 만나도 배운 것이 없습니다.
  2. 새 버그를 심는다. "온 김에" 손댄 곳이 멀쩡했다면, 그 변경이 오히려 새로운 문제를 만들 수 있습니다. 그러면 원래 버그와 새 버그가 뒤엉켜 디버깅이 훨씬 어려워집니다.

그래서 가설은 하나씩 세우고, 수정은 그 가설을 검증할 가장 작은 변경으로 제한합니다. 통과하면 그 가설이 맞았던 것이고, 실패하면 그 가설이 틀렸으니 변경을 되돌리고 다음 가설로 넘어갑니다. 이렇게 하면 매 회전이 명확한 정보를 남깁니다.

에이전트에게 규율을 거는 지시. 에이전트는 때로 여러 개선을 한꺼번에 제안합니다. 이때 "지금은 이 버그만 최소한으로 고치고, 다른 개선 제안은 별도로 정리만 해 줘"라고 명시하세요. 6장에서 배운 플랜 모드로 먼저 계획을 받아 "이 수정 한 줄만"으로 범위를 좁히는 것도 좋은 방법입니다. 리팩터링과 버그 수정은 섞지 않습니다.

11.8 회귀 테스트로 수정 검증·재발 방지

디버깅 루프의 마지막 단계이자, 신입이 가장 자주 빠뜨리는 단계가 회귀 테스트입니다. 회귀(regression)란 한 곳을 고쳤더니 멀쩡하던 다른 곳이 망가지는 현상을 말합니다. 회귀 테스트는 이를 잡아내고 같은 버그의 재발을 막는 안전망입니다. 회귀 테스트는 두 가지 일을 합니다.

첫째, 이 수정이 정말 고쳤는지 증명합니다. 재현용으로 쓴 실패 테스트가 통과로 바뀌면, "고친 것 같다"가 아니라 "고쳤다"가 됩니다. 둘째, 다른 곳을 깨지 않았는지 확인합니다. 저장소 전체 테스트를 돌려 모두 통과하면, 내 수정이 의도한 곳만 바꿨다는 증거가 됩니다.

여기에 한 가지를 더합니다. 방금 잡은 버그가 다시는 같은 모습으로 돌아오지 못하게 못 박는 테스트를 추가하는 것입니다. 11.6의 422 버그를 예로 들면, "제목만으로도 생성된다"와 "우선순위를 줘도 정상 생성된다"를 각각 테스트로 남깁니다(응답 모델은 1장의 Task라 priority를 본문에 포함하지 않으므로, 여기서는 생성 성공 여부만 검증합니다).

python
# tests/test_tasks_priority.py (회귀 테스트 보강)
def test_create_task_minimal():
    # 제목만 보내도 (기본 우선순위로) 생성된다 — 이번에 고친 버그를 못 박음
    response = client.post("/tasks", json={"title": "배포"})
    assert response.status_code == 201


def test_create_task_with_priority():
    # 우선순위를 명시해도 정상 생성된다 — 기존 동작이 깨지지 않았는지 확인
    response = client.post("/tasks", json={"title": "리뷰", "priority": 1})
    assert response.status_code == 201

이렇게 해 두면, 나중에 누군가 priority를 다시 필수로 바꾸는 변경을 하면 첫 번째 테스트가 빨갛게 떠 즉시 경고합니다. 버그를 한 번 잡은 경험이 영구적인 안전망으로 남는 것입니다. 이것이 디버깅을 단순한 "땜질"에서 "재발 방지"로 끌어올리는 핵심 습관입니다.

왜 버그를 잡을 때마다 테스트를 남기나요? 버그가 났다는 것은 그 경우를 검증하는 테스트가 없었다는 뜻이기도 합니다. 잡은 김에 그 빈틈을 테스트로 메우면, 코드베이스의 안전망이 버그를 만날 때마다 촘촘해집니다. 7장에서 배운 "테스트로 완료를 증명한다"가 디버깅에서는 "테스트로 재발을 막는다"로 이어집니다.

11.9 즉시 연습(2종 1세트)과 단원 미니 프로젝트

이 단원은 단일 챕터이므로, 즉시 연습과 단원 미니 프로젝트를 여기서 함께 진행합니다. 먼저 모범 예시를 보고, 그다음 빈 템플릿을 직접 채운 뒤 자가체크로 점검합니다.

연습 1 (모범): 디버깅 진술 작성

다음은 잘 작성된 디버깅 요청의 모범입니다. 증상·기대·실제·전체 출력이 모두 담겨 있습니다.

GET /tasks?status=done에 요청하면(증상) 빈 목록 []이 돌아온다. 완료된 할 일 2건이 돌아와야(기대) 하는데, 실제로는 완료 항목이 하나도 안 잡힌다(실제). 아래는 실패한 pytest 전체 출력이다.

```text

  assert len(response.json()) == 2

E assert 0 == 2 tests/test_filter.py:14: AssertionError ```

재현은 python -m pytest tests/test_filter.py다. 한 번에 한 가설로, 필터 조건부터 최소 수정으로 확인해 줘.

연습 1 (직접 해보기): 실제 실패 메시지로 디버깅 진술 쓰기

종이에 빈칸을 채우는 대신, 1장에서 준비한 실제 team-tasks-api 저장소에 작은 실패를 일부러 만들어 진짜 pytest 메시지를 뽑고, 그 실제 출력으로 디버깅 진술을 완성합니다. 추측한 메시지가 아니라 화면에 찍힌 그대로를 옮기는 것이 핵심입니다.

과제 — 실패를 실제로 재현하고, 그 출력으로 진술을 채워라.

team-tasks-api의 routers/tasks.py에서 get_task가 없는 할 일에 던지는 HTTPException의 상태 코드를 404에서 400으로 잠깐 바꿔, 일부러 실패를 만드세요(기존 테스트에 없는 작업 조회는 404를 기대하는 단언이 있다면 빨갛게 떨어집니다). 그다음 python -m pytest -q를 돌려 화면에 실제로 나타난 실패 메시지를 그대로 옮겨 적으세요.

text
[실제 실패 출력] python -m pytest -q에 찍힌 실패 테스트와 단언(화면 그대로):

[수정 후 검증] python -m pytest -q 실제 출력(초록으로 돌아왔는가?):

자가체크 — 머리로가 아니라 손으로 했는지 확인하세요.

  • [ ] 일부러 만든 실패를 python -m pytest -q로 실제로 재현하고 출력을 화면에서 봤다.
  • [ ] [전체 출력]에 적은 것이 추측이 아니라 화면에 찍힌 실제 pytest 메시지다.
  • [ ] 증상·기대·실제를 각각 구체적으로, 위 실제 출력을 근거로 적었다.
  • [ ] "한 번에 한 가설", "최소 수정" 규율을 요청에 명시했다.
  • [ ] 수정 뒤 python -m pytest -q가 통과(7 passed)로 돌아온 것을 직접 확인했다.

단원 미니 프로젝트 (모범): 버그를 에이전트와 함께 잡기

이 단원에서 배운 개념만으로 완성하는 작은 산출물입니다. 이번에는 1장에서 준비한 실제 team-tasks-api 저장소에 일부러 버그를 심어, 그 저장소의 진짜 테스트(python -m pytest -q)로 재현하고 디버깅 루프로 잡습니다. 마일스톤을 증분으로 진행합니다.

  • M1 재현 확보. 실패하는 테스트를 돌려 같은 실패가 반복됨을 확인하고, 전체 출력을 확보합니다. (적용 개념: 재현, 에러 통째 전달)
  • M2 진술·진단. 증상·기대·실제를 한 문장 틀로 적어 에이전트에게 전체 출력과 함께 건네고, 원인 가설 하나를 받습니다. (적용 개념: 구체적 진술, 가설)
  • M3 최소 수정. 가설을 검증할 가장 작은 변경 하나만 적용합니다. 리팩터링·다른 개선은 섞지 않습니다. (적용 개념: 최소 수정, 한 번에 한 가설)
  • M4 회귀 검증·재발 방지. 재현 테스트가 통과로 바뀌는지 + 전체 테스트가 모두 통과하는지 확인하고, 이 버그를 못 박는 회귀 테스트를 추가합니다. (적용 개념: 회귀 테스트)

각 마일스톤 끝에서 다음 체크포인트(단위 테스트 통과)를 확인합니다. M1은 "실패가 재현됨", M3은 "재현 테스트가 통과로 바뀜", M4는 "전체 테스트 초록 + 새 회귀 테스트 추가됨"입니다.

단원 미니 프로젝트 (학생 작성형 빈 스타터)

스타터. team-tasks-api 저장소의 store.py에 아래처럼 일부러 버그를 심어 시작합니다. 새로 만든 할 일의 상태(status)를 todo가 아니라 done으로 잘못 설정하는 한 줄입니다. 이렇게 하면 1장에서 받은 기존 테스트(tests/test_tasks.py)가 빨갛게 떨어지므로, 추가 테스트 없이도 실패를 재현할 수 있습니다.

python
# store.py — create_task 에 일부러 심은 버그
def create_task(data: TaskCreate) -> Task:
    """새 할 일을 저장하고 반환"""
    global _next_id
    task = Task(id=_next_id, title=data.title, status=TaskStatus.done)  # 버그: todo 여야 한다
    _db[_next_id] = task
    _next_id += 1
    return task

기존 테스트 tests/test_tasks.py에는 "생성 직후 상태는 todo"를 검증하는 단언이 이미 들어 있습니다(예: assert items[0]["status"] == "todo"). 이 버그를 심으면 그 단언이 실패합니다.

직접 실행·기록할 것 (추측을 적지 말고, team-tasks-api에서 실제로 돌린 뒤 화면 출력을 그대로 옮깁니다)

text
1. [M1 재현] 위 버그를 심은 뒤 python -m pytest -q를 실제로 돌려, 어떤 테스트가
   어떤 단언에서 실패하는지 전체 출력을 그대로 붙입니다:
2. [M2 진술·진단] 증상·기대·실제를 한 문장 틀로 적고, 에이전트에게 전체 출력과
   함께 건넸을 때 받은 원인 가설을 그대로 적습니다:
3. [M3 최소 수정] 실제로 적용한 최소 수정 한 줄(힌트: status= 인자)과,
   에이전트가 제시한 diff의 + 줄을 그대로 적습니다:
  1. python -m pytest -q를 다시 돌려 7 passed(빨강 → 초록)로 바뀌는지 화면 출력으로 확인하고, 그 출력을 위 3번 아래에 적습니다.
  2. 재발을 막기 위해, "생성 직후 상태가 todo"임을 명시적으로 검증하는 회귀 테스트가 이미 있는지 확인하고(없다면 보강), 전체 통과를 확인합니다.

자가체크

  • [ ] 기대값을 코드 실행 전에 스스로 정했는가
  • [ ] 한 번에 한 가설만 세우고 그 가설을 검증할 최소 변경만 했는가
  • [ ] 재현 테스트가 빨강 → 초록으로 바뀐 것을 확인했는가
  • [ ] 전체 테스트가 모두 통과하는지 확인했는가
  • [ ] 잡은 버그를 못 박는 회귀 테스트를 추가했는가

11.10 흔한 오류와 오개념

오개념 1: "그냥 고쳐 줘"라고만 해도 에이전트가 알아서 잘 고친다. 막연한 요청은 에이전트를 추측에 의존하게 만들고, 추측은 엉뚱한 수정으로 이어집니다. 증상·기대·실제를 구체적으로 주지 않으면, 에이전트는 무엇이 "올바른 동작"인지조차 모릅니다. 11.5의 한 문장 틀("무엇을 했더니 무슨 일이 일어난다, 무엇을 기대한다, 전체 출력은 이렇다")로 적는 습관을 들이세요. 정보를 주는 만큼 진단이 정확해집니다.

오개념 2: 에러 메시지는 핵심 한 줄만 주면 된다. 스택 트레이스를 마지막 줄(KeyError: 'done')만 잘라 주면, 에이전트는 그 에러가 어느 파일 몇 번째 줄에서, 어떤 호출 경로로 터졌는지 알 수 없습니다. 결국 다시 되묻거나 추측합니다. 스택 트레이스는 처음부터 끝까지 통째로 주세요. 가장 좋은 방법은 에이전트가 직접 명령을 실행해 전체 출력을 읽게 하는 것입니다.

오개념 3: 테스트가 초록이면 디버깅은 끝이다(회귀는 안 봐도 된다). 방금 고친 그 테스트만 통과하는 것으로는 부족합니다. 내 수정이 다른 기능을 깨뜨렸을 수 있기 때문입니다. 반드시 저장소 전체 테스트를 돌려 모두 통과하는지 확인하고, 잡은 버그를 못 박는 회귀 테스트를 추가하세요. 회귀 확인 없이 "고쳤다"고 말하는 것은 절반만 한 것입니다.

오개념 4: 의심되는 곳을 한꺼번에 다 고치면 빨리 끝난다. 여러 곳을 동시에 손대면 무엇이 진짜 원인이었는지 알 수 없고, "온 김에" 고친 곳에서 새 버그가 생기기 쉽습니다. 한 번에 한 가설, 그 가설을 검증할 최소 변경만 적용하세요. 통과하면 그 가설이 맞았던 것이고, 실패하면 되돌리고 다음 가설로 갑니다. 느려 보이지만 결국 가장 빠르고 안전한 길입니다.

11.11 정리

이 장에서 우리는 에이전트와 함께 디버깅하는 법을 배웠습니다. 핵심은 세 가지입니다. 첫째, 정보를 제대로 건넨다 — 에러 메시지·스택 트레이스를 통째로, 증상·기대·실제를 구체적으로. 둘째, 루프를 통제한다 — 재현 → 가설(한 번에 하나) → 최소 수정 → 회귀 테스트. 셋째, 재발을 막는다 — 잡은 버그를 회귀 테스트로 못 박는다.

다음 장에서는 온보딩 이후 더 나아갈 길로, 서브에이전트와 MCP를 맛봅니다. 디버깅 같은 경계가 분명한 작업을 별도 컨텍스트의 서브에이전트에 위임하고, 외부 도구·데이터를 표준 방식으로 연결하는 방법을 가볍게 살펴봅니다.
