Chapter 03

효과적인 작업 지시: 목표·맥락·제약·완료 조건

입문

3장 효과적인 작업 지시: 목표·맥락·제약·완료 조건

이 장은 단원 3(u3)의 유일한 챕터이며, 여기서 배우는 개념은 효과적 프롬프팅과 작업 지시(effective prompting and task instruction, c03) 한 가지입니다. 앞 단원에서 익힌 에이전트 루프(c02) 위에, 그 루프를 원하는 방향으로 움직이게 만드는 말하기를 다룹니다. 신입에게 이 장의 기술은 시니어에게 일을 부탁하듯 명확하게 요청하는 법과 같습니다.

이 장을 마치면 할 수 있는 것

  • 주어진 모호한 한 줄 요청을 목표·맥락·제약·완료 조건 네 요소를 모두 갖춘 작업 지시로 다시 작성할 수 있습니다.
  • 하나의 큰 작업을 각각 검증 가능한 3단계 이상으로 쪼개, 한 번에 한 단계씩 순차 지시문으로 작성할 수 있습니다.
  • 기존 코드 파일을 @파일 멘션으로 참조시켜, 그 파일의 스타일과 일치하는 결과를 내도록 지시문을 작성할 수 있습니다.
  • 에이전트가 내놓은 계획·중간 산출을 검토해 어긋난 점 1개 이상을 찾아 교정 지시로 작성할 수 있습니다.

3.1 도입: 결과는 지시의 명확성에 달렸다

앞 단원에서 우리는 Claude Code가 관찰 → 계획 → 도구 호출 → 결과 확인의 루프를 돌며 일한다는 것을 보았습니다(c02). 그런데 이 루프는 출발점이 하나 있습니다. 바로 여러분이 준 작업 지시(프롬프트)입니다. 루프 전체는 그 한 문장에서 시작해 그 문장이 가리키는 목표를 향해 굴러갑니다. 그래서 지시가 흐릿하면 루프 전체가 흐릿한 방향으로 굴러가고, 지시가 또렷하면 루프가 또렷한 결과로 수렴합니다.

신입이 가장 먼저 겪는 오해가 여기서 생깁니다. "AI니까 알아서 잘하겠지"라고 생각하고 "엔드포인트 좀 고쳐 줘" 같은 한 줄을 던지는 것입니다. 그러면 에이전트는 어떤 엔드포인트인지, 무엇이 잘못됐는지, 어떻게 고쳐야 끝인지를 스스로 추측합니다. 추측이 맞으면 운이 좋은 것이고, 빗나가면 엉뚱한 파일을 고치거나, 멀쩡한 코드를 바꾸거나, 여러분이 원하지 않은 라이브러리를 새로 끌어옵니다. 이건 에이전트가 멍청해서가 아니라, 줄 정보가 부족하면 빈칸을 가정으로 메우기 때문입니다.

왜 이 개념이 지금 필요한가

지금까지(1~2장) 우리는 "에이전트가 어떻게 일하는가"를 배웠습니다. 이 장부터는 "에이전트를 어떻게 부리는가"로 넘어갑니다. 코드베이스 탐색(4장)·안전한 변경(5~6장)·검증(7장)·커밋과 PR(9장)까지, 앞으로 하는 모든 작업은 결국 에이전트에게 무언가를 시키는 일입니다. 그 모든 작업의 품질이 이 장에서 배우는 "지시하는 법"에 달려 있습니다. 그래서 온보딩 여정의 이른 자리에 이 개념을 둡니다.

선수 개념 한 줄 상기(c02). 에이전트는 한 번에 정답을 내는 기계가 아니라, 관찰·계획·도구 호출·결과 확인을 반복하는 루프였습니다. 이 점을 기억해야 이 장의 핵심 두 가지가 자연스럽게 이해됩니다. 첫째, 계획 단계가 정확하려면 지시가 구체적이어야 합니다(빈칸이 적어야 가정이 줄어듭니다). 둘째, 루프는 반복이므로 한 번에 완벽을 기대하기보다 검토하고 다시 지시하는 교정이 정석입니다.

3.2 정의: 좋은 지시의 네 요소(목표·맥락·제약·완료 조건)

먼저 개념을 한 문장으로 못 박겠습니다.

효과적 프롬프팅과 작업 지시(c03)란, 에이전트에게 일을 시킬 때 목표(무엇을), 맥락(어떤 코드·상황에서), 제약(무엇은 하지 말 것), 완료 조건(무엇이 되면 끝인지) 네 가지를 구체적으로 담아, 큰 작업은 검증 가능한 단계로 쪼개고, 검토→피드백→재시도로 다듬어 가는 작업 요청 방식을 말합니다.

이 정의에서 가장 중요한 알맹이는 네 요소입니다. 하나씩 풀어 봅니다.

요소 무엇인가 빠지면 생기는 일 예
목표(goal) 무엇을 만들거나 바꾸려는가 엉뚱한 일을 함 "할 일 1건을 ID로 삭제하는 DELETE 엔드포인트를 추가"
맥락(context) 어느 코드·상황에서 하는가 엉뚱한 파일을 헤맴 "routers/tasks.py의 기존 /tasks 엔드포인트와 같은 스타일로"
제약(constraint) 무엇은 하지 말 것인가 원하지 않은 변경·의존성 "새 라이브러리는 추가하지 말고, 기존 store를 통해 데이터를 다룬다"
완료 조건(done criteria) 무엇이 되면 끝인가 "됐다"의 기준이 없음 "없는 ID면 404를 반환하고, 이 동작을 확인하는 pytest 테스트가 통과하면 끝"

이 네 가지는 사실 여러분이 시니어 동료에게 일을 부탁할 때 자연스럽게 말하는 것과 똑같습니다. "이거(목표) 우리 routers/tasks.py 스타일대로(맥락) 새 라이브러리 쓰지 말고(제약) 테스트 통과하게(완료 조건) 해 줄 수 있나요?"라고 부탁하지, "이거 좀 해 줘"라고만 던지지는 않습니다. 사람에게 일을 잘 맡기는 사람은 에이전트에게도 일을 잘 맡깁니다.

프롬프트는 길수록 좋은 게 아닙니다

흔히 "길고 정중하게 쓰면 더 잘하겠지"라고 생각하지만, 길이가 아니라 밀도가 중요합니다. "정말 정말 꼼꼼하게 최고의 코드로 부탁드립니다" 같은 수식어는 네 요소 중 어디에도 해당하지 않아 정보량이 0입니다. 같은 글자 수라면 "없는 ID면 404"라는 한 줄(완료 조건)이 훨씬 값집니다. 짧아도 네 요소가 차 있으면 좋은 지시입니다.

3.3 동작 원리: 모호한 지시가 잘못된 가정으로 이어지는 흐름

왜 모호한 지시가 위험한지를 루프의 관점에서 들여다봅니다.

에이전트는 지시를 받으면 곧바로 계획을 세웁니다. 계획을 세우려면 "무엇을, 어디서, 어떻게, 어디까지"가 정해져야 하는데, 지시에 그 정보가 없으면 에이전트는 빈칸을 가장 그럴듯한 추측으로 메웁니다. 이 추측이 곧 "잘못된 가정"의 씨앗입니다.

두 경로를 비교하면 흐름이 또렷해집니다.

경로 A — 모호한 지시:

  1. 지시: "엔드포인트 좀 고쳐 줘."
  2. 빈칸 발생: 어떤 엔드포인트? 무엇이 문제? 어떻게 고쳐야 끝?
  3. 가정으로 메움: "아마 가장 최근에 본 /tasks겠지", "아마 에러 처리가 없는 게 문제겠지", "예외를 던지게 바꾸면 되겠지".
  4. 계획: 그 가정 위에 세워짐(이미 어긋났을 수 있음).
  5. 도구 호출: 어긋난 계획대로 파일을 바꿈.
  6. 결과: 여러분이 원한 것과 다름 → 처음부터 다시 설명.

경로 B — 네 요소를 갖춘 지시:

  1. 지시: "(목표) DELETE /tasks/{id} 엔드포인트 추가, (맥락) routers/tasks.py의 기존 스타일로, (제약) 새 의존성 없이 기존 store를 통해 데이터 처리, (완료 조건) 없는 ID면 404 + pytest 통과."
  2. 빈칸 거의 없음.
  3. 가정 최소화.
  4. 계획: 여러분의 의도와 거의 일치.
  5. 도구 호출: 의도대로 변경.
  6. 결과: 한 번에 기대에 근접 → 작은 교정만 남음.

핵심은 빈칸의 개수입니다. 지시에 빈칸이 많을수록 에이전트가 메워야 할 가정이 많아지고, 가정이 많을수록 어긋날 확률이 커집니다. 네 요소는 바로 그 빈칸을 미리 채워 주는 체크리스트입니다.

"알아서 해 줘"가 통할 때와 안 통할 때

탐색·요약처럼 읽기만 하고 결과가 되돌릴 수 있는 작업은 다소 모호해도 괜찮습니다("이 폴더 뭐 하는지 요약해 줘"). 하지만 파일을 바꾸는 작업은 모호하면 비용이 큽니다. 잘못 바꾼 것을 되돌려야 하기 때문입니다. 변경 작업일수록 네 요소를 또렷이 채우는 습관이 중요합니다.

3.4 worked example: 모호한 지시 vs 구체 지시 비교

말로만 보면 와닿지 않으니, 같은 일을 두 가지 지시로 시켜 결과 차이를 봅니다. 무대는 1장에서 셋업한 실습 저장소 team-tasks-api이고, 핵심 파일 routers/tasks.py의 기존 코드는 다음과 같습니다.

python
# routers/tasks.py  (team-tasks-api 기존 코드)
from fastapi import APIRouter, HTTPException
from models import Task, TaskCreate
import store

router = APIRouter(prefix="/tasks", tags=["tasks"])


@router.get("", response_model=list[Task])
def list_tasks() -> list[Task]:
    return store.get_all_tasks()


@router.post("", response_model=Task, status_code=201)
def create_task(data: TaskCreate) -> Task:
    return store.create_task(data)

목표는 "할 일 1건을 ID로 삭제하는 엔드포인트 추가"입니다(이 저장소에는 아직 삭제 기능이 없습니다). 같은 목표를 두 가지로 지시해 봅니다. 아래는 Claude Code 대화형 세션(REPL)에서의 입력과, 그에 따른 에이전트의 진행을 요약한 것입니다.

① 모호한 지시:

console
> task 삭제 기능 좀 추가해 줘

이 지시에는 맥락(어느 파일·어떤 스타일)도, 제약(무엇은 하지 말 것)도, 완료 조건(무엇이 되면 끝)도 없습니다. 에이전트는 빈칸을 가정으로 메우며, 흔히 다음과 같은 어긋남이 생깁니다.

  • 단건 삭제가 아니라 일괄 삭제·필터 삭제까지 끼워 넣음(목표를 과하게 추측).
  • 없는 ID 처리(404)를 빠뜨림(완료 조건이 없으므로).
  • store를 거치지 않고 데이터 저장 방식을 멋대로 바꿈(제약이 없으므로).

결과적으로 변경 범위가 커지고, 여러분은 "이게 아닌데"를 다시 설명해야 합니다.

② 네 요소를 갖춘 구체 지시:

console
> routers/tasks.py에 할 일 1건을 ID로 삭제하는 DELETE /tasks/{task_id}
  엔드포인트를 추가해 줘. 기존 list_tasks·create_task와 같은 스타일을 따르고,
  데이터는 store를 통해 다루되 store.py에 delete_task 함수를 더해 써. 없는 ID면
  HTTPException으로 404를 반환해야 하고, 변경 후 이 동작을 확인하는 방법을 알려 줘.

이번에는 목표(DELETE /tasks/{task_id}), 맥락(routers/tasks.py·기존 스타일), 제약(store를 통해서만 데이터 처리), 완료 조건(없는 ID면 404)이 모두 들어 있습니다. 에이전트는 빈칸이 거의 없어, 다음과 같이 좁고 정확한 변경을 제시합니다.

python
# store.py 에 추가된 함수
def delete_task(task_id: int) -> bool:
    """id로 할 일을 삭제. 있었으면 True, 없었으면 False."""
    return _db.pop(task_id, None) is not None
python
# routers/tasks.py 에 추가된 엔드포인트
@router.delete("/{task_id}", status_code=204)
def delete_task(task_id: int) -> None:
    if not store.delete_task(task_id):
        raise HTTPException(status_code=404, detail="Task not found")

이 변경이 의도대로인지 확인해 봅니다. 아래는 핵심 로직만 떼어내 직접 실행해 본 것입니다.

python
# 동작 확인(핵심 로직만 발췌 실행)
_db = {1: {"id": 1, "title": "배포 문서 읽기", "status": "todo"}}

def delete_task(task_id):
    return _db.pop(task_id, None) is not None

print(delete_task(1))   # 있던 것 삭제
print(delete_task(99))  # 없는 것
# 출력: True
# 출력: False

존재하는 ID(1)는 삭제 후 True(라우터에서 204), 없는 ID(99)는 False(라우터에서 404)를 끌어내 완료 조건을 정확히 만족합니다.

무엇이 결과를 갈랐나

  • 지시 ②는 목표를 단건 삭제로 좁혀 일괄 삭제 같은 군더더기를 막았습니다.
  • "기존 스타일을 따르라"는 맥락이 응답 모델·함수 형태를 기존 코드에 정렬시켰습니다.
  • "store를 통해서만 데이터를 다루라"는 제약이 저장 방식을 멋대로 바꾸는 일을 차단했습니다.
  • "없는 ID면 404"라는 완료 조건이 에러 처리를 명시해, 빠지기 쉬운 엣지 케이스를 끌어냈습니다.
  • 같은 에이전트, 같은 목표인데 지시의 밀도만으로 결과 품질이 갈렸습니다.

3.5 작업 분해와 단계적 지시(한 번에 하나)

네 요소를 갖췄어도, 한 번에 너무 큰 일을 시키면 루프가 길어지고 검토가 어려워집니다. 그래서 두 번째 기법이 작업 분해(task decomposition)입니다. 큰 작업을 검증 가능한 작은 단계로 쪼개 한 번에 하나씩 지시하는 것입니다.

"검증 가능한"이 핵심입니다. 각 단계는 끝났을 때 눈으로 또는 테스트로 확인할 수 있어야 합니다. 예를 들어 "할 일 완료 처리 기능 추가"라는 작업은 다음처럼 쪼갤 수 있습니다.

단계 지시 어떻게 검증하나(완료 조건)
1 "완료 처리 동작을 검증할 pytest 테스트를 먼저 작성해 줘(아직 구현 없이 실패하는 상태로)." 테스트가 실행되고, 예상대로 실패하면 끝
2 "이제 그 테스트를 통과하도록 PATCH /tasks/{id}/done 엔드포인트를 구현해 줘." 1단계 테스트가 통과하면 끝
3 "기존 테스트가 모두 통과하는지 한 번에 돌려 확인해 줘." 전체 테스트 초록색이면 끝

이렇게 쪼개면 좋은 점이 셋입니다. 첫째, 각 단계가 작아 검토가 쉽습니다(diff가 짧습니다). 둘째, 어디서 어긋났는지 바로 보입니다(3단계 중 2단계에서 틀리면 거기만 고치면 됩니다). 셋째, 중간 검증으로 가정이 일찍 교정됩니다(1단계에서 테스트 형태가 마음에 안 들면 구현 전에 바로잡습니다).

반대로, "완료 처리 기능을 테스트까지 다 만들어서 한 번에 끝내 줘"라고 한 덩어리로 시키면, 결과가 100줄짜리 diff로 돌아와 어디가 맞고 틀린지 검토하기 버겁고, 한 곳만 틀려도 전체를 의심하게 됩니다.

이제 이 분해를 종이에 적지 말고 team-tasks-api에서 실제로 단계별로 지시해 봅니다. 한 덩어리로 던지는 것과, 단계로 쪼개 한 번에 하나씩 주는 것의 차이를 직접 겪어야 분해의 이득이 손에 잡힙니다.

3.6 @파일 멘션·참조로 맥락 주입하기

네 요소 중 맥락을 가장 정확하게 주는 도구가 @파일 멘션입니다. Claude Code 대화형 세션에서 @를 입력하면 저장소의 파일·폴더 경로를 자동완성으로 고를 수 있고, 그렇게 멘션한 파일의 내용이 그 지시의 맥락으로 직접 주입됩니다.

console
> @routers/tasks.py 의 list_tasks와 같은 스타일로 status가 todo인 항목만 돌려주는
  GET /tasks/pending 엔드포인트를 추가해 줘.

여기서 @routers/tasks.py는 "이 파일을 보고, 이 파일의 스타일을 따르라"는 맥락을 한 토큰으로 전달합니다. 폴더도 멘션할 수 있어, @routers/처럼 디렉터리를 가리키면 그 안의 구조를 참고하게 할 수 있습니다.

@멘션이 중요한 이유는 붙여넣기보다 정확하고 안전하기 때문입니다. 신입이 흔히 하는 실수가 채팅창에 코드를 통째로 복사·붙여넣기 하는 것인데, 이러면 세 가지 문제가 생깁니다.

  • 버전 불일치: 붙여넣은 코드가 디스크의 진짜 현재 파일과 다를 수 있습니다(이미 누가 고쳤을 수도). @멘션은 항상 디스크의 실제 파일을 읽습니다.
  • 맥락 누락: 함수 하나만 붙여넣으면 그 함수가 의존하는 import·모델이 빠집니다. @로 파일을 가리키면 에이전트가 필요한 부분을 알아서 같이 읽습니다.
  • 수고: 긴 파일을 복사하는 것보다 @경로 한 번이 빠릅니다.

"같은 스타일로"를 가능하게 하는 게 @멘션입니다

신입이 가장 자주 듣는 리뷰 지적이 "우리 컨벤션과 다르다"입니다. @routers/tasks.py로 기존 파일을 참조시키고 "이 스타일을 따르라"고 하면, 에이전트는 함수 명명·타입 힌트·에러 처리 방식을 그 파일에서 직접 학습해 따라 합니다. 8장에서 배울 CLAUDE.md가 팀 규칙을 영속적으로 주입하는 장치라면, @멘션은 그 작업 한정으로 맥락을 주입하는 즉석 도구입니다.

3.7 worked example: @main.py 참조로 같은 스타일 엔드포인트 추가

이제 네 요소 + 작업 분해 + @멘션을 한데 묶어, 실제 작업 하나를 끝까지 해 봅니다. 목표는 "끝나지 않은 할 일만 돌려주는 GET /tasks/pending 추가"입니다.

1단계 — @멘션으로 맥락을 주며 테스트부터 지시:

console
> @routers/tasks.py 를 참고해서, status가 todo인 할 일만 돌려주는
  GET /tasks/pending 엔드포인트의 동작을 검증할 pytest 테스트를 먼저 작성해 줘.
  TestClient를 쓰고, 아직 엔드포인트 구현은 하지 마. 테스트는 일부러 실패해야 해.

에이전트는 routers/tasks.py와 models.py를 읽어 Task·TaskStatus 모델과 store 사용, 기존 엔드포인트 형태를 파악한 뒤, 같은 스타일의 테스트를 만듭니다.

python
# tests/test_pending.py
from fastapi.testclient import TestClient

from main import app
import store
from models import TaskStatus

client = TestClient(app)


def test_pending_returns_only_unfinished():
    store.reset()
    client.post("/tasks", json={"title": "문서 읽기"})   # id=1, todo
    client.post("/tasks", json={"title": "환경 설정"})    # id=2, todo
    store.get_task(2).status = TaskStatus.done           # 2번을 완료 상태로

    response = client.get("/tasks/pending")

    assert response.status_code == 200
    titles = [t["title"] for t in response.json()]
    assert titles == ["문서 읽기"]

아직 /tasks/pending이 없으므로 이 테스트는 실패합니다(404가 와서 assert response.status_code == 200에서 멈춥니다). 완료 조건("일부러 실패")을 만족합니다.

2단계 — 테스트를 통과하도록 구현 지시:

console
> 이제 그 테스트가 통과하도록 GET /tasks/pending 엔드포인트를 routers/tasks.py에
  구현해 줘. list_tasks와 같은 스타일로, store를 통해 데이터를 읽고 status로 걸러 줘.
  단, /{task_id}보다 위에 둬야 해.
python
# routers/tasks.py 에 추가된 엔드포인트
@router.get("/pending", response_model=list[Task])
def list_pending_tasks() -> list[Task]:
    return [t for t in store.get_all_tasks() if t.status == TaskStatus.todo]

이 로직이 맞는지 핵심만 떼어 실행해 확인합니다.

python
# 동작 확인(핵심 로직만 발췌 실행)
class Task:
    def __init__(self, title, status):
        self.title = title
        self.status = status

all_tasks = [
    Task("문서 읽기", "todo"),
    Task("환경 설정", "done"),
]

pending = [t.title for t in all_tasks if t.status == "todo"]
print(pending)
# 출력: ['문서 읽기']

status가 done인 "환경 설정"은 빠지고 "문서 읽기"만 남아, 1단계 테스트의 기대(titles == ["문서 읽기"])와 일치합니다.

이 worked example에서 쓴 세 기법

  • @멘션(맥락): @routers/tasks.py로 기존 스타일을 직접 참조시켜, 새로 만든 코드가 기존 함수와 같은 모양(타입 힌트·반환형·명명)을 따르게 했습니다.
  • 작업 분해(한 번에 하나): 테스트(1단계)와 구현(2단계)을 나눠, 구현 전에 "무엇이 통과하면 끝인지"를 코드로 못 박았습니다. 이것이 7장에서 깊게 다룰 TDD의 씨앗입니다.
  • 완료 조건: 1단계는 "일부러 실패", 2단계는 "그 테스트 통과"라는 검증 가능한 조건을 줘서, "됐다"를 느낌이 아니라 테스트 결과로 판정했습니다.

3.8 반복 교정(iterate): 검토 → 피드백 → 재시도

마지막 기법은 반복 교정(iterate)입니다. 1~2장에서 에이전트는 한 번에 정답을 내는 기계가 아니라 루프를 돈다고 했습니다. 이 성질을 적극적으로 활용하는 것이 반복 교정입니다. 즉, 첫 결과를 완성품으로 보지 않고 초안으로 보고, 검토해서 구체적 피드백을 주고 다시 시키는 것입니다.

흔한 신입의 두 가지 잘못된 반응이 있습니다.

  • 무비판 수용: 에이전트가 준 코드를 검토 없이 그대로 받아들입니다 → 잘못된 가정이 그대로 묻어 들어갑니다.
  • 통째로 포기: 결과가 마음에 안 들면 "역시 AI는 못 쓰겠네" 하고 직접 처음부터 합니다 → 교정 한 번이면 될 일을 버립니다.

정석은 구체적 피드백으로 한 단계 다듬기입니다. 피드백도 네 요소처럼 구체적일수록 좋습니다.

나쁜 피드백 좋은 피드백
"그거 아닌데 다시 해 줘" "404 대신 빈 리스트를 반환하게 바꿔 줘. 없는 게 에러는 아니야."
"코드가 별로야" "list_pending_tasks 안의 조건을 한 줄 컴프리헨션 대신 명시적 for 루프로 풀어 줘. 팀 컨벤션이야."
"테스트 더 해 줘" "모든 할 일의 status가 done일 때 빈 리스트가 오는지 확인하는 테스트 케이스를 하나 더 추가해 줘."

예를 들어 위 worked example 뒤에 이렇게 교정할 수 있습니다.

console
> 좋아. 그런데 모든 항목의 status가 done일 때 빈 리스트가 오는지 확인하는
  테스트 케이스를 test_pending.py에 하나 더 추가해 줘.

이렇게 검토 → 구체적 피드백 → 재시도를 한두 번 돌리면, 첫 결과가 70점이어도 곧 95점으로 올라갑니다. 이게 에이전트를 잘 쓰는 사람과 못 쓰는 사람을 가르는 가장 큰 차이입니다.

교정은 새 세션이 아니라 같은 대화에서

교정 피드백은 방금 그 작업을 한 같은 세션에서 이어 주는 게 좋습니다. 에이전트가 직전에 무엇을 왜 그렇게 했는지의 맥락을 그대로 갖고 있어, "그것 말고 이렇게"가 정확히 통합니다. 세션을 닫았다면 1장에서 배운 --continue로 직전 대화를 이어 교정하면 됩니다.

3.9 즉시 연습(2종 1세트): 모호한 지시 vs 4요소 지시를 team-tasks-api에 실제로 줘 보기

이번에는 종이에 4요소를 채우는 것이 아니라, 모호한 한 줄과 네 요소를 갖춘 지시를 team-tasks-api에 실제로 줘 보고 결과 차이를 직접 기록합니다. 같은 의도라도 지시의 구체성에 따라 에이전트의 동작이 얼마나 달라지는지 손으로 겪는 것이 목적입니다.

모범: 같은 의도를 모호하게 vs 4요소로 줬을 때(실제 실행 예)

상황: team-tasks-api의 POST /tasks가 빈 제목(title="")도 그대로 만들어 줍니다. "빈 제목이면 거부하게" 바꾸고 싶습니다.

모호한 지시를 주면 에이전트가 추측으로 메웁니다.

text
> 빈 제목 좀 막아 줘.
→ 어디서(라우터? 모델?) 어떻게(400? 422? 무시?) 막을지 추측. 테스트도 안 함.

같은 의도를 네 요소로 주면 추측의 여지가 사라집니다.

text
[목표]   POST /tasks에서 title이 비어 있으면 생성하지 말고 거부한다.
[맥락]   routers/tasks.py의 create_task, models.py의 TaskCreate. 기존 스타일을 따른다.
[제약]   새 라이브러리 추가 금지. 기존 store·모델만 사용(pydantic 검증 활용).
[완료]   빈 title이면 422(또는 400)를 반환하고, 이 동작을 확인하는
         pytest 테스트가 통과하면 끝. 기존 테스트도 모두 통과해야 한다.

대화형 세션에서는 한 문단으로 풀어 줍니다.

console
> @routers/tasks.py 의 create_task와 @models.py 의 TaskCreate를 같은 스타일로 고쳐서,
  title이 비어 있으면 만들지 말고 422를 반환하게 해 줘. 새 라이브러리는 쓰지 말고,
  이 동작을 검증하는 pytest 테스트를 추가한 뒤 전체 테스트가 통과하는지 확인해 줘.

3.10 흔한 오류와 오개념: 과대 요청·모호한 형용사·검증 누락

오개념 1 — "한 번에 다 시키는 게 효율적이다"

신입이 "할 일 완료 처리, 필터, 검색, 정렬을 다 만들고 테스트도 붙여서 한 번에 끝내 줘"처럼 큰 덩어리를 던지는 경우가 많습니다. 이러면 100줄짜리 변경이 한꺼번에 돌아와 어디가 맞고 틀린지 검토가 불가능해지고, 한 곳만 어긋나도 전체를 의심하게 됩니다.

교정: 작업을 검증 가능한 단계로 쪼개 한 번에 하나씩 시킵니다(3.5). "완료 처리 테스트 작성 → 구현 → 전체 테스트 확인"처럼 각 단계가 끝났는지 확인 가능해야 합니다. 큰 작업일수록 분해의 이득이 큽니다.

오개념 2 — "정중하고 길게 쓰면 더 잘한다(모호한 형용사의 함정)"

"아주 깔끔하고 효율적이고 안전하게, 베스트 프랙티스로 부탁드립니다"는 길지만 정보량이 거의 0입니다. "깔끔하게"가 무엇을 뜻하는지(함수 분리? 주석? 줄 길이?)가 지시에 없으면 에이전트는 또 추측합니다. 모호한 형용사는 빈칸을 늘릴 뿐입니다.

교정: 형용사를 검증 가능한 제약·완료 조건으로 바꿉니다. "깔끔하게" → "한 함수는 20줄을 넘기지 말고", "안전하게" → "없는 id면 404, 잘못된 입력이면 422를 반환". 추상적 칭찬어 대신 구체적 기준을 줍니다.

오개념 3 — "에이전트가 됐다고 하면 된 것이다(검증 누락)"

지시에 완료 조건을 넣지 않으면, 에이전트는 코드를 작성한 것만으로 "완료했습니다"라고 말합니다. 하지만 그 코드가 실제로 도는지, 엣지 케이스를 처리하는지는 확인되지 않은 상태입니다. "됐다"는 말은 검증이 아닙니다.

교정: 모든 변경 지시에 "이 동작을 확인하는 pytest 테스트가 통과하면 끝"처럼 검증을 완료 조건에 포함시킵니다. 이 습관은 7장(실행·테스트로 검증)에서 본격화되지만, 지시 단계에서부터 완료 조건에 검증을 박아 두는 것이 출발점입니다.

3.11 단원 미니 프로젝트: 지시문 4요소로 엔드포인트 추가하기

이 단원에서 배운 것(네 요소·작업 분해·@멘션·반복 교정)을 한 번에 적용해, 작은 기능 하나를 지시만으로 끝까지 끌고 가 봅니다. 이것이 u3의 미니 프로젝트입니다.

미니 프로젝트 — "모호한 한 줄 → 네 요소 지시 → 단계 실행" (2종 1세트)

목표 산출물: 1장에서 셋업한 team-tasks-api 저장소에서 새 작업 브랜치를 만들고, "특정 할 일을 완료 처리하는 PATCH /tasks/{task_id}/done 엔드포인트"를 테스트와 함께 routers/tasks.py에 추가합니다. 이것은 13~16장 종합 프로젝트의 "완료 처리" 기능을 미리 맛보는 것이기도 합니다.

python
# 동작 확인(핵심 로직만 발췌 실행)
_db = {1: {"id": 1, "title": "문서 읽기", "status": "todo"}}

def mark_done(task_id):
    if task_id not in _db:
        return (404, "Task not found")
    _db[task_id]["status"] = "done"
    return (200, _db[task_id])

print(mark_done(1))
print(mark_done(99))
# 출력: (200, {'id': 1, 'title': '문서 읽기', 'status': 'done'})
# 출력: (404, 'Task not found')

3.12 마무리: 이 장에서 무엇을 가져가나

이 장에서 우리는 에이전트를 부리는 기본기를 배웠습니다. 핵심은 네 가지입니다.

  1. 네 요소 — 목표·맥락·제약·완료 조건을 채우면 빈칸(가정)이 줄어 결과가 의도에 수렴합니다.
  2. 작업 분해 — 큰 작업을 검증 가능한 단계로 쪼개 한 번에 하나씩 시키면 검토와 교정이 쉬워집니다.
  3. @멘션 — 붙여넣기 대신 실제 파일을 참조시켜 맥락을 정확·안전하게 주입합니다.
  4. 반복 교정 — 첫 결과를 초안으로 보고 구체적 피드백으로 다듬는 것이 에이전트 활용의 정석입니다.

다음 장(4장)에서는 이 지시 기술을 낯선 팀 코드를 파악하는 일에 적용합니다. 잘 묻는 것도 잘 지시하는 것의 한 갈래이며, 무엇을 바꿀지 정하기 전에 코드를 이해하는 안전한 탐색을 배웁니다.
