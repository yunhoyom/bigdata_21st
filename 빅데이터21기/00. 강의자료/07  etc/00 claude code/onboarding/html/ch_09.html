Chapter 09

첫 커밋과 첫 PR: git 워크플로

실무

첫 커밋과 첫 PR: git 워크플로

이 챕터에서 배우는 것

  • 여러 변경을 작은 논리 단위로 나눠 스테이징하고, 관례(Conventional Commits) 형식(feat:/fix:)의 메시지로 커밋하게 할 수 있습니다.
  • 작업용 브랜치를 만들고 git status·git diff를 확인해 무엇이 어느 커밋에 들어갈지 커밋 단위를 직접 통제할 수 있습니다.
  • 변경 요약·근거·테스트 결과 세 가지를 담아, 리뷰어가 빠르게 이해할 수 있는 PR 초안 1건을 작성할 수 있습니다.
  • 커밋·PR 관련 명령을 allowlist(예: Bash(git commit:*)·gh)로 좁혀 안전하게 운용할 수 있습니다.

도입: 신입의 통과의례, 첫 PR

앞 단원(u6)에서 우리는 "검증 전까지는 끝난 게 아니다"를 배웠습니다. 변경을 실제로 실행하고 pytest로 통과를 확인해야 비로소 작업이 끝났다고 말할 수 있다는 습관이었습니다. 그런데 한 가지 질문이 남습니다. 내 컴퓨터에서 테스트가 통과한 그 코드를, 어떻게 팀의 코드로 합류시킬까요? 혼자 만든 변경이 아무리 잘 동작해도, 팀의 메인 브랜치에 안전하게 들어가 동료들이 함께 쓰게 되기 전까지는 절반만 끝난 일입니다.

이 마지막 절반을 책임지는 절차가 git 워크플로(git workflow), 그중에서도 신입의 통과의례로 불리는 첫 PR(Pull Request, 풀 리퀘스트)입니다. PR은 "내가 이런 변경을 만들었으니, 검토하고 메인 브랜치에 합쳐 주세요"라고 팀에 공식적으로 요청하는 단위입니다. 신입이 팀에서 처음으로 존재감을 드러내는 순간이자, 동료들이 여러분의 일하는 방식을 처음 보는 창문이기도 합니다. 이 장의 핵심 개념은 git 워크플로: 커밋과 첫 PR입니다.

문제는, git을 처음 다루는 신입에게 이 절차가 의외로 가파른 벽이라는 점입니다. "브랜치를 어떻게 만들지", "무엇을 한 커밋에 묶을지", "커밋 메시지를 어떻게 쓸지", "PR 본문에 뭘 적을지" 같은 결정이 한꺼번에 밀려옵니다. 여기서 Claude Code(클로드 코드)가 큰 도움이 됩니다. Claude Code는 버전 관리(version control)를 작업 흐름의 일부로 다룹니다. 무엇이 어떻게 바뀌었는지 맥락을 알기에, 변경을 스테이징하고 관례에 맞는 커밋 메시지를 제안하며, 브랜치 생성·diff 검토·gh를 이용한 PR 생성까지 도울 수 있습니다.

다만 한 가지를 분명히 해 둡니다. 무엇을·언제 커밋할지는 끝까지 사람이 통제합니다. 에이전트는 손이 빠른 동료일 뿐이고, "이 변경들을 어떤 단위로 역사에 남길지"를 정하는 책임은 여러분에게 있습니다. 이 챕터는 그 통제력을 갖춘 채 에이전트와 함께 첫 커밋을 만들고 첫 PR을 올리는 전 과정을 다룹니다.

선수 개념 상기

이 챕터는 실행·테스트로 검증하기(c07)를 바로 앞 선수로 합니다. 좋은 PR의 핵심 재료 중 하나가 "이 변경이 동작함을 어떻게 증명했는가", 곧 테스트 결과입니다. ch_07에서 pytest로 통과를 확인하는 습관을 들였다면, 그 통과 결과가 이번 챕터에서 PR 본문의 "어떻게 검증했는지" 항목으로 그대로 이어집니다. 또 멀게는 권한과 승인(c05)도 다시 등장합니다. 커밋·푸시·PR 생성은 파일을 바꾸고 외부(원격 저장소)에 영향을 주는 부수효과 작업이므로, 이번 챕터 끝에서 이 명령들을 allowlist로 어떻게 안전하게 허용할지 설계합니다.

git 상태·diff 확인과 변경 맥락 파악

커밋을 만들기 전에 가장 먼저 할 일은 지금 무엇이 바뀌었는지 정확히 아는 것입니다. 자기 변경을 모른 채 커밋하는 것은, 내용을 읽지 않고 서류에 서명하는 것과 같습니다. git에는 이 "현재 상태"를 보는 두 가지 핵심 명령이 있습니다.

  • git status: 어떤 파일이 새로 생겼는지(untracked), 수정됐는지(modified), 스테이징됐는지(staged)를 목록으로 보여 줍니다. "무엇이 바뀌었나"의 개요입니다.
  • git diff: 각 파일에서 어떤 줄이 어떻게 바뀌었는지 추가(+)·삭제(-) 단위로 보여 줍니다. "어떻게 바뀌었나"의 세부입니다.

Claude Code와 함께 일할 때 좋은 점은, 이 두 명령을 직접 외워 입력하지 않아도 변경의 의미를 사람 말로 요약해 달라고 할 수 있다는 것입니다. 에이전트는 git status와 git diff를 읽기 전용 도구로 실행해 결과를 해석하고, "지금 routers/tasks.py에 완료 처리 엔드포인트가 하나 추가됐고, 테스트 파일이 새로 생겼습니다" 같은 요약을 돌려줍니다.

다음은 받은 팀 저장소 team-tasks-api에서 작은 변경을 만든 직후, 상태를 확인하는 대화입니다. 입력한 줄은 >로 시작하는 자연어 지시이고, 그 아래는 에이전트가 실제로 실행한 명령과 요약입니다.

console
> 지금 워킹 트리에 어떤 변경이 있는지 git status와 git diff로 확인하고,
  무엇이 바뀌었는지 한국어로 요약해 줘. 아직 커밋하지는 말고.

(Claude Code가 Bash 도구로 git status를 실행)
$ git status --short
 M routers/tasks.py
?? tests/test_tasks_complete.py

(이어서 git diff를 실행해 내용을 읽고 요약)

요약하면 변경은 두 가지입니다.
1. routers/tasks.py: 기존 tasks 라우터에 PATCH /tasks/{task_id}/complete
   엔드포인트가 추가되어, 특정 작업을 완료 상태로 바꿉니다.
2. tests/test_tasks_complete.py: 위 엔드포인트를 검증하는 새 테스트 파일입니다.
아직 어떤 변경도 스테이징되지 않았습니다.
  • git status --short의 M은 수정됨(modified), ??은 git이 추적하지 않는 새 파일(untracked)을 뜻합니다. 한눈에 "수정 1개, 새 파일 1개"임을 읽을 수 있습니다.
  • 에이전트가 git diff까지 읽어 두 변경의 의미를 묶어 설명했습니다. 단순히 "두 파일이 바뀜"이 아니라 "엔드포인트 추가 + 그 테스트"라는 한 덩어리의 작업임을 파악한 점이 중요합니다. 이 파악이 다음 단계인 "커밋 단위 정하기"의 출발점입니다.
  • "아직 커밋하지는 말고"라는 제약을 명시했습니다. 상태 파악 단계에서는 읽기만 하고 역사를 바꾸지 않습니다. 무엇을 커밋할지는 내가 본 다음에 정합니다.

git diff는 변경을 스스로 다시 읽는 가장 좋은 습관입니다. 에이전트의 요약을 믿되, 핵심 변경은 diff를 직접 보거나 에이전트에게 "이 엔드포인트가 잘못된 상태 값을 받으면 어떻게 되나?" 같은 질문을 던져 한 번 더 확인하는 것이 좋습니다. 변경 맥락을 정확히 파악했다면, 이제 이 변경을 어떤 순서로 역사에 남길지 정할 차례입니다.

동작 원리: 브랜치 → 커밋 → 푸시 → PR 흐름

첫 PR까지 가는 길은 정해진 네 단계의 흐름을 따릅니다. 각 단계가 "무엇을, 왜" 하는지 이해하면, 에이전트에게 단계별로 정확히 지시할 수 있습니다.

  1. 작업 브랜치 생성(branch) — 팀의 메인 브랜치(main)에서 직접 작업하지 않고, feature/task-complete 같은 별도의 작업용 가지를 만들어 그 위에서 변경합니다. 이렇게 하면 내 작업이 완성되어 검토를 통과하기 전까지 메인 브랜치는 안전하게 유지됩니다. 여러 사람이 동시에 일할 수 있는 것도 이 분리 덕분입니다.

  2. 논리 단위 스테이징·커밋(stage·commit) — 변경 중 한 가지 의미를 이루는 묶음만 골라 git add로 스테이징하고, 그 묶음을 설명하는 메시지로 git commit합니다. 커밋은 "되돌릴 수 있는 의미 있는 한 걸음"입니다. 한 커밋이 한 가지 일만 담아야 나중에 역사를 읽고 되돌리기가 쉽습니다.

  3. 푸시(push) — 내 컴퓨터(로컬)에만 있던 커밋들을 원격 저장소(GitHub 등)의 내 브랜치로 올립니다. 이 시점부터 동료들이 내 작업을 볼 수 있게 됩니다.

  4. PR 초안 작성(pull request) — "이 브랜치의 변경을 메인에 합쳐 주세요"라고 요청하는 PR을 만듭니다. 제목·설명·테스트 결과를 담아, 리뷰어가 무엇을·왜·어떻게 검증했는지를 빠르게 이해하게 합니다.

이 네 단계를 표로 정리하면 각 단계의 책임과 도구가 분명해집니다.

단계 핵심 명령 하는 일 무엇이 바뀌나
브랜치 생성 git switch -c feature/... 메인에서 작업 가지를 침 현재 브랜치 위치
스테이징 git add <경로> 커밋할 변경을 고름 스테이징 영역
커밋 git commit -m "feat: ..." 고른 변경을 역사에 기록 로컬 git 역사
푸시 git push -u origin feature/... 로컬 커밋을 원격에 올림 원격 브랜치
PR 초안 gh pr create --draft ... 합치기 요청을 만듦 원격에 PR 생성

왜 메인에서 바로 작업하지 않는가

신입이 가장 자주 하는 실수가 메인 브랜치에서 곧장 변경하는 것입니다. 메인은 "언제나 동작하는, 모두가 공유하는 기준선"입니다. 검토받지 않은 내 변경이 메인에 섞이면 다른 동료의 작업까지 영향을 받습니다. 작업 브랜치는 내 실험실입니다. 여기서 마음껏 만들고 부수고, 검토를 통과한 결과만 PR을 통해 메인으로 보냅니다. 이 분리가 협업의 안전장치입니다.

worked example: 작업 브랜치에서 feat: 메시지로 커밋

이제 앞에서 파악한 변경(완료 처리 엔드포인트 + 테스트)을 실제로 브랜치에 올려 커밋해 보겠습니다. 목표는 "작업 브랜치를 만들고, 변경을 하나의 논리 단위로 커밋하기"입니다.

먼저 작업 브랜치를 만들도록 지시합니다.

console
> 지금 main 브랜치에 있는지 확인하고, feature/task-complete 라는
  작업 브랜치를 새로 만들어 그쪽으로 옮겨 줘.

(Claude Code가 현재 브랜치를 확인하고 새 브랜치를 생성)
$ git branch --show-current
main
$ git switch -c feature/task-complete
Switched to a new branch 'feature/task-complete'

작업 브랜치 feature/task-complete 로 옮겼습니다. 이제 이 브랜치에서
변경을 커밋해도 main 은 영향을 받지 않습니다.
  • git branch --show-current로 지금 어디에 서 있는지 먼저 확인했습니다. main에서 출발해 가지를 쳐야 깨끗한 브랜치가 됩니다.
  • git switch -c feature/task-complete의 -c는 "create", 곧 새 브랜치를 만들면서 동시에 그쪽으로 이동(switch)한다는 뜻입니다. 브랜치 이름 feature/task-complete는 "기능 추가(feature) 중 작업 완료 처리(task-complete)"라는 의미를 담아, 이름만 봐도 무슨 작업인지 알 수 있게 지었습니다.
  • 옛 명령 git checkout -b도 같은 일을 하지만, 최신 git에서는 브랜치 전환 전용인 git switch가 더 명확해 권장됩니다.

다음으로 변경을 스테이징하고 커밋합니다. 이번 변경은 "완료 처리 엔드포인트와 그 테스트"라는 하나의 일관된 일이므로, 한 커밋으로 묶는 것이 자연스럽습니다.

console
> 변경된 routers/tasks.py 와 새 테스트 파일을 스테이징하고,
  Conventional Commits 규칙에 맞는 커밋 메시지로 커밋해 줘.
  메시지는 무엇을·왜 바꿨는지 한 줄 제목과 간단한 본문으로 적어 줘.

(Claude Code가 스테이징 후 커밋)
$ git add routers/tasks.py tests/test_tasks_complete.py
$ git commit -m "feat(tasks): 작업 완료 처리 엔드포인트 추가" -m "PATCH /tasks/{id}/complete 로 작업을 완료 상태로 전환한다. 동작을 검증하는 테스트를 함께 추가했다."
[feature/task-complete 3f9a1c2] feat(tasks): 작업 완료 처리 엔드포인트 추가
 2 files changed, 41 insertions(+)
 create mode 100644 tests/test_tasks_complete.py
  • git add에 바꿀 파일 경로를 명시했습니다. git add .로 전부 쓸어 담는 대신 두 파일을 짚어 스테이징하면, 의도하지 않은 파일(예: 디버깅용 임시 파일)이 섞여 들어가는 사고를 막습니다. 무엇을 커밋할지 사람이 통제하는 지점입니다.
  • git commit -m "..." -m "..."처럼 -m을 두 번 쓰면 첫 번째가 제목, 두 번째가 본문이 됩니다. 제목은 "무엇을 했나"(완료 처리 엔드포인트 추가), 본문은 "구체적으로 무엇이고 왜인가"를 담았습니다.
  • 제목 feat(tasks): ...이 다음 절에서 다룰 Conventional Commits 형식입니다. feat은 새 기능, (tasks)는 영향 범위(scope), 콜론 뒤가 요약입니다.
  • 출력의 2 files changed, 41 insertions(+)는 이 커밋이 담은 변경 규모를, [feature/task-complete 3f9a1c2]는 커밋이 만들어진 브랜치와 커밋 해시(앞 7자리)를 보여 줍니다. 커밋이 main이 아니라 작업 브랜치에 안전하게 쌓였음을 확인할 수 있습니다.

이렇게 한 커밋이 완성되었습니다. 핵심은 에이전트가 명령을 대신 실행했지만, 무엇을 한 커밋에 묶을지(완료 엔드포인트 + 테스트)와 메시지의 의미를 결정한 것은 사람이라는 점입니다. 다음 절에서 이 "한 커밋에 무엇을 담을지"의 기준을 더 깊이 봅니다.

작은 논리 단위 커밋과 Conventional Commits

방금 우리는 자연스럽게 "완료 엔드포인트와 그 테스트"를 한 커밋으로 묶었습니다. 이 판단의 바탕에 있는 두 가지 원칙을 명시적으로 배웁니다.

정의: 작은 논리 단위 커밋

작은 논리 단위 커밋(atomic commit, 원자적 커밋)은 하나의 완결된 의미만 담아, 그 자체로 설명되고 단독으로 되돌릴 수 있는 가장 작은 변경 묶음입니다. 한 커밋은 "한 가지 일"만 합니다.

"엔드포인트를 추가하면서, 동시에 무관한 오타도 고치고, 설정값도 바꾼" 커밋은 나쁜 커밋입니다. 나중에 "엔드포인트 추가만 되돌리고 싶을 때" 오타 수정과 설정 변경까지 함께 딸려 와 되돌릴 수 없기 때문입니다. 반대로 좋은 커밋은 다음과 같이 나뉩니다.

  • 커밋 1: feat(tasks): 작업 완료 처리 엔드포인트 추가
  • 커밋 2: docs(readme): 완료 엔드포인트 사용법 문서화
  • 커밋 3: fix(tasks): 잘못된 상태 값 입력 시 422 응답하도록 수정

각 커밋이 하나의 의미만 담으므로, 리뷰어는 한 번에 한 가지만 검토하면 되고, 문제가 생기면 그 커밋만 정확히 되돌릴 수 있습니다. "작게, 자주, 의미 단위로"가 좋은 커밋의 리듬입니다.

정의: Conventional Commits

Conventional Commits(컨벤셔널 커밋)는 커밋 메시지 제목을 type(scope): 설명 형식으로 통일하는 관례로, 메시지만 보고도 변경의 종류를 기계와 사람 모두 빠르게 파악하게 하는 약속입니다.

제목의 맨 앞 type(유형)이 변경의 성격을 한눈에 알려 줍니다. 신입이 가장 자주 쓰는 유형은 다음과 같습니다.

type 언제 쓰나 예시 제목
feat 새 기능 추가 feat(tasks): 상태 필터 쿼리 파라미터 추가
fix 버그 수정 fix(tasks): 빈 제목 작업 생성 시 500 오류 수정
docs 문서만 변경 docs(api): 완료 엔드포인트 예시 추가
test 테스트 추가·수정 test(tasks): 완료 처리 경계 케이스 테스트 추가
refactor 동작 변화 없는 구조 개선 refactor(tasks): 저장소 접근 함수 분리
chore 빌드·설정 등 잡무 chore: pytest 의존성 추가

(scope)는 영향 범위로, 어느 모듈·기능이 바뀌었는지(tasks, api, auth 등)를 적습니다. 생략할 수도 있지만, 적으면 검색과 분류가 쉬워집니다. 콜론 뒤 설명은 명령형 현재 시제로 간결하게 적는 것이 관례입니다("추가한다"보다 "추가"처럼 짧게).

Claude Code는 변경 내용을 이미 읽었기에, "Conventional Commits로 커밋해 줘"라고만 해도 feat·fix 같은 유형을 변경 성격에 맞게 골라 제안합니다. 다만 제안된 유형이 맞는지(새 기능인데 fix로 잘못 붙지 않았는지) 확인하는 것은 사람의 몫입니다.

한 작업이 여러 의미를 담았다면

실수로 엔드포인트 추가와 무관한 리팩터링을 한 번에 만들었다면, 에이전트에게 "엔드포인트 변경만 먼저 스테이징해서 feat으로 커밋하고, 리팩터링은 따로 refactor로 커밋해 줘"라고 나눠 커밋하도록 지시할 수 있습니다. git add로 파일·변경을 선택하는 단위가 곧 커밋의 단위가 되므로, 무엇을 함께 묶을지를 사람이 정하면 됩니다.

PR 초안: 변경 요약·근거·테스트 결과

커밋이 쌓였다면, 이제 그 브랜치를 원격에 푸시하고 PR을 만들 차례입니다. 두 가지 도구가 등장합니다.

첫째, gh(GitHub CLI, 깃허브 명령줄 도구)입니다. GitHub를 터미널에서 다루는 공식 도구로, gh pr create 명령으로 PR을 만듭니다. Claude Code는 git을 직접 다루듯 gh도 Bash 도구로 실행해 PR 생성을 도울 수 있습니다.

1장에서 이미 해 둔 것: 1장 11절에서 gh를 설치하고 gh auth login으로 로그인한 뒤, gh repo create ... --remote=origin --push로 team-tasks-api를 GitHub에 올려 원격 origin을 만들어 두었습니다. 그래서 이 장에서는 바로 푸시·PR로 넘어갈 수 있습니다. 막히면 두 가지를 먼저 확인하세요 — git remote -v(원격 origin이 보이는가)와 gh auth status(GitHub에 로그인돼 있는가). 둘 중 하나라도 없으면 1장 11절의 셋업을 다시 합니다.

이 장에서 쓰는 git·GitHub 명령을 한자리에 정리합니다. 로컬(내 컴퓨터)에서 한 일을 원격(GitHub)으로 올려 PR로 잇는 흐름입니다.

명령 무엇을 하나 언제 쓰나
git remote -v 연결된 원격 저장소(origin)를 확인 푸시 전 한 번 점검
git push -u origin <브랜치> 로컬 브랜치를 원격 origin에 처음 올리고 연결(-u=upstream) 그 브랜치를 처음 올릴 때
git push -u로 이미 연결된 브랜치에 이후 커밋을 올림 추가 커밋을 올릴 때
gh auth status gh가 GitHub에 로그인돼 있는지 확인 인증이 의심될 때
gh pr create --draft 푸시된 브랜치로 초안 PR을 생성 푸시 직후
gh pr view <번호> 만든 PR의 상태·주소를 확인 PR 생성 후

둘째, 커스텀 슬래시 커맨드입니다. 커밋→푸시→PR 생성은 거의 항상 같은 순서로 반복되므로, 팀이 이 절차를 하나의 슬래시 커맨드로 묶어 두는 경우가 많습니다.

사실 확인: /commit-push-pr은 내장이 아니라 커스텀 커맨드입니다

/commit-push-pr 같은 이름의 커맨드는 Claude Code에 기본 내장된 명령이 아닙니다. 팀이 .claude/commands/ 또는 스킬로 직접 정의해 두면 /이름으로 부를 수 있는 커스텀 슬래시 커맨드입니다. 즉 "커밋하고 푸시한 뒤 PR 초안을 만든다"는 절차를 한 파일에 적어 두고, 한 번의 호출로 실행하는 것입니다. Claude Code 자체는 별도 커맨드 없이도 자연어("이 변경을 커밋하고 PR 초안 만들어 줘")로 git·gh를 다룰 수 있으므로, 커스텀 커맨드는 그 반복을 줄이는 편의일 뿐입니다. 반면 다음 챕터에서 다룰 /code-review·/security-review는 실제 기본 내장(번들) 명령입니다. 둘을 혼동하지 마십시오.

좋은 PR은 본문에 다음 네 가지를 담습니다. 리뷰어가 PR을 열었을 때 읽는 순서대로 구성하는 것이 좋습니다.

요소 답하는 질문 왜 필요한가
변경 요약(What) 무엇을 바꿨나 리뷰어가 전체 그림을 1분 안에 파악
변경 근거(Why) 왜 바꿨나 의도를 알아야 적절성을 판단
변경 내용(How) 어떻게 구현했나 핵심 설계·선택을 빠르게 따라감
테스트 결과(Verify) 어떻게 검증했나 동작한다는 주장의 근거 제시

특히 테스트 결과가 신입의 PR에서 신뢰를 좌우합니다. "잘 됩니다"가 아니라 "pytest로 3개 테스트가 통과했고, 그 출력은 다음과 같습니다"라고 근거를 보이면, 리뷰어는 여러분을 "검증할 줄 아는 사람"으로 신뢰하기 시작합니다. ch_07에서 들인 검증 습관이 바로 여기서 빛을 발합니다.

다음은 브랜치를 푸시하고 PR 초안을 만드는 흐름입니다.

console
> feature/task-complete 브랜치를 원격에 푸시하고, gh로 PR을 초안(draft)
  상태로 만들어 줘. 제목은 Conventional Commits 형식으로, 본문에는
  변경 요약·근거·테스트 결과를 담아 줘.

(Claude Code가 푸시 후 gh로 PR 생성)
$ git push -u origin feature/task-complete
$ gh pr create --draft --title "feat(tasks): 작업 완료 처리 엔드포인트 추가" --body "(아래 본문)"
https://github.com/team/team-tasks-api/pull/42

PR 초안을 만들었습니다. 위 주소에서 확인할 수 있습니다. 초안(draft)
이므로 아직 리뷰 요청이 자동으로 가지 않습니다. 검토 후 'Ready for
review'로 바꾸면 됩니다.
  • git push -u origin feature/task-complete의 -u는 로컬 브랜치와 원격 브랜치를 연결(upstream 설정)해, 이후로는 git push만 입력해도 같은 곳으로 올라가게 합니다. origin은 원격 저장소의 기본 이름입니다.
  • gh pr create --draft의 --draft는 초안 PR을 만듭니다. 초안은 "아직 리뷰 요청 전" 상태로, 본문을 다듬거나 추가 커밋을 올린 뒤 준비가 되면 정식 리뷰로 전환합니다. 신입의 첫 PR을 초안으로 시작하면 마음의 여유가 생깁니다.
  • 출력의 마지막 줄 https://.../pull/42가 만들어진 PR의 주소입니다. 이 번호(42)가 PR의 식별자가 됩니다.

worked example: 좋은 PR 본문 작성으로 리뷰어 돕기

PR 본문이 빈약하면("작업 완료 처리 추가함") 리뷰어는 코드를 처음부터 끝까지 혼자 해석해야 합니다. 잘 쓴 본문은 리뷰어의 시간을 아끼고, 그만큼 빠르고 정확한 리뷰를 끌어냅니다. 앞에서 만든 PR의 본문을 직접 작성해 보겠습니다.

Claude Code에 변경과 테스트 결과를 근거로 본문 초안을 만들게 한 뒤, 사람이 다듬습니다.

console
> 이 PR의 본문을 마크다운으로 작성해 줘. 변경 요약·변경 근거·변경 내용·
  테스트 결과(방금 돌린 pytest 출력 포함)·범위 항목으로 나누고, 리뷰어가
  1분 안에 파악할 수 있게 간결하게 써 줘.

에이전트가 돌려준 본문은 다음과 같습니다. 이 형식을 그대로 PR 본문 템플릿으로 익혀 두면 좋습니다.

markdown
## 변경 요약
작업을 완료 상태로 바꾸는 PATCH /tasks/{task_id}/complete 엔드포인트를
추가했습니다.

## 변경 근거
완료 여부를 표시할 방법이 없어 사용자가 끝낸 작업을 구분하지 못했습니다.
(이슈 #37) 가장 작은 단위로 "완료 처리"만 먼저 추가합니다.

## 변경 내용
- routers/tasks.py: 완료 처리 엔드포인트 추가. 없는 task_id 는 404,
  이미 완료된 작업은 변경 없이 현재 상태를 반환합니다.
- tests/test_tasks_complete.py: 정상 완료·없는 작업(404)·중복 완료의
  3가지 경우를 검증하는 테스트를 추가했습니다.

## 테스트 결과
\`\`\`
$ pytest tests/test_tasks_complete.py -q
...                                                       [100%]
3 passed in 0.21s
\`\`\`

## 범위
- 포함: 완료 처리 엔드포인트와 그 테스트
- 제외: 완료 취소(되돌리기) 기능, 완료 시각 기록 — 후속 PR에서 다룹니다.
  • 변경 요약은 한 문장입니다. 리뷰어가 제목과 이 한 줄만 읽어도 "무엇인지" 알게 합니다.
  • 변경 근거에 이슈 번호(#37)를 연결했습니다. "왜 이걸 지금 하는가"의 맥락을 PR 밖의 논의와 이어 줍니다.
  • 변경 내용에서 단순히 "엔드포인트 추가"가 아니라 경계 동작(없는 작업은 404, 중복 완료는 현재 상태 반환)까지 밝혔습니다. 리뷰어가 신경 쓸 엣지 케이스를 먼저 짚어 주는 것입니다.
  • 테스트 결과에 실제 pytest 출력을 붙였습니다. "3 passed"라는 근거가 "동작합니다"라는 주장을 뒷받침합니다. 출력은 꾸며 내지 말고 실제로 돌린 결과를 그대로 붙여야 합니다.
  • 범위에서 "이번에 하지 않은 것"(완료 취소·완료 시각)을 명시했습니다. 이렇게 하면 리뷰어가 "왜 이건 빠졌지?"라고 묻기 전에 "의도적으로 후속으로 미뤘다"는 것을 알게 되어, 작은 PR이 오히려 신뢰를 얻습니다.

신입의 PR은 작을수록 좋다

"한 PR에 많은 것을 담아 인상을 남기고 싶다"는 유혹이 있지만, 신입의 첫 PR은 작을수록 좋습니다. 변경이 작으면 리뷰어가 빠르게·정확하게 봐 주고, 문제가 생겨도 영향 범위가 좁습니다. "완료 처리"와 "상태 필터"를 한 PR에 몰지 말고, 두 개의 작은 PR로 나누는 편이 거의 항상 낫습니다. 위 본문의 "범위 - 제외" 항목이 이 작은 단위를 정당화해 줍니다.

커밋·PR 권한(Bash(git commit:*)·gh) 설계

커밋·푸시·PR 생성은 모두 부수효과 도구(Bash)를 통해 일어납니다(c05). 기본 설정에서는 이런 명령마다 Claude Code가 승인을 묻습니다. 매번 묻는 것은 안전하지만, git 작업처럼 자주 반복하는 안전한 명령까지 매번 멈추면 흐름이 끊깁니다. 그래서 자주 쓰는 안전한 git 명령은 미리 허용(allow)하고, 위험한 명령은 차단(deny)하는 설정을 둡니다.

.claude/settings.json(프로젝트 공유 범위)에 다음과 같이 적습니다. 이렇게 체크인하면 팀 모두가 같은 안전 규칙을 공유합니다.

json
{
  "permissions": {
    "allow": [
      "Bash(git status)",
      "Bash(git diff:*)",
      "Bash(git switch:*)",
      "Bash(git add:*)",
      "Bash(git commit:*)",
      "Bash(git push:*)",
      "Bash(gh pr create:*)"
    ],
    "deny": [
      "Bash(git push --force:*)",
      "Bash(git reset --hard:*)",
      "Bash(git branch -D:*)"
    ]
  }
}
  • "Bash(git commit:*)"에서 끝의 :*는 "git commit으로 시작하는 모든 명령"을 뜻하는 패턴입니다. -m "..." 같은 뒤 인자가 무엇이든 허용합니다. git status처럼 인자가 거의 없는 명령은 패턴 없이 그대로 적었습니다.
  • allow 목록에는 역사를 안전하게 쌓는 명령(상태 확인·diff·브랜치 전환·스테이징·커밋·푸시·PR 생성)만 넣었습니다. 이들은 "되돌릴 수 있거나 새로 더하는" 작업이라 비교적 안전합니다.
  • deny 목록의 명령들은 역사를 파괴적으로 바꿉니다. git push --force는 원격 역사를 덮어써 동료의 작업을 날릴 수 있고, git reset --hard는 커밋하지 않은 변경을 복구 불가하게 지우며, git branch -D는 병합되지 않은 브랜치를 강제로 삭제합니다. deny에 두면 실수로라도 실행되지 않습니다.
  • deny가 allow보다 우선합니다. git push:*를 허용했어도 git push --force:*가 deny에 있으면 강제 푸시는 차단됩니다. "넓게 허용하되 위험한 변형만 콕 집어 막는" 설계입니다.

이 설계의 핵심은 최소 권한(least privilege)입니다. "git 전부 허용"이나 "전체 자동 승인(bypass)"은 편하지만, 한 번의 실수가 팀 저장소를 망칠 수 있습니다. 자주 쓰는 안전한 명령만 골라 허용하고, 파괴적 명령은 명시적으로 막는 것이 신입에게 맞는 안전한 기본값입니다. PR 본문에 비밀 토큰을 넣지 않고, gh auth login으로 인증을 분리하는 것도 같은 원칙의 연장입니다.

즉시 연습 (2종 1세트)

이제 종이에 빈칸을 채우는 대신, 1장에서 준비한 실제 team-tasks-api 저장소에서 작업 브랜치를 만들고, 작은 변경을 feat: 커밋으로 올린 뒤, 그 변경의 PR 본문에 실제 pytest 출력을 붙여 작성합니다. 핵심은 "추측한 커밋 메시지"가 아니라 화면에 실제로 찍힌 git log·git status·python -m pytest -q 출력을 그대로 옮기는 것입니다.

1) 모범 예시 (실제 실행 예)

작업 도중 "상태 필터 엔드포인트 추가"와 "관련 없는 README 오타 수정"을 한꺼번에 만들었다고 합시다. 이를 두 개의 논리 단위로 나눕니다.

console
> git status로 변경을 확인한 다음, routers/tasks.py 의 필터 추가는
  feat 커밋으로, README.md 오타 수정은 docs 커밋으로 따로 나눠 커밋해 줘.

$ git add routers/tasks.py
$ git commit -m "feat(tasks): 상태별 작업 조회 필터 추가"
$ git add README.md
$ git commit -m "docs(readme): 엔드포인트 설명 오타 수정"

두 변경이 서로 다른 의미이므로 두 커밋으로 분리했습니다. 나중에 둘 중 하나만 되돌리기 쉬워집니다.

2) 직접 해보기 (team-tasks-api에서 실제 브랜치·커밋·PR)

연습 1 — 작업 브랜치에서 작은 기능을 실제로 커밋하라.

team-tasks-api 폴더에서 새 작업 브랜치를 만들고(git checkout -b feat/task-titles), claude를 실행해 다음을 그대로 지시하세요.

text
> routers/tasks.py에 할 일 제목만 모아 반환하는 GET /tasks/titles 엔드포인트를 추가하고,
  tests/test_tasks.py에 그 테스트를 더한 뒤 python -m pytest -q로 통과를 확인해 줘.
  통과하면 feat: 커밋으로 올려 줘.

작업이 끝나면 직접 git log --oneline -1과 python -m pytest -q를 돌려, 화면에 실제로 나타난 출력을 그대로 옮겨 적으세요(추측한 메시지가 아니라 실제 커밋 제목).

text
[실제 커밋] git log --oneline -1 출력(type(scope): 형식인가?):
[실제 테스트] python -m pytest -q 출력(예: 8 passed):
[브랜치 확인] git branch로 본 현재 브랜치(메인이 아니라 작업 브랜치인가?):

연습 2 — 두 변경을 두 커밋으로 실제로 나눠라.

같은 브랜치에서 README.md에 한 줄 설명을 추가하는 무관한 변경을 더 만든 뒤, 에이전트에게 "기능 변경과 문서 변경을 서로 다른 커밋으로 나눠 줘"라고 지시하세요. git log --oneline -2로 두 커밋이 실제로 나뉘었는지 확인하고 옮겨 적으세요.

text
[두 커밋 분리] git log --oneline -2 실제 출력(의미가 다른 두 커밋인가?):

연습 3 — PR 본문에 실제 pytest 출력을 붙여라.

연습 1의 변경을 PR로 올립니다(gh pr create 또는 GitHub 웹). 본문에는 방금 직접 돌린 python -m pytest -q의 실제 출력을 그대로 붙이세요(꾸며 쓰지 말 것).

markdown

(GET /tasks/titles 엔드포인트 추가 — 실제로 무엇을 했는지)

- tests/test_tasks.py: (실제 추가한 테스트)

## 테스트 결과
(여기에 방금 화면에 찍힌 python -m pytest -q 출력을 그대로 붙임)

## 범위
- 포함:
- 제외:

자가체크 — 머리로가 아니라 손으로 했는지 확인하세요.

  • [ ] 메인이 아니라 실제 작업 브랜치에서 커밋한 것을 git branch로 확인했다.
  • [ ] [실제 커밋]에 적은 것이 추측이 아니라 git log에 찍힌 실제 커밋 제목이며 type(scope): 설명 형식이다.
  • [ ] python -m pytest -q가 통과(8 passed)하는 것을 화면 출력으로 확인했다.
  • [ ] 의미가 다른 두 변경을 실제로 두 커밋으로 나눈 것을 git log로 확인했다.
  • [ ] PR 본문의 테스트 결과가 "잘 됨"이 아니라 방금 직접 돌려 화면에 찍힌 실제 출력이다.
  • [ ] PR을 실제로 올려 보고, 변경 요약·내용·테스트 결과·범위가 모두 들어간 것을 확인했다.

단원 미니 프로젝트: team-tasks-api에 첫 PR 올리기

종이 위 빈칸을 넘어, 1장에서 준비한 실제 team-tasks-api 저장소에 작은 변경을 만들고 첫 PR까지 올리는 과제입니다. 저장소는 1장 11절에서 git init·첫 커밋이 되어 있고, gh auth login·gh repo create로 GitHub 원격(origin)까지 연결돼 있으며, python -m pytest -q가 7 passed 상태라고 가정합니다. 시작 전에 git remote -v로 origin이 보이는지 한 번 확인하세요.

마일스톤(증분):

  1. M1 작업 브랜치. team-tasks-api 루트에서 main에 있는지 확인하고 git switch -c feature/health-detail 같은 작업 브랜치를 만듭니다. (적용 개념: 작업 브랜치)
  2. M2 작은 변경 구현. 에이전트에게 작은 변경 하나를 맡깁니다. 예: "main.py의 GET /health가 {\"status\": \"ok\"} 대신 버전도 함께 반환하도록 {\"status\": \"ok\", \"version\": \"0.1.0\"}로 바꾸고, 그 동작을 검증하는 테스트를 tests/에 추가해 줘." 변경 범위를 작게 유지합니다. (적용 개념: 작은 논리 단위)
  3. M3 논리 단위 커밋. git status·git diff로 무엇이 바뀌었는지 확인한 뒤, 변경된 파일만 골라 스테이징하고 feat(health): /health 응답에 version 추가 같은 Conventional Commits 메시지로 커밋합니다. (적용 개념: 스테이징 통제·Conventional Commits)
  4. M4 푸시·PR 본문. 브랜치를 원격 origin에 푸시하고(git push -u origin feature/health-detail), gh pr create --draft로 변경 요약·근거·내용·테스트 결과·범위를 담은 초안 PR을 만듭니다(원격은 1장 11절에서 연결해 두었습니다). 만약 1장 셋업을 건너뛰어 origin이 없다면, 1장 11절로 돌아가 gh repo create로 원격을 만든 뒤 진행합니다. (적용 개념: PR 본문)

실제 검증 단계. 커밋 전과 PR 작성 전에 반드시 저장소에서 테스트를 돌려 통과를 확인하고, 그 출력을 PR 본문의 "테스트 결과"에 그대로 붙입니다.

console
> python -m pytest -q
........                                                                 [100%]
8 passed

기존 7개에 version 동작 테스트 1개가 더해져 8 passed가 나오면, "잘 됩니다"가 아니라 실제 출력으로 변경을 증명한 것입니다.

미니 프로젝트 자가체크

  • [ ] main이 아니라 feature/... 작업 브랜치에서 변경했는가(git branch --show-current로 확인)
  • [ ] 변경된 파일만 골라 스테이징했는가(git add .로 쓸어 담지 않았는가)
  • [ ] 커밋 제목이 type(scope): 설명 형식(feat(health): ...)인가
  • [ ] PR 본문에 변경 요약·근거·내용·테스트 결과·범위가 모두 있는가
  • [ ] python -m pytest -q의 실제 출력(8 passed)을 테스트 결과로 붙였는가
  • [ ] 파괴적 명령(git push --force 등)이 권한 설계로 차단돼 있는가

흔한 오류와 오개념

1. 무엇을 커밋할지 통제하지 않고 에이전트에 맡긴다

"알아서 커밋해 줘"라고만 하면 에이전트가 임의 단위로 묶거나 의도하지 않은 파일까지 담을 수 있습니다. 무엇을·어떤 단위로 커밋할지는 끝까지 사람이 정합니다. 커밋 전 git status로 무엇이 스테이징됐는지 확인하고, "이 파일들만 이 메시지로 커밋해 줘"처럼 단위를 명시하세요. 커밋은 되돌리기 어려운 팀의 공식 기록이므로, 자동화의 편의보다 통제가 우선입니다.

2. 모든 변경을 한 커밋에 몰아 담는다

하루 작업을 "오늘 한 일"이라는 한 커밋에 전부 넣으면, 리뷰어가 무엇을 봐야 할지 길을 잃고, 나중에 일부만 되돌리는 것도 불가능합니다. 작은 논리 단위로 자주 커밋하세요. "이 변경 하나를 한 문장으로 설명할 수 있는가?"가 기준입니다. 한 문장에 "그리고"가 여러 번 들어가면 커밋을 나눌 신호입니다.

3. PR 설명이 "무엇"만 있고 "왜"와 "검증"이 없다

"엔드포인트 추가함"으로 끝나는 PR은 리뷰어에게 코드 해석의 모든 부담을 떠넘깁니다. 좋은 PR은 무엇(What)·왜(Why)·어떻게 검증했나(Verify)를 함께 담습니다. 특히 "어떻게 검증했나"에 실제 테스트 출력을 붙이는 습관이 신입의 신뢰를 만듭니다. "잘 됩니다"는 근거가 아닙니다.

4. 메인 브랜치에서 바로 작업하고 커밋한다

작업 브랜치를 만들지 않고 main에서 곧장 변경·커밋하면, 검토받지 않은 코드가 팀의 기준선을 오염시킵니다. 항상 작업 브랜치를 만든 뒤 그 위에서 작업하세요(git switch -c feature/...). 커밋 전에 git branch --show-current로 지금 위치를 확인하는 습관이 사고를 막습니다.

5. /commit-push-pr이 내장 명령이라고 오해한다

/commit-push-pr은 Claude Code에 기본 내장된 명령이 아니라, 팀이 직접 정의하는 커스텀 커맨드입니다. 내 환경에서 동작한다면 누군가 만들어 둔 것입니다. 반대로 다음 챕터에서 다룰 /code-review·/security-review는 진짜 내장 명령입니다. "이 슬래시 커맨드가 어디서 왔는가"(내장인가 팀 커스텀인가)를 구분하면, 다른 환경에서 동작하지 않을 때 당황하지 않습니다.

이 챕터 한 줄 정리

첫 PR은 "작은 논리 단위 커밋(Conventional Commits) → 작업 브랜치 → 푸시 → 변경·근거·검증을 담은 PR 본문"의 흐름이며, 에이전트는 명령을 대신 실행하되 무엇을 커밋할지와 메시지의 의미는 사람이 통제하고, 위험한 git 명령은 권한 설계로 차단합니다. 다음 챕터(ch_10)에서는 이렇게 올린 PR에 따라오는 코드 리뷰를 받고 대응하는 법을 배웁니다.
