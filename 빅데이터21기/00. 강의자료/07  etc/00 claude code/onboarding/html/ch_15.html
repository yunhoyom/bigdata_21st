Chapter 15

종합 프로젝트: 첫 기능·첫 PR — 구현(마일스톤 증분)

실무

종합 프로젝트: 첫 기능·첫 PR — 구현(마일스톤 증분)

이 챕터에서 배우는 것

  • CLAUDE.md·권한·플랜 모드부터 테스트·구현·커밋·PR·리뷰까지를 5개 마일스톤(M1~M5)의 증분으로 구현할 수 있습니다.
  • 각 마일스톤이 어느 단원 개념(c01~c12)을 적용했는지 마일스톤↔개념으로 짝지어 설명할 수 있습니다.
  • 각 마일스톤 끝에서 pytest 테스트와 실행 결과로 동작을 확인해, 체크포인트 통과 여부로 검증할 수 있습니다.
  • 5개 마일스톤을 통합해 테스트가 통과하는 두 엔드포인트와, 변경 요약·근거·테스트 결과를 담은 첫 PR을 완성할 수 있습니다.

이 챕터는 종합 프로젝트의 구현(implementation) 단계입니다. 새 개념을 배우지 않습니다. 앞의 12개 개념 챕터(c01~c12)와 분석(ch_13)·설계(ch_14)에서 정한 요구사항·ADR을 실제 코드로 옮기고, 그 과정을 안전·검증·협업의 흐름으로 엮습니다.

구현 전략과 마일스톤 개요

분석(ch_13)에서 우리는 기존 팀 저장소 team-tasks-api에 두 가지 기능을 더하기로 정했습니다.

  • 완료 처리 — PATCH /tasks/{task_id}/complete: 특정 할 일의 상태를 done으로 바꿉니다(FR2).
  • 상태 필터 — GET /tasks?status=done|todo: 목록을 상태로 거릅니다(FR3).

그리고 없는 id는 404, 잘못된 status는 422로 응답하기로 했습니다(FR4). 설계(ch_14)에서는 상태를 불리언이 아니라 todo|done 문자열 enum으로 표현하기로(ADR2), 완료 처리는 부분 변경이므로 PATCH로(ADR1), 필터는 쿼리 파라미터로(ADR3) 결정했습니다.

이제 이것을 한 번에 다 만들지 않습니다. 신입이 첫 기능을 안전하게 추가하는 가장 좋은 방법은, 검증 가능한 작은 단계(마일스톤)로 나누어 한 걸음마다 통과를 확인하며 나아가는 것입니다. 이 챕터는 다음 여섯 마일스톤을 증분으로 진행합니다. 각 마일스톤은 앞 단원에서 배운 개념을 적용하며, 끝에는 반드시 체크포인트로 다음 단계로 넘어가도 되는지 확인합니다.

마일스톤 하는 일 적용 단원·개념 체크포인트
M1 셋업·계획 CLAUDE.md·권한·플랜 모드로 환경과 계획을 갖춤 u5·u7 / c05·c06·c08 계획이 검증 가능한 단계로 승인되고 CLAUDE.md·권한이 준비됨
M2 테스트 먼저 두 엔드포인트의 기대 동작을 pytest로 먼저 작성(TDD) u3·u6 / c03·c07 테스트가 기대 동작을 표현하고 아직 실패함
M3 구현·검증 두 엔드포인트를 구현하고 pytest를 통과시킴 u2·u6 / c02·c07 두 엔드포인트의 테스트가 모두 통과
M4 커밋·PR 작은 논리 단위로 커밋하고 첫 PR 초안을 올림 u8 / c09 작업 브랜치 커밋과 PR 본문이 리뷰 가능하게 작성됨
M5 리뷰·디버깅 /code-review로 점검하고 지적을 디버깅·반영 u9·u10 / c10·c11 타당한 지적 반영, 부적절한 지적에 근거 답변, 회귀 테스트 통과
M6 확장(선택) 테스트 실행을 서브에이전트에, 외부 자료를 MCP로 u11 / c12 서브에이전트 호출 또는 MCP 참조가 동작

MVP를 먼저, 그다음 증분 확장

분석에서 정한 MVP(최소 기능)는 "완료 처리 엔드포인트 하나를 테스트와 함께 추가해 통과시키고 첫 커밋·PR을 올리는 것"이었습니다. 그래서 M2~M4에서는 두 엔드포인트를 함께 다루되, 막히면 완료 처리 하나만 먼저 통과시키고 상태 필터를 뒤에 붙여도 됩니다. "작게 만들어 통과시키고, 통과한 것 위에 더한다"가 증분 구현의 리듬입니다.

M1: CLAUDE.md·권한·플랜 모드로 셋업·계획

코드를 한 줄도 바꾸기 전에, 안전하게 일할 환경부터 갖춥니다. 이 마일스톤은 단원 5(권한 c05·플랜 c06)와 단원 7(CLAUDE.md c08)의 적용입니다.

1) CLAUDE.md로 팀 규약을 영속화한다 (c08)

세션마다 "이 프로젝트는 어떻게 빌드하고 테스트하나요"를 다시 설명하지 않도록, 빌드·테스트 명령과 컨벤션을 CLAUDE.md에 적어 둡니다. /init로 골격을 만든 뒤 핵심만 간결하게 채웁니다.

markdown
# team-tasks-api

할 일(tasks)을 관리하는 작은 FastAPI 서비스입니다.

## 빌드·실행·테스트
- 의존성 설치: `python -m pip install -r requirements.txt`
- 개발 서버: `python -m uvicorn app.main:app --reload`
- 테스트: `python -m pytest -q`

## 코딩 컨벤션
- 들여쓰기 4칸, 타입 힌트 필수
- 엔드포인트는 `app/routers/`에, 데이터 보관은 `app/store.py`에 둔다
- 상태(status)는 `todo|done` 문자열 enum으로 표현한다

## 금지사항
- main 브랜치에 직접 커밋하지 않는다(작업 브랜치 + PR)
- 테스트가 통과하지 않은 변경은 커밋하지 않는다
  • 빌드·실행·테스트 명령을 가장 먼저 적었습니다. 에이전트가 "검증해 줘"라는 지시를 받으면 여기 적힌 python -m pytest -q를 그대로 쓰므로, 팀이 정한 검증 방식이 자동으로 통일됩니다.
  • 컨벤션에 "상태는 todo|done 문자열 enum"을 박아 두었습니다. 설계(ADR2)의 결정을 메모리에 영속화해, 이번 구현은 물론 다음 작업도 같은 규칙을 따르게 합니다.
  • 금지사항은 짧고 구체적입니다. "main에 직접 커밋 금지"가 곧 M4의 작업 브랜치 규칙으로 이어집니다. 길고 추상적인 규칙보다 검증 가능한 짧은 규칙이 잘 지켜집니다.

2) 최소 권한 settings.json을 둔다 (c05)

이번 작업에 필요한 안전한 명령(테스트·서버 실행·app/** 편집)만 허용하고, 파괴적 명령은 차단합니다. 프로젝트 공유 범위인 .claude/settings.json에 적어 체크인하면 팀 모두가 같은 안전 규칙을 공유합니다.

json
{
  "permissions": {
    "allow": [
      "Bash(python -m pytest:*)",
      "Bash(python -m uvicorn:*)",
      "Edit(app/**)",
      "Edit(tests/**)",
      "Bash(git status)",
      "Bash(git diff:*)",
      "Bash(git switch:*)",
      "Bash(git add:*)",
      "Bash(git commit:*)",
      "Bash(git push:*)",
      "Bash(gh pr create:*)"
    ],
    "deny": [
      "Bash(git push --force:*)",
      "Bash(git reset --hard:*)",
      "Bash(rm -rf:*)"
    ]
  }
}
  • Bash(python -m pytest:*)는 검증에 쓸 테스트 실행만, Edit(app/**)·Edit(tests/**)는 코드와 테스트 디렉터리 편집만 허용합니다. 이번 작업에 필요한 만큼만 여는 최소 권한 원칙입니다.
  • deny의 명령들은 역사를 파괴적으로 바꾸거나 파일을 지웁니다. deny가 allow보다 우선하므로, 실수로라도 강제 푸시·하드 리셋이 실행되지 않습니다.
  • 커밋·푸시·PR 명령을 미리 허용해 두면 M4에서 흐름이 끊기지 않습니다. 안전한 반복 작업은 허용하고, 위험한 변형만 콕 집어 막는 설계입니다.

3) 플랜 모드로 단계별 계획을 받아 검토·확정한다 (c06)

이제 Shift+Tab으로 플랜 모드(읽기 전용 계획 단계)에 들어가, 변경 계획을 먼저 받습니다. 코드를 바꾸지 않고 "어떻게 바꿀지"만 제안받아 검토하는 안전장치입니다.

text
나: (플랜 모드) @app/routers/tasks.py 와 @app/store.py 를 참고해서,
    PATCH /tasks/{task_id}/complete(완료 처리)와 GET /tasks?status= 필터를
    추가하려고 해. 기존 스타일을 따르고, 없는 id는 404·잘못된 status는 422로.
    바로 고치지 말고, 검증 가능한 단계로 나눈 구현 계획부터 세워 줘.

에이전트가 돌려준 계획을 검토합니다.

text
구현 계획(플랜):
1. app/models.py 에 Status(todo|done) enum을 추가하고 Task.status 필드에 적용
2. app/store.py 에 get_task·save_task 가 있는지 확인(없으면 추가)
3. tests/test_tasks.py 에 완료 처리·필터의 기대 동작 테스트를 먼저 작성(실패 확인)
4. app/routers/tasks.py 에 complete_task·list_tasks(status) 구현
5. python -m pytest -q 로 전체 통과 확인

이 계획에서 한 가지를 교정합니다. 설계에서 status는 처음부터 enum이었으므로 1번은 "추가"가 아니라 "확인·정리"가 맞습니다. 또 3번을 4번보다 앞에 두어 테스트 우선(TDD)을 분명히 합니다.

text

    1번은 그 정의를 확인·정리하는 것으로 하고, 테스트(3번)를 구현(4번)보다
    먼저 진행하는 순서를 지켜 줘. 이 계획으로 확정하자.

M1 체크포인트

다음을 모두 만족하면 M2로 넘어갑니다.

  • [ ] CLAUDE.md에 빌드·테스트 명령·컨벤션·금지사항이 들어 있는가
  • [ ] .claude/settings.json이 필요한 명령만 allow하고 파괴적 명령을 deny하는가
  • [ ] 플랜 모드로 받은 계획이 검증 가능한 단계로 나뉘고, 교정해 확정했는가

M2: 테스트 먼저(TDD) — 완료 처리·필터 테스트 작성

확정한 계획대로, 구현 전에 기대 동작을 테스트로 못 박습니다(c07 TDD). 이때 단원 3의 좋은 지시 네 요소(목표·맥락·제약·완료 조건, c03)를 그대로 씁니다.

text
나: 아직 엔드포인트는 구현하지 말고, tests/test_tasks.py 에 다음 기대 동작을
    검증하는 pytest 테스트부터 작성해 줘. fastapi TestClient 를 쓰고,
    각 테스트는 store 를 초기화한 상태에서 시작해야 해.
    - 완료 처리: PATCH /tasks/{id}/complete 하면 200 과 status=done 이 온다
    - 없는 id: PATCH /tasks/999/complete 는 404
    - 상태 필터: GET /tasks?status=done 은 done 인 항목만 돌려준다
    - 잘못된 status: GET /tasks?status=working 은 422
    작성한 뒤 pytest 로 돌려서, 구현이 없으니 실패하는 것을 먼저 보여 줘.

에이전트가 작성한 테스트 파일입니다.

python
# tests/test_tasks.py
import pytest
from fastapi.testclient import TestClient

from app import store
from app.main import app

client = TestClient(app)


@pytest.fixture(autouse=True)
def clear_store():
    # 테스트마다 저장소를 비워 서로 영향을 주지 않게 한다
    store.reset()
    yield
    store.reset()


def _seed_two_tasks():
    client.post("/tasks", json={"id": 1, "title": "온보딩 문서 읽기", "status": "todo"})
    client.post("/tasks", json={"id": 2, "title": "개발 환경 설정", "status": "done"})


def test_complete_task_sets_status_done():
    _seed_two_tasks()
    response = client.patch("/tasks/1/complete")
    assert response.status_code == 200
    assert response.json()["status"] == "done"


def test_complete_unknown_task_returns_404():
    _seed_two_tasks()
    response = client.patch("/tasks/999/complete")
    assert response.status_code == 404


def test_filter_done_returns_only_done():
    _seed_two_tasks()
    client.patch("/tasks/1/complete")  # 1번도 done 으로 만든다
    response = client.get("/tasks", params={"status": "done"})
    assert response.status_code == 200
    assert all(task["status"] == "done" for task in response.json())


def test_filter_invalid_status_returns_422():
    response = client.get("/tasks", params={"status": "working"})
    assert response.status_code == 422
  • @pytest.fixture(autouse=True)로 매 테스트 전후에 store.reset()을 호출합니다. 인메모리 저장소는 테스트 간에 데이터가 남을 수 있으므로, 격리해야 결과가 안정적입니다(설계의 인메모리 저장소 유지 결정에 맞춘 처리).
  • _seed_two_tasks()는 todo 1건·done 1건을 미리 넣는 보조 함수입니다. 같은 준비를 여러 테스트가 재사용해 중복을 줄입니다.
  • 네 테스트는 분석의 유스케이스·요구사항과 1:1로 대응합니다. 완료 처리(UC1·FR2), 없는 id(FR4의 404), 필터(UC2·FR3), 잘못된 status(FR4의 422). 요구사항이 곧 테스트가 되는 것이 TDD의 핵심입니다.
  • 아직 PATCH .../complete 라우트도, status 필터도 없으므로 이 테스트들은 지금 실패해야 정상입니다.

테스트를 먼저 돌려 "빨강"을 확인합니다.

왜 하나는 통과했을까 — 의미 있는 빨강과 우연한 초록

test_complete_unknown_task_returns_404가 통과(1 passed)한 점을 눈여겨보십시오. 아직 완료 처리 라우트가 없어 FastAPI가 경로를 못 찾아 404를 돌려주는데, 이 테스트가 기대하는 값도 마침 404라 우연히 통과한 것입니다. 즉 "없는 id라서 404"가 아니라 "라우트 자체가 없어서 404"입니다. 이것은 아직 의미 있는 검증이 아닙니다. M3에서 라우트를 구현한 뒤 이 테스트가 여전히 통과하는지 다시 봐야 비로소 "없는 id를 제대로 404로 처리한다"가 증명됩니다. 빨강·초록의 이유까지 읽는 것이 TDD를 제대로 쓰는 법입니다.

M2 체크포인트

  • [ ] 네 가지 기대 동작이 모두 테스트로 표현되었는가(요구사항 ↔ 테스트 매핑)
  • [ ] 테스트가 저장소를 초기화한 상태에서 시작하는가(격리)
  • [ ] 핵심 동작 테스트가 아직 실패(빨강)하는 것을 눈으로 확인했는가

M3: 엔드포인트 구현과 실행·테스트 검증

이제 빨강을 초록으로 바꿉니다. 에이전트 루프(c02)를 의식하며, "구현하고 pytest로 통과까지 확인해 줘"라고 검증을 지시의 일부로 못 박습니다(c07).

text

1) 데이터 모델: 상태 enum (models.py)

python
# app/models.py
from enum import Enum

from pydantic import BaseModel


class Status(str, Enum):
    todo = "todo"
    done = "done"


class Task(BaseModel):
    id: int
    title: str
    status: Status = Status.todo
  • class Status(str, Enum): 상태를 todo|done 문자열 enum으로 정의했습니다(ADR2). str을 함께 상속해, JSON으로 직렬화하면 "done" 같은 문자열로 나갑니다.
  • status: Status = Status.todo: 새 할 일의 기본 상태를 todo로 두었습니다. 불리언 done 대신 enum을 쓰면 나중에 in_progress 같은 상태를 확장하기 쉽습니다.
  • enum이라서 FastAPI가 잘못된 status 값(예: working)을 자동으로 422로 막아 줍니다. FR4의 422 요구를 모델 정의만으로 상당 부분 충족하는 지점입니다.

2) 저장소: 조회·저장 함수 (store.py)

python
# app/store.py
from app.models import Task

_tasks: dict[int, Task] = {}


def reset() -> None:
    """테스트 격리를 위해 저장소를 비웁니다."""
    _tasks.clear()


def add_task(task: Task) -> Task:
    _tasks[task.id] = task
    return task


def all_tasks() -> list[Task]:
    return list(_tasks.values())


def get_task(task_id: int) -> Task | None:
    return _tasks.get(task_id)


def save_task(task: Task) -> Task:
    _tasks[task.id] = task
    return task
  • get_task는 해당 id가 없으면 None을 돌려줍니다. 라우터는 이 None을 보고 404를 던집니다. "찾기"와 "에러 응답"의 책임을 분리한 구조입니다.
  • save_task는 변경된 할 일을 다시 저장합니다. 완료 처리는 상태만 바꾸므로 add_task와 동작이 같지만, 의도를 드러내려 이름을 나눴습니다.
  • 데이터베이스 없이 dict만 쓰는 인메모리 저장소를 유지했습니다(설계의 scope_out: DB 연동 제외). 범위를 작게 지키는 결정이 코드에도 그대로 반영됩니다.

3) 엔드포인트: 완료 처리·상태 필터 (routers/tasks.py)

python
# app/routers/tasks.py
from fastapi import APIRouter, HTTPException

from app import store
from app.models import Status, Task

router = APIRouter(prefix="/tasks", tags=["tasks"])


@router.post("", status_code=201)
def create_task(task: Task) -> Task:
    return store.add_task(task)


@router.get("")
def list_tasks(status: Status | None = None) -> list[Task]:
    tasks = store.all_tasks()
    if status is None:
        return tasks
    return [task for task in tasks if task.status == status]


@router.patch("/{task_id}/complete")
def complete_task(task_id: int) -> Task:
    task = store.get_task(task_id)
    if task is None:
        raise HTTPException(status_code=404, detail="task not found")
    task.status = Status.done
    return store.save_task(task)
  • def list_tasks(status: Status | None = None): 기존 목록 엔드포인트에 선택적 쿼리 파라미터 status를 더했습니다(ADR3). 기본값이 None이라 status를 안 주면 전체를 반환해, 기존 동작과 호환됩니다. enum 타입이라 working 같은 잘못된 값은 FastAPI가 422로 막습니다.
  • if status is None: return tasks: 필터가 없으면 전체를, 있으면 그 상태인 항목만 거릅니다. 한 엔드포인트가 "전체 조회"와 "필터 조회"를 모두 처리합니다.
  • @router.patch("/{task_id}/complete"): 부분 상태 변경이므로 PATCH를 썼습니다(ADR1). prefix="/tasks"와 합쳐져 실제 경로는 PATCH /tasks/{task_id}/complete입니다.
  • if task is None: raise HTTPException(status_code=404, ...): 없는 id를 404로 처리합니다. M2에서 "우연히" 통과하던 404 테스트가, 이제 라우트가 있는데도 id가 없어서 404를 내는 진짜 검증으로 바뀝니다.
  • task.status = Status.done: 완료 처리의 핵심 한 줄입니다. 상태만 바꾸고 다른 필드는 건드리지 않습니다.

모범 예시: 완료 취소(되돌리기) 엔드포인트를 TDD로 추가

후속 작업으로 "완료를 취소해 다시 todo로 되돌리는" PATCH /tasks/{id}/reopen을 TDD로 추가하는 모범입니다. 테스트를 먼저 쓰고(빨강), 구현해(초록) 통과시킵니다.

python
# tests/test_tasks.py (모범 — 테스트 먼저)
def test_reopen_task_sets_status_todo():
    client.post("/tasks", json={"id": 5, "title": "되돌릴 일", "status": "done"})
    response = client.patch("/tasks/5/reopen")
    assert response.status_code == 200
    assert response.json()["status"] == "todo"
python
# app/routers/tasks.py (모범 — 통과시키는 구현)
@router.patch("/{task_id}/reopen")
def reopen_task(task_id: int) -> Task:
    task = store.get_task(task_id)
    if task is None:
        raise HTTPException(status_code=404, detail="task not found")
    task.status = Status.todo
    return store.save_task(task)

완료 처리(complete_task)와 대칭 구조입니다. 상태를 done 대신 todo로 바꾸는 한 줄만 다릅니다.

team-tasks-api에서 자신이 실제로 진행한 마일스톤마다 무엇을 했는지, 어떤 단원 개념을 적용했는지 한 줄로 직접 작성하고, 체크포인트 통과 여부를 표시하세요(추측이 아니라 실제로 한 일을 적습니다).

흔한 함정과 점검

1. 마일스톤을 건너뛰고 한 번에 다 만든다

"빨리 끝내자"며 셋업·테스트 없이 곧장 구현·커밋·PR을 한 번에 진행하면, 어디서 잘못됐는지 좁히기 어렵고 리뷰어도 큰 덩어리를 한꺼번에 떠안습니다. 작게 나눠 한 걸음마다 통과를 확인하세요. 각 마일스톤의 체크포인트가 그 걸음을 검증합니다.

2. 테스트 없이 "동작하는 것 같다"로 PR을 올린다

서버에서 한 번 눌러 보고 PR을 올리면, 빈 목록·잘못된 입력·중복 호출 같은 경우는 검증되지 않은 채 남습니다. 요구사항을 테스트로 못 박고(M2), 그 통과 출력을 PR 본문의 근거로 붙이세요. "잘 됩니다"는 근거가 아닙니다.

3. 리뷰 지적을 무조건 반영하거나 무조건 방어한다

타당성을 따지지 않고 다 반영하면 불필요한 변경이 늘고, 무조건 방어하면 배울 기회를 잃습니다. 지적마다 반영·검증·근거 있는 반론을 구분하세요. 확인이 필요한 지적은 디버깅 루프(재현→검증)로 사실을 확인한 뒤, 회귀 테스트로 못 박아 답하면 됩니다.

이 챕터 한 줄 정리

첫 기능 구현은 "셋업·계획(M1) → 테스트 먼저(M2) → 구현·검증(M3) → 커밋·PR(M4) → 리뷰·디버깅(M5)"의 증분 마일스톤이며, 각 단계는 앞 단원 개념을 적용하고 체크포인트로 검증합니다. 다음 챕터(ch_16)에서는 이 산출물을 시연하고 루브릭으로 평가하며, 12개 개념을 어떻게 적용했는지 성찰합니다.
