실무

12장 더 나아가기(맛보기): 서브에이전트와 MCP

이 장은 단원 11 "더 나아가기(맛보기): 서브에이전트와 MCP"의 단일 챕터입니다. 여기서는 개념 자동화 맛보기: 서브에이전트와 MCP(a taste of automation: subagents and MCP) 하나를 다룹니다. 다만 이 개념 안에는 성격이 다른 두 도구, 서브에이전트(subagent)와 MCP(Model Context Protocol)가 들어 있으므로, 각각을 정의 → 동작 → 예제 → 오개념의 순서로 충실히 가르칩니다. 제목에 "맛보기"라고 적은 이유는, 깊은 설계와 운영은 온보딩 다음 단계의 몫으로 남기고 여기서는 "여기서 더 갈 수 있다"를 정확히 알게 하는 데 초점을 두기 때문입니다.

이 장의 학습 목표

  • 서브에이전트가 컨텍스트 격리·병렬 처리에 왜 유리한지 위임에 적합한 작업 예를 들어 설명할 수 있습니다.
  • .claude/agents에 역할·도구를 지정한 서브에이전트 정의 파일 1개를 작성해 작업을 위임할 수 있습니다.
  • MCP가 외부 도구·데이터를 어떻게 표준 프로토콜로 연결하는지 설명할 수 있습니다.
  • .mcp.json에 서버 1개를 등록하되 권한은 동일 체계로 통제하고 토큰은 환경으로 주입하는 비밀 관리 원칙에 맞게 작성할 수 있습니다.

12.1 도입: 온보딩 이후, 어디로 더 갈 수 있나

여기까지 오느라 수고했습니다. 1장에서 Claude Code를 설치한 뒤, 에이전트 루프를 이해하고(2장), 명확히 지시하고(3장), 낯선 코드를 파악하고(4장), 안전하게 변경하고(5·6장), 실행·테스트로 검증하고(7장), 팀 규약을 주입하고(8장), 첫 커밋과 첫 PR을 올리고(9장), 리뷰에 대응하고(10장), 막힘을 디버깅으로 풀었습니다(11장). 이제 여러분은 한 사람의 팀원으로서 첫 기능을 끝까지 끌고 갈 수 있습니다.

그런데 익숙해지면 새로운 답답함이 보이기 시작합니다. 긴 작업을 하다 보면 메인 대화에 테스트 로그·리뷰 코멘트·조사 메모가 뒤섞여 맥락이 어지러워집니다. 또 팀이 쓰는 GitHub 이슈나 사내 문서를 매번 손으로 복사해 에이전트에게 붙여 넣는 일이 반복됩니다. 이 두 가지 답답함을 푸는 다음 단계가 바로 이 장의 두 도구입니다.

선수 개념 한 줄 상기. 이 장은 9장의 git 워크플로(개념 c09)를 선수로 둡니다. 서브에이전트에 "테스트 실행"이나 "리뷰" 같은 작업을 위임한다는 발상은, 여러분이 이미 그 작업들(검증·커밋·PR·리뷰 대응)을 손으로 해 봤기에 이해됩니다. 해 본 일을 자동화로 넘기는 것이지, 모르는 일을 떠넘기는 것이 아닙니다.

  • 서브에이전트는 "이 경계가 분명한 작업은 별도의 일꾼에게 맡기자"는 발상입니다. 테스트 실행, 코드 리뷰, 조사처럼 독립적으로 떼어 낼 수 있는 일을 자체 컨텍스트와 도구를 가진 별도 세션에 위임합니다.
  • MCP는 "외부 서비스를 표준 방식으로 연결하자"는 발상입니다. GitHub·데이터베이스·사내 문서 같은 외부 도구·데이터를 매번 복사해 붙이지 않고, 정해진 프로토콜로 에이전트에 이어 줍니다.

이 장은 맛보기입니다. 두 도구의 정의·동작·기본 사용법과, 신입이 흔히 빠지는 오해를 정확히 짚는 데까지만 갑니다. 본격적인 다중 에이전트 오케스트레이션이나 MCP 서버 직접 개발은 이 책의 범위를 넘어서며, 다음 학습 단계에서 다룰 주제입니다.

12.2 서브에이전트란: 독립 컨텍스트·프롬프트·도구

정의. 서브에이전트(subagent)란 메인 세션과 분리된, 자체 컨텍스트·시스템 프롬프트·도구 권한을 가진 별도의 에이전트입니다. .claude/agents/ 폴더에 마크다운 파일(YAML 프런트매터 + 본문)로 정의하며, 코드 리뷰·테스트 실행·조사처럼 경계가 분명한 작업을 위임받아 독립적으로 수행한 뒤 결과 요약만 메인 세션에 돌려줍니다.

핵심 용어를 한글(영문)으로 정리합니다.

  • 컨텍스트(context, 맥락): 에이전트가 현재 들고 있는 대화·파일·도구 호출 기록의 묶음입니다. 길어질수록 무거워지고 잡음이 섞입니다.
  • 컨텍스트 격리(context isolation): 서브에이전트가 자기만의 별도 컨텍스트를 가지므로, 그 안에서 무슨 일이 오가든 메인 세션의 맥락을 어지럽히지 않는 성질입니다.
  • 위임(delegation): 메인 에이전트가 특정 작업을 서브에이전트에 넘겨 처리하게 하는 것입니다.
  • 병렬 처리(parallelism): 서로 독립적인 작업을 여러 서브에이전트가 동시에 처리하는 것입니다.

서브에이전트가 일반적인 "프롬프트로 부탁하기"와 다른 점을 표로 못 박습니다.

구분 메인 세션에 그냥 부탁 서브에이전트에 위임
컨텍스트 모든 대화·로그가 한곳에 쌓임 작업별 별도 컨텍스트(격리)
시스템 프롬프트 하나(공통) 작업에 특화된 별도 프롬프트
도구 권한 세션 전체 권한 그 작업에 필요한 도구만 좁혀 부여 가능
결과 과정·로그가 메인에 다 남음 결과 요약만 메인에 돌려줌
동시성 순차 처리 독립 작업은 병렬 가능

쉽게 비유하면, 메인 에이전트는 여러분 자신이고 서브에이전트는 특정 일을 맡긴 전담 동료입니다. "테스트만 돌려 결과를 알려 줘", "이 PR만 리뷰해 줘"처럼 명확한 임무를 주면, 그 동료는 자기 책상(별도 컨텍스트)에서 일하고 결과만 보고합니다. 여러분의 책상(메인 세션)은 그동안 깔끔하게 유지됩니다.

12.3 동작 원리: 위임·컨텍스트 격리·병렬 처리

서브에이전트가 어떻게 동작하는지 단계로 따라가 봅니다.

  1. 정의. .claude/agents/이름.md 파일에 서브에이전트를 정의합니다. YAML 프런트매터에 이름(name)·설명(description)·사용할 도구(tools)를 적고, 본문에 그 에이전트의 역할을 지시하는 시스템 프롬프트를 씁니다.
  2. 위임 판단. 메인 에이전트는 작업이 어떤 서브에이전트의 description에 맞는지 보고 위임할지 결정합니다. 여러분이 명시적으로 "test-runner 서브에이전트로 테스트를 돌려 줘"라고 호출할 수도 있습니다.
  3. 격리된 실행. 서브에이전트는 자기만의 빈 컨텍스트에서 시작합니다. 메인 세션의 긴 대화를 물려받지 않으므로, 메인은 필요한 맥락(예: "어떤 테스트 파일을 돌릴지")을 명시해 넘겨야 합니다. 서브에이전트는 부여받은 도구만 써서 작업합니다.
  4. 결과 반환. 서브에이전트는 작업을 마치면 결과 요약만 메인 세션에 돌려줍니다. 중간 과정의 수많은 도구 호출·로그는 서브에이전트의 컨텍스트에 남고 메인을 더럽히지 않습니다.
  5. 병렬화(선택). 서로 독립적인 작업이라면 여러 서브에이전트를 동시에 돌려 시간을 절약할 수 있습니다.

이 흐름에서 서브에이전트의 두 가지 이점이 나옵니다.

  • 컨텍스트 격리의 이점. 메인 세션이 깨끗하게 유지됩니다. 테스트 로그 수백 줄이 메인에 쌓이면 이후 작업의 품질이 떨어지지만, 서브에이전트가 그 로그를 자기 안에서 소화하고 "3건 실패, 원인은 X"라는 요약만 돌려주면 메인은 가볍게 유지됩니다.
  • 병렬 처리의 이점. "테스트 실행"과 "보안 점검"처럼 서로 무관한 두 작업을 동시에 진행해 대기 시간을 줄일 수 있습니다.

언제 서브에이전트가 어울리나요? 경계가 분명하고, 메인 대화의 세세한 맥락이 없어도 수행할 수 있으며, 결과를 요약으로 받으면 충분한 작업이 좋은 후보입니다. 테스트 실행, 코드 리뷰, 특정 주제 조사가 대표적입니다. 반대로, 메인의 흐름과 긴밀히 얽혀 한 줄씩 협의해야 하는 작업은 굳이 위임하지 않는 편이 낫습니다.

12.4 worked example: 테스트 실행 서브에이전트 정의·호출

말로만 들으면 막연하니, 실제로 테스트 실행을 맡는 서브에이전트를 하나 만들어 봅니다. 목표는 "긴 pytest 로그를 메인에 쌓지 않고, 별도 컨텍스트에서 테스트를 돌려 결과 요약만 받기"입니다.

서브에이전트는 프로젝트 루트의 .claude/agents/ 폴더에 마크다운 파일로 정의합니다. 파일 위쪽의 YAML 프런트매터에 메타데이터를 적고, 아래 본문에 역할을 지시합니다. 다음은 test-runner 서브에이전트의 정의 파일입니다.

yaml
---
name: test-runner
description: pytest를 실행하고 실패한 테스트와 원인을 간결히 요약합니다. 변경 후 테스트 검증이 필요할 때 사용하세요.
tools: Read, Grep, Bash
model: sonnet
---
당신은 테스트 실행 전담 에이전트입니다. 다음 절차를 따르세요.

1. 지시받은 테스트 대상(파일 또는 전체)을 python -m pytest 로 실행합니다.
2. 전체 통과면 "모두 통과(N건)"로 한 줄 보고합니다.
3. 실패가 있으면 실패한 테스트 이름, 핵심 에러 메시지, 추정 원인 위치(파일·줄)만 간결히 정리합니다.
4. 코드를 직접 수정하지 않습니다. 진단과 보고까지만 합니다.
  • name: test-runner: 서브에이전트의 식별자입니다. 메인 세션에서 이 이름으로 호출합니다.
  • description: 이 에이전트가 무엇을 하고 언제 쓰는지를 적습니다. 메인 에이전트는 이 설명을 보고 위임 여부를 판단하므로, 용도를 구체적으로 적는 것이 중요합니다.
  • tools: Read, Grep, Bash: 이 작업에 필요한 도구만 부여했습니다. 테스트를 읽고(Read), 검색하고(Grep), 실행(Bash)하면 충분합니다. Edit·Write를 주지 않았으므로 이 에이전트는 코드를 바꿀 수 없습니다(역할을 진단·보고로 좁힘).
  • model: sonnet: 사용할 모델을 지정합니다. 생략하면 기본 모델을 따릅니다.
  • 본문: YAML 아래 본문은 이 서브에이전트의 시스템 프롬프트입니다. 절차와 금지사항("코드를 직접 수정하지 않습니다")을 명시해 역할을 분명히 했습니다.

이 파일을 저장하면 서브에이전트가 등록됩니다. 메인 세션에서는 다음처럼 호출합니다.

console
> test-runner 서브에이전트로 tests/ 전체를 돌려 결과를 요약해 줘

서브에이전트는 자기 컨텍스트에서 python -m pytest를 돌리고, 수백 줄의 로그를 자기 안에서 소화한 뒤, 메인에는 다음과 같은 요약만 돌려줍니다.

text
모두 통과(7건). 실패 없음. 소요 0.3s.

만약 실패가 있었다면(예: 11장 미니 프로젝트에서 store.py에 심은 상태 버그가 남아 있다면) 다음처럼 핵심만 보고합니다.

text
7건 중 2건 실패.
- 실패: tests/test_tasks.py::TestListTasks::test_list_after_create 외 1건
- 에러: assert 'done' == 'todo'
- 추정 원인: store.py 의 create_task 가 새 할 일 상태를 todo 가 아닌 done 으로 설정

메인 세션에는 이 요약만 남고, 장황한 pytest 출력은 서브에이전트의 컨텍스트에 머뭅니다. 이것이 컨텍스트 격리의 실제 효과입니다. 메인은 가벼운 상태로 다음 작업(예: 수정)을 이어 갈 수 있습니다.

맥락은 물려받지 않습니다. 서브에이전트는 빈 컨텍스트에서 시작하므로, 메인 대화에서 방금 논의한 내용을 알지 못합니다. "방금 그 버그"처럼 메인 맥락에 의존하는 지시는 통하지 않습니다. "tests/test_tasks_api.py를 돌려 줘"처럼 필요한 정보를 명시해 위임해야 합니다.

12.5 정의 파일: YAML 프런트매터(name·description·tools)

서브에이전트 정의 파일의 형식을 한 번 더 정리합니다. 파일은 두 부분으로 나뉩니다. 위쪽의 YAML 프런트매터(세 개의 하이픈 --- 사이)는 메타데이터이고, 아래쪽 본문은 시스템 프롬프트입니다.

필드 필수 여부 역할
name 필수 서브에이전트 식별자(호출에 사용)
description 필수 무엇을 하고 언제 쓰는지 — 위임 판단 근거
tools 선택 부여할 도구 목록(생략 시 기본 도구 상속)
model 선택 사용할 모델(생략 시 기본값)

저장 위치도 두 가지로 나뉩니다. 권한 범위(5장)와 같은 발상입니다.

  • 프로젝트 범위 .claude/agents/: 그 저장소에 한정되며 git으로 팀과 공유됩니다. 팀 공통 작업(테스트·리뷰)은 여기에 둡니다.
  • 사용자 범위 ~/.claude/agents/: 모든 프로젝트에서 쓸 수 있는 개인 서브에이전트입니다.

description을 구체적으로 쓰세요. 메인 에이전트가 "이 작업을 어느 서브에이전트에 맡길까"를 판단하는 근거가 바로 description입니다. "테스트 관련"처럼 막연하면 엉뚱하게 위임되거나 위임되지 않습니다. "pytest를 실행하고 실패 원인을 요약합니다. 변경 후 검증이 필요할 때 사용"처럼 무엇을·언제를 함께 적으세요. 3장에서 배운 "명확한 지시"의 원칙이 여기에도 그대로 적용됩니다.

12.6 MCP란: 외부 통합을 위한 표준 프로토콜

이제 두 번째 도구로 넘어갑니다.

정의. MCP(Model Context Protocol, 모델 컨텍스트 프로토콜)란 Claude Code 같은 AI 도구를 GitHub·데이터베이스·문서 같은 외부 서비스에 잇는 표준 프로토콜입니다. .mcp.json에 MCP 서버를 등록하면, 그 서버가 노출한 도구·리소스를 Claude Code가 기존과 동일한 권한 체계 안에서 사용할 수 있고, 인증 토큰 같은 비밀은 코드가 아니라 환경 변수로 안전하게 주입합니다.

핵심 용어를 한글(영문)으로 정리합니다.

  • 프로토콜(protocol, 표준 규약): 서로 다른 프로그램이 같은 방식으로 대화하기로 정한 약속입니다. USB 단자처럼, 한 번 표준을 따르면 여러 서비스를 같은 방식으로 꽂을 수 있습니다.
  • MCP 서버(MCP server): 외부 서비스(예: GitHub) 앞에 서서, 그 기능을 MCP 표준으로 노출하는 중개 프로그램입니다.
  • 도구·리소스(tools and resources): MCP 서버가 노출하는 기능(예: "이슈 목록 가져오기")과 데이터(예: "문서 본문")입니다.

MCP의 가치는 표준화에 있습니다. MCP가 없다면 GitHub용 연동, 사내 문서용 연동, 데이터베이스용 연동을 각각 다른 방식으로 만들어야 합니다. MCP는 이 모두를 하나의 규약으로 통일합니다. 그래서 새로운 외부 서비스를 붙이고 싶을 때, 그 서비스의 MCP 서버만 .mcp.json에 등록하면 Claude Code가 같은 방식으로 그 도구들을 쓸 수 있습니다.

구분 MCP 없이 MCP로
외부 자료 주입 매번 손으로 복사·붙여넣기 서버 등록 후 에이전트가 직접 조회
연동 방식 서비스마다 제각각 하나의 표준 프로토콜
권한 별도 관리 필요 Claude Code의 동일 권한 체계
확장 통합마다 새로 개발 서버만 추가 등록

12.7 worked example: 문서 MCP 서버를 .mcp.json에 등록·참조

팀이 사내 문서를 제공하는 MCP 서버를 운영한다고 합시다. 매번 문서를 복사해 붙이는 대신, 이 서버를 등록해 에이전트가 직접 문서를 참조하게 만들어 봅니다.

MCP 서버는 두 가지 방법으로 등록할 수 있습니다. 하나는 claude mcp add 명령으로 등록하는 것이고, 다른 하나는 .mcp.json 파일을 직접 작성하는 것입니다. 먼저 명령으로 등록하는 방법입니다.

bash
claude mcp add docs --scope project -- npx -y @example/docs-mcp-server

--scope project는 이 서버 등록을 프로젝트 범위의 .mcp.json에 기록해 팀과 공유한다는 뜻입니다. 범위는 서브에이전트·권한과 같은 세 종류입니다. 로컬(나만, 현재 프로젝트), 프로젝트(팀 공유, .mcp.json), 사용자(내 모든 프로젝트)입니다. 이 명령은 결국 다음과 같은 .mcp.json을 만듭니다(직접 작성해도 동일합니다).

json
{
  "mcpServers": {
    "docs": {
      "command": "npx",
      "args": ["-y", "@example/docs-mcp-server"],
      "env": {
        "DOCS_API_TOKEN": "${DOCS_API_TOKEN}"
      }
    }
  }
}
  • "mcpServers": 등록할 MCP 서버들을 담는 최상위 키입니다. 여러 서버를 나란히 등록할 수 있습니다.
  • "docs": 이 서버에 붙인 이름입니다. 에이전트가 이 서버의 도구를 쓸 때 이 이름을 씁니다.
  • "command"·"args": 서버를 실행하는 명령과 인자입니다. 여기서는 npx로 문서 MCP 서버 패키지를 실행합니다.
  • "env": 서버에 전달할 환경 변수입니다. ${DOCS_API_TOKEN} 은 토큰 값을 파일에 직접 쓰지 않고, 실행 시점에 환경 변수에서 값을 가져오라는 표기입니다. 토큰 자체는 .mcp.json에 절대 적지 않습니다.

토큰은 셸 환경 변수로 따로 설정합니다. 예를 들어 PowerShell에서는 세션 환경 변수로 두거나, 운영체제의 환경 변수에 등록합니다. 핵심은 비밀 값이 .mcp.json(그리고 git)에 들어가지 않는다는 것입니다.

등록이 끝나면 메인 세션에서 그 서버의 도구를 쓸 수 있습니다. 예를 들어 다음처럼 지시합니다.

console
> docs 서버에서 "배포 절차" 문서를 찾아 핵심 단계를 요약해 줘

이제 에이전트는 문서를 손으로 붙여 넣지 않아도 docs 서버를 통해 직접 조회해 답합니다. /mcp 명령으로 현재 연결된 MCP 서버와 그 상태를 확인할 수 있습니다.

아무 MCP 서버나 붙이지 마세요. MCP 서버는 외부 코드를 실행하고 외부 서비스에 접근합니다. 신뢰할 수 있는 제공자의 서버만 등록하고, 팀이 공유하는 프로젝트 범위(.mcp.json)에 넣을 때는 동료와 합의하세요. 출처가 불분명한 서버는 권한·데이터 위험이 있습니다.

12.8 권한·비밀 관리: 동일 권한 체계·토큰은 환경으로

서브에이전트와 MCP를 맛본 신입이 가장 먼저 챙겨야 할 것은 안전입니다. 두 도구 모두 5장에서 배운 권한 체계의 연장선에 있습니다. 새로운 예외가 아닙니다.

  • MCP 도구도 같은 권한 체계 안에 있습니다. MCP 서버가 더한 도구라고 해서 권한 밖에서 멋대로 동작하지 않습니다. Claude Code는 그 도구들도 기존 allow·deny·ask 판정으로 통제합니다. 외부 서비스에 쓰기·삭제 같은 부수효과를 일으키는 도구라면, 5장의 최소 권한 원칙대로 신중히 허용하세요.
  • 토큰·비밀은 코드가 아니라 환경으로. 인증 토큰을 .mcp.json에 직접 적으면, 그것이 git에 올라가 유출됩니다. 반드시 ${TOKEN_NAME} 표기로 환경 변수를 참조하고, 실제 값은 셸 환경 변수나 운영체제 환경 변수로 둡니다. 이것은 9장에서 배운 "비밀은 커밋하지 않는다"의 연장입니다.
  • 서브에이전트의 도구도 좁힙니다. 12.4에서 test-runner에 Edit·Write를 주지 않은 것처럼, 서브에이전트에는 그 역할에 필요한 도구만 부여합니다. 진단만 하는 에이전트에 편집 권한을 줄 이유가 없습니다.

한 줄 원칙. "새 도구가 늘어도 안전의 기본은 그대로다 — 최소 권한, 비밀은 환경으로." 서브에이전트와 MCP는 능력을 넓혀 주지만, 5장에서 배운 안전 원칙을 면제해 주지 않습니다. 오히려 외부와 닿는 만큼 더 엄격히 적용해야 합니다.

12.9 즉시 연습(2종 1세트)과 단원 미니 프로젝트

이 단원은 단일 챕터이므로, 즉시 연습과 단원 미니 프로젝트를 여기서 함께 진행합니다.

연습 (모범): 리뷰 서브에이전트 정의

다음은 코드 리뷰를 맡는 서브에이전트의 모범 정의입니다. 역할에 맞게 도구를 좁히고, description에 용도를 구체적으로 적었습니다.

yaml
---
name: pr-reviewer
description: 변경(diff)을 읽고 버그·중복·단순화 지점을 짚어 인라인 형식으로 보고합니다. PR을 올리기 전 자가 점검에 사용하세요.
tools: Read, Grep, Bash
model: sonnet
---
당신은 코드 리뷰 전담 에이전트입니다. git diff 를 읽고 버그 가능성,
중복, 단순화 여지를 항목별로 짚되, 코드를 직접 수정하지 않고 보고만 합니다.

연습 (직접 해보기): team-tasks-api에 서브에이전트·MCP를 실제로 구성하기

종이에 빈칸을 채우는 대신, 1장에서 준비한 실제 team-tasks-api 저장소에서 서브에이전트를 직접 정의해 호출하고, MCP 서버를 등록해 연결을 확인합니다. 핵심은 추측한 YAML이 아니라 화면에 실제로 나타난 호출 결과·/mcp 출력을 그대로 옮기는 것입니다.

과제 A — 서브에이전트를 실제로 정의하고 호출하라. team-tasks-api 루트에 .claude/agents/dep-checker.md(또는 경계가 분명한 다른 작업) 파일을 직접 만드세요. tools는 역할에 필요한 것만으로 좁힙니다(예: 의존성 점검에는 Read, Grep, Bash만, Edit·Write는 빼기).

yaml
---
name: dep-checker
description: requirements.txt와 import를 대조해 빠진/불필요한 의존성을 보고합니다. 의존성 점검이 필요할 때 사용하세요.
tools: Read, Grep, Bash
---
당신은 의존성 점검 전담 에이전트입니다. requirements.txt와 코드의 import를
대조해 불일치를 항목별로 보고하되, 코드를 직접 수정하지 않고 보고만 합니다.

파일을 만든 뒤 claude 세션에서 "dep-checker 서브에이전트로 이 프로젝트의 의존성을 점검해 줘"라고 실제로 호출하고, 메인 세션에 무엇이 남는지 확인해 옮겨 적으세요.

text
[실제 호출 결과] 서브에이전트가 보고한 내용(화면 그대로):
[컨텍스트 격리] 메인에 긴 로그가 쌓였는가, 요약만 남았는가:

과제 B — MCP 서버를 실제로 등록하고 연결을 확인하라. 같은 저장소에서 외부 서비스 하나(문서·이슈 트래커 등)를 .mcp.json에 등록하세요. 토큰은 직접 적지 말고 환경 변수 표기(${...})를 씁니다.

json
{
  "mcpServers": {
    "docs": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-everything"],
      "env": {
        "API_TOKEN": "${DOCS_API_TOKEN}"
      }
    }
  }
}

등록한 뒤 /mcp를 실행해 연결 상태를 확인하고, 화면에 실제로 나타난 결과를 옮겨 적으세요.

text
[/mcp 실제 출력] 서버가 연결됐는가(상태):
[비밀 점검] .mcp.json에 실제 토큰 값이 없고 ${...} 참조만 있는가:

자가체크 — 머리로가 아니라 손으로 했는지 확인하세요.

  • [ ] .claude/agents/에 서브에이전트 정의 파일을 실제로 만들고 호출까지 했다.
  • [ ] [실제 호출 결과]에 적은 것이 추측이 아니라 화면에 나타난 서브에이전트 보고다.
  • [ ] 메인 세션에 긴 로그가 아니라 요약만 남는 컨텍스트 격리를 직접 확인했다.
  • [ ] 서브에이전트 tools를 역할에 필요한 것만으로 좁혔다(불필요한 Edit·Write 배제).
  • [ ] .mcp.json을 실제로 작성하고 /mcp로 연결 상태를 확인했다.
  • [ ] .mcp.json에 토큰 값을 직접 적지 않고 ${...} 환경 변수 표기만 썼다.

단원 미니 프로젝트 (모범): 위임과 외부 연동 맛보기

이 단원 개념만으로 완성하는 작은 산출물입니다. 이번 과제는 1장에서 준비한 실제 team-tasks-api 저장소 안에서 서브에이전트와 MCP를 직접 구성해 봅니다. 마일스톤을 증분으로 진행합니다.

  • M1 테스트 서브에이전트 정의·호출. team-tasks-api 루트에 .claude/agents/test-runner.md를 작성하고(앞 12.4의 정의 그대로 써도 됩니다), 메인 세션에서 "test-runner 서브에이전트로 tests/ 전체를 돌려 결과를 요약해 줘"라고 호출합니다. 메인에는 긴 pytest 로그가 아니라 결과 요약만 남는 것을 확인합니다. (적용 개념: 서브에이전트, 컨텍스트 격리, 도구 좁히기)
  • M2 MCP 서버 등록. 같은 저장소에서 문서 또는 이슈 MCP 서버를 .mcp.json에 등록하고(claude mcp add ... --scope project), 토큰을 환경 변수로 분리합니다. /mcp로 연결을 확인합니다. (적용 개념: MCP 등록, 비밀은 환경으로)
  • M3 안전 점검. 서브에이전트의 도구가 역할에 맞게 좁혀졌는지(test-runner에 Edit·Write 미부여), .mcp.json에 비밀이 직접 들어 있지 않은지 점검합니다. (적용 개념: 동일 권한 체계, 최소 권한)

실제 검증 단계. M1에서 서브에이전트가 돌린 결과가 실제 저장소 상태와 일치하는지, 직접 python -m pytest -q를 돌려 대조합니다. 기본 상태라면 서브에이전트 요약과 직접 실행이 모두 같은 결과여야 합니다.

console
> python -m pytest -q
.......                                                                  [100%]
7 passed

체크포인트: M1은 "메인에 요약만 남고 긴 로그가 안 쌓임 + 서브에이전트 요약이 직접 실행한 7 passed와 일치", M2는 "/mcp에 서버가 연결됨 + 토큰이 파일에 없음", M3은 "불필요한 권한·노출된 비밀 0건"입니다.

단원 미니 프로젝트 (학생 작성형 빈 스타터)

직접 작성·실행. 추측을 적지 말고, team-tasks-api에서 위임 + 외부 연동을 실제로 구성·호출한 뒤 화면에 나타난 것을 그대로 옮겨 적으세요.

text
1. [위임 작업 정하기] 내가 정한 위임 작업(경계가 분명한가? 메인 맥락 없이 가능한가?):
2. [서브에이전트 실제 작성] 내가 만든 .claude/agents/ 파일 경로 / name / 좁힌 tools:
   [실제 호출 결과] 메인 세션에서 호출했을 때 화면에 남은 서브에이전트 요약(긴 로그가 아니라 요약만 남았는가?):
3. [MCP 실제 등록] 등록한 외부 서비스 / .mcp.json의 서버 이름 / 토큰 환경 변수 이름(${...}):
   [/mcp 실제 출력] 서버 연결 상태:
4. [호출 지시문] 내가 실제로 준 호출 지시 한 줄과 그 결과:

자가체크

  • [ ] 위임 작업이 경계가 분명하고 메인 맥락 없이도 수행 가능한가
  • [ ] 서브에이전트에게 필요한 맥락(어떤 파일·범위)을 지시에 명시했는가
  • [ ] 서브에이전트 도구를 최소로 좁혔는가
  • [ ] .mcp.json에 실제 토큰 값이 들어 있지 않은가(환경 변수 참조만)
  • [ ] /mcp로 서버 연결 상태를 확인했는가

12.10 흔한 오류와 오개념

오개념 1: 서브에이전트는 메인 세션의 맥락을 그대로 물려받는다. 서브에이전트는 빈 컨텍스트에서 시작합니다. 메인 대화에서 방금 논의한 "그 버그", "아까 그 파일"을 알지 못합니다. 그래서 "방금 그거 고쳐 줘" 같은 지시는 통하지 않습니다. 위임할 때는 "tests/test_tasks_api.py를 돌려 줘"처럼 필요한 맥락을 명시해야 합니다. 컨텍스트 격리는 장점(메인이 깨끗함)인 동시에, 맥락을 직접 넘겨야 하는 책임이기도 합니다.

오개념 2: MCP는 잡다한 플러그인을 마구 꽂는 난립이다. MCP는 난립이 아니라 그 반대입니다. 서비스마다 제각각이던 연동을 하나의 표준 프로토콜로 통일해 통합을 캡슐화합니다. USB 단자처럼, 표준을 따르므로 여러 서비스를 같은 방식으로 꽂고 같은 권한 체계로 통제합니다. 다만 표준이라 해도 신뢰할 수 있는 서버만 등록해야 한다는 점은 변하지 않습니다.

오개념 3: MCP가 더한 도구는 권한 밖에서 자유롭게 동작한다. MCP 서버가 노출한 도구도 Claude Code의 동일한 권한 체계(5장의 allow·deny·ask) 안에서 통제됩니다. 외부 서비스에 쓰기·삭제를 일으키는 도구라면 최소 권한 원칙대로 신중히 허용하세요. 그리고 인증 토큰은 절대 .mcp.json에 직접 적지 말고 ${TOKEN} 환경 변수로 주입해, git에 비밀이 올라가지 않게 합니다.

오개념 4: 모든 작업을 서브에이전트로 위임하면 더 빠르다. 서브에이전트는 경계가 분명하고 결과를 요약으로 받으면 충분한 작업에 어울립니다. 메인의 흐름과 긴밀히 얽혀 한 줄씩 협의해야 하는 작업까지 위임하면, 맥락을 넘기는 비용이 오히려 더 큽니다. 위임은 도구이지 만능이 아닙니다. "이 일이 독립적으로 떼어 낼 수 있는가"를 먼저 판단하세요.

12.11 자주 묻는 질문(FAQ)

Q. 서브에이전트와 그냥 새 세션을 여는 것은 무엇이 다른가요? 새 세션을 직접 열면 여러분이 그 창을 오가며 관리해야 하고, 결과를 손으로 메인에 옮겨야 합니다. 서브에이전트는 메인 에이전트가 자동으로 위임하고 결과 요약만 돌려받습니다. 또 description·tools로 역할과 권한을 미리 못 박아 둘 수 있어, 매번 같은 작업을 일관되게 맡길 수 있습니다.

Q. 서브에이전트는 메인보다 똑똑한가요? 아닙니다. 똑똑함의 문제가 아니라 분업과 격리의 문제입니다. 서브에이전트의 이점은 별도 컨텍스트로 메인을 깨끗이 유지하고, 독립 작업을 병렬로 처리하며, 역할에 맞게 도구를 좁힐 수 있다는 데 있습니다. model 필드로 어떤 모델을 쓸지 정할 수는 있지만, 핵심 가치는 능력이 아니라 구조입니다.

Q. MCP 서버는 직접 만들어야 하나요? 이 단원(맛보기) 수준에서는 만들 필요가 없습니다. 많은 서비스가 이미 MCP 서버를 제공하므로, claude mcp add나 .mcp.json 등록으로 가져다 쓰기만 하면 됩니다. 서버를 직접 개발하는 것은 다음 학습 단계의 주제입니다.

Q. .mcp.json을 git에 올려도 되나요? 프로젝트 범위의 .mcp.json은 팀과 공유하려고 올리는 파일입니다. 단, 토큰 같은 비밀이 그 안에 없을 때만 안전합니다. 비밀은 항상 ${TOKEN} 환경 변수 표기로 두고 실제 값은 각자의 환경에 둡니다. 이렇게 하면 설정은 공유하되 비밀은 유출되지 않습니다.

Q. 여기서 배운 것으로 충분한가요? 이 장은 의도적으로 "맛보기"입니다. 두 도구가 무엇이고 어떻게 시작하는지, 그리고 안전의 기본을 정확히 아는 것까지가 목표입니다. 다중 에이전트 오케스트레이션, MCP 서버 개발, 훅을 통한 자동화 강제 같은 심화 주제는 온보딩을 마친 뒤 별도로 익히면 됩니다.

12.12 정리: 온보딩을 마치며

이 장에서 우리는 온보딩 이후로 나아갈 두 도구를 맛봤습니다. 서브에이전트는 경계가 분명한 작업을 별도 컨텍스트·도구를 가진 일꾼에게 위임해, 메인 세션을 깨끗이 유지하고 병렬 처리까지 가능하게 합니다. MCP는 외부 도구·데이터를 표준 프로토콜로 연결해, 매번 복사·붙여넣기 하던 외부 자료를 에이전트가 직접 다루게 합니다. 두 도구 모두 5장의 안전 원칙(동일 권한 체계·최소 권한·비밀은 환경으로)을 그대로 따릅니다.

이로써 12개 개념을 모두 배웠습니다. 첫날 설치부터 코드베이스 파악, 안전한 변경, 검증, 팀 규약, 첫 PR, 리뷰 대응, 디버깅, 그리고 자동화의 맛보기까지. 다음 장부터는 이 모든 개념을 하나로 모아, 기존 팀 FastAPI 저장소에 첫 기능을 추가하고 첫 PR을 올리는 종합 프로젝트를 분석 → 설계 → 구현 → 발표·성찰의 단계로 진행합니다. 여기서 배운 것을 진짜 첫 업무에서 통합해 적용할 차례입니다.
