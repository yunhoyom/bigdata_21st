Chapter 07

실행·테스트로 검증하기

중급

실행·테스트로 검증하기

학습 목표

  • 에이전트가 만든 변경을 실제로 실행하게 지시해, 그 실행 결과를 근거로 의도대로 동작하는지 확인할 수 있습니다.
  • 추가·수정한 엔드포인트에 대해 에이전트에게 pytest(파이테스트) 테스트를 작성·실행시켜, 통과 로그를 근거로 동작을 증명할 수 있습니다.
  • 구현 전에 통과해야 할 테스트를 먼저 작성하게 해 완료 조건을 세우고(TDD, 테스트 주도 개발), 그 테스트를 통과하도록 구현을 유도할 수 있습니다.
  • 실패한 테스트의 메시지를 근거로 원인을 짚어, 회귀 없이 통과시키는 최소 수정을 요청할 수 있습니다.

지금까지 우리는 신입으로서 안전하게 일하는 토대를 차곡차곡 쌓았습니다. 5단원에서 권한(c05)으로 무엇을 허용할지 통제했고, 같은 단원의 플랜 모드(c06)로 바꾸기 전에 계획을 먼저 받아 검토했습니다. 그렇게 계획을 승인하고 실행에 들어가면, 에이전트는 파일을 고치고 새 코드를 만들어 냅니다. 그리고 마지막에 이렇게 말합니다. "엔드포인트를 추가했습니다. 완료했습니다."

여기서 신입이 가장 자주 빠지는 함정이 있습니다. 그 "완료했습니다"를 그대로 믿고 다음 일로 넘어가는 것입니다. 그러나 코드가 고쳐졌다는 사실과 코드가 동작한다는 사실은 전혀 다릅니다. 이 장에서 배우는 실행·테스트로 검증하기(verifying with execution and tests) 는, 에이전트 루프(c02)의 마지막 단계인 "결과 확인"을 신입의 손에 쥐여 주는 기술입니다. 핵심 문장은 단 하나로 요약됩니다. 검증 전까지는 끝난 게 아닙니다.

선수 개념 상기: 이 장은 2단원에서 배운 에이전트 루프(c02) 의 네 단계(관찰 → 계획 → 도구 호출 → 결과 확인) 위에 세워집니다. 우리는 그 루프의 앞 세 단계는 자주 보지만, 마지막 "결과 확인"은 자칫 건너뛰기 쉽습니다. 이 장은 바로 그 마지막 고리를 실행과 테스트로 단단히 채웁니다. 또 6단원의 플랜 모드(c06) 가 "바꾸기 전"의 안전장치였다면, 이 장의 검증은 "바꾼 후"의 안전장치입니다. 둘이 합쳐져야 변경의 앞뒤가 모두 통제됩니다.

이 장의 모든 예제는 신입이 첫 출근에서 받게 될 법한 FastAPI(파이썬 웹 백엔드 프레임워크) 저장소를 무대로 합니다. 작은 할 일 관리 API(team-tasks-api)에 엔드포인트를 더하고, 그것이 정말 동작하는지 pytest로 증명하는 과정을 처음부터 끝까지 따라가 봅니다.

도입: 검증 전까지는 끝난 게 아니다

"됐습니다"라는 말의 함정

상황을 그려 보겠습니다. 여러분은 팀 저장소에 "할 일 목록을 조회하는 GET /tasks 엔드포인트를 추가해 줘"라고 지시했습니다. 에이전트는 라우터 파일을 열어 코드를 더하고, 잠시 뒤 이렇게 답합니다. "/tasks 엔드포인트를 추가했습니다. 저장된 할 일 목록을 반환합니다." 코드를 열어 보니 그럴듯한 함수가 들어가 있습니다. 마음이 놓여 "고맙다"고 하고 PR을 올리려 합니다.

그런데 그 코드는 정말 동작할까요? 임포트(import) 한 줄이 빠졌을 수도 있고, 반환 타입이 FastAPI가 직렬화하지 못하는 객체일 수도 있고, 저장소가 비었을 때 예외를 던질 수도 있습니다. 에이전트의 "추가했습니다"는 코드를 작성했다는 뜻이지, 실행해서 통과를 확인했다는 뜻이 아닐 수 있습니다. 둘 사이의 간극을 메우는 것이 바로 검증입니다.

왜 신입에게 검증이 특히 중요한가

경력자는 코드를 눈으로 훑기만 해도 "이건 안 돌아가겠다"를 어느 정도 압니다. 그러나 신입은 그 직관이 아직 없습니다. 그래서 신입일수록 눈이 아니라 실행에 판단을 맡겨야 합니다. 실행과 테스트는 경험이 부족해도 누구에게나 똑같이 객관적인 증거를 줍니다. "초록색 통과 막대를 보기 전까지는 믿지 않는다"는 태도는 신입의 약점을 그대로 강점으로 바꿔 줍니다.

검증을 에이전트에게 맡긴다는 것

좋은 소식은, 검증조차 에이전트와 함께 할 수 있다는 점입니다. 우리는 에이전트에게 "코드를 짜라"고만 시키는 것이 아니라, "짠 코드를 실행해서 결과를 보여 달라", "그 동작을 증명할 테스트를 작성하고 돌려 달라"고 시킬 수 있습니다. 에이전트는 Bash 도구로 pytest나 uvicorn을 직접 실행할 수 있으므로, 작성과 검증을 한 흐름 안에서 끝낼 수 있습니다. 이 장은 그 "작성 → 실행 → 테스트 → 통과 확인"의 한 바퀴를 신입이 능숙하게 돌리도록 만드는 데 목표가 있습니다.

정의: 결과 확인은 실행·테스트로 하는 증명이다

실행·테스트로 검증하기(verifying with execution and tests) 란, 에이전트가 만든 변경을 실제로 실행 하고 테스트 로 동작을 증명해, 에이전트 루프의 마지막 단계인 "결과 확인"을 완결하는 작업입니다. 여기서 테스트(test) 란 코드가 기대대로 동작하는지 자동으로 검사하는 또 다른 코드이고, pytest(파이테스트) 는 파이썬에서 가장 널리 쓰이는 테스트 실행 도구입니다.

세 가지 핵심 용어를 먼저 정리하겠습니다.

  • 실행(execution): 코드를 실제로 돌려 보는 것입니다. FastAPI라면 서버를 띄워 요청을 보내 보거나, 스크립트를 돌려 출력을 확인하는 것입니다.
  • 단위 테스트(unit test)·통합 테스트(integration test): 함수 하나의 동작을 좁게 검사하면 단위 테스트, 여러 부품(라우터·모델·저장소)이 함께 도는 흐름을 검사하면 통합 테스트입니다. FastAPI 엔드포인트 검증은 보통 후자에 가깝습니다.
  • TestClient(테스트 클라이언트): FastAPI가 제공하는 도구로, 서버를 진짜 네트워크에 띄우지 않고도 메모리 안에서 엔드포인트에 요청을 보내 응답을 받을 수 있게 해 줍니다. 덕분에 테스트가 빠르고 안정적입니다.

이 정의의 핵심은 "증명"이라는 단어입니다. 검증은 주장 이 아니라 증거 를 만드는 일입니다. "동작합니다"는 주장이고, "이 테스트가 통과합니다"는 증거입니다. 신입은 주장 대신 증거로 말하는 법을 익혀야 합니다.

동작 원리: 변경 → 실행 → 테스트 → 통과 확인 루프

검증은 한 번 찍고 끝나는 점이 아니라, 통과할 때까지 도는 루프(loop) 입니다. 이 루프의 각 단계를 따라가 보겠습니다.

1단계 — 변경(change). 에이전트가 Edit·Write 도구로 코드를 바꿉니다. 새 엔드포인트를 더하거나 버그를 고친 직후의 상태입니다. 이 시점의 코드는 아직 "추정"일 뿐입니다. 동작 여부는 아무도 모릅니다.

2단계 — 실행(run). 바꾼 코드를 실제로 돌립니다. 서버를 띄워 보거나(uvicorn), 모듈을 임포트해 봅니다. 여기서 임포트 에러나 문법 오류 같은 가장 기본적인 문제가 즉시 드러납니다. 코드가 "켜지기는 하는가"를 확인하는 단계입니다.

3단계 — 테스트(test). pytest를 실행해, 미리 정해 둔 기대(예: "GET /tasks는 200과 리스트를 반환한다")가 실제로 충족되는지 검사합니다. 테스트는 사람의 눈보다 훨씬 꼼꼼하고, 한 번 써 두면 다음에도 똑같이 검사해 줍니다.

4단계 — 통과 확인(verify). 테스트 결과를 읽습니다. 모두 통과(passed)면 이 변경은 증명된 것입니다. 루프를 빠져나가 다음 일로 넘어갑니다. 하나라도 실패(failed)하면 루프는 끝나지 않습니다.

실패 시 — 메시지 근거 수정. 실패한 테스트의 메시지(어떤 값이 기대됐고 실제로 무엇이 나왔는지)를 에이전트에게 그대로 전달해 수정을 요청합니다. 그리고 다시 2단계로 돌아가 실행·테스트를 반복합니다. 이 되먹임이 검증 루프의 심장입니다.

팁: "돌려서 통과를 보여 줘"를 한 문장으로 붙여라

지시 끝에 "그리고 pytest로 돌려서 통과하는 것까지 확인해 줘"를 습관처럼 덧붙이세요. 그러면 에이전트는 작성에서 멈추지 않고 위 루프를 스스로 한 바퀴 돌아, 통과한 테스트 출력까지 보여 줍니다. 검증을 지시의 일부로 못 박는 것이 "완료" 정의를 분명히 하는 가장 간단한 방법입니다.

worked example: 엔드포인트를 pytest(TestClient)로 검증

이제 실제 세션을 처음부터 끝까지 따라가며, 엔드포인트 하나를 추가하고 그것을 테스트로 증명하는 흐름을 완전히 풀어 보겠습니다. 무대는 작은 할 일 관리 API입니다. 현재 저장소 구조는 다음과 같습니다.

text
team-tasks-api/
  main.py
  models.py
  store.py
  routers/
    __init__.py
    tasks.py
  tests/
    __init__.py
    test_tasks.py
  requirements.txt

store.py에는 메모리에 할 일을 보관하는 아주 단순한 저장소가 있고, routers/tasks.py에는 GET /tasks·POST /tasks·GET /tasks/{task_id}가 이미 있습니다. 이 절에서는 그중 할 일 목록을 조회하는 GET /tasks 의 동작을, 우리 손으로 pytest 테스트를 작성해 증명해 봅니다(엔드포인트를 새로 만드는 게 아니라, 이 장의 주제인 "검증"을 익히는 것이 목표입니다).

1) 작업과 검증을 한 번에 지시한다

text
나: routers/tasks.py의 GET /tasks가 정말 기대대로 동작하는지 증명하는 pytest 테스트를
    tests/test_tasks.py에 추가해 줘. 응답이 200이고 할 일 객체의 리스트인지,
    그리고 POST로 만든 할 일이 목록에 보이는지 검사해야 해.
    작성한 뒤 python -m pytest -q로 돌려서 통과하는 것까지 확인해 줘.

이 지시에는 3단원에서 배운 좋은 지시의 네 요소가 들어 있습니다. 목표(GET /tasks 검증 테스트 추가), 맥락(routers/tasks.py), 제약(200·리스트·목록 반영 검사), 완료 조건(테스트 작성·통과 확인)입니다. 특히 마지막 한 문장이 검증을 작업의 일부로 못 박습니다.

2) 검증 대상 엔드포인트 코드 (이미 저장소에 있음)

에이전트는 기존 라우터를 읽어(Read·Grep) 무엇을 검증할지 파악합니다.

python
# routers/tasks.py (발췌)
from fastapi import APIRouter, HTTPException
from models import Task, TaskCreate
import store

router = APIRouter(prefix="/tasks", tags=["tasks"])


@router.post("", response_model=Task, status_code=201)
def create_task(data: TaskCreate) -> Task:
    return store.create_task(data)


@router.get("", response_model=list[Task])
def list_tasks() -> list[Task]:
    return store.get_all_tasks()
  • import store: 메모리 저장소 모듈을 가져옵니다. 데이터 보관 로직을 라우터에서 분리해 두는 구조입니다.
  • router = APIRouter(prefix="/tasks", ...): 이 라우터의 모든 경로 앞에 /tasks가 붙습니다. 그래서 @router.get("")은 실제로 GET /tasks가 됩니다.
  • def list_tasks() -> list[Task]: 반환 타입을 list[Task]로 명시했습니다. FastAPI는 이 타입 힌트를 보고 응답을 자동으로 JSON 리스트로 직렬화합니다. 우리 테스트가 "응답은 리스트"를 검사할 근거가 되는 지점입니다.
  • return store.get_all_tasks(): 저장소에 보관된 모든 할 일을 그대로 반환합니다.

3) 에이전트가 작성한 테스트 코드

이어서 에이전트는 이 엔드포인트의 동작을 증명할 테스트를 작성합니다. 각 테스트 전에 저장소를 비우는 reset_store 픽스처는 1장 저장소에 이미 들어 있습니다.

python
# tests/test_tasks.py (추가분)
from fastapi.testclient import TestClient

from main import app
import store

client = TestClient(app)


def test_list_tasks_returns_200_and_list():
    response = client.get("/tasks")
    assert response.status_code == 200
    assert isinstance(response.json(), list)


def test_created_task_appears_in_list():
    client.post("/tasks", json={"title": "온보딩 문서 읽기"})

    response = client.get("/tasks")
    titles = [task["title"] for task in response.json()]
    assert "온보딩 문서 읽기" in titles
  • from fastapi.testclient import TestClient: FastAPI가 제공하는 테스트 클라이언트를 가져옵니다. 진짜 서버를 띄우지 않고도 요청을 보낼 수 있게 해 줍니다.
  • client = TestClient(app): 우리 앱(main.py의 app)을 감싼 클라이언트를 만듭니다. 이제 client.get·client.post로 엔드포인트를 호출할 수 있습니다.
  • response = client.get("/tasks"): 실제 HTTP 요청처럼 GET /tasks를 보냅니다. 네트워크가 아니라 메모리 안에서 처리되므로 빠릅니다.
  • assert response.status_code == 200: 정상 응답인지 확인합니다. assert는 "이게 참이 아니면 테스트를 실패시켜라"는 뜻입니다.
  • assert isinstance(response.json(), list): 응답 본문이 리스트인지 확인합니다. 지시한 "응답은 리스트" 제약을 테스트가 직접 검사하는 부분입니다.
  • 두 번째 테스트는 POST로 할 일을 하나 넣은 뒤, GET으로 그 제목이 목록에 보이는지 확인합니다. 두 엔드포인트가 같은 저장소를 공유하는 흐름을 통합적으로 검증합니다.

테스트 주도 개발(TDD): 테스트 먼저 → 구현

지금까지는 "코드를 만든 뒤 테스트로 검증"하는 순서였습니다. 이제 순서를 뒤집어 보겠습니다. 테스트를 먼저 쓰고, 그 테스트를 통과하도록 코드를 구현 하는 방식입니다. 이것을 테스트 주도 개발(TDD, Test-Driven Development) 이라고 부릅니다.

왜 테스트를 먼저 쓰는가

언뜻 비효율적으로 보입니다. 아직 없는 코드의 테스트를 어떻게 쓴단 말일까요? 그러나 바로 그 점이 핵심입니다. 테스트를 먼저 쓴다는 것은 "이 기능이 완성되면 무엇이 참이어야 하는가"를 코드로 못 박는 일입니다. 즉, 완료 조건을 구현보다 먼저 정의하는 것입니다. 에이전트에게 이 완료 조건을 미리 주면, 에이전트는 "통과해야 할 명확한 목표"를 갖고 구현합니다. 모호한 "잘 만들어 줘" 대신, "이 테스트를 통과시켜 줘"라는 검증 가능한 목표가 생깁니다.

TDD는 보통 세 박자로 돕니다.

단계 이름 하는 일
1 빨강(Red) 아직 구현이 없어 실패하는 테스트를 먼저 쓴다
2 초록(Green) 그 테스트를 통과시키는 최소 구현을 한다
3 정리(Refactor) 통과를 유지하며 코드를 다듬는다

from models import TaskStatus


@router.post("/{task_id}/done", response_model=Task)
def mark_task_done(task_id: int) -> Task:
    task = store.get_task(task_id)
    if task is None:
        raise HTTPException(status_code=404, detail="Task not found")
    task.status = TaskStatus.done
    return task
  • @router.post("/{task_id}/done", response_model=Task): 경로의 {task_id} 부분이 함수 인자 task_id로 들어옵니다. prefix와 합쳐져 실제 경로는 POST /tasks/{task_id}/done입니다.
  • task = store.get_task(task_id): 저장소에서 해당 id의 할 일을 찾습니다. 없으면 None을 돌려줍니다.
  • if task is None: raise HTTPException(status_code=404, ...): 없는 id면 404를 던집니다. 두 번째 테스트(test_mark_done_unknown_id_returns_404)가 검사하는 바로 그 동작입니다.
  • task.status = TaskStatus.done: 찾은 할 일을 완료 상태로 바꿉니다. store.get_task가 돌려준 객체는 저장소 안의 바로 그 객체라, 값을 바꾸면 저장소에도 반영됩니다. 첫 번째 테스트가 기대하는 status == "done"을 만드는 부분입니다.
  • return task: 갱신된 할 일을 반환합니다. FastAPI가 Task를 JSON으로 직렬화해 응답합니다.

팁: 실패 메시지에서 세 가지를 읽어라

pytest 실패 메시지에서 신입이 챙겨야 할 정보는 셋입니다. (1) 어느 테스트가 실패했나(test_mark_task_done_...), (2) 기대값과 실제값이 무엇인가(assert 201 == 200), (3) 어느 줄에서 났나(test_tasks.py:42). 이 셋을 그대로 에이전트에게 넘기면, 막연한 "안 돼" 대신 정확한 좌표를 준 셈이라 진단이 훨씬 빠릅니다. 이 습관은 11단원 디버깅에서 다시 본격적으로 다룹니다.

'검증 전까지는 끝난 게 아니다' 습관화

이 장의 모든 내용은 결국 하나의 습관으로 수렴합니다. 에이전트가 "완료했다"고 말해도, 실행과 테스트로 통과를 확인하기 전까지는 작업을 끝난 것으로 치지 않는다. 이 습관을 몸에 붙이는 세 가지 작은 규칙을 제안합니다.

  1. 지시에 검증을 붙인다. "추가해 줘"가 아니라 "추가하고, 테스트를 써서 통과를 확인해 줘"라고 말합니다. 완료 정의를 지시에 못 박는 것입니다.
  2. 초록 막대를 직접 본다. 에이전트의 "통과했습니다"라는 문장 이 아니라, N passed라는 출력 을 눈으로 확인합니다. 가능하면 출력 전체를 보여 달라고 합니다.
  3. 새 기능엔 새 테스트. 동작을 바꾸거나 더했다면, 그 동작을 검사하는 테스트도 함께 남깁니다. 그래야 다음에 누가 코드를 건드려도 이 동작이 깨지지 않았는지 자동으로 확인됩니다.

이 습관은 다음 단원들의 토대가 됩니다. 8단원 git 커밋·PR에서 우리는 "테스트가 통과한 변경만 커밋·PR로 올린다"를 배우고, 9단원 코드 리뷰에서는 "테스트 결과를 PR 본문에 증거로 첨부한다"를 배웁니다. 검증은 이 책 후반부 전체를 떠받치는 기둥입니다.

즉시 연습 (2종 1세트): team-tasks-api에서 TDD를 직접 돌려 보기

이제 종이에 빈칸을 채우는 대신, 1장에서 준비한 실제 team-tasks-api 저장소를 Claude Code로 열고 TDD 루프를 직접 한 바퀴 돌립니다. 핵심은 "테스트 먼저 → 빨강(실패)을 눈으로 확인 → 구현 → 초록(통과)을 눈으로 확인"을 화면에서 실제로 겪는 것입니다. 미리 정한 답을 적는 것이 아니라, 화면에 실제로 나타난 pytest 출력을 그대로 옮겨 적습니다.

1) 모범 예시 (실제 실행 예)

상황: 할 일을 삭제하는 DELETE /tasks/{task_id} 엔드포인트의 동작을, 구현보다 먼저 테스트로 정의합니다. 기대 동작은 "존재하는 할 일을 삭제하면 204(본문 없음)를 반환하고, 그 뒤 목록에서 사라진다"입니다. team-tasks-api에는 아직 삭제 엔드포인트가 없으므로, 이 테스트는 처음엔 빨갛게 떨어집니다(TDD의 출발점).

python
# tests/test_tasks.py (테스트 먼저)
def test_delete_task_returns_204_and_removes_it():
    client.post("/tasks", json={"title": "삭제 대상"})  # id=1

    response = client.delete("/tasks/1")
    assert response.status_code == 204

    listed = client.get("/tasks").json()
    ids = [task["id"] for task in listed]
    assert 1 not in ids

흔한 오류와 오개념

오개념 1: "에이전트가 '됐다'고 하면 된 것이다"

가장 위험한 착각입니다. 에이전트의 "완료했습니다"는 코드를 작성했다 는 뜻이지, 실행해서 통과를 확인했다 는 뜻이 아닐 수 있습니다. 코드를 작성하는 일과 그 코드가 동작함을 증명하는 일은 별개입니다.

→ 교정: 문장이 아니라 출력으로 확인하세요. "통과했습니다"라는 말 대신 N passed라는 pytest 출력을 눈으로 봐야 비로소 끝난 것입니다. 지시 끝에 "pytest로 돌려서 통과를 보여 줘"를 붙이는 습관을 들이세요.

오개념 2: "테스트는 나중에, 일단 기능부터"

테스트를 "여유 있을 때 하는 뒷정리"로 미루면, 보통 영영 하지 않게 됩니다. 그리고 완료 조건이 모호한 채로 구현이 진행돼, "무엇이 되면 끝인지"를 아무도 모르는 상태가 됩니다.

→ 교정: 테스트를 먼저 쓰면(TDD) 오히려 완료 조건이 분명해져 구현이 빨라집니다. 에이전트에게 "구현하기 전에 기대 동작을 테스트로 먼저 정의해 줘"라고 시키면, 목표가 코드로 못 박혀 작업이 흔들리지 않습니다.

오개념 3: "코드를 읽어 보니 맞으니까 동작한다"

눈으로 코드를 훑어 "맞는 것 같다"고 판단하는 것은 주장이지 증거가 아닙니다. 임포트 누락, 타입 불일치, 빈 입력에서의 예외처럼 눈으로 놓치기 쉬운 문제는 실행해야만 드러납니다. 통과한 테스트가 하나도 없다면 "동작한다"는 말에는 근거가 없습니다.

→ 교정: "동작한다"고 말하고 싶을 때마다, 그것을 뒷받침하는 통과한 테스트나 실행 결과가 있는지 자문하세요. 증거가 없으면 그 말은 아직 추정일 뿐입니다. 신입은 주장 대신 증거로 말하는 법을 익혀야 합니다.

이 장에서 익힌 것

이 장에서 우리는 에이전트 루프의 마지막 단계인 "결과 확인"을 실행과 테스트로 완결하는 법을 배웠습니다. 핵심을 다시 정리합니다.

  • 검증은 변경 → 실행 → 테스트 → 통과 확인 의 루프이며, 실패하면 메시지를 근거로 수정해 루프를 다시 돕니다.
  • FastAPI 엔드포인트는 TestClient + pytest 로 빠르고 반복 가능하게 검증하고, 필요하면 uvicorn으로 서버를 띄워 눈으로도 확인합니다.
  • TDD(테스트 먼저 → 구현) 는 완료 조건을 앞당겨 정의해, 에이전트에게 통과해야 할 명확한 목표를 줍니다.
  • 실패 메시지는 통째로 전달해야 정확한 진단을 끌어냅니다.
  • 무엇보다, 검증 전까지는 끝난 게 아닙니다.

다음 단원에서는 이렇게 검증한 변경을, 팀의 규약에 맞춰 다루는 법을 배웁니다. 세션마다 팀 규칙을 다시 설명하지 않도록 CLAUDE.md로 컨벤션을 명문화하는 8단원으로 이어집니다.
